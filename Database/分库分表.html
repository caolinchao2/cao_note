分库分表 ​

分库分表深度聚合：从数据量演进路径、垂直/水平拆分、ShardingSphere 原理与实战、全局主键，到扩容迁移与生产大坑。与《MySQL 深入》第六章互为补充，本文聚焦"分库分表"本身。

一、为什么分库分表 ​

1.1 单表数据量增长曲线 ​

单表性能与数据量不是线性关系，而是"平台期后断崖"。数据量增长带来的变化：

数据量级单表通常表现开始出现的问题
百万级一切正常，索引都在内存里几乎无感
千万级多数场景仍可接受慢查询变多、缓存命中率开始下降
2000 万-5000 万到达拐点区间索引体积变大、DDL 变慢、备份恢复时间长
亿级以上明显劣化写入放大、B+ 树层级加深、单点 IO/连接成为瓶颈

真正的问题不是"某一刻突然变慢"，而是增长曲线上存在拐点：在拐点之前优化收益大，拐点之后任何单机优化都难以挽回，只能拆分。

1.2 性能拐点：B+ 树与 IO 成本 ​

MySQL InnoDB 的聚簇索引是一棵 B+ 树，点查的成本主要是一次次"页的随机读"。估算树高：

  • InnoDB 页默认 16KB，非叶子节点每条索引项约 主键 8B + 指针 6B = 14B；
  • 一个非叶子页可容纳约 16384 / 14 ≈ 1170 个索引项；
  • 若叶子页每页存约 16 行（按行均 1KB 估算），则 3 层树可容纳 1170 × 1170 × 16 ≈ 2190 万 行。

也就是说单表两千万上下时树高普遍还在 3 层；继续增长到 4 层后，每次点查理论上多一次磁盘 IO，加上内存放不下索引导致缓存命中下降，性能开始明显劣化。千万级并不必然要拆，但"树高 + 缓存 + DDL"三个因素叠加，使业界普遍把"单表两三千万、且持续增长"作为评估分库分表的启动线。

1.3 大表引发的连锁问题 ​

问题具体表现
索引失效/膨胀索引体积超过 Buffer Pool，随机读退化为磁盘 IO
DDL 锁表大表 ALTER TABLE 耗时长，期间阻塞读写，主从延迟放大
备份与恢复慢物理备份/逻辑备份时间线性增长，恢复同样慢
写放大二级索引多时，一次 UPDATE 要维护多棵索引树
单点资源CPU/磁盘/连接池都集中在一台实例，无法水平扩展
连接池耗尽慢查询占住连接，其它请求拿不到连接

1.4 何时该分：判断指标 ​

分库分表是"最后的手段"，复杂度极高。动手前先看四类指标：

指标参考阈值说明
单表行数持续逼近/超过 2000 万-5000 万且仍在增长行数本身不是唯一标准，要与增速结合
表容量单表 50GB+与备份、DDL 成本相关
QPS/TPS单实例连接/IO 打满，优化后仍不足只读放大先做读写分离，写放大才考虑分库
增长趋势业务处于高速增长期在拐点前 1-2 个季度规划，避免"被迫拆分"

重要提醒：如果数据量增长缓慢、查询简单，千万不要为了"架构先进"而分——分库分表的复杂度（分布式事务、跨库查询、扩容）会吞掉那点性能收益。

二、数据量演进路径 ​

2.1 演进路线总览 ​

正确的拆分节奏是"由轻到重、一步一个门槛"，而不是一步到位分库分表：

单表 + 索引优化
  -> 缓存与冷热归档（Redis / 历史表）
    -> 读写分离（一主多从）
      -> 垂直拆分（分库按业务域 / 分表按字段热度）
        -> 水平拆分（只分表 -> 分库分表）
          -> 分库分表 + 缓存/归档/ES 组合架构
单表 + 索引优化
  -> 缓存与冷热归档（Redis / 历史表）
    -> 读写分离（一主多从）
      -> 垂直拆分（分库按业务域 / 分表按字段热度）
        -> 水平拆分（只分表 -> 分库分表）
          -> 分库分表 + 缓存/归档/ES 组合架构

每一步都解决上一阶段解决不了的问题，每一步都要求先满足前置条件，避免跨级跳跃。

2.2 阶段一：单表 + 索引优化 ​

适用条件：数据量千万以内、慢查询集中在少数 SQL。 做什么：合适的索引与查询改写（联合索引、覆盖索引、避免隐式转换、深翻页改游标），详见《MySQL 深入》二、三章。 先决条件/退出标准：索引已建到位但依然慢，或慢 SQL 数量失控，进入下一阶段。

2.3 阶段二：缓存与冷热分离 ​

适用条件：读多写少、热点数据占比小（二八原则）。 做什么：Redis 缓存热点读；把历史数据按月/年归档到历史表或冷存储，主表只保留热数据。 先决条件：能明确区分热冷数据，且业务可接受"查冷数据走归档链路"。 注意：缓存解决"读"，归档解决"表膨胀"，都解决不了"写放大与单点写瓶颈"。

2.4 阶段三：读写分离 ​

适用条件：读 QPS 远超写 QPS，从库延迟可接受。 做什么：一主多从 + 读写分离，主库承担写，从库扛读；配套主从延迟监控（半同步/并行复制压延迟）。 先决条件：对"读到旧数据"容忍（或走强制主库路由）；复制链路稳定。 注意：读写分离只扩展"读"，主库的写压力、单表容量问题依旧。

2.5 阶段四：垂直拆分 ​

适用条件：业务模块间耦合低、单库连接/资源吃紧，或单表字段宽导致 IO 浪费。 做什么：垂直分库按业务域拆实例，垂直分表按字段热度拆窄表（详见第三章）。 先决条件：跨库调用可控（服务化/接口化），避免应用里到处跨库 JOIN。 注意：垂直拆分到一定程度后，单表仍可能继续膨胀，水平拆分迟早要上。

2.6 阶段五：水平拆分 ​

适用条件：单表行数逼近拐点、单库写/存瓶颈，且前面的手段都用尽。 做什么：只分表（同实例多张结构相同的表）、分库分表（多实例多表），用中间件/客户端路由。 先决条件：确定分片键与分片策略、全局主键方案、跨分片问题的解法（见第四、七、八章），并设计好扩容路径。 注意：水平拆分是"拆分终点"，进入后查询模型被分片键约束，务必在业务早期就规划分片键。

2.7 各阶段适用条件对比表 ​

阶段解决的核心问题前置条件引入的成本
索引优化慢查询无极低
缓存/归档读压力、热数据膨胀热点可识别缓存一致性
读写分离读 QPS 高主从延迟可控延迟/一致性
垂直分库分表连接/字段宽/模块耦合业务域清晰跨库调用
水平分库分表单表/单库容量与写瓶颈分片键清晰分布式事务、跨片查询、扩容

三、垂直拆分 ​

3.1 垂直分库（按业务域） ​

把不同业务模块的表从一个大库拆到多个数据库实例，例如用户库、订单库、商品库、日志库各占一个实例。核心是按业务边界切，与微服务拆分同源。

   user / order / product / log
              |
    +---------+---------+--------+
    |         |         |        |
  用户库     订单库    商品库   日志库

适用条件：单库连接数吃紧、各业务模块 QPS 差异大（避免日志类高 IO 业务拖垮交易库）、团队按域划分要独立治理。 成本：原本一条 SQL 跨表 JOIN 变成跨库调用，需要服务化或应用层聚合；跨库事务上升为分布式事务。

3.2 垂直分表（按字段热度） ​

把一张"宽表"按列拆成多张窄表：高频小字段留在主表，大字段/低频字段放扩展表，用相同主键关联。

sql
-- 原表：所有字段挤在一张表
CREATE TABLE article (
    id BIGINT PRIMARY KEY,
    title VARCHAR(200),      -- 高频
    summary VARCHAR(500),    -- 高频
    author VARCHAR(50),      -- 高频
    content LONGTEXT,        -- 大字段、低频
    create_time DATETIME
);

-- 垂直拆分后：列表页只查主表，详情页再查内容表
CREATE TABLE article_main (
    id BIGINT PRIMARY KEY,
    title VARCHAR(200),
    summary VARCHAR(500),
    author VARCHAR(50),
    create_time DATETIME
);
CREATE TABLE article_content (
    id BIGINT PRIMARY KEY,   -- 与主表同主键
    content LONGTEXT
);
-- 原表：所有字段挤在一张表
CREATE TABLE article (
    id BIGINT PRIMARY KEY,
    title VARCHAR(200),      -- 高频
    summary VARCHAR(500),    -- 高频
    author VARCHAR(50),      -- 高频
    content LONGTEXT,        -- 大字段、低频
    create_time DATETIME

-- 垂直拆分后：列表页只查主表，详情页再查内容表

    id BIGINT PRIMARY KEY,
    title VARCHAR(200),
    summary VARCHAR(500),
    author VARCHAR(50),
    create_time DATETIME
);
CREATE TABLE article_content (
    id BIGINT PRIMARY KEY,   -- 与主表同主键
    content LONGTEXT

3.3 垂直拆分的优缺点 ​

优点缺点
实现简单，不需要中间件，SQL 语义基本不变拆得不彻底时单表仍会膨胀
按业务域隔离故障与资源跨库/跨表关联查询成本上升
字段热度分离直接优化行宽与 IO应用层要维护多张表的组装逻辑
配合服务化演进自然事务边界被打破

经验：垂直拆分是"性价比最高"的拆分手段，很多系统做到垂直分库 + 归档就够了，未必需要走到水平拆分。

四、水平拆分（核心） ​

4.1 水平拆分形态 ​

水平拆分是把同一张表的数据行按规则分散到多个结构相同的表中，可以只分表、只分库，或分库又分表：

形态说明示例
只分表（单库）一个实例内多张表，缓解单表过大order_0 ~ order_15 在同一库
只分库数据分到多个实例的同名表，缓解单库压力ds0.order、ds1.order
分库 + 分表先分库再分表，容量与并发同时扩展ds0.order_0、ds1.order_15

4.2 分片键选择原则 ​

分片键（Sharding Key）决定一条数据落在哪个分片，是全系统最重要、最难改的决策。原则：

  1. 查询覆盖率最高：绝大多数查询都带这个条件。订单场景选 user_id（用户查自己的订单）或 order_id（按订单查）；
  2. 数据分布均匀：键的取值要分散，避免热点（如按 seller_id 分片而大商家集中）；
  3. 稳定不可变：业务上不更新的字段（user_id 几乎不变，status 这种会变的值绝不能当分片键）；
  4. 支持核心业务闭环：让最频繁的关联查询（订单 + 订单明细）落在同分片。
sql
-- 错误示范：按 create_time 分片，但业务大量按 user_id 查
-- -> 每次查询都要扫所有分片（全路由）
SELECT * FROM t_order WHERE user_id = 10086 AND create_time > '2026-01-01';

-- 正确示范：分片键 user_id 参与查询，中间件直接路由到单个分片
SELECT * FROM t_order WHERE user_id = 10086 AND create_time > '2026-01-01';
-- 错误示范：按 create_time 分片，但业务大量按 user_id 查
-- -> 每次查询都要扫所有分片（全路由）
SELECT * FROM t_order WHERE user_id = 10086 AND create_time > '2026-01-01';

-- 正确示范：分片键 user_id 参与查询，中间件直接路由到单个分片
SELECT * FROM t_order WHERE user_id = 10086 AND create_time > '2026-01-01';

4.3 哈希取模分片（MOD） ​

分片 = hash(分片键) % N，最常用。整数键直接取模，字符串键先哈希再取模（ShardingSphere 的 HASH_MOD 即此思路，让非整数键也能均匀分布）。

sql
-- 分 16 片：路由到 order_0 ~ order_15
-- 分片号 = order_id % 16（或 user_id % 16）
SELECT * FROM t_order WHERE order_id = 1024;   -- 路由到 order_0（1024 % 16 = 0）
SELECT * FROM t_order WHERE order_id = 1039;   -- 路由到 order_15（1039 % 16 = 15）
-- 分 16 片：路由到 order_0 ~ order_15
-- 分片号 = order_id % 16（或 user_id % 16）
SELECT * FROM t_order WHERE order_id = 1024;   -- 路由到 order_0（1024 % 16 = 0）
SELECT * FROM t_order WHERE order_id = 1039;   -- 路由到 order_15（1039 % 16 = 15）

优点缺点
实现简单，数据分布均匀（键本身均匀时）扩容困难：N 变化后几乎所有数据要重新路由
单条查询精准定位一个分片范围查询退化为全分片扫描
各分片数据量基本均衡取模结果无法表达"时间冷热"

4.4 范围分片（Range） ​

按分片键的数值区间切分，如 user_id 0-1000 万 到库 0，1000 万-2000 万 到库 1；或按时间分库分表。

sql
-- 按 user_id 范围路由
SELECT * FROM t_user WHERE user_id BETWEEN 100000 AND 200000;  -- 只在库 0
-- 按 user_id 范围路由
SELECT * FROM t_user WHERE user_id BETWEEN 100000 AND 200000;  -- 只在库 0
1
2
优点缺点
范围查询友好，天然支持按区间扫描数据可能倾斜：新用户集中在最新分片
扩容简单：新增分片承接新区间，老数据不动区间边界是热点（如按时间分片时"今天"最热）
实现直观、易理解需要预估区间大小，预估不准会提前拆

4.5 一致性哈希 ​

把分片键哈希到 2^32 的哈希环上，每个物理分片在环上占据若干虚拟节点，数据归属"顺时针遇到的第一个节点"。

优点缺点
增删节点只影响环上相邻的一小段数据实现与运维复杂（虚拟节点、路由表维护）
节点增减时迁移量小（约 1/N 量级）仍然无法解决热点键问题
适合节点动态伸缩的缓存/存储数据库分片场景较少用到（DB 扩容周期长，不如 2N 翻倍法直接）

实际工程中数据库扩容更多用"翻倍法"而非一致性哈希（见 11.3），一致性哈希常用于 Redis 集群分片、负载均衡等场景。

4.6 按时间分片 ​

时间天然是范围维度，常见于流水、日志、订单类数据：

sql
-- 按月分表：order_202601、order_202602 ...
CREATE TABLE order_202601 (...);
CREATE TABLE order_202602 (...);
-- 按月分表：order_202601、order_202602 ...
CREATE TABLE order_202601 (...);
CREATE TABLE order_202602 (...);

优点缺点
冷热分明：老表可归档/压缩，新表保持高性能单月数据量不可控，热点永远在当月表
按月/按年 DDL 与归档简单跨月统计要跨多表/多分片
扩容=加新表，成本极低只能解决"单表大"，解决不了"单库写并发高"

实践：订单常用"user_id 取模分库 + 时间归档"组合——热数据按用户分片保证查询单分片命中，超期数据定期迁移归档表。

4.7 分片策略对比总表 ​

策略均匀性扩容难度范围查询热点控制适用
哈希取模好（键均匀时）高（需重路由/翻倍法）差中用户/订单等按 ID 高频点查
范围分片差（区间热点）低（新增区间即可）好低有自然区间边界的键
一致性哈希较好低-中（小范围迁移）差中节点弹性伸缩场景
按时间差（当月热点）低好低（配冷热归档）流水、日志、归档型数据

4.8 只分表 / 只分库 / 分库分表组合怎么选 ​

场景选择
单表行数大、但单库资源充裕只分表（省去多数据源复杂度）
单库连接/写并发瓶颈、单表尚可只分库
两者都到瓶颈分库 + 分表
数据量大且有自然时间维度分表（按时间）+ 冷热归档

五、路由与执行流程 ​

5.1 ShardingSphere-JDBC 形态（客户端） ​

ShardingSphere-JDBC 以 Jar 包形式嵌入应用，应用直连各个真实数据库，中间件在 JDBC 层拦截 SQL 做分片。无额外进程、无网络跳转、性能损耗最小，是 Java 应用最主流的接入方式（《MySQL 深入》6.4 即此形态）。

业务应用
  |  DataSource（ShardingSphere 代理）
  |    解析/路由/改写/执行/归并
  +---> ds0.order_0 ... order_7

5.4 核心执行流程（解析 -> 路由 -> 改写 -> 执行 -> 归并） ​

阶段做什么输入 -> 输出
SQL 解析ANTLR 把 SQL 解析成抽象语法树（AST），识别表名、条件、排序分页SQL -> AST
路由按分片规则与条件计算目标分片；无分片键条件则全路由（广播到所有分片）AST -> 路由结果
改写改写表名为实际分片表名、改写分页/聚合等（如把 limit 改写到每个分片）逻辑 SQL -> 真实 SQL
执行把真实 SQL 发到各分片执行；按连接模式控制并发与结果集真实 SQL -> 结果集
归并多分片结果合并：普通合并、聚合函数、分组、排序、分页（流式/内存归并）多结果集 -> 单一结果

路由类型：全库表路由（无分片键条件）、单播路由（带分片键，精准命中一个分片）、广播路由（绑定表 JOIN、广播表）、混合路由。

5.5 归并模式 ​

归并模式原理适用
流式归并各分片结果边拉取边归并，不全部载入内存ORDER BY、LIMIT、GROUP BY 的排序归并
内存归并全部结果载入内存再统一处理聚合函数、无排序约束的分组
装饰者归并在结果集上做增量修饰（如补充分页总数）count() 等

流式归并保障了大偏移量分页/大结果集排序不爆内存，但深翻页仍会把 offset+size 的数据拉到内存参与排序（见 8.3）。

七、全局主键方案 ​

7.1 为什么不能用数据库自增 ​

分库分表后各分片各自 AUTO_INCREMENT，必然产生重复主键（两张表都可能生成 id=1）；即使让不同库设置不同起始值（如库 0 从 0 开始步长 2），扩容和迁移时依旧会撞。因此需要全局唯一、且最好是趋势递增的主键生成器。趋势递增的意义：InnoDB 聚簇索引按主键顺序插入，B+ 树写友好、页分裂少。

7.2 UUID 方案 ​

java
String id = UUID.randomUUID().toString().replace("-", "");

优点缺点

无需任何组件无时间语义，不便排查与排序

结论：UUID 基本不适合做数据库主键，只适合做业务流水号等不落索引的标识。

7.5 时钟回拨问题与解决方案 ​

时钟回拨（NTP 校时、物理机跳变）会导致新生成的时间戳小于上一次，产生重复 ID。常用对策：

方案思路取舍
拒绝生成/抛异常检测到回拨直接报错，等待时钟追平简单但不可用窗口
等待追平记录上次最大时间戳，回拨则 sleep 到追平阻塞可用性
备用时钟/预留位时间戳预留回拨空间或用备用时钟源实现复杂
外部协调发号由 Redis/ZK/DB 统一发号，本地只做序列引入额外依赖与延迟

生产上"拒绝 + 等待"最常用；对回拨容忍度低的系统直接采用美团 Leaf 这类带回拨保护的发号服务。

7.6 美团 Leaf 方案 ​

Leaf 提供两种模式：

模式原理特点
Segment（号段）数据库号段 + 双 buffer 预加载，当前号段快用完时后台提前加载下一段高可用、趋势递增、依赖 DB
Snowflake雪花算法，用 ZooKeeper 管理 workerId，并检查时钟回拨（回拨超阈值拒绝/小于阈值用前序时间）无 DB 依赖、本地发号

双 buffer 预取让 Segment 模式对 DB 的访问频率降到极低，是"分布式 ID 服务"的经典落地方案。

7.7 ID 方案对比表 ​

方案全局唯一趋势递增性能额外依赖适用
UUID是否高无非索引标识
数据库自增否（分片后）是低无单表单库
号段模式是是高DB 发号表自建发号服务
雪花算法是是极高机器 ID 管理绝大多数分片场景

八、分库分表带来的问题与解法 ​

8.1 跨库 JOIN ​

分片后不同分片/不同库的表无法直接 JOIN。解法从优到劣：

方案做法适用
反范式冗余字段把关联要用的字段冗余进主表，消除 JOIN字段少、更新不频繁
同分片设计（绑定表）关联表用同一分片键，JOIN 落在单分片内订单+明细等强关联
应用层组装分两次查，内存里聚合（批量 IN 查询）数据量可控
广播表字典类小表每片冗余一份全局字典
宽表/数仓/ES把查询需求落到异构存储复杂分析查询

8.2 分布式事务 ​

跨库写操作无法再用本地事务。按一致性强度选型：

方案一致性吞吐实现成本适用
XA 两阶段提交强一致低中（数据库原生支持）短小、低频、要求严格一致
TCC（Try-Confirm-Cancel）最终一致（业务补偿）中高（每事务三接口）资金类等需明确补偿
本地消息表 + MQ最终一致高中常规业务（下单+扣库存等）
Seata AT最终一致（自动补偿）中-高低（框架自动生成 undo log）不想写补偿逻辑的团队

更优解是避免分布式事务：按业务聚合把要一起提交的数据设计到同一分片（同一 user_id 的订单/明细同库），从根上减少跨分片事务。

8.3 分页与排序 ​

LIMIT offset, size 在分片下语义被破坏：中间件必须从每个分片取 offset+size 条再归并，且深翻页越深，各分片取的数据越多，内存与耗时线性膨胀，排序还可能因各片数据到达顺序产生非严格全局序。

方案做法适用
禁止深翻页产品上限制最多翻前 100 页大部分 C 端列表
游标分页（keyset）WHERE id > last_id ORDER BY id LIMIT 20按主键/有序字段翻页
时间游标WHERE create_time < ? 结合索引列表按时间倒序
数据同步到 ES由 ES 承担搜索与深分页复杂查询/搜索场景
sql
-- 深翻页（每页都要各分片取 offset+size，很差）
SELECT * FROM t_order ORDER BY order_id LIMIT 1000000, 20;

-- 游标分页（每次只取 20 条，天然支持到任意深度）
SELECT * FROM t_order WHERE order_id < :lastOrderId ORDER BY order_id LIMIT 20;

8.4 聚合查询与统计 ​

COUNT/SUM/AVG/GROUP BY 会广播到所有分片再归并，可用但性能随分片数下降；跨分片 GROUP BY + ORDER BY 归并成本更高。

实践建议：实时精确统计不要在分片库上做。方案：

方案说明
汇总表/计数器表写时同步维护汇总（当日/当月/累计），读汇总
异构到 OLAP数据同步到 ClickHouse/Doris/数仓做分析
定时任务聚合用调度框架（见《定时任务调度》）定时把明细聚合进报表表
ES 聚合日志/检索类用 ES 的聚合能力

8.5 数据倾斜 ​

取模分片要求分片键分布均匀，但现实常有热点：头部商家订单占 80%、个别大 V 数据量巨大。表现：某几个分片数据量/请求量远高于其它分片，拆分形同虚设。

解法做法
热点键加盐给热点键拼随机后缀拆散到多片（如 seller_1_0~9），查询时扇出
热点表独立把大卖家/大客户数据单独放超大分片或独立存储
冗余广播热点只读数据冗余一份到公共缓存/ES
换分片键业务允许时用分布更均匀的键

8.6 扩容再平衡 ​

取模分片扩容（N -> 2N）需要迁移数据并处理增量。两种思路：

方式成本停机说明
全量重分布高通常需要所有数据按新规则重算迁移
2N 翻倍法中较短老数据一半原地不动、一半迁到新库（见 11.3）
范围分片扩容低无新数据进新区间即可，老数据不动

8.7 跨分片唯一约束 ​

分片后数据库唯一索引只在单分片内生效，全局唯一要靠业务层：

场景解法
主键唯一分布式 ID（第七章），天然全局唯一
业务唯一（手机号、订单流水号）独立"唯一键登记表"（独立库/独立分片）先占位再落库
唯一键与分片键一致唯一约束天然成立（同一分片内）
需要防并发重复唯一登记表 + 去重，或 Redis SETNX 前置

8.8 分布式锁与本地锁 ​

分片后"锁"也分片：SELECT ... FOR UPDATE 只能锁住本分片内记录，跨分片的一致性要靠分布式锁（Redis/ZK，细节见《定时任务调度》8.4）。注意事务内加锁的粒度与释放顺序，避免锁等待 + 长事务放大。

8.9 事务内多分片写 ​

单事务里同时更新两个分片会触发分布式事务。设计上应：

  • 事务内尽量只写"同分片"的数据（分片键相同）；
  • 必须跨片时显式选择分布式事务方案（8.2），并控制事务时长；
  • 把"聚合根"作为分片边界：一个订单聚合（订单+明细+流水）整体落在一个分片，多数事务变成本地事务。

九、MyCat 简介与对比 ​

9.1 MyCat 是什么 ​

MyCat 是国产开源的数据库分库分表中间件，脱胎于阿里的 Cobar，以独立代理（Proxy）形式部署，对应用暴露 MySQL 协议。核心配置三件套：

配置文件作用
schema.xml逻辑库/表到物理分片的映射、分片表与全局表声明
rule.xml分片规则（取模、范围等）与分片算法定义
server.xml服务端口、用户权限等

能力：分库分表、读写分离、全局序列（号段式）、ER 分片（父子表同分片 JOIN）、SQL 路由与改写。适合"不想改应用、由 DBA 集中管控"的传统团队。

9.2 MyCat vs ShardingSphere-Proxy 对比表 ​

对比维度MyCatShardingSphere-Proxy
形态独立代理独立代理
SQL 解析能力较弱，复杂 SQL（子查询/多表 JOIN）支持有限强（ANTLR + 内核持续演进）
分片算法取模/范围等固定算法，扩展要写 XML内置丰富算法 + Java SPI 自定义
周边能力较少数据加密、影子库、分布式事务、可观测（同一 ShardingSphere 生态）

十、扩容与平滑迁移 ​

10.1 停机迁移 ​

流程：停写（或低峰窗口）→ 旧库全量导出 → 按新分片规则导入新库 → 校验 → 切换读。适合数据量小、可接受停机窗口（小时级）的系统。

优点缺点
流程最简单，无增量一致性问题有停机窗口，业务不可用
校验简单（两边 count + 抽样）数据量大时导出导入时间不可控

10.2 双写迁移 ​

新库就绪后，应用对同一业务同时写旧库与新库（新库失败不阻塞主流程），历史数据用批量任务回放，最后校验一致后切读、停旧写。

优点缺点
无长时间停机双写代码有侵入，需灰度开关
可逐步切流量、随时回滚双写期间要持续对账，脏数据要补偿
一致性靠对账任务收敛上线期间每笔写多一次开销

10.3 binlog 订阅回放（Canal 方案） ​

利用 MySQL binlog，用 Canal 订阅旧库变更，按新路由规则把增删改回放到新分片，实现"无代码双写"的增量同步：

旧库 binlog -> Canal -> 同步程序（按分片规则改写）-> 新分片各库
旧库 binlog -> Canal -> 同步程序（按分片规则改写）-> 新分片各库
1
  1. 先开启旧库 binlog（ROW 格式）并授权 Canal 账号；
  2. Canal 全量 + 增量同步到新分片（先导历史数据，再持续追增量）；
  3. 追平延迟后校验一致性，切读，最后停掉同步任务。
优点缺点
应用零侵入（不需要双写代码）需要维护 Canal/同步链路
支持持续增量，可反复校验DDL、无主键表、大事务同步要特殊处理
回放程序可复用为日常异构同步binlog 延迟要监控

10.4 数据一致性校验 ​

迁移切流前必须对账，常用手段：

手段做法定位
总数对比旧表 count 与各新分片 count 之和粗校验，快速发现漏数
抽样明细按主键范围抽 N 条逐行比对字段中粒度
校验和对 id、update_time、关键业务字段做聚合校验（sum/crc）中粒度
全量比对拉全量数据比对（可用工具/离线任务）最终兜底

对账发现不一致时，用 binlog 回放或重跑对应区间数据修复，直至连续多个周期零差异再切流。

10.5 迁移方案对比表 ​

方案停机应用改造风险适用
停机迁移有（小时级）无低小数据量、可停服
双写迁移几乎无中（双写+开关）中（要持续对账）中大型系统
binlog 订阅回放几乎无低中（同步链路要运维）大中型、长期增量同步

十一、生产实践与常见坑 ​

11.1 分片键选错的后果 ​

分片键一旦定错，代价极高：核心查询全变全路由（扫全部分片）、跨片 JOIN 泛滥、扩容时还要连带换键。典型错误：

  • 用会变化的字段（status、手机号可换绑）当分片键；
  • 用分布不均的字段（seller_id、region）导致数据倾斜；
  • 分片键与主要查询条件不一致（表按 order_id 分，业务却总按 user_id 查）。

经验：上线前用真实数据分布模拟一遍"高频 SQL 是否都能单分片命中"，并明确该键"业务上不可变"。

11.2 范围查询退化为多次查询 ​

取模分片下，BETWEEN、IN、>= 等范围条件无法定位单分片，中间件会把一条 SQL 拆成 N 条发往 N 个分片再归并。N=16 时，一次范围查询等于 16 次查询。

应对：

  • 范围查询里尽量带上分片键等值条件（WHERE user_id=88 AND create_time>? 命中单片）；
  • 纯范围/分析型查询丢给 ES/OLAP，不要让分片库硬扛；
  • 用绑定表让 JOIN 不跨片，减少放大系数。

11.3 扩容翻倍法（2N 扩容） ​

取模分片扩容时用"翻倍法"把迁移量降到一半：从 mod 4 扩到 mod 8 时，每个老分片的数据按新模只会去两个新位置（老库 0 的数据只可能属于新库 0 或新库 4），因此每台老库只需迁出一半数据到新增库，另一半原地不动。

mod 4（扩前）              mod 8（扩后）
ds0(0,4,8,12..)  ->  ds0 保留 mod8==0；mod8==4 迁去 ds4
ds1(1,5,9,13..)  ->  ds1 保留 mod8==1；mod8==5 迁去 ds5
...

ds0(0,4,8,12..)  ->  ds0 保留 mod8==0；mod8==4 迁去 ds4
ds1(1,5,9,13..)  ->  ds1 保留 mod8==1；mod8==5 迁去 ds5

11.4 与表分区（PARTITION）的区别 ​

MySQL 表分区是把一张表按分区键拆成多个分区文件，对应用完全透明：

对比维度表分区（PARTITION）分库分表
物理位置同一实例内多实例/多表
对应用透明性完全透明需中间件/改代码
解决单表容量部分（仍是单实例，总容量不变）是（横向扩展）
解决单实例写瓶颈/连接瓶颈不能能（分库）
运维自动管理分区需迁移与扩容方案
限制分区键必须包含在表的主键/唯一键中无此限制但查询受分片键约束

结论：分区表适合"单实例内治理超大表 + 按时间淘汰数据"；当瓶颈在单机 IO/连接/写并发时，只有分库能解决。

11.5 与 ES / 归档冷热分离的配合 ​

分库分表不是终点，典型分层架构：

历史归档（按月归档表/冷存储）         承担低频查询与合规留存

11.6 其它高频坑汇总 ​

坑说明与规避

自增主键分片后必须换分布式 ID

count/sum 精度聚合在分片归并中可能因去重/浮点产生偏差，精确统计走 OLAP

十二、面试考点速查 ​

12.1 Q1：单表数据量多大才需要分库分表？ ​

没有绝对阈值。经验线：单表持续增长逼近 2000 万-5000 万、或单表 50GB 以上、或单实例连接/写并发打满且优化无效时启动评估。更关键的是看增长趋势与瓶颈位置：只读瓶颈先做读写分离与缓存，写/容量瓶颈才考虑分片；数据量不涨就别分。

12.2 Q2：分片键怎么选？ ​

高频查询必须能带上它（查询覆盖率最高）；取值分布均匀；业务上稳定不变；能让核心关联数据（订单+明细）落同分片。常见：订单按 user_id 或 order_id。反面典型：用状态字段、按时间分但业务按用户查。

12.3 Q3：取模分片和范围分片各自的优缺点？ ​

取模：分布均匀、点查精准单片，但扩容难（需翻倍法/重分布）、范围查询退化全路由。范围：区间友好、扩容简单（新数据进新区间），但可能倾斜与区间热点。时间分片是特殊的范围分片，配冷热归档效果好。

12.4 Q4：分库分表后主键怎么生成？ ​

不能用自增（各片重复）。方案：雪花算法（趋势递增、本地生成、注意时钟回拨）、号段模式（DB 发号、双 buffer 预取）、美团 Leaf（Segment/Snowflake 双模式）、UUID（无序长，只适合非索引）。生产默认雪花或公司发号服务。

12.5 Q5：跨库 JOIN 怎么解决？ ​

反范式冗余、绑定表同分片 JOIN、应用层多次查询组装、广播表（字典）、异构到 ES/数仓。核心思路是"设计上让 JOIN 尽量落在单分片内"。

12.6 Q6：分布式事务有哪些方案？ ​

XA（强一致、低吞吐）、TCC（业务补偿）、本地消息表 + MQ（最终一致）、Seata AT（自动补偿）。最优解是避免跨片事务：按聚合根/分片键设计，让一个业务事务落在同一分片。

12.7 Q7：分片下的深分页问题？ ​

LIMIT offset, size 会让每个分片都取 offset+size 条再归并，翻页越深开销越大且全局排序可能不稳。解法：限制翻页深度、游标分页（id > last_id）、时间游标、或查询走 ES。

12.8 Q8：分库分表后怎么做扩容？ ​

取模分片用 2N 翻倍法（每库只迁一半）；配合 binlog（Canal）增量回放减少停机；切流前做 count/抽样/校验和对账。范围分片扩容最简单：新数据进新区间，老数据不动。

12.9 Q9：什么情况下不该分库分表？ ​

数据量没到拐点、查询模型简单、或团队没有分布式基础设施时。分片引入分布式事务、跨片查询、扩容、运维复杂度，可能抵消收益。先做索引、缓存、归档、读写分离、垂直拆分，是更稳的演进。

12.10 Q10：绑定表和广播表是什么？ ​

绑定表：分片键与路由规则相同的关联表集合，JOIN 只在同分片内进行，避免笛卡尔积。广播表：每个分片都冗余的全局字典小表，读写时自动同步到所有分片。

12.11 Q11：ShardingSphere 一次查询的执行流程？ ​

SQL 解析（AST）→ 路由（按分片规则定位物理分片，无分片键则全路由）→ 改写（逻辑表名改物理表名、分页改写）→ 执行（分发到各分片）→ 归并（流式/内存归并出最终结果）。

12.12 Q12：分库分表和 MySQL 表分区有什么区别？ ​

分区是单实例内的透明拆分，解决单表治理（含按时间淘汰），不解决单机 IO/连接/写并发瓶颈；分库分表是多实例横向扩展，能解决容量与并发，但要付出路由、分布式事务与扩容成本。两者可以配合使用。

12.13 Q13：数据倾斜怎么处理？ ​

取模分片要求键均匀，热点键（大卖家）会导致个别分片过热。解法：热点键加盐拆散后扇出查询、热点数据独立超大分片或独立存储、只读热点冗余到缓存/ES。设计期选分布均匀的分片键是根本。

12.14 Q14：分片后 COUNT 和 GROUP BY 还能用吗？ ​

能用，中间件会广播到所有分片再归并，但性能随分片数线性下降，且不适合高频实时统计。生产上精确统计走汇总表/OLAP/ES，分片库只保留"按分片键维度"的轻聚合查询。
