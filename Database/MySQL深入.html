一、连接池 ​

数据库连接池是位于应用程序与数据库之间的连接缓存层，负责管理连接的创建、分配、销毁和回收。Java 生态中最主流的两个连接池是 HikariCP 和 Druid。

1.1 HikariCP vs Druid 对比 ​

对比维度HikariCPDruid
性能极快（号称零开销），吞吐量最高中等，因监控拦截器有额外开销
代码量约 130KB，极致精简约 1MB+，功能丰富
监控能力自带 light 级监控，需集成 Micrometer内置 StatViewServlet，Web 监控面板
SQL 审计无支持 WallFilter（防 SQL 注入）、日志审计
扩展能力通过 JDBI 原生接口扩展支持 Filter-Chain 模式，可自定义插件
连接泄露检测支持 leakDetectionThreshold支持 removeAbandoned
阿里生态无关完美适配，阿里巴巴官方出品
社区活跃度极高（Spring Boot 默认）高（国内使用广泛）

选型建议：

  • Spring Boot 项目：默认 HikariCP，无脑使用，性能最佳。
  • 需要监控大屏：选择 Druid，内置 StatViewServlet 可直接在浏览器查看连接池状态。
  • 需要 SQL 防注入：Druid 的 WallFilter 非常成熟，开箱即用。
  • 高并发低延迟场景：HikariCP 更优，性能损耗极低。

配置要点说明：

  • maximum-pool-size：并非越大越好。MySQL 的默认 max_connections 通常为 151，连接数过多会导致上下文切换加剧。计算公式建议：(core_count * 2) + effective_spindle_count。
  • minimum-idle：建议与 maximum-pool-size 相同，避免频繁创建销毁连接（短连接场景）。
  • max-lifetime：应小于 MySQL 的 wait_timeout（默认 28800 秒），避免服务端主动断开后客户端仍使用已失效连接。
  • leak-detection-threshold：建议开启，定位连接未归还的 Bug。

二、MySQL 索引（重点） ​

2.1 索引原理 ​

B+ 树结构 ​

MySQL InnoDB 存储引擎使用 B+ 树 作为索引结构。B+ 树具有以下特征：

  • 所有数据都存储在叶子节点，非叶子节点只存储键值（索引列的值）和指针。
  • 叶子节点之间通过双向链表链接，形成有序链表，支持高效的范围查询。
  • 每个节点对应一个磁盘页（InnoDB 默认 16KB），通过大量页内数据降低树的高度。

B+ 树结构示意图：

         /       |       \
    [内部节点] [内部节点] [内部节点]
    /    \     /    \     /    \
  [叶]  [叶] [叶]  [叶] [叶]  [叶]
   ⇄     ⇄    ⇄     ⇄    ⇄     ⇄    ← 双向链表
              [根节点]
         /       |       \
    [内部节点] [内部节点] [内部节点]

为什么用 B+ 树而不是其他结构？

结构缺点对比结论
哈希表不支持范围查询（>、<、BETWEEN），不支持排序仅适用于等值查询场景
二叉树树高随数据量指数增长，磁盘 I/O 次数多数据量大时性能急剧下降
红黑树本质是二叉平衡树，数据量大时树高约 20~30 层百万级数据需要 20+ 次 I/O，不可接受
B 树非叶子节点也存数据，单节点存储的键数量少，树更高B+ 树非叶节点不存数据，单节点可存更多键，树更矮
B+ 树非叶子节点只存键，叶子节点存数据 + 双向链表树高通常 3~4 层，3 次 I/O 即可定位数据

B+ 树的核心优势总结：

  1. 树高低：InnoDB 16KB 页大小，假设键值 + 指针约 1KB，一个非叶子节点可存 16 个键。三层 B+ 树可存 16 × 16 × 16 = 4096 页数据，每页约 200 条记录，总计约 80 万条。四层可达千万级别。
  2. 范围查询高效：叶子节点的双向链表，只需定位到起始记录，然后顺序扫描即可。
  3. 磁盘 I/O 友好：节点大小与磁盘页对齐，每次 I/O 读取一个完整节点。

聚簇索引 vs 二级索引 ​

  • 聚簇索引（Clustered Index）：InnoDB 中表就是索引组织表（IOT），聚簇索引的叶子节点存储整行数据。默认以主键作为聚簇索引，未定义主键时选择第一个 NOT NULL UNIQUE 列，再无则隐式生成 6 字节的 row_id。
  • 二级索引（Secondary Index / 辅助索引）：叶子节点存储的是主键值（而非行指针），通过二级索引查找需要先得到主键，再回表查询聚簇索引获取完整行数据。

-- 2. 通过聚簇索引 id = 100 回表查询完整行数据

联合索引（复合索引） ​

联合索引是指在多个列上建立的索引，遵循 最左前缀法则（Leftmost Prefix Rule）。

sql
CREATE INDEX idx_name_age ON user (name, age);
CREATE INDEX idx_name_age ON user (name, age);
1

最左前缀法则：

  • 查询条件必须从索引的最左列开始，且不能跳过中间的列。
  • 走索引的情况：WHERE name = ?、WHERE name = ? AND age = ?
  • 不走索引的情况：WHERE age = ?（跳过了最左列 name）

联合索引的排序特性：

联合索引的排序规则是先按第一列排，再按第二列排，以此类推。因此联合索引也可以用于 ORDER BY 的场景：

sql
-- idx_name_age 可以优化以下排序：
SELECT * FROM user WHERE name = '张三' ORDER BY age;   -- 走索引
SELECT * FROM user ORDER BY name, age;                  -- 走索引
-- 无法优化的排序：
SELECT * FROM user WHERE age = 25 ORDER BY name;         -- 索引跳跃扫描可能无法生效
-- idx_name_age 可以优化以下排序：
SELECT * FROM user WHERE name = '张三' ORDER BY age;   -- 走索引
SELECT * FROM user ORDER BY name, age;                  -- 走索引
-- 无法优化的排序：
SELECT * FROM user WHERE age = 25 ORDER BY name;         -- 索引跳跃扫描可能无法生效

索引下推（Index Condition Pushdown, ICP） ​

MySQL 5.6 引入的优化。在没有 ICP 时，存储引擎通过索引查询到数据行后，会将整行数据返回给 Server 层，Server 层再对 WHERE 条件中无法使用索引的列进行过滤。

启用 ICP 后，Server 层将部分 WHERE 条件下推到存储引擎层，在索引遍历过程中直接过滤不满足条件的记录，减少回表次数。

sql
-- 联合索引 idx_name_age (name, age)
-- ICP 生效场景
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
-- 联合索引 idx_name_age (name, age)
-- ICP 生效场景
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;

ICP 优化前后的对比：

无 ICP 时：

  1. 通过索引找到 name LIKE '张%' 的所有记录（可能很多）。
  2. 对每条记录回表查询完整行。
  3. Server 层检查 age = 25，丢弃不满足条件的行。

有 ICP 时：

  1. 通过索引找到 name LIKE '张%' 的记录。
  2. 在索引层面同时检查 age = 25，只对满足条件的记录回表。

ICP 可通过 EXPLAIN 的 Extra 列看到 Using index condition。

覆盖索引（Covering Index） ​

当查询所需的所有列都包含在索引中时，无需回表，直接通过索引即可获取数据。

sql
-- idx_name_age (name, age)
-- 覆盖索引查询
EXPLAIN SELECT name, age FROM user WHERE name = '张三';
-- Extra: Using index  （表示使用了覆盖索引）

-- 非覆盖索引查询（需要回表）
EXPLAIN SELECT * FROM user WHERE name = '张三';
-- Extra: NULL （需要回表查其他列）
-- idx_name_age (name, age)
-- 覆盖索引查询
EXPLAIN SELECT name, age FROM user WHERE name = '张三';
-- Extra: Using index  （表示使用了覆盖索引）

-- 非覆盖索引查询（需要回表）
EXPLAIN SELECT * FROM user WHERE name = '张三';
-- Extra: NULL （需要回表查其他列）

  • 避免回表，减少磁盘 I/O。
  • 对于二级索引，叶子节点只存储主键和索引列，数据量更小，单次 I/O 可读取更多记录。

2.2 索引优化 ​

字段选择（区分度与长度） ​

  • 区分度：索引列的重复率越低，索引效果越好。可用以下 SQL 计算区分度：
sql
SELECT COUNT(DISTINCT column_name) / COUNT(*) AS selectivity FROM table_name;
SELECT COUNT(DISTINCT column_name) / COUNT(*) AS selectivity FROM table_name;
1

区分度越接近 1 越好。区分度过低（如性别列，区分度约 0.5）的列不适合单独建索引。

  • 前缀索引：对于长字符串（如 URL、文章标题），可以使用前缀索引，只对前 N 个字符建立索引。
sql
CREATE INDEX idx_title_prefix ON article (title(10));
CREATE INDEX idx_title_prefix ON article (title(10));
1

选择前缀长度时，可通过以下方式评估：

sql
SELECT COUNT(DISTINCT LEFT(title, 5)) / COUNT(*) AS s5,
       COUNT(DISTINCT LEFT(title, 10)) / COUNT(*) AS s10,
       COUNT(DISTINCT LEFT(title, 15)) / COUNT(*) AS s15
FROM article;
SELECT COUNT(DISTINCT LEFT(title, 5)) / COUNT(*) AS s5,
       COUNT(DISTINCT LEFT(title, 10)) / COUNT(*) AS s10,
       COUNT(DISTINCT LEFT(title, 15)) / COUNT(*) AS s15
FROM article;

索引设计原则 ​

  1. 为频繁查询和排序的列建立索引：WHERE、JOIN、ORDER BY、GROUP BY 中出现的列。
  2. 使用联合索引替代多个单列索引：多个单列索引 MySQL 通常只会选择其中一个（Index Merge 有限场景可用），且占用更多空间。
  3. 索引列不宜过多：索引会降低写入性能（INSERT、UPDATE、DELETE 需要同时维护索引），单表索引建议控制在 5 个以内。
  4. 优先选择区分度高的列：区分度高的列放在联合索引的前面，可以更快地缩小数据范围。
  5. 使用覆盖索引：尽量让查询的列都在索引中，避免回表。
  6. 索引列尽量定义为 NOT NULL：NULL 值在索引中占用额外空间，且 IS NULL 查询可能无法走索引。

MySQL InnoDB 如何解决幻读：

在 REPEATABLE READ 级别下，InnoDB 使用 间隙锁（Gap Lock） + 临键锁（Next-Key Lock） 来防止幻读。范围查询时，不仅锁定命中的记录，还锁定记录之间的间隙，阻止其他事务在间隙中插入新记录。

4.4 MVCC 原理 ​

MVCC（Multi-Version Concurrency Control，多版本并发控制） 是 InnoDB 实现高并发事务隔离的核心机制。它通过维护数据的多个版本，让读操作不阻塞写操作，写操作也不阻塞读操作。

undo log 版本链 ​

InnoDB 每行记录包含两个隐藏列：

  • DB_TRX_ID：最近修改该行的事务 ID。
  • DB_ROLL_PTR：回滚指针，指向 undo log 中该行的上一个版本。

每次 UPDATE 操作，InnoDB 不会直接覆盖原数据，而是：

  1. 将当前行的数据拷贝到 undo log 中，作为历史版本。
  2. 修改当前行，更新 DB_TRX_ID 和 DB_ROLL_PTR，使其指向 undo log 中的旧版本。

这样就形成了一个版本链：

当前行（最新版本）
  ↑ DB_ROLL_PTR
版本 2（undo log）
  ↑ DB_ROLL_PTR
版本 3（undo log）
  ↑ DB_ROLL_PTR
...（更早的版本）
当前行（最新版本）
  ↑ DB_ROLL_PTR
版本 2（undo log）
  ↑ DB_ROLL_PTR
版本 3（undo log）
  ↑ DB_ROLL_PTR

对于版本链中的某个版本（trx_id 为修改该版本的事务 ID）：

  1. trx_id == creator_trx_id：当前事务修改的版本，可见。
  2. trx_id < min_trx_id：版本在 ReadView 生成前已提交，可见。
  3. trx_id >= max_trx_id：版本在 ReadView 生成后才开始，不可见。
  4. min_trx_id <= trx_id < max_trx_id：检查 trx_id 是否在 m_ids 中：
    • 如果在 m_ids 中（事务未提交），不可见。
    • 如果不在 m_ids 中（事务已提交），可见。

4.5 RC vs RR 级别 MVCC 区别 ​

对比维度READ COMMITTED（RC）REPEATABLE READ（RR）
ReadView 生成时机每条 SQL 执行时生成事务第一次执行 SELECT 时生成，复用至事务结束
相同事务两次读取可能不同（不可重复读）始终一致（可重复读）
间隙锁不使用使用（防止幻读）
性能更高（不用间隙锁）略低（间隙锁开销）
默认级别Oracle、PostgreSQL 默认MySQL InnoDB 默认
适用场景对一致性要求不高，追求高并发需要事务内多次读取一致

核心区别一句话总结：

RC 每条语句生成一个新的 ReadView，所以能看到其他事务已提交的修改；RR 只在事务开始时生成一次 ReadView，所以事务内看到的数据始终一致。

5.3 间隙锁产生条件 ​

6.5 分片策略 ​

策略原理优点缺点
取模（MOD）hash(key) % N数据分布均匀扩容需重新分布（翻倍扩容可缓解）
范围（RANGE）按 ID 区间划分（1~1000 在库 1，1001~2000 在库 2）扩容方便，范围查询友好可能数据倾斜
一致性哈希将哈希值空间组织成环，按顺时针方向分配扩容仅影响相邻节点，数据迁移量小实现复杂，可能有数据倾斜（引入虚拟节点缓解）
时间（TIME）按年 / 月分片适合日志、时序数据数据热点随时间迁移

一致性哈希 vs 取模：

java
// 取模分片算法（简单实现）
public class ModShardingAlgorithm {
    public String doSharding(Long shardingKey, int databaseCount) {
        return "ds" + (shardingKey % databaseCount);
    }
}

// 一致性哈希（关键代码思路）
public class ConsistentHashShardingAlgorithm {
    private final TreeMap<Integer, String> circle = new TreeMap<>();
    private static final int VIRTUAL_NODES = 160;

    public ConsistentHashShardingAlgorithm(List<String> nodes) {
        for (String node : nodes) {
            for (int i = 0; i < VIRTUAL_NODES; i++) {
                int hash = hash(node + "#" + i);
                circle.put(hash, node);
            }
        }
    }

    public String getNode(Long key) {
        int hash = hash(String.valueOf(key));
        // 找到第一个大于等于 hash 的节点
        Map.Entry<Integer, String> entry = circle.ceilingEntry(hash);
        if (entry == null) {
            entry = circle.firstEntry();
        }
        return entry.getValue();
    }

    private int hash(String key) {
        // FNV1_32_HASH 或其他哈希算法
        return key.hashCode() & 0x7fffffff;
    }
}

雪花算法（Snowflake） 是 Twitter 开源的分布式 ID 生成算法，生成的 ID 为 64 位 Long 型整数。

特点：

  • 全局唯一，趋势递增。
  • 时间戳高位在前，ID 整体呈递增趋势。

Java 实现：

java
public class SnowflakeIdGenerator {
    // 起始时间戳（2021-01-01 00:00:00）
    private static final long START_EPOCH = 1609459200000L;

    // 位数分配
    private static final long WORKER_ID_BITS = 10L;        // 工作节点 ID 10 位
    private static final long SEQUENCE_BITS = 12L;         // 序列号 12 位

    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);
    private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);

    // 位移
    private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;

    private final long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdGenerator(long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException("Worker ID out of range");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();

        if (timestamp < lastTimestamp) {
            // 时钟回拨处理：可等待或抛出异常
            throw new RuntimeException("Clock moved backwards");
        }

        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0) {
                // 当前毫秒序列号用完，等待下一毫秒
                while ((timestamp = System.currentTimeMillis()) <= lastTimestamp) {
                    // busy spin
                }
            }
        } else {
            sequence = 0L;
        }

        lastTimestamp = timestamp;

        return ((timestamp - START_EPOCH) << TIMESTAMP_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence;
    }
}

7.3 binlog 恢复 ​

binlog（Binary Log） 是 MySQL 的二进制日志，记录所有数据变更操作（DDL 和 DML），用于数据恢复和主从复制。

binlog 配置：

ini
[mysqld]
# 开启 binlog
log_bin = /var/log/mysql/mysql-bin.log
# binlog 格式（推荐 ROW）
binlog_format = ROW
# binlog 保留天数
expire_logs_days = 7
# 单个 binlog 文件大小
max_binlog_size = 1G
# 缓存大小
binlog_cache_size = 4M
# 每次事务提交时写入并刷新磁盘（最安全）
sync_binlog = 1

误删数据的快速恢复流程：

1. 立即停止应用写入，防止新 binlog 覆盖旧数据
2. 找到最近一次全量备份
3. 恢复到临时数据库（或同一实例的不同库）
4. 从 binlog 导出从备份时间点到误操作前的增量 SQL
5. 将增量 SQL 应用到恢复的数据库
6. 导出误删除的数据，导入生产库
