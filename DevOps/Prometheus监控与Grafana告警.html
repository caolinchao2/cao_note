Prometheus 监控与 Grafana 告警 ​

面向生产环境的指标监控与告警体系，覆盖 Prometheus 原理、exporter 生态、PromQL、Alertmanager、Grafana 可视化的完整落地笔记。

一、监控体系概览 ​

1.1 为什么需要监控 ​

监控是运维的"眼睛"，回答三个问题：系统现在是否健康、过去发生了什么、未来是否会出现故障。没有监控就没有告警，没有告警就只能等用户投诉，再被动排查，MTTR（平均修复时间）会被无限拉长。

一个完整的监控体系应当具备的能力：

能力说明典型工具
指标采集周期性抓取 CPU、内存、请求量等数值Prometheus、Zabbix Agent
可视化将指标绘制成趋势图、仪表盘Grafana、Kibana
告警通知指标异常时触发通知到人Alertmanager、Zabbix
数据存储保存时序数据供回溯查询Prometheus TSDB、Thanos
链路与日志定位单次请求的详细原因SkyWalking、ELK

1.2 监控四类黄金指标与 USE/RED 方法论 ​

业界有两套经典的指标建模方法论：USE 与 RED，分别面向"资源"和"服务"两个视角。

USE 方法（面向基础设施资源）

字母含义问题示例
UUtilization 利用率资源是否繁忙CPU 使用率、磁盘使用率
SSaturation 饱和度资源排队/过载CPU 运行队列、磁盘 IO 等待
EErrors 错误资源是否出错磁盘坏道、网卡丢包

USE 适合评估一台机器、一个存储、一条网络链路是否健康，node_exporter 的指标基本都围绕 USE 展开。

RED 方法（面向应用服务）

字母含义示例
RRate 请求速率QPS、RPS
EErrors 错误请求数5xx 数量、错误率
DDuration 请求耗时平均耗时、P99 耗时

RED 适合评估一个 API 服务、一个 RPC 调用是否健康。Redis 官方推荐的监控即为此模式。

1.3 Google SRE 四个黄金信号 ​

Google《SRE 运维解密》提出监控网络系统最应关注的四个信号，比 USE/RED 更高一层：

信号含义对应问题典型指标
延迟（Latency）请求处理耗时服务慢不慢请求耗时 P50/P99
流量（Traffic）系统负载压力服务忙不忙QPS、带宽吞吐
错误（Errors）请求失败比例服务对不对错误率、5xx 比例
饱和度（Saturation）资源耗尽程度还能撑多久CPU/内存/队列深度

SRE 要求所有服务至少暴露这四类信号，内部称为"黄金信号"，任何告警都应能映射到其中一个信号，否则这条告警大概率没有意义。

1.4 监控分层 ​

监控对象从上到下分层，每一层关注的指标与工具不同：

层次监控对象关注指标常用工具
业务层订单量、支付成功率、转化率业务 KPI、漏斗埋点平台、自定义 exporter
应用层服务接口、中间件客户端QPS、错误率、耗时、JVMmicrometer + Prometheus
容器/编排层Pod、容器、K8s 集群容器 CPU/内存、调度状态cAdvisor、kube-state-metrics
基础设施层服务器、网络、存储CPU/内存/磁盘/IO/网络node_exporter、SNMP
中间件层MySQL、Redis、MQ连接数、慢查询、延迟mysqld_exporter 等

分层的好处是故障时可以快速"从上往下"定位：先看业务指标是否异常，再看应用层，最后落到基础设施，逐层缩小范围。

1.5 监控系统如何选择 ​

维度小型/初创中大型互联网传统企业
指标监控Prometheus 单机Thanos/ VictoriaMetrics 集群Zabbix
可视化GrafanaGrafana自带 Web / Grafana
告警AlertmanagerAlertmanager + 自愈平台短信/邮件平台
链路/日志SkyWalking + ELKOpenTelemetry + Loki商用 APM

Prometheus 是目前云原生事实标准的监控系统，本篇以其为主线。

二、Prometheus 核心概念与原理 ​

2.1 Prometheus 是什么 ​

Prometheus 是由 SoundCloud 开发、后捐献给 CNCF 的开源监控与告警系统，是 Kubernetes 监控的事实标准。核心特点：

特性说明
指标采集基于 HTTP 周期性拉取（Pull）
数据模型多维数据模型，指标名 + 标签（Label）
查询语言PromQL，支持聚合、运算、函数
存储内置本地 TSDB，支持远程存储对接
告警独立组件 Alertmanager 负责通知
生态官方 + 社区 exporter 极其丰富

Prometheus 的定位是"指标（Metrics）监控"，它不采集日志、不做分布式追踪，那部分由 ELK/SkyWalking 等负责。

2.3 四种指标类型 ​

类型含义典型值适用场景关键点
Counter（计数器）只增不减的累计值请求总数、CPU 总时长QPS、错误数用 rate() 求速率
Gauge（仪表）可增可减的当前值CPU 使用率、内存、温度资源水位可直接查询当前值
Histogram（直方图）桶累计分布请求耗时分布P99、耗时统计自带 _bucket/_sum/_count
Summary（摘要）客户端计算分位数耗时 P99无法聚合的分位分位数无法跨实例聚合

Counter 只能上升或归零重置，不能下降；计算"每秒速率"必须配合 rate/irate。Histogram 由服务端（Prometheus）计算分位数，可以跨实例聚合；Summary 在客户端算好分位数，多个实例无法合并，这是两者最重要的区别。

2.4 Pull 模型 vs Push 模型 ​

对比项Pull（Prometheus）Push（Zabbix/自研 push）
数据流向Prometheus 主动拉取Agent 主动上报
服务发现天然支持（K8s、DNS、Consul）需要中心端管理 Agent 列表
存活探测拉不到即知目标挂了需额外超时判断
安全性目标端只需暴露端口中心端需开放接收端口
扩展性每实例拉取，目标数受抓取能力限制中心端易成瓶颈

Pull 的优势在于"谁监控谁拉取"的职责清晰，配合服务发现在动态环境（容器/K8s）中非常自然；缺点是网络不通时无法拉取，因此跨网络（如采集公网第三方数据、离线任务数据）需借助 Pushgateway。

2.5 Pushgateway 及其适用场景 ​

Pushgateway 是一个独立组件，允许无法被 Pull 的任务把指标推送到一个中间网关，Prometheus 再从网关拉取。

适用场景：

  • 短生命周期批处理任务（定时 Job、离线跑批）：任务启动到结束过快，Prometheus 拉不到
  • 位于防火墙后、Prometheus 无法直连的目标

不适用场景（常见误用）：

  • 业务接口指标推送（应直接暴露 /metrics 端点由 Prometheus 拉取）
  • 多实例聚合推送同一组指标（Pushgateway 上旧值不会自动清除，容易产生"僵尸指标"导致误告警）

使用 Pushgateway 时务必在任务结束时调用 delete API 删除旧指标，或为标签带上任务唯一 ID。

2.7 本地存储与 TSDB 要点 ​

Prometheus 内置高性能时序数据库 TSDB，默认数据目录 /prometheus，每个样本占约 1~2 字节（压缩后）。

要点说明
存储格式每 2 小时为一个 block，包含 chunks、index、tombstones
压缩后台对旧 block 做压缩合并，减少文件数
写入方式追加写 WAL，崩溃后可恢复
查询支持按时间范围下钻，删除标记用 tombstone 实现
保留策略--storage.tsdb.retention.time（默认 15 天）
删除限制删数据按序列匹配，打 tombstone 异步清理

单机 Prometheus 的局限：数据不复制、无水平扩展，查询压力大时会影响抓取。规模上来后需要用 Thanos 或 VictoriaMetrics 做联邦/分片/长期存储（见 8.3）。

2.8 relabel 与 service discovery ​

服务发现让 Prometheus 知道"该抓谁"，relabel 让它在抓取前改写目标。

常用服务发现方式：

方式适用场景配置
static_configs固定 IP 的物理机/虚拟机静态列表
kubernetes_sd_configsPod/Service/EndpointK8s 原生发现
file_sd_configs动态变化的文件列表配合 CMDB/脚本生成
consul_sd_configs / dns_sd注册中心 / DNS服务网格等场景

relabel 的核心用途：

  • keep/drop：按标签过滤，只保留要采集的目标，降低基数
  • replace：把 __meta_* 元标签改写为正式标签（如把 Pod 名映射为 instance）
  • labelmap：批量拷贝标签
  • labeldrop：丢弃高基数标签

relabel 在抓取前作用于目标元数据，与 PromQL 里的 label 操作不是一回事。

四、exporter 生态 ​

4.1 exporter 机制 ​

6.1 告警链路与 Alertmanager 定位 ​

Prometheus 只负责"产生告警事件"，真正的通知发送由 Alertmanager 完成：

Prometheus 规则评估
   │  触发（pending → firing）
   ▼
Alertmanager ──去重 → 分组 → 抑制 → 静默──> 通知（email/webhook/企微/钉钉）
Prometheus 规则评估

6.2 分组 / 抑制 / 静默原理 ​

分组（grouping）：把拥有相同 group_by 标签的告警合并成一条通知。例如 50 台机器同时 CPU 高，若按 instance 分组会发 50 条；若按 job 分组只发 1 条列出 50 个实例。

8.1 高基数问题（High Cardinality） ​

每个唯一的标签组合都会产生一条独立时间序列，序列数量 = 各标签取值数的笛卡尔积。高基数会导致：

  • 抓取数据量大，内存/磁盘暴涨
  • 查询变慢，图表加载卡顿
  • Prometheus 被拖垮（OOM）

http_request_total{method="POST", status="200", uri="/api/order/{id}"}

8.5 告警风暴治理 ​

告警风暴（Alert Storm）指短时间内大量告警轰炸，根因通常是单一故障引发级联。治理清单：

手段说明
根因抑制上游宕机抑制下游告警（inhibit_rules）
分组合并同类告警归并成一条
依赖告警降级只对"用户可感知"发 critical
容量告警带预估磁盘"还能撑 N 小时"比"85%"更有行动价值

一个经验法则：告警应能回答"然后呢？"，否则就是噪音。每次告警都应能说清影响范围、处理动作、升级路径。

场景表现对策
手工写 PromQL 时间误按本地时间计算明确写入时为 UTC
告警消息模板通知时间显示 UTC 差 8 小时模板中 humanizeTimestamp 或转本地格式化
业务低峰判定以 UTC 判定业务低谷做静默/维护转换到 Asia/Shanghai 再判断
Grafana 服务端时区多时区团队看到不同时间轴统一面板设置固定时区

十、面试考点速查 ​

10.1 Q1：Prometheus 为什么用 Pull 模型而不是 Push？ ​

Pull 的优势：1）目标清单由 Prometheus 侧控制，通过服务发现在动态环境自动管理，Push 则需要在中心端登记每个目标；2）拉取天然具备健康检查能力，拉不到即代表目标或 exporter 异常；3）监控端只读访问目标端口，便于网络与安全管控；4）天然规避"监控端成为写瓶颈"，扩缩容只需加 Pull 循环。Push 只在短任务、跨网络隔离等无法被拉取的场景由 Pushgateway 兜底。

10.2 Q2：Counter、Gauge、Histogram、Summary 的区别与选型？ ​

Counter 只增不减用于计数，必须配合 rate 使用；Gauge 可增可减表示当前状态；Histogram 与 Summary 都用于耗时/大小分布，但 Histogram 由服务端聚合计算分位、可跨实例求和，Summary 在客户端计算、不可聚合。需要全局 P99（如网关聚合全量流量）选 Histogram，单实例独立统计且无聚合需求可选 Summary。

10.3 Q3：rate 与 irate 的区别，如何选择？ ​

两者都用于 counter：rate 计算整个时间窗口的平均每秒增长率，曲线平滑，适合慢变量与告警阈值判断；irate 只取窗口内最后两个样本计算瞬时速率，能反映突刺但曲线锯齿明显。常规监控选 rate（窗口 ≥ 4 倍抓取间隔），捕捉瞬时限流/突刺可辅助看 irate。

10.4 Q4：Prometheus 高基数问题如何发现和治理？ ​

发现：用 count(metric_name) 观察单指标序列数，比较日增量、抓取耗时与内存增长。治理：标签只放有限维度的分类字段（method/status/uri 模板），禁止放用户 ID、IP、时间戳等无限取值；relabel 阶段 labeldrop；路径归一化；必要时拆指标单独统计。长期方案是控制业务埋点规范并在发布流程加入基数 review。

10.5 Q5：如何避免告警风暴？ ​

五板斧：1）规则加 for 等待期过滤瞬断；2）Alertmanager 按 alertname/job 分组合并同类告警；3）inhibit_rules 用根因告警抑制级联告警（如节点宕机抑制其上的服务告警）；4）告警分级与静默，维护窗口主动屏蔽；5）告警阈值贴合真实容量（用历史 P95 定阈值而非拍脑袋），并持续按误报率复盘收敛规则。

10.6 Q6：为什么计算 QPS 用 rate 而不是直接用 counter 的当前值？ ​

counter 是累计值，从进程启动累加至今，单看当前值没有意义，且进程重启后会归零重计。rate 取窗口内增量除以时长，得到有业务含义的每秒速率，同时正确跳过 counter 的归零重置（Prometheus 内部按递增插值处理）。同理，increase 求的是窗口内"真实增量"，也避开了重启归零。

10.7 Q7：histogram_quantile 的误差来源与正确用法？ ​

histogram_quantile(0.99, rate(x_bucket[5m])) 的入参必须是累积 _bucket 序列的速率，输出是对目标分位所在桶的线性插值估计而非精确值，桶设计越密误差越小（通常按 10ms/50ms/100ms/250ms/500ms/1s/2.5s/5s 指数分布）。要点：1）用 rate 包裹 bucket；2）跨实例用 sum by (le) 聚合后再算分位；3）le 边界与业务耗时分布匹配，否则 P99 会"卡"在某档位失真。

10.8 Q8：Pushgateway 的坑有哪些，什么场景才用它？ ​

坑：1）Pushgateway 不会自动清除指标，短任务崩溃后旧值残留造成假告警，须任务结束调 delete API 或给标签带任务唯一 ID；2）不适合大批量业务指标，它会成为单点与性能瓶颈；3）多实例往同一组标签推值会互相覆盖。正确场景：无法被 Pull 的短生命周期批处理（cron、离线跑批）与网络隔离目标。能用 Pull 解决的都不要上 Pushgateway。

10.9 Q9：Grafana 变量在面板中如何工作？ ​

变量本质是"查询参数的占位符"。Query 类型变量通过 label_values(指标, 标签名) 从 Prometheus 动态拉取可选项（如全部 instance），面板查询中用 $var 引用；变量可级联（后一个变量查询引用前一个变量）实现 instance → 相关指标的联动过滤。多环境共用一套面板就靠环境变量（Constant）或数据源变量切换。

10.10 Q10：从告警到定位一次故障，标准排查路径是什么？ ​

以"订单服务 P99 升高"告警为例：1）看 Grafana 确认影响面（该接口还是全站、错误率是否同步升高）；2）看饱和度信号（CPU/内存/连接池/GC）判断是资源瓶颈还是代码问题；3）若资源正常，用 traceId 到链路系统看耗时分布在哪一段调用；4）到日志系统按 traceId/时间段拉错误堆栈与慢日志；5）对比发布记录与变更窗口，确认是否新版本引入；6）恢复后补告警与复盘。指标定位"在哪"，链路定位"哪一段"，日志定位"为什么"。
