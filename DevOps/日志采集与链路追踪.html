日志采集与链路追踪 ​

面向生产环境的日志体系与分布式链路追踪落地笔记，覆盖 ELK/Loki、OpenTelemetry、SkyWalking、traceId 贯穿排障的完整方法论。

一、可观测性三支柱 ​

1.1 什么是可观测性（Observability） ​

可观测性指通过系统外部输出的数据（指标、日志、链路），推断系统内部状态的能力。它与传统"监控"的区别在于：监控回答"是否出问题"，可观测性回答"为什么出问题"，并且能回答"未知的未知问题"。

DevOps 演进到微服务 + 容器化后，一次请求跨多个服务、几十个实例，单机 tail 日志的方式已不可行，可观测性成为生产运维的刚需。

1.2 Metrics / Logs / Traces 三支柱 ​

支柱数据形态回答的问题成本特征代表工具
Metrics（指标）数值时序现在是否有问题、趋势如何低（采样/聚合后很小）Prometheus、Grafana
Logs（日志）带时间戳的文本事件出错时的细节、上下文是什么高（量大、占存储）ELK、Loki、Splunk
Traces（链路）一次请求的调用树（span）慢请求卡在哪一段、依赖如何中（按采样控制）SkyWalking、Jaeger、Zipkin

三者互补，单独任何一柱都无法完成根因分析：

  • 指标发现异常（订单服务 P99 升高）
  • 链路定位范围（慢在调用下游 A 服务）
  • 日志还原现场（A 服务抛出的具体异常堆栈）

1.3 三者的关联方式 ​

关联字段含义打通方式
instance / hostname指标与日志归属同一台机器日志采集端补充 instance 标签
traceId一次全链路请求的唯一 ID日志埋入 traceId（MDC），链路与日志按 ID 互查
timestamp所有数据都带时间统一时区、统一时钟（NTP）
service.name / app服务维度统一命名指标、日志、链路统一打服务标签

工程上最常见的目标是：在 Grafana 面板上看到指标异常，点击即可跳转到该实例、该时间段的日志与链路。这要求日志平台、指标平台共享一套服务命名与时间对齐规则。

1.4 从监控到可观测的演进 ​

阶段特征手段
监控单机脚本 + 定时巡检Nagios、cron + shell
集中监控统一采集平台，阈值告警Zabbix、云监控
集中日志日志统一检索ELK、Splunk
链路追踪微服务调用关系可视化SkyWalking、Jaeger
可观测性平台三支柱统一打通 + SLOGrafana Stack、云厂商可观测平台

二、日志体系 ​

2.1 日志规范：格式 / 级别 / 脱敏 ​

日志是排障的第一手资料，规范决定了日志系统可检索性的上限。

格式规范（推荐 JSON 或 KV 结构化）：

text
# 非结构化（难以检索，不推荐）
2026-09-09 10:00:01 ERROR 订单创建失败

# KV 结构化（可检索，够用）
time=2026-09-09T10:00:01.123+08:00 level=ERROR app=order-service traceId=ab12cd user=10086 msg="订单创建失败" orderId=998877

# JSON 结构化（最推荐，日志平台解析最省事）
{"ts":"2026-09-09T10:00:01.123+08:00","level":"ERROR","app":"order-service","traceId":"ab12cd","user":"10086","msg":"订单创建失败","orderId":"998877"}

级别规范：

级别使用时机示例
DEBUG本地/测试联调细节参数、中间态
INFO关键业务节点下单成功、支付回调
WARN可恢复的异常/降级重试、缓存穿透、限流触发
ERROR需要关注的失败调用下游失败（含堆栈）
FATAL进程不可继续初始化失败退出

脱敏规范：

数据类型处理
手机号、身份证打码 138****1234
银行卡、支付 token不落盘，只记后四位
密码、密钥禁止打印，误打需走密钥轮换
请求头 Cookie默认不打，必要时打码

注意：脱敏应在"业务代码打日志时"就完成，不要在日志平台后处理——后处理意味着数据已经落盘，已存在泄露风险。

2.2 日志采集架构演进 ​

阶段架构问题
单机时代上服务器 grep 日志文件无法检索历史、多机低效
简单集中应用把日志写到共享存储/NFS格式不一、无检索、单点
ELK 集中检索Filebeat → Logstash → ES → Kibana解决检索，运维成本上升
轻量云原生Promtail → Loki → Grafana基于 label 索引，成本低
可观测一体OpenTelemetry + 统一后端三支柱打通

Logstash 解析配置：

ruby
# logstash.conf
input {
  beats { port => 5044 }
}

filter {
  # 按 grok 规则解析 JSON 格式日志
  if [message] =~ /^{.*}$/ {
    json { source => "message" }
  } else {
    grok {
      match => { "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} %{DATA:msg}" }
    }
  }
  date {
    match => ["ts", "ISO8601"]           # 用日志自带时间，而非采集时间
    target => "@timestamp"
  }
  mutate {
    add_field => { "app" => "order-service" }
    remove_field => ["message"]           # 已解析则去除原始字段，节省存储
  }
}

output {
  elasticsearch {
    hosts => ["http://elasticsearch:9200"]
    index => "app-logs-%{+yyyy.MM.dd}"
  }
}

2.4 Loki + Promtail + Grafana 轻量方案 ​

Loki 是 Grafana Labs 推出的"日志版 Prometheus"：不建立全文索引，只索引日志的标签（label），正文按块压缩存储。查询时先按 label 缩小范围再扫正文。

对比项ELKLoki
索引方式全文倒排索引仅标签索引 + 正文扫描
资源消耗高（需要大内存 ES 集群）低（单机可跑）
查询语法KQL/LuceneLogQL（类 PromQL）
与 Grafana 集成需插件原生集成
全文模糊检索强弱（数据量大时扫描慢）
适合场景复杂检索、安全审计云原生环境排障为主

三、Elasticsearch 在日志场景的要点 ​

3.1 为什么日志场景的 ES 要单独设计 ​

日志是"写多读少、可丢失、按时间冷热分明"的数据，与业务检索场景差异很大。直接用默认配置跑日志，很快会遇到：索引无限增长、磁盘打满、分片过多、写入被 bulk 压垮。因此日志场景的 ES 需要专门设计索引生命周期与分片策略。本节只聚焦日志场景，不展开 ES 全部知识。

3.2 索引生命周期管理（ILM） ​

ILM 让索引按"年龄/大小/文档数"自动流转阶段：

hot（热：写入+近期查询）→ warm（温：只读优化）→ cold（冷：压缩）→ delete（删除）
hot（热：写入+近期查询）→ warm（温：只读优化）→ cold（冷：压缩）→ delete（删除）

3.3 冷热架构 ​

日志数据访问频率随时间快速下降：当天的日志需要频繁查，30 天前的几乎无人问津。冷热架构把不同温度的数据放到不同性能的节点上：

节点角色硬件存放数据职责
Hot（热节点）SSD、内存大最近 1~3 天承接写入与高频查询
Warm（温节点）普通 SAS数周~数月低频查询
Cold（冷节点）大容量 HDD数月历史极少访问、合规保留

配合 ILM 的 allocate action 把数据按阶段迁移到对应节点。若历史数据连冷查询都很少，可以定期把老索引 snapshot 到对象存储（OSS/S3），需要时再恢复。

4.1 Trace 与 Span 概念 ​

分布式链路追踪记录一次业务请求从入口到所有下游调用的完整路径。

Trace（链路）一次完整请求，由根 span 和它的所有子孙 span 组成

Parent-Childspan 间的父子关系，构成调用树
root span链路根节点（通常是入口网关/控制器）

字段长度含义
trace-id32 位十六进制全链路唯一

4.4 采样策略 ​

全量采集每条链路的成本很高，生产环境必须采样。核心权衡：数据量 vs 覆盖率。

采样方式说明优缺点
固定比例采样（概率采样）按概率（如 10%）决定是否记录实现简单，但低流量接口可能一条都采不到
头部采样（Head-based）在请求入口决定整条链路是否采样一旦决定不可更改，尾端错误可能漏采
尾部采样（Tail-based）链路结束后按结果决定是否保留可保证错误链路 100% 保留，成本高、需缓冲
动态采样按错误率/延迟自适应调整复杂，多为商业 APM 能力

工程推荐组合：入口按 10%~20% 概率采样 + 错误链路强制全采（很多系统用 head 采样无法事后补采，于是退而求其次"提高错误接口的采样率"或对慢请求单独打点）。另有一类关键链路（支付、下单）可配置 100% 采样并设配额上限，防止极端流量打爆后端。

6.3 与日志系统关联：traceId 注入 MDC ​

要把日志与链路打通，需要在日志里带上 traceId。SkyWalking Agent 已自动把 traceId 放入 SLF4J MDC（key 为 tid），若用 OTel + 手动方案，通常用一个过滤器在入口设置：

java
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

@Component
public class TraceIdMdcFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws java.io.IOException, jakarta.servlet.ServletException {
        // 优先取链路系统下发的 traceparent，否则自生成
        String traceParent = request.getHeader("traceparent");
        String traceId = extractTraceId(traceParent);   // 解析 32 位 trace-id
        if (traceId == null) {
            traceId = java.util.UUID.randomUUID().toString().replace("-", "");
        }
        MDC.put("traceId", traceId);
        response.setHeader("x-trace-id", traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove("traceId");   // 必须清理，防止线程池串号
        }
    }
}

九、生产实践与坑 ​

9.1 采样率过高导致的成本与容量问题 ​

trace 每条 span 大约 0.5~2 KB（含标签），亿级 QPS 的服务若全量采集，一天就是 TB 级。成本失控常表现为：存储暴涨、ES 写入打满、OAP/后端成为新瓶颈。

手段说明
分级采样核心链路 100%，普通接口 10%，日志型/轮询类接口 1%
错误全采通过 OTel 尾部采样或提高失败分支采样权重
健康检查去噪过滤健康检查/心跳请求的 span
配额与熔断Agent 侧设置每秒最大 span 数，超限降级丢弃
定期归档老 trace 移到冷存储，只保留近期全量

9.3 时区与时间戳的坑 ​

坑说明对策
日志时间用本地时区服务器时区不一致导致排序错乱统一 Asia/Shanghai，或用 ISO8601 带时区
Logstash 用采集时间网络/缓冲导致 @timestamp 偏移date filter 以日志自带时间为准
服务器时钟漂移多机时间不一致，跨服务排序失真全量 NTP/chrony 校时
Kibana 显示 UTC界面默认 UTC 观感差设置 Kibana 时区为本地

跨服务日志按时间线排列是排查的基本功，前提是全链路同一时区、同一时钟源。

9.4 多语言接入差异 ​

语言常用接入注意点
JavaSkyWalking Agent / OTel javaagent注意与自身 agent（如 Arthas、APM）冲突

9.5 ES 日志索引膨胀治理 ​

症状原因治理
索引数持续上涨无 ILM/删除策略必须上 ILM（见 3.2）
单索引分片过多默认 5 分片 × 30 天按日写入量重算分片数
字段无限增长动态映射被日志撑爆关闭动态 mapping 或白名单字段
磁盘缓慢增长未压缩、未冷化forcemerge、冷节点、snapshot 到对象存储
查询越来越慢索引太多扫全量时间过滤 + 索引模式按天聚合

一个可落地的治理节奏：每天例行检查索引数与集群存储水位，设置"索引数 > N 或存储 > 70%"自动告警；每月归档一次超过查询窗口的老索引。

9.6 告警与日志联动 ​

实践说明
ERROR 日志率告警按服务统计 ERROR 条数/分钟，超过基线告警（LogQL/ES agg）
关键字告警特定致命错误（OOM、连接池耗尽）出现即告警
告警附日志链接通知模板里带 Kibana/Loki 深链，点开即看上下文
指标告警关联日志指标触发后自动附带最近 5 分钟 ERROR 日志摘要（webhook 加工）
避免日志告警风暴关键字告警必须去重合并（同 traceId 只报一次）并设静默

日志告警的定位是"补充"，不能替代指标告警：错误日志多往往是指标异常的结果而非原因，两者联动（先指标后日志）才能避免海量日志刷屏掩盖真问题。

十、面试考点速查 ​

10.1 Q1：如何排查线上慢接口？ ​

标准三级下钻：1）先看指标缩小范围——该接口 P99 升高是全局还是单实例，错误率是否同步（Prometheus/Grafana）；2）用链路追踪看调用瀑布——慢在自身代码还是下游（DB/Redis/下游 HTTP），对比跨服务 span 耗时；3）拿 traceId 到日志系统查上下文——异常堆栈、慢 SQL、GC、连接池等待。最后核对发布窗口与变更。核心是"指标定范围、链路定位置、日志定原因"，而不是上服务器瞎猜。

10.2 Q2：全链路压测时如何观测？ ​

压测前：确认采样率（压测流量大，通常压测链路单独打标或调低采样，避免观测系统被打爆）、确认监控指标齐全（QPS/RT/错误率/饱和度）。压测中：实时盯四层——网关/入口 QPS 与错误率、各服务 RT 分位、资源饱和度（CPU/内存/连接池/GC）、链路拓扑是否出现新瓶颈边。压测后：结合 trace 分析长尾请求与跨服务排队，输出瓶颈清单与容量结论。压测流量的 trace 建议带特殊标签（如 load_test=true），便于与生产流量区分统计。

10.3 Q3：traceId 如何透传？从入口到下游完整讲一遍。 ​

入口（如网关/Filter）生成或解析 traceId：有上游 traceparent 头则沿用其 trace-id，否则生成新的；把 traceId 放入 MDC 供本服务日志使用。发起下游调用（HTTP/gRPC/MQ）时在请求头写入 traceparent: 00-<trace-id>-<新span-id>-01（MQ 则放消息属性）。下游服务同样逻辑：解析头 → 生成子 span → 继续透传。注意：1）异步线程要手动传递 MDC 与 span 上下文；2）用 RestTemplate/Feign/HTTP Client 需确保拦截器已加；3）响应头回写 x-trace-id 便于客户端报障时提供。技术栈用 SkyWalking Agent 或 OTel 后，这些自动完成。

10.4 Q4：日志采集为什么用 Filebeat 而不用 Logstash 直接采集？ ​

职责分离与资源占用：Logstash 是重量级管道（JVM，吃内存），适合做复杂解析/富化/路由；Filebeat 是 Go 写的轻量采集器（常驻内存几十 MB），只做"读文件 + 转发"，还内置背压、多行合并、断点续传。架构上让 Filebeat 贴近业务机做采集，Logstash 集中做清洗，采集抖动不影响业务、解析抖动不丢原始日志（Filebeat 本地缓冲可重传）。小规模场景也可 Filebeat 直连 ES 省掉 Logstash。

10.5 Q5：Elasticsearch 日志索引为什么按天拆分？怎么防止无限膨胀？ ​

按天拆分的好处：1）过期清理按天删除整个索引，成本远低于按文档删；2）索引大小可控，分片与查询性能稳定；3）配合 ILM 冷热分层（热 1~3 天 SSD → 温数周 → 冷数月 → 删除）与时间过滤查询。防膨胀三板斧：ILM 强制删除/归档策略、按日写入量反推分片数（单分片 30~50GB）、关闭或约束动态 mapping。没有 ILM 的日志集群必然会被打满磁盘，这是必须预设而非事后补救的。

10.6 Q6：SkyWalking 与 Zipkin/Jaeger 怎么选？ ​

看诉求：存量 Java 微服务、要"接入即用"的拓扑图与告警 → SkyWalking（Agent 无侵入、OAP 自带聚合分析）；追求标准统一、多语言、自建可替换后端 → OTel + Jaeger（埋点端标准，后端随意换）；两者都要可叠加——OTel 数据可经 Collector 导给 SkyWalking。Zipkin 更适合历史 Sleuth 技术栈平滑过渡。云上资源丰富且不想运维 ES/OAP，则直接云厂商 APM。

10.7 Q7：日志系统的时区与多行日志如何处理？ ​

时区：日志格式用 ISO8601 带时区偏移或统一 Asia/Shanghai，服务器统一 NTP 校时，Logstash 用 date filter 以日志自带时间作为 @timestamp，而不是采集时间，避免缓冲造成的时序错乱。多行：Java 异常堆栈跨多行，采集端配置 multiline 合并——匹配到新日志起始行（如 ^yyyy-MM-dd）即开启新事件，否则追加到上一条，保证一条异常 = 一条日志 = 一个可检索单元，否则异常堆栈会被拆得七零八落。

10.8 Q8：日志脱敏怎么做才合格？ ​

三层：1）源头（应用层）——打日志前对手机号/身份证打码，密码/密钥/token 一律不打，这是最有效的一层；2）采集管道（Logstash/采集器）——对特定字段做正则脱敏兜底，防漏网；3）展示层——Kibana 对敏感字段按角色隐藏/脱敏。原则：能不在源头落盘的就不落盘（密钥只记引用不记明文），脱敏不能只靠展示层，因为数据已落盘即存在泄露面。审计上要定期用脱敏规则扫描历史索引验证效果。

10.9 Q9：Metrics、Logs、Traces 如何协同定位一次"下单慢"？ ​

指标层：Grafana 看到 /order/create P99 突增且错误率未变 → 排除大面积故障；饱和度面板确认资源正常 → 排除资源瓶颈。链路层：SkyWalking 打开该接口一条慢 trace，瀑布图显示 80% 耗时在下游 user-service 的调用。日志层：按 traceId 过滤两服务日志，发现 user-service 在打 Redis 连接池获取超时，进而查 Redis 慢命令与 bigkey。整个过程用 traceId 贯穿，指标负责"发现"，trace 负责"定位"，日志负责"归因"。

10.10 Q10：采样后丢了错误链路怎么办？ ​

几种互补策略：1）头部 + 动态调整——入口统一概率采样，但把"高错误率接口/错误状态响应"的请求标记为必采（错误信息在入口已知时可行）；2）尾部采样——链路结束后由 Collector 按结果决定保留（可 100% 保错误与慢链路），成本高但最可靠；3）日志兜底——即使 trace 没采到，日志仍全量，可先用 traceId 反查错误日志重建现场（前提日志带 traceId 且全量保存）；4）对核心交易链路单独高采样率并设配额。工程上通常组合 1+3，成本敏感型系统再加 2 只对错误分支生效。
