JUC 并发编程 ​

从「为什么会有并发问题」讲到「线上线程池打满怎么查」。02 篇的多线程只讲到「怎么创建线程」，这篇补的是内存模型、锁、AQS、线程池源码、并发容器这一层。

1. 并发问题的三个根源 ​

所有并发 bug 都能归到三条里：

问题含义典型现象
原子性一个或多个操作要么全做、要么全不做i++ 丢更新、先查后改的竞态
可见性一个线程改了共享变量，另一个线程要能立刻看到死循环读不到 stop 标志位
有序性编译器 / CPU 的指令重排不能改变单线程语义，但会打乱多线程下的执行顺序半初始化对象被别的线程看到

为什么会有可见性问题：CPU 有自己的 L1/L2 缓存，写操作先落到缓存，靠缓存一致性协议（MESI）同步；同时为了压榨性能，写缓冲区和无效化队列会让「写入」和「其他核看到」之间存在延迟。Java 不去直接管硬件，而是抽象出一套 JMM（Java 内存模型） 来规定「什么时候必须可见」。

2. JMM 与 happens-before ​

2.1 happens-before 是什么 ​

JMM 用 happens-before 定义可见性：如果 A happens-before B，那么 A 的结果对 B 可见，且 A 在 B 之前执行（对程序员可见的顺序，不代表 CPU 真的按这个顺序跑）。

8 条规则（记住前 6 条够用）：

  1. 程序顺序：单线程内，前面的操作 hb 后面的操作。
  2. 监视器锁：对同一个锁的 unlock hb 后续的 lock。
  3. volatile：对 volatile 变量的写 hb 后续对这个变量的读。
  4. 线程启动：Thread.start() hb 该线程里的任何操作。
  5. 线程终止：线程里的所有操作 hb 其他线程检测到它终止（join() 返回）。
  6. 中断：对线程 interrupt() hb 被中断线程检测到中断。
  7. 对象终结：构造函数结束 hb finalize() 开始。
  8. 传递性：A hb B、B hb C，则 A hb C。

2.2 as-if-serial 与指令重排 ​

单线程里，只要最终结果不变，编译器、JIT、CPU 都可以重排。所以这段代码里 a 和 b 的赋值顺序不保证：

java
int a = 1;   // 可能后执行
int b = 2;   // 可能先执行
int a = 1;   // 可能后执行
int b = 2;   // 可能先执行
1
2

但 x = 1; y = x + 1; 不会重排成先算 y —— 这就是 as-if-serial 的边界：有数据依赖的不能重排。

2.3 内存屏障 ​

JMM 把屏障分成四类，是 volatile 和锁的底层实现手段：

屏障作用
LoadLoad前面的读先于后面的读
StoreStore前面的写先于后面的写
LoadStore前面的读先于后面的写
StoreLoad前面的写先于后面的读（开销最大，volatile 写后必插）

x86 上只有 StoreLoad 需要显式指令（lock 前缀 / mfence），其余三种靠 x86 本身较强的内存模型天然满足 —— 所以「volatile 在 x86 上几乎无额外开销」这句话只对读成立。

3. volatile：只管可见性和有序性 ​

3.1 三个语义 ​

  1. 可见性：写 volatile 变量时，会把该线程工作内存中的值刷回主内存；读时会从主内存重新读。
  2. 禁止重排：写前插 StoreStore，写后插 StoreLoad；读后插 LoadLoad / LoadStore。
  3. 不保证原子性：volatile int i; i++ 依然是「读-改-写」三步，照样丢更新。

3.2 为什么 DCL 单例必须加 volatile ​

java
public class Singleton {
    private static volatile Singleton instance;   // 少了 volatile 就可能拿到半初始化对象

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();   // 1.分配内存 2.初始化 3.引用指向内存
                }
            }
        }
        return instance;
    }
}

3.3 什么时候用 volatile ​

  • 状态标志位（volatile boolean running）
  • 一次性安全发布（DCL 的 instance）
  • 读多写少、写不依赖当前值（比如配置项、计数器只用于统计可容忍误差）

不要用它做 i++、复合判断、需要互斥的临界区。

4. synchronized 与锁升级 ​

4.1 字节码层面 ​

java
synchronized (lock) { ... }
synchronized (lock) { ... }
1

编译后是 monitorenter / monitorexit（正常退出一个、异常退出一个，所以必须成对）。方法是 ACC_SYNCHRONIZED 标志位。二者最终都落到 monitor 对象（HotSpot 里是 ObjectMonitor，有 _owner、_EntryList、_WaitSet、_recursions）。

4.2 锁状态存在哪：对象头 Mark Word ​

64 位 JVM 的 Mark Word（8 字节）：

锁状态62 位内容
无锁unused:25 + hash:31 + unused:1 + age:4 + 0 + 01
偏向锁线程 ID:54 + epoch:2 + unused:1 + age:4 + 1 + 01
轻量级锁指向栈中锁记录的指针:62 + 00
重量级锁指向 ObjectMonitor 的指针:62 + 10
GC 标记空 + 11

4.3 升级路径 ​

无锁 --(第一个线程 CAS 记 ID)--> 偏向锁 --(第二个线程竞争)--> 轻量级锁 --(自旋失败/竞争加剧)--> 重量级锁
无锁 --(第一个线程 CAS 记 ID)--> 偏向锁 --(第二个线程竞争)--> 轻量级锁 --(自旋失败/竞争加剧)--> 重量级锁
1
  • 偏向锁：只有一个线程反复进同一个锁，把线程 ID 写在 Mark Word 里，之后进来连 CAS 都省了。JDK 15 起默认关闭、JDK 18 起彻底废弃（撤销成本高于收益），新项目直接按「无锁 → 轻量 → 重量」理解即可，但面试仍会问，答的时候补一句「JDK 15+ 已默认禁用偏向锁」会加分。
  • 轻量级锁：在当前线程栈帧里建 Lock Record，CAS 把 Mark Word 指向它；失败就自旋，自旋到阈值（自适应自旋）还不行就膨胀。
  • 重量级锁：竞争线程进 _EntryList 排队，由操作系统 mutex 挂起 —— 涉及用户态/内核态切换，所以「synchronized 慢」指的是这一层。

4.4 锁优化 ​

  • 锁消除：逃逸分析发现锁对象不会逃出方法，直接去掉（如方法内 new Object() 加锁）。
  • 锁粗化：循环里反复加解锁会被合并成一次。
  • 自适应自旋：根据上次自旋成功率决定这次自旋多久。

4.5 synchronized vs ReentrantLock ​

synchronizedReentrantLock
实现JVM 关键字，monitorJDK 类，基于 AQS
释放自动（异常也释放）必须 finally { unlock(); }
可中断不支持lockInterruptibly()
超时不支持tryLock(timeout)
公平锁只有非公平可选公平 / 非公平
条件队列一个 wait/notify多个 Condition，可精准唤醒
性能JDK6 后优化得差不多高竞争下更可控

结论口径：能不用显式锁就不用；需要超时、可中断、多条件队列时才上 ReentrantLock。

5.1 CAS 是什么 ​

对应 CPU 的 cmpxchg 指令，Java 里通过 Unsafe.compareAndSwapInt（JDK9+ 是 VarHandle）调用。它是乐观锁：先假设没人改，改的时候校验，失败就重试（自旋）。

5.2 三个问题 ​

  1. ABA：值从 A→B→A，CAS 察觉不到。解决：AtomicStampedReference 带版本号。
  2. 自旋开销：高竞争下大量空转。解决：LongAdder 分段、或者直接上锁。
  3. 只能保证一个变量：多个变量要么合并成一个对象用 AtomicReference，要么加锁。

6.2 独占与共享 ​

子类只需实现 tryAcquire / tryRelease（独占）或 tryAcquireShared / tryReleaseShared（共享），AQS 负责排队、阻塞、唤醒。这就是模板方法模式。

java
// 以 ReentrantLock 非公平锁为例（简化）
final boolean nonfairTryAcquire(int acquires) {
    Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        if (compareAndSetState(0, acquires)) {   // 直接抢，不排队 —— 这就是"非公平"
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        setState(c + acquires);                  // 重入，直接加 state
        return true;
    }
    return false;
}

7.3 InheritableThreadLocal 与 TTL ​

  • InheritableThreadLocal：在 new Thread() 时把父线程的 map 浅拷贝一份给子线程 —— 只在线程创建时生效，线程池复用线程时失效。
  • TransmittableThreadLocal（阿里 TTL）：配合 TtlExecutors 包装线程池，在任务提交和执行的瞬间做上下文快照/回放，解决线程池传递问题。

8.2 执行流程（背下来） ​

提交任务
  ├─ 当前线程数 < core            → 新建核心线程执行

  └─ 队列满且线程数 = max          → 触发拒绝策略

为什么先入队而不是先开满线程：创建线程成本高（栈内存 + 内核调度），队列能缓冲突发流量；只有在队列也满了才说明真的扛不住。

8.3 四种拒绝策略 ​

策略行为适合
AbortPolicy（默认）抛 RejectedExecutionException必须让上游感知失败
CallerRunsPolicy提交任务的线程自己跑削峰，天然限速
DiscardPolicy静默丢弃日志、埋点等可丢数据
DiscardOldestPolicy丢队头最老的，再重试提交只要最新数据

8.4 为什么禁用 Executors 的默认工厂 ​

  • newFixedThreadPool / newSingleThreadExecutor：队列是 LinkedBlockingQueue，无界，任务堆积到 OOM。
  • newCachedThreadPool：最大线程数 Integer.MAX_VALUE，无限创建线程，直接 OOM。

面试口径：必须手写 ThreadPoolExecutor，队列要有界，线程数要按业务算，并且给线程起名。

8.5 线程数怎么定 ​

  • CPU 密集（计算、序列化）：N + 1，N 是核数。
  • IO 密集（RPC、DB、文件）：N × (1 + 等待时间 / 计算时间)，实测 2N ~ 4N 起步再压测。
  • 混合型按瓶颈拆分两个池，别用一个池扛所有。

9. 并发容器 ​

9.1 ConcurrentHashMap（JDK 1.8） ​

版本并发控制
1.7Segment 分段锁，默认 16 段
1.8CAS 初始化 + synchronized 锁桶头节点 + 红黑树

关键点：

  • 锁粒度到「链表/树的头节点」，不是整表。
  • size() 用 baseCount + CounterCell[] 分散计数（和 LongAdder 同思路）。
  • get() 不加锁，靠 volatile 读 Node 的 val 和 next。
  • 不允许 null key / null value —— 因为并发下无法区分「不存在」和「值是 null」。

9.2 CopyOnWriteArrayList ​

写时复制整个数组，读完全无锁。只适合读多写极少（白名单、监听器列表），写多了会疯狂 GC。

9.3 BlockingQueue 家族 ​

实现特点场景
ArrayBlockingQueue有界数组，单锁两 Condition线程池队列（推荐）
LinkedBlockingQueue链表，默认无界（坑）一定传容量
SynchronousQueue不存储，直接交接newCachedThreadPool
PriorityBlockingQueue无界优先队列按优先级消费
DelayQueue延迟到期才能取本地延迟任务
LinkedTransferQueue无锁，transfer 语义高吞吐生产者消费者

10. CompletableFuture：异步编排 ​

12.3 线程池打满 ​

现象：接口 RT 飙升但 CPU 不高、getActiveCount() 顶到 max、队列持续增长。排查顺序：

  1. 队列大小和拒绝计数（有没有在丢任务）
  2. 任务里有没有阻塞调用（DB 慢查询、同步 HTTP、锁等待）
  3. 线程栈里都在等什么：jstack | grep -c "waiting on condition"

13. 速查表 ​

问题一句话答案
volatile 能保证原子性吗不能，只能保证可见性和有序性
synchronized 锁的是什么对象头 Mark Word + monitor；锁代码块锁的是括号里的对象
锁能降级吗不能，只能升级
AQS 的 state 是什么由子类定义的同步状态：重入次数 / 许可数 / 剩余计数
线程池先入队还是先扩容先入队，队列满了才扩到 max
为什么不用 Executors队列无界或线程无上限，都会 OOM
ThreadLocal 为什么会泄漏key 弱引用 value 强引用，线程不死 value 不释放
CountDownLatch 和 CyclicBarrier 区别前者一次性、一个等多个；后者可重用、互相等
CompletableFuture 用哪个线程池必须传自定义的，默认 commonPool 只有 N-1 个线程
CAS 的 ABA 怎么解决加版本号，AtomicStampedReference
