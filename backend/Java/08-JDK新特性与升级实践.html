JDK 新特性与升级实践 ​

相关笔记：03 Java 高级特性（Lambda / Stream / 虚拟线程入门）、JVM 深入（GC 与参数）

03 篇讲的是「语法糖怎么用」；这篇讲版本路线、落地取舍、升级踩坑。面试问「JDK 21 有什么新特性」时，能答出「所以我升不升、升了要注意什么」，比背 JEP 编号有用得多。

1. 版本节奏：为什么大家都在追 LTS ​

2017 年之后，JDK 变成 6 个月一个 feature 版本，每 2 年一个 LTS：

版本发布LTS现状建议
82014✅大量存量系统仍在此，无官方免费更新（Oracle 收费，可用 Temurin/Corretto）
112018✅保守升级的落点，仍有免费更新
172021✅当前主流基线，Spring Boot 3 最低要求
212023✅新项目首选，虚拟线程正式版
252025✅下一代 LTS，逐步进入视野

关键分水岭：Spring Boot 3 要求 JDK 17+，Spring Framework 6 也是。所以「还在 JDK 8」的项目，升级链路通常是 8 → 17 → 21，中间不跳 11 也行（但 11 更稳、依赖兼容更好）。

配合 switch 模式匹配，编译器能检查是否穷尽，这是「代数数据类型」进入 Java 的标志。

3.2 强封装（最重要的升级障碍） ​

JDK 16 起默认强封装 JDK 内部 API，JDK 17 彻底移除 --illegal-access。后果：

  • 反射访问 sun.misc.*、jdk.internal.* 会抛 InaccessibleObjectException；
  • 需要显式 --add-opens java.base/java.lang=ALL-UNNAMED；
  • 大量老框架（老版本 Spring、Dubbo、Hibernate、Lombok 早期版本）要靠这个参数才能跑。

3.3 其他 ​

  • 移除 CMS（JDK 14），-XX:+UseConcMarkSweepGC 直接报错；
  • 移除 Nashorn（JDK 15）、移除 JAXB / JAX-WS（JDK 11，迁到 Jakarta）；
  • 弃用 Security Manager（JDK 17 标记 forRemoval）；
  • 引入伪随机数新接口 RandomGenerator、AppCDS 默认开启、外部函数 API 预览。

4. JDK 21 LTS：虚拟线程是主角 ​

4.1 虚拟线程（JEP 444，正式） ​

java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> {
            Thread.sleep(1000);      // 阻塞时自动让出载体线程
            return "ok";
        });
    }
}
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> {
            Thread.sleep(1000);      // 阻塞时自动让出载体线程
            return "ok";
        });
    }
}

原理：虚拟线程由 JVM 调度，多个虚拟线程复用一个平台线程（载体线程）。遇到阻塞（sleep、IO、锁等待）时，虚拟线程把栈冻结到堆上、让出载体线程，恢复时再挂回来。所以「阻塞」不再等于「占线程」。

三条铁律：

  1. 不要池化虚拟线程。它创建成本极低（几十字节 + 堆上栈），池化反而丢掉了「用完即弃」的优势。用 newVirtualThreadPerTaskExecutor 或 Thread.ofVirtual().start()。
  2. 别用 ThreadLocal 存大对象（百万虚拟线程 = 百万份副本），改用 ScopedValue（JDK 21 预览）。
  3. 注意 pinning（钉住）：在 synchronized 块里阻塞，会让载体线程被钉住，无法切换。JDK 21 上这是真问题（JDK 24 的 JEP 491 才修好）。所以在虚拟线程里优先用 ReentrantLock 而不是 synchronized。

什么时候有用：IO 密集、高并发、每请求一线程的传统写法（Spring MVC + Tomcat 每请求一线程）。一个 8 核机器从「几千线程」变成「几十万虚拟线程」。

什么时候没用：CPU 密集型（瓶颈是核数，不是线程数）；已经在用 WebFlux/Reactor 的场景（本身就不占线程）。

Spring Boot 3.2 起只需一行 spring.threads.virtual.enabled=true 就能让 Tomcat 用上虚拟线程。

4.2 结构化并发（预览，JEP 453） ​

把「一组子任务」当一个整体：一起开始、一起结束、出错一起取消，解决 ExecutorService 里任务泄漏、异常丢失、取消不传播的问题。

java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user  = scope.fork(() -> userService.get(id));
    var order = scope.fork(() -> orderService.list(id));
    scope.join().throwIfFailed();
    return new Detail(user.get(), order.get());
}

    var order = scope.fork(() -> orderService.list(id));

6. 升级实战：从 8 到 17/21 会遇到什么 ​

6.1 依赖与包 ​

问题表现处理
JAXB / JAX-WS 被移除javax.xml.bind.* 找不到显式引入 jakarta 依赖
Nashorn 被移除ScriptEngine 拿不到 js换 GraalJS
sun.misc.Unsafe 受限警告/后续不可用换 VarHandle / MethodHandles

6.2 JVM 参数变化 ​

旧参数现状
-XX:+UseConcMarkSweepGC报错（14 起移除），改 -XX:+UseG1GC
-XX:PermSize/-XX:MaxPermSize早就无效，改 -XX:MetaspaceSize

6.3 升级方法论（能讲出来就很加分） ​

  1. 先升依赖再升 JDK：框架版本（Spring Boot）往往比 JDK 更卡；
  2. CI 里加多版本矩阵：8/17/21 同时跑测试，灰度切换；
  3. 先 17 再 21，不要 8 直接跳 21（两个大步的问题会混在一起）；
  4. 用 jdeps 扫内部 API 依赖：
bash
jdeps --jdk-internals -R target/app.jar
jdeps --jdk-internals -R target/app.jar

  1. -XX:+PrintFlagsFinal 对比参数默认值（升级后默认 GC、堆比例都可能变）；
  2. 压测对比：GC 日志、P99、内存占用、启动时间四项。

6.4 升级到 21 的收益怎么量化 ​

指标8 → 21 的典型变化（因系统而异，要实测）
吞吐G1 + 更好的 JIT，普遍提升 5%~20%
停顿CMS 消失，G1 停顿更可控
内存Compact Strings 省 10%~20% 字符串内存

启动AppCDS 默认，快一些；GraalVM 原生镜像更快（另一条路）

7. 面试怎么答 ​

被问「JDK 21 有什么新特性」时，按这个结构答：

  1. 一句话定位：21 是 LTS，最大的变化是虚拟线程转正。
  2. 原理：虚拟线程由 JVM 调度、复用车载平台线程，阻塞时把栈冻结到堆，所以「阻塞不再占线程」。
  3. 用法与禁忌：不要池化；synchronized 里阻塞会 pinning，改用 ReentrantLock；ThreadLocal 换 ScopedValue。
  4. 其他：分代 ZGC、记录模式 + switch 模式匹配（配合 sealed 能穷尽检查）、顺序集合。
  5. 落地判断：IO 密集 + 传统每请求一线程的架构收益最大；已经是 WebFlux 收益有限；CPU 密集没用。
  6. 升级注意事项：Spring Boot 3 最低 17；synchronized pinning 要排查；--add-opens 要补。
