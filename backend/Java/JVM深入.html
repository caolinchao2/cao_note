1. JVM 架构概述 ​

1.1 什么是 JVM ​

JVM（Java Virtual Machine）是 Java 实现"一次编写，到处运行"的基石。它是一个抽象的计算机，有自己完善的指令集、寄存器、栈、堆和方法区。JVM 屏蔽了底层操作系统的差异，使得 Java 字节码可以在任何安装了 JVM 的平台上执行。

1.3 HotSpot VM ​

HotSpot 是 Oracle JDK / OpenJDK 的默认虚拟机，也是目前使用最广泛的 JVM。名称源自其具备"热点代码探测"能力：

  • 热点探测：通过执行计数器找出频繁执行的代码（热点代码），将其编译为本地机器码。
  • 即时编译（JIT）：C1（Client Compiler）和 C2（Server Compiler）两级编译器。
  • 分代收集：成熟的垃圾回收体系，支持从 Serial 到 ZGC 的多种回收器。

2. 类加载机制（重点） ​

2.1 类加载过程总览 ​

前三阶段（加载、验证、准备）是按顺序开始的，而解析阶段则不一定：为了支持动态绑定，解析可以在初始化之后进行。

2.2 加载（Loading） ​

加载阶段完成三件事：

  1. 通过类的全限定名获取定义该类的二进制字节流。
  2. 将字节流所代表的静态存储结构转化为方法区的运行时数据结构。
  3. 在内存中生成代表该类的 java.lang.Class 对象，作为方法区这个类的各种数据的访问入口。
java
// 触发类加载的几种方式
public class ClassLoadingDemo {
    public static void main(String[] args) throws Exception {
        // 1. new 关键字
        MyClass obj = new MyClass();

        // 2. Class.forName() - 会执行初始化
        Class<?> clazz1 = Class.forName("com.example.MyClass");

        // 3. ClassLoader.loadClass() - 不会执行初始化
        Class<?> clazz2 = ClassLoader.getSystemClassLoader()
                .loadClass("com.example.MyClass");

        // 4. 访问静态字段/方法
        int val = MyClass.STATIC_FIELD;

        // 5. 反射调用
        Class<?> clazz3 = MyClass.class;
    }
}

2.3 链接（Linking） ​

验证（Verification） ​

确保 Class 文件的字节流包含的信息符合规范，不会危害虚拟机自身安全。包括：

  • 文件格式验证：魔数 0xCAFEBABE、版本号等。
  • 元数据验证：语义检查（是否有父类、是否继承了 final 类等）。
  • 字节码验证：通过数据流和控制流分析，确保语义合法。
  • 符号引用验证：对常量池中的符号引用进行匹配性检查。

准备（Preparation） ​

为类变量（static 修饰的变量）分配内存并设置初始值。注意：

  • 仅包含类变量（static），不包含实例变量。
  • 初始值通常是零值，而非代码中赋的值。
java
public class PrepareDemo {
    // 准备阶段后 value = 0，而非 123
    // 初始化阶段才将 value 赋值为 123
    public static int value = 123;

    // 对于 final static 常量，准备阶段直接赋值为常量值
    public static final String CONST = "hello";

    // 引用类型准备阶段为 null
    public static Object obj = new Object();
}

解析（Resolution） ​

将常量池中的符号引用替换为直接引用的过程。

  • 符号引用：用字面量描述目标，与内存布局无关。
  • 直接引用：直接指向目标的指针、相对偏移量或句柄。

解析时机：虚拟机实现可以自行决定，HotSpot 采用延迟解析，在指令真正使用到符号引用时才解析。

2.4 初始化（Initialization） ​

<clinit>() 执行规则：

  • 线程安全：虚拟机会保证多个线程同时初始化一个类时，只有一个线程执行 <clinit>()。
  • 父类先于子类：父类的 <clinit>() 先执行。
  • 接口例外：接口初始化不要求父接口先初始化，除非用到父接口中的变量。
  • 可选：如果没有静态变量和静态代码块，编译器不会生成 <clinit>()。

不会触发初始化的场景（被动引用）：

2.5.2 双亲委派模型 ​

当一个类加载器收到类加载请求时，它首先不会自己去尝试加载这个类，而是把请求委派给父加载器去完成，每一层如此，最终所有加载请求都会传到启动类加载器。只有当父加载器反馈自己无法完成加载时，子加载器才会尝试自己加载。

java
// 双亲委派的核心逻辑（java.lang.ClassLoader.loadClass() 简化版）
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 第一步：检查是否已经加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    // 第二步：父加载器未加载过，委托给父加载器
                    c = parent.loadClass(name, false);
                } else {
                    // 第三步：没有父加载器，委托给 Bootstrap ClassLoader
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器无法完成加载
            }

            if (c == null) {
                // 第四步：父加载器加载失败，自己尝试加载
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}

为什么需要双亲委派：

  1. 安全性：防止核心 API 被篡改。例如自己写一个 java.lang.String 类，双亲委派机制会让 Bootstrap ClassLoader 优先加载 JDK 自带的 String，确保核心类不被替换。
  2. 唯一性：保证同一个类在全加载器层次中具有唯一性。如果两个类加载器各自加载了同一个类，在 JVM 中会被视为两个不同的类。

2.5.4 线程上下文类加载器 ​

Java 的 SPI（Service Provider Interface）如 JDBC、JNDI 等，通常由 Bootstrap ClassLoader 加载核心接口，但具体实现由第三方提供（在 classpath 下）。这产生了"父加载器要访问子加载器加载的类"的矛盾。

解决方案：线程上下文类加载器（Thread Context ClassLoader）。

java
// JDBC 驱动加载示例（DriverManager 由 Bootstrap ClassLoader 加载）
public class DriverManager {
    static {
        loadInitialDrivers();
    }

为什么用元空间替代永久代：

  1. 字符串常量池：在永久代中容易触发 Full GC，移至堆中更方便管理。

  4. 促进 HotSpot 与 JRockit 合并：JRockit 没有永久代。

3.2.4 栈上分配与逃逸分析 ​

逃逸分析：JIT 编译器分析对象的作用域，判断对象是否逃逸出方法或线程。

    // 对象不逃逸：可以在栈上分配
    public String noEscape() {
        StringBuilder sb = new StringBuilder();
        sb.append("hello");
        sb.append("world");
        return sb.toString();  // sb 本身没有逃逸，仅返回了 String 结果
    }

    public void threadEscape() {

3.3 程序计数器（PC Register） ​

线程私有，记录当前线程正在执行的字节码指令地址。

  • 如果执行的是 Java 方法，PC 指向当前执行指令的地址。
  • 如果执行的是 Native 方法，PC 值为 undefined。
  • 是 JVM 规范中唯一没有规定 OOM 情况的区域。

3.4 本地方法栈（Native Method Stack） ​

线程私有，为 JVM 执行 Native 方法（通常是 C/C++ 实现）提供服务。

  • HotSpot 将本地方法栈和虚拟机栈合二为一。
  • 同样会抛出 StackOverflowError 和 OutOfMemoryError。

4.2 实例数据（Instance Data） ​

存储对象的真正有效信息，即类中定义的各种字段。存储顺序受分配策略参数影响：

  • 父类字段在子类字段之前（HotSpot 默认）。

4.3 对齐填充（Padding） ​

HotSpot 要求对象起始地址必须是 8 字节的整数倍。如果实例数据部分没有对齐，就需要通过填充来补全。

4.4 指针压缩 ​

从 JDK 6 开始，64 位 JVM 支持指针压缩（默认开启，堆小于 32GB 时）。

原理：64 位 JVM 中的引用指针原本占用 8 字节，开启压缩后占用 4 字节。由于对象是 8 字节对齐的，JVM 可以通过 4 字节指针左移 3 位（乘以 8）来寻址最大 32GB 的堆。

影响：

  • 减少内存占用。
  • 提升缓存命中率。
  • 当堆大于 32GB 时，指针压缩自动失效。

5.5 分代收集理论 ​

基于两个弱分代假设：

  1. 弱分代假说：绝大多数对象朝生夕灭。
  2. 强分代假说：熬过越多次 GC 的对象越难回收。

跨代引用处理：

  • 老年代对象可能引用新生代对象。
  • 引入记忆集（Remembered Set），避免扫描整个老年代。

6.7.3 SATB（Snapshot At The Beginning） ​

G1 用于并发标记的算法，解决三色标记中的对象漏标问题。

SATB 核心思想：
1. 并发标记开始时，给堆拍一个"快照"（逻辑快照，实际记录变更）
2. 标记过程中，对象引用变化被记录到 SATB 队列
3. 最终标记阶段，处理 SATB 队列中的引用变更
4. 所有在快照中存活的对象都被视为存活

优点：不需要重新扫描整个堆，效率高
缺点：可能保留部分浮动垃圾（本应回收的对象被保留）

Young GC：

  1. 选定 Eden 区中所有 Region。
  2. 计算暂停时间目标，决定是否需要加入 Survivor 区。
  3. 将存活对象复制到 Survivor Region 或老年代 Region。
  4. 清空原来的 Eden Region。

Mixed GC：

6.8 ZGC（JDK 11+） ​

ZGC 是一款以低延迟（亚毫秒级暂停）为目标的高性能垃圾回收器，适用于大内存（几百 GB 到 TB 级）场景。

6.8.1 ZGC 核心特性 ​

  • 暂停时间不超过 1ms（与堆大小无关）。
  • 支持 8MB ~ 16TB 的堆。
  • 并发标记-整理，不产生碎片。
  • 染色指针（Colored Pointer） 技术。
  • 读屏障（Load Barrier） 技术。

6.8.2 染色指针（Colored Pointer） ​

ZGC 将 64 位指针的高几位用作"颜色"标记，存储对象状态信息。

64 位地址空间布局 (x86-64)：

+----+----+----+----+----+----+----+----+
| 63 | 62 | 61 | 60 | 59-48 | 47-0      |
+----+----+----+----+----+----+----+----+
| M0 | M1 | R  | R  | 保留   | 偏移量    |
+----+----+----+----+----+----+----+----+

M0/M1: Mark Bit（标记位，标记对象是否存活）
R:     Remapped Bit（重映射位，指向对象的新地址）

  • 对象的存活信息可以直接从指针读取，不需要访问对象本身。
  • 标记和重映射完全并发进行，不暂停用户线程。

限制：

  • 不支持 32 位平台。
  • 不支持指针压缩（因为需要全部 64 位）。

6.8.3 读屏障（Load Barrier） ​

ZGC 在读对象引用时插入屏障逻辑（在 ldc、getfield、arrayload 等指令处）。

读屏障执行逻辑：
1. 读取对象引用指针
2. 检查指针的染色位，判断对象状态
3. 如果指针需要修正（对象被移动），则进行自愈 (Self-Healing)
4. 返回修正后的指针

"自愈"：后续读取同一引用时不再需要修正，性能逐渐提升

|  - 特供老年代的染色指针    |

优点：
- 新生代 GC 更频繁但更快
- 老年代 GC 更少，整体延迟更低

解释执行：
  字节码 → [解释器] → 逐条翻译为机器码 → 执行

  字节码 → [JIT 编译器] → 编译为机器码 → 缓存并执行
  优点：执行快
  缺点：启动慢（需要预热）

分层级别：

Level 0 - 解释执行 (Interpreter)
Level 1 - C1 简单编译 (无 profiling)
Level 2 - C1 编译 + 部分 profiling
Level 3 - C1 编译 + 完全 profiling
Level 4 - C2 编译

升级路径：
0 → 3 (解释执行到 C1 完全 profiling)
3 → 4 (C1 收集 profiling 数据后升级到 C2)

总结 ​

知识点核心要点
类加载双亲委派保障安全性，自定义打破用于隔离。加载、链接、初始化三阶段。
运行时数据区堆（对象主力）、栈（帧结构 + 逃逸分析）、元空间（替代永久代）。
对象布局对象头 Mark Word(Klass Pointer) + 实例数据 + 对齐填充。指针压缩节省空间。
GC 理论分代收集、三色标记（漏标问题）、Stop-The-World 不可避免。
GC 选型小内存→Serial，吞吐量→Parallel，低延迟→G1/ZGC。
G1 核心Region + RSet + SATB。可预测暂停时间，JDK 9+ 默认。
ZGC 核心染色指针 + 读屏障。亚毫秒级暂停，JDK 17+ 大内存标配。
JIT分层编译 + 方法内联 + 逃逸分析 + 锁优化。预热带来高性能。
调优先诊断再优化。工具链：jstat/jmap/jstack → MAT/Arthas。

JVM 调优没有银弹。理解原理、使用工具、持续观察，找到最适合业务场景的配置才是正道。
