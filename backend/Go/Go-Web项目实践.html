Go Web 项目实践 ​

一套可演进的 Go Web 工程范式：目录分层、GORM、Redis、日志、依赖注入、Docker 与生产坑。

一、工程结构：可演进的分层单体 ​

1.1 标准目录布局 ​

Go 社区对业务项目推荐"cmd + internal + pkg"布局（参考 GitHub 的 golang-standards/project-layout，注意它仅是社区约定、非官方规范）：

text
demo/
├── cmd/
│   └── server/

│   ├── router/                # 路由与中间件装配
│   ├── handler/               # HTTP 层：绑定参数、翻译响应
│   ├── service/               # 业务逻辑层
│   ├── repository/            # 数据访问层（DB / 缓存）
│   ├── model/                 # 数据模型与 DTO

│   └── pkg/                   # 本服务内的通用小件（响应、错误码）
├── pkg/                       # 可被外部复用的公共库（可选）

1.2 internal 的强制封装 ​

internal 是 Go 编译器层面的可见性约束：只有该目录的父目录内的代码可以 import 它。以仓库 github.com/me/demo 为例，github.com/me/demo/internal/... 只能被 demo 仓库内的代码引用——外部项目 import 会直接编译失败。这让"分层不跨层"不止是代码评审约定，而是编译期纪律。

1.3 依赖方向与演进路线 ​

依赖只允许从上往下：handler -> service -> repository -> model，禁止反向或跳层：

text
router -> handler -> service -> repository -> model(零依赖)
                       |            |
                       +---> pkg（响应封装 / 错误码）
router -> handler -> service -> repository -> model(零依赖)
                       |            |
                       +---> pkg（响应封装 / 错误码）

演进到微服务时按"业务边界竖切"：每个模块（用户 / 订单）的服务包可单独拆出，分层边界保持不变。Go 微服务生态（gRPC + protobuf）与单体共用同样的 internal 纪律，迁移成本主要在协议层而非架构思想。

2.2 viper 加载代码 ​

go
package config

import (
    "strings"
    "github.com/spf13/viper"
)

type Config struct {
    App   AppConfig   `mapstructure:"app"`
    MySQL MySQLConfig `mapstructure:"mysql"`
    Redis RedisConfig `mapstructure:"redis"`
    JWT   JWTConfig   `mapstructure:"jwt"`
}

type MySQLConfig struct {
    DSN          string `mapstructure:"dsn"`
    MaxOpenConns int    `mapstructure:"max_open_conns"`
    MaxIdleConns int    `mapstructure:"max_idle_conns"`
}

func Load(path string) (*Config, error) {
    v := viper.New()
    v.SetConfigFile(path)
    v.SetEnvPrefix("DEMO")            // 环境变量前缀：DEMO_PORT
    v.SetEnvKeyReplacer(strings.NewReplacer(".", "_")) // app.port -> DEMO_APP_PORT
    v.AutomaticEnv()                  // 环境变量优先于文件

    if err := v.ReadInConfig(); err != nil {
        return nil, err
    }
    var cfg Config
    if err := v.Unmarshal(&cfg); err != nil { // mapstructure 标签对应 yaml 键
        return nil, err
    }
    return &cfg, nil
}

2.3 敏感信息管理 ​

  • 密钥（DB 密码、JWT secret）不要写进仓库的 yaml；用环境变量 / K8s Secret / 密钥管理服务（Vault、云 KMS）注入。

三、GORM 操作 MySQL ​

3.1 连接与连接池 ​

go
package repository

import (
    "gorm.io/driver/mysql"
    "gorm.io/gorm"
    "gorm.io/gorm/logger"
)

func NewDB(dsn string, maxOpen, maxIdle int) (*gorm.DB, error) {
    db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{
        Logger: logger.Default.LogMode(logger.Warn), // 生产只打印慢 SQL 与错误
    })
    if err != nil {
        return nil, err
    }
    sqlDB, err := db.DB() // 取底层 database/sql 连接池
    if err != nil {
        return nil, err
    }
    sqlDB.SetMaxOpenConns(maxOpen)   // 最大打开连接
    sqlDB.SetMaxIdleConns(maxIdle)   // 最大空闲连接
    sqlDB.SetConnMaxLifetime(time.Hour) // 防 MySQL 8 小时断连 / 老连接回收
    sqlDB.SetConnMaxIdleTime(30 * time.Minute)
    return db, nil
}

4.2 Cache Aside 与三大缓存问题 ​

**Cache Aside（旁路缓存）**是最常用模式：读先查缓存，未命中查库并回填；写先更新库再删缓存（删而非更新，避免并发写覆盖旧值）。

go
func (r *userRepo) GetUser(ctx context.Context, id int64) (*model.User, error) {
    key := fmt.Sprintf("user:%d", id)
    // 1. 读缓存
    var u model.User
    if err := r.rdb.Get(ctx, key).Scan(&u); err == nil {
        return &u, nil
    } else if !errors.Is(err, redis.Nil) {
        return nil, err // 缓存故障不要拖垮主流程，可降级直查 DB
    }
    // 2. 查库
    u, err := r.findFromDB(ctx, id)
    if err != nil { return nil, err }
    // 3. 回填
    r.rdb.Set(ctx, key, u, 10*time.Minute)
    return &u, nil
}

雪崩大量 key 同时过期TTL 加随机抖动；多级缓存

        return r.loadAndCache(ctx, id)

5.3 错误日志分级纪律 ​

级别场景例子
Info关键业务事件下单成功、登录成功

Debug开发期细节生产关闭该级别

6.1 手动组装 vs 框架 ​

Go 没有 Spring 那种运行时注解容器，主流的三种依赖注入方案：

方案原理适用
构造函数手写组装main 里 new 全部依赖，一层层传入中小项目（推荐起步）

十、常见生产坑 ​

10.1 时区：八年老坑 ​

Go 的 time.Now() 返回本地时区，但容器默认 UTC，且 time.LoadLocation("Asia/Shanghai") 在没有 tzdata 的 scratch/distroless 镜像里直接报错。三件事一起做：

  1. 存储与传输统一 UTC：DB 连接 loc=UTC 或 time.Now().UTC()。
  2. 输出到用户侧（响应 JSON、日志）再转业务时区。
  3. Docker 运行阶段装 tzdata，并设置环境变量：
    yaml
    # docker-compose.yml
environment:
  - TZ=Asia/Shanghai
    # docker-compose.yml
environment:
  - TZ=Asia/Shanghai
    1
    2
    3

另一个高频坑：MySQL DSN loc=Local 与服务时区不一致会导致 time.Time 读出偏移 8 小时。

10.2 JSON 大小写与字段名 ​

encoding/json 解码对 interface{} / map[string]any 时数字统一变 float64，10001 会变 10001.0；与前端数字精度（如雪花 ID 超 2^53）对接时必须用 json.Number：

go
dec := json.NewDecoder(strings.NewReader(raw))
dec.UseNumber() // map 里数字变成 json.Number
dec := json.NewDecoder(strings.NewReader(raw))
dec.UseNumber() // map 里数字变成 json.Number
1
2

结构体字段未写 tag 时用字段名原文序列化（大驼峰）；前后端约定不一致是联调第一吵架点，DTO 一律显式写 tag。

10.3 空切片、空结构体与 null ​

场景结果对策
nil slice 序列化null返回 []model.X{} 或封装层兜底转 []
空 struct 无 omitempty"field":{}指针字段 + omitempty
值为 0 的 int不省略omitempty 对 0 无效，用 *int
time.Time 零值"0001-01-01T00:00:00Z"指针 / 自定义类型 / omitempty

原则：给前端的响应模型单独定义 DTO，与 DB model 分离，宁多写几个字段结构，不把 orm 结构直接吐出去。

10.4 连接池参数缺失 ​

不设 SetMaxOpenConns 等于无上限，慢 SQL 一多就打满 DB 连接导致雪崩；设太小又会在尖峰期排队。起步建议：max_open_conns = 核数 x 10 左右，配合慢 SQL 日志与 P99 监控再调；ConnMaxLifetime 必须小于 MySQL wait_timeout。

10.5 其它值得记住的坑 ​

坑说明
循环里 defer文件/连接资源在循环内打开必须包函数，否则攒到函数结束才关
错误里带敏感信息fmt.Errorf 拼接 SQL / token 会进日志，脱敏
