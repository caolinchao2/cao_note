AI 与大模型 ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

⚠️ 本篇通用说明（重要）：我的主线项目（充电桩、T-CEC 互联互通、支付对账）目前还没上 AI 能力。所以这一章所有内容都按「学习方向 / 技术储备」对待，面试时绝对不要说成线上项目经历。 但我是有优势的：RAG 和 Agent 的后端落地用到的是 Spring Boot + SSE + 向量库，这些正好是我熟悉的技术栈。所以我的说法是「AI 这块我在学、也动手做过 demo，业务上还没落地，但我清楚后端要怎么做」。

1. 大模型基础概念：LLM、Token、上下文窗口、Temperature ★★★ ​

通俗理解

  • LLM：基于 Transformer、在海量文本上预训练的模型，本质能力就是「预测下一个 token」，一个字一个字往外蹦（自回归）。
  • Token：模型处理文本的最小单位，一个汉字大概 1-2 个 token，计费和上下文长度都按它算。
  • 上下文窗口：单次「输入 + 输出」的 token 上限，输出也占额度，超了就得截断或压缩。
  • Temperature：随机性开关。越低越稳定（代码、事实问答用 0-0.3），越高越发散（写作、创意用 0.7-1）。

我的项目关联说明一下：这是纯概念，我们项目里没用。我能关联的只有一点 —— 我们的日志/traceId 串链路思路和「上下文窗口」是同一种取舍：信息不能无限塞，得挑重点。

面试答题话术 「我理解 LLM 就是自回归预测下一个 token，所以它有概率性。Token 是计费和上下文的基本单位，上下文窗口是输入输出合计。Temperature 控制随机性——做代码和事实问答要调到很低。这些都是概念，我们业务还没上，但我清楚成本主要按 token 算。」

2. 大模型幻觉 ★★★ ​

通俗理解 模型一本正经地编造事实（假数据、假引用）。根因是它本质在「生成最像答案的内容」，不是查库，而且训练数据可能过时、有噪声。 缓解：RAG 喂真实资料、限定知识范围、Few-shot 给示例、降低 temperature、要求给依据、人工复核。幻觉不能彻底消除，只能缓解。

我的项目关联说明一下：我们没上 AI，所以没有线上幻觉问题。但这个风险我很能理解 —— 我们的 T-CEC 对接和支付对账都是「数据必须准」的场景，如果引入 AI 生成内容，一定要走 RAG + 溯源，绝不能让它自由发挥。这是我对 AI 落地到我们业务的判断。

面试答题话术 「幻觉是模型编造内容，根因是它在生成而不是查询。缓解手段主要是 RAG 喂真实资料、降 temperature、要求给依据，但不能彻底消除。我们做的是计费对账这类要求数据准确的业务，所以我的判断是——AI 只能辅助，关键数据必须可溯源。」

3. 提示词工程（Prompt Engineering）★★☆ ​

通俗理解 用输入设计引导输出。常用技巧：角色设定、Few-shot（给几个例子）、CoT 思维链（要求一步步想）、输出格式约束（JSON/Markdown）。 套路：明确任务 → 给上下文 → 给示例 → 限格式 → 要求依据。CoT 有效的原理是让模型展开中间推理，而不是直接跳结论。

我的项目关联说明一下：属于了解层面，项目里没用。日常我用 AI 辅助写代码、查资料，会用到这些技巧，但那不算项目经验，面试要老实说。

面试答题话术 「提示词常用的是角色设定、Few-shot 和思维链。思维链有效是因为它逼模型展开推理而不是跳结论。这块我是日常用 AI 时练的，不算项目经验，但技巧和原理我都清楚。」

4. RAG 检索增强生成 ★★★ 【重点，后端最该掌握】 ​

通俗理解RAG = 检索 + 增强 + 生成。为什么要它：模型没见过我们公司的私有文档、知识有截止时间、会幻觉、微调又贵。 完整流程五步：

  1. 切分：文档按语义/长度切成小片段（chunk）
  2. 向量化：用 Embedding 模型把片段转成向量
  3. 存储：写进向量库
  4. 召回：把用户问题也向量化，按相似度（余弦）找 Top-K 最相关片段
  5. 拼接生成：把召回的片段拼进 Prompt，交给 LLM 生成答案 细节：切片要有重叠（overlap）避免语义断裂；召回后可以用 Rerank 重排提升精度。

我的项目关联这是我在重点学的方向，而且我能落地。如果给我们业务做，我的思路很具体：

  • 把充电桩接入文档、故障码表、T-CEC 协议规范、接入手册切分入库，做成运维/客服的知识库问答；
  • 后端这块就是 Spring Boot + 向量库 + RAG 流程 + SSE 流式返回 —— 技术栈我完全熟。 必须说清楚：这是我们业务还没落地的规划，不是线上功能，面试我会如实说「我在学、也做过 demo」。

面试答题话术 「RAG 的流程是：切分、向量化、存向量库、按语义召回 Top-K、拼进 Prompt 让模型生成。它的价值是解决私有知识和时效性问题。我把它当成一个具体项目的方向在看——我们充电业务有大量接入文档、故障码表、协议规范，很适合做运维知识库问答。后端这块就是 Spring Boot 加向量库加 SSE，栈我是熟的。要说明的是我们业务还没落地，这是我做的技术储备。」

5. 向量数据库 ★★★ ​

通俗理解 传统库按「精确值」查，向量库按「语义相似」查，靠 ANN（近似最近邻）索引加速 —— HNSW（图索引）、IVF（倒排）、PQ（量化），牺牲一点精度换速度。 选型：Milvus（专业、大规模）、pgvector（PostgreSQL 插件，中小规模省心）、Redis Vector（已有 Redis 栈）、FAISS（偏库）。

我的项目关联真实背景：我们自己的业务库是 MySQL + InfluxDB（时序），还没引入向量库。选型上如果做我会倾向 pgvector —— 因为我们本来就是 MySQL 生态，运维成本最低，这个判断是基于我们真实技术栈得出的，不是我背的选型表。

面试答题话术 「向量库和传统库的区别是——一个按语义近似查，一个按精确值查，底层靠 ANN 索引。选型我会优先看现有技术栈：我们主库是 MySQL，所以会优先考虑 pgvector，运维成本最低；数据量真上来了再换 Milvus。这个判断是从我们实际环境出发的。」

6. Function Calling / Tool Use / Agent ★★★ ​

通俗理解

  • Function Calling：模型不直接给答案，而是输出「要调哪个函数 + 参数」，由应用真正去执行，再把结果喂回模型继续生成。
  • Agent：让模型自己规划、调工具、多步执行，核心是「思考 → 行动 → 观察」的循环（ReAct 模式）。
  • 关键分工：模型负责「决定调什么」，后端负责「真正执行 + 校验参数」。

我的项目关联这里我有个特别的共鸣点：我们充电桩协议网关干的事，本质就是「解析指令 → 校验 → 执行 → 回结果」，跟 Function Calling 的模式非常像。所以我理解 Agent 的后端职责很快 —— 模型是决策者，后端是执行者，安全性必须由后端兜住（不能把模型输出直接拼 SQL 或命令，这是通用安全原则）。

面试答题话术 「Function Calling 是模型输出要调用的函数和参数，后端真正执行再回传结果。Agent 就是在这个基础上让模型多步循环——思考、行动、观察。我觉得后端在这块的核心职责是两件事：真正执行，以及校验参数、防注入。这点我们有共鸣，因为我们的协议网关也是『解析指令再校验执行』，模型输出绝对不能直接拼进 SQL 或命令里。」

7. 模型微调（Fine-tuning）★★☆ ​

通俗理解 预训练是在通用语料上训底座，微调是在特定任务数据上继续训。LoRA 只训练注入的低秩矩阵、冻结原权重，大幅省显存和成本，是主流轻量方案。RLHF 是用人类偏好对齐模型输出。 选择原则：要引入私有知识、要能及时更新 → RAG；要稳定改变风格/格式/领域能力 → 微调。多数业务优先 RAG。

我的项目关联了解层面。微调对我们不现实 —— 成本高、也没有标注数据。真有需求我会先上 RAG，这个判断是成本驱动的，不是技术偏好。

面试答题话术 「微调是改模型本身，LoRA 是省显存的主流做法。选择上：私有知识、要更新就用 RAG；改风格和输出格式才考虑微调。对大多数业务来说 RAG 性价比更高，我们也是这个思路。」

8. 大模型应用工程（Java 后端方向）★★★ 【重点，最贴合我的栈】 ​

通俗理解

  • Spring AI：Spring 官方的 AI 框架，把各家模型（OpenAI、DeepSeek、通义、Ollama）统一成一套接口（ChatClient、EmbeddingModel），还封装了 VectorStore、提示词模板、Function Calling、RAG 流程、流式输出。跟 Spring Boot 无缝集成，starter 开箱即用。
  • SSE 流式输出（重点）：模型生成慢，等整段返回体验差，所以用 SSE 边生成边推（打字机效果）。
    • 实现：Controller 返回 SseEmitter，分片 send()、最后 complete()；或返回 Flux<ServerSentEvent>（WebFlux）。
  • SSE vs WebSocket：SSE 是单向（服务端推客户端）、基于 HTTP、能自动重连、更轻、好穿网关；WebSocket 是双向全双工。大模型场景只需要服务端单向推，所以 SSE 更合适。
  • 网关注意：Nginx 要关缓冲（proxy_buffering off）、设长超时、加 X-Accel-Buffering: no，不然流式会被攒着一起发，打字机效果就没了。
  • 其他工程点：token 成本控制（限 max_tokens、缓存 prompt）、多轮对话记忆（摘要压缩/滑动窗口）、超时重试降级（多模型冗余、限流）、内容安全（防 Prompt Injection）。

我的项目关联这块是我最有底气的地方 —— 不是因为我做过 AI，而是因为技术栈完全对得上：

  • SSE：我们后台的 3D 大屏实时刷新用的是 WebSocket（07 笔记讲过），所以我非常清楚「长连接推送」的工程问题 —— 超时、网关缓冲、断线重连。换成 SSE 做流式输出，我理解起来是同一个坑。
  • Spring Boot + 异步/流式：Spring 全家桶（04 笔记）是我的主场。
  • 网关配置：我们的服务前面就有网关，proxy_buffering 这类配置我是真的处理过类似问题。 诚实声明：AI 应用本身还是我的学习储备，业务没上。

面试答题话术 「Java 做 AI 应用我会用 Spring AI，它把各家的模型统一成一套接口，还封装了 RAG 和流式输出。流式我用 SSE，Controller 返回 SseEmitter 分片推；选 SSE 而不是 WebSocket，是因为大模型只需要服务端单向推，SSE 更轻、更好穿网关。这里有个真实的坑——网关不关缓冲流式就失效了，会攒着一起发，我们做实时推送时踩过类似的问题。AI 应用本身我还在学习阶段，但这些工程细节我是有实战基础的。」

9. 常见 AI 面试速答 ★★★（口述骨架） ​

通俗理解 把高频问法串成几句话，面试时直接说骨架。

我的项目关联 统一话术：AI 是我的技术储备方向，业务主线还没落地，但技术栈能对上（Spring Boot + SSE + 向量库），这个定位要说在最前面，避免被追问「你线上 AI 项目的数据指标」时卡住。

面试答题话术

  • 怎么做企业知识库问答：「文档切分 → Embedding → 向量库 → RAG 召回 → LLM 生成 → SSE 流式 → 加权限和内容安全，分阶段上线。我还在学习落地阶段。」
  • RAG 和微调怎么选：「引入私有知识、要能及时更新用 RAG；改风格和领域能力才用微调。多数业务先 RAG。」
  • 怎么解决幻觉：「RAG、限定知识范围、Few-shot、降 temperature、要求给依据。不能彻底消除。」
  • 向量库为什么快：「靠 ANN 近似最近邻索引，HNSW、IVF 这些，牺牲一点精度换速度。」
  • 怎么保证 AI 服务高可用：「多模型冗余、超时重试、限流、缓存、降级兜底。」

附：一句话速记（可以跳过 ★☆☆） ​

  • Transformer / 注意力机制：LLM 的底层架构，理解「自注意力让模型关注上下文相关部分」即可，面试问到不用展开公式。
  • MoE（混合专家）：大模型省算力的架构思路，知道「按需激活部分专家」这个概念就行。
  • 多模态：模型能同时处理文本、图片、语音，了解概念即可。
