AI 与大模型 ​

常问等级：★★★ 高频必考 / ★★☆ 中频常见 / ★☆☆ 低频了解 深度标准：每个考点讲清「是什么 → 为什么 → 关键原理 → 追问应对 → 易错点」。 前端转全栈重点：RAG、Function Calling/Agent、Spring AI + SSE 流式输出。这三块是 Java 后端 AI 方向最高频的，也和你的技术栈（SpringBoot + SSE + SpringAI）直接对上。

大模型基础概念：LLM、Token、上下文窗口、Temperature ★★★ ​

是什么 ​

  • LLM（大语言模型）：基于 Transformer 架构、在海量文本上预训练的语言模型（GPT、Claude、DeepSeek、Qwen、GLM 等），核心能力是「预测下一个 token」。
  • Token：模型处理文本的最小单位（一个汉字≈1-2 token，一个英文单词≈1-2 token）；计费、上下文长度都按 token 算。
  • 上下文窗口（Context Window）：单次输入 + 输出能容纳的最大 token 数（如 4K/32K/128K），超长需截断、压缩或分段。
  • Temperature（温度）：控制随机性，越低越稳定确定（代码/翻译用 0-0.3），越高越发散（创意写作用 0.7-1）。
  • Top-p / Top-k：核采样/前 k 采样，从概率最高的候选里选，控制多样性。

为什么是预测下一个 token ​

  • LLM 本质是「自回归」生成，每一步基于前文预测最可能的下一个 token，循环直到输出结束符；概率采样（temperature/top-p）决定多样性。

追问应对 ​

  • 「token 和字节/字符什么关系？」→ token 是子词单位（BPE 分词），介于字符和词之间，一个词可能拆多个 token。
  • 「温度设为 0 就完全确定吗？」→ 接近贪婪解码，但浮点误差下仍可能有细微差异；代码/事实问答建议低温。

易错点 ​

  • 上下文窗口是「输入 + 输出」合计，输出也要占 token；长文档要先切分/压缩再塞入。

大模型幻觉（Hallucination）★★★ ​

是什么 ​

  • 模型生成看似合理但事实错误、无依据的内容（编造数字、引用、人物）。

为什么 ​

  • 概率生成本质（不是查数据库，是「编最像的答案」）、训练数据有噪声/过时、缺乏外部知识检索、模型被鼓励「流畅回答」而非「承认不知道」。

缓解 ​

  • RAG（检索增强，喂真实资料）、限定知识范围、Few-shot 给示例、降低 temperature、要求给出依据/出处、人工校验。

追问应对 ​

  • 「幻觉能彻底消除吗？」→ 不能完全消除，只能缓解；关键场景（医疗/法律/金融）需人工复核或严格 RAG + 溯源。

提示词工程（Prompt Engineering）★★☆ ​

是什么 ​

  • 通过设计输入来引导模型输出符合预期的结果。

常用技巧 ​

  • 角色设定：让模型扮演某角色（「你是资深 Java 工程师」）。
  • Few-shot：给几个输入输出示例，让模型照格式作答。
  • CoT（思维链）：要求「一步步思考」，提升推理题准确率。
  • 输出约束：指定格式（JSON/Markdown/表格）、长度、语言。
  • 结构化套路：明确任务 → 提供上下文 → 给出示例 → 限定格式 → 要求依据。

追问应对 ​

  • 「CoT 为什么有效？」→ 引导模型展开中间推理步骤，而不是直接跳结论，减少推理错误。

RAG 检索增强生成 ★★★ ​

是什么 / 为什么 ​

  • RAG = 检索（Retrieval）+ 增强（Augmented）+ 生成（Generation）。
  • 为什么需要：解决① 私有知识（内部文档模型没见过）；② 知识时效性（训练数据有截止时间）；③ 幻觉；④ 微调成本高。不重新训练模型，用「检索」把相关知识喂给模型。

完整流程 ​

  1. 文档切分（Chunking）：把长文档按语义/固定长度切成小片段。
  2. Embedding 向量化：用向量模型把每个片段转成高维向量。
  3. 向量存储：写入向量数据库（Milvus/pgvector/Redis Vector 等）。
  4. 检索召回：把用户问题也向量化，用相似度（余弦）检索最相关的 Top-K 片段。
  5. 拼接上下文：把召回片段拼进 Prompt，连同问题交给 LLM 生成答案。

关键细节 ​

  • Embedding：文本→向量的模型，语义相近的文本向量距离近。
  • 相似度：余弦相似度、内积、欧氏距离。
  • Rerank（重排序）：召回后再用重排模型精排，提升 top 相关度。
  • 切分策略：按段落/标题/固定 token，重叠切片（overlap）避免语义断裂。

追问应对 ​

  • 「为什么不能直接把整个文档塞给模型？」→ 超出上下文窗口 + token 成本高 + 无关内容干扰 + 检索精度差。
  • 「RAG 和微调怎么选？」→ 私有知识及时更新、可解释、成本低 → RAG；改风格/输出格式/领域能力稳定 → 微调。多数业务优先 RAG。

易错点 ​

  • 切分太碎会丢上下文，太大又降低召回精度；需按文档结构调优，配合 Rerank 提升。

向量数据库 ★★★ ​

是什么 / 为什么 ​

  • 传统数据库按精确匹配查询；向量检索需按「语义相似度」找近邻，需要向量索引（ANN 近似最近邻）。
  • ANN：HNSW（图索引）、IVF（倒排）、PQ（乘积量化）等，牺牲一点精度换亚线性检索速度。

常见选型 ​

  • Milvus：专业向量库，功能全、分布式，适合大规模。
  • pgvector：PostgreSQL 插件，向量 + 关系数据一体，中小规模够用、运维简单。
  • Redis Vector：Redis 扩展，适合已有 Redis 栈、低延迟。
  • FAISS：Meta 开源向量检索库，偏库而非服务。

追问应对 ​

  • 「向量库和传统数据库本质区别？」→ 传统按「精确值」查，向量库按「语义近似」查，底层是 ANN 索引。
  • 「选型怎么定？」→ 根据数据量、是否需与业务数据联查、运维成本；中小项目 pgvector 省心，大规模 Milvus。

Function Calling / Tool Use / Agent ★★★ ​

是什么 ​

  • Function Calling（函数调用/工具调用）：模型不直接给最终答案，而是输出「要调用哪个函数 + 参数」的 JSON，由应用真正执行函数，再把结果回传给模型继续生成。
    • 例：问「杭州明天天气」，模型输出 getWeather(city="杭州")，应用调天气 API 拿结果喂回模型。

Agent（智能体） ​

  • 让模型自主规划、调用工具、多步执行完成目标，核心是「思考-行动-观察」循环。
  • ReAct 模式：Reasoning（推理下一步）+ Acting（调用工具）+ Observation（观察结果），循环直到完成。
  • 多 Agent：多个 Agent 分工协作（规划者 + 执行者 + 评审者）。

追问应对 ​

  • 「Function Calling 和普通 API 调用区别？」→ 普通调用是「人决定调什么接口」，Function Calling 是「模型决定调什么工具和参数」，工具定义提前告诉模型（JSON Schema）。
  • 「后端在 Function Calling 里干什么？」→ 真正执行函数、做校验、返回结构化结果给模型；模型只负责「决策」，不负责「执行」。

易错点 ​

  • 模型输出的参数可能是错的，后端要对参数做校验；工具调用要防注入（别把模型输出直接拼 SQL/命令）。

模型微调（Fine-tuning）★★☆ ​

是什么 ​

  • 预训练 vs 微调：预训练在大规模通用语料上训练底座模型；微调（SFT 有监督微调）在特定任务的标注数据上继续训练。
  • LoRA（低秩适配）：冻结原模型权重，只训练注入的低秩矩阵，大幅降低显存和成本，主流轻量微调方案。
  • RLHF（人类反馈强化学习）：用人类偏好训练奖励模型，再强化学习对齐，让回答更符合预期。

追问应对 ​

  • 「什么时候微调、什么时候 RAG？」→ 需引入私有知识、及时更新 → RAG；需稳定改变风格/格式/领域能力 → 微调；两者可结合（微调 + RAG）。

大模型应用工程（Java 后端方向）★★★ ​

Spring AI ★★★ ​

  • Spring 官方 AI 框架，把各大模型（OpenAI、DeepSeek、Qwen、Ollama 等）统一成一套接口（ChatClient、EmbeddingModel 等）。
  • 提供：模型调用抽象、Embedding、向量存储（VectorStore 对接 pgvector/Milvus）、提示词模板、Function Calling、RAG 流程封装、流式输出。
  • 与 SpringBoot 无缝集成，starter 开箱即用（如 spring-ai-openai-spring-boot-starter）。

SSE 流式输出（前端转全栈必考）★★★ ​

  • 为什么用 SSE：大模型生成慢，整段返回用户等待久；用 SSE（Server-Sent Events）让后端把结果一段段「流式」推给前端，边生成边显示（打字机效果）。
  • 实现（SpringBoot）：
    • Controller 返回 SseEmitter，emitter.send(...) 分段推送，emitter.complete() 结束。
    • 或返回 Flux<ServerSentEvent>（WebFlux/Reactor）流式响应。
  • SSE vs WebSocket：SSE 单向（服务端→客户端）、基于 HTTP、自动重连、更简单；WebSocket 双向全双工。大模型场景只需服务端单向推送，SSE 更轻量、易穿透网关。

Token 计数与成本控制 ★★☆ ​

  • 计费按输入 + 输出 token；做 token 预算、限制最大输出长度（max_tokens）、缓存重复 prompt、压缩上下文。

多轮对话记忆管理 ★★☆ ​

  • 模型无状态，每次需把历史对话 + 新问题一起发给模型；通过维护对话列表，超出上下文窗口时做「摘要压缩」「滑动窗口截断」或「向量检索历史」。

超时、重试、降级 ★★☆ ​

  • 大模型调用慢且可能超时，设合理超时、指数退避重试、失败降级（返回缓存/兜底话术/切换备用模型）、限流防打爆上游。

内容安全 ★★☆ ​

  • 输入侧敏感词过滤、输出侧合规校验；防提示词注入（Prompt Injection）诱导模型泄露系统提示或执行危险操作。

追问应对 ​

  • 「为什么大模型接口要 SSE 而不是普通同步返回？」→ 生成耗时长，同步返回用户干等、易超时；SSE 边生成边推，体验好。
  • 「SSE 在网关（Nginx）要注意什么？」→ 关闭缓冲（proxy_buffering off）、设置长超时、X-Accel-Buffering: no 头。

常见 AI 面试速答 ★★★ ​

  • 「你会怎么给公司做知识库问答机器人？」→ 文档切分 + Embedding + 向量库 + RAG 检索 + LLM 生成 + SSE 流式 + 权限/内容安全，分阶段上线。
  • 「RAG 和微调怎么选？」→ 私有知识及时更新用 RAG，改风格/领域能力用微调，多数先 RAG。
  • 「怎么解决大模型幻觉？」→ RAG、限定范围、Few-shot、降 temperature、要求给出依据。
  • 「向量数据库为什么快？」→ ANN 近似最近邻 + 专用索引（HNSW/IVF），牺牲少量精度换亚线性检索。
  • 「怎么保证大模型服务高可用？」→ 多模型冗余、超时重试、限流、缓存、降级兜底。
