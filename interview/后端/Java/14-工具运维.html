1. Git 常用命令、merge 与 rebase 区别 ★★☆ ​

常用命令写代码天天用，不必背；真正要讲清楚的是 merge、rebase、reset、revert 的差别。

  • merge：把目标分支合并进来，保留分支历史，多一个合并提交，历史是分叉的 —— 安全。
  • rebase：把自己的提交挪到目标分支后面，历史是一条直线，但会改写提交记录 —— 所以只能用在没推送出去的本地分支。
  • reset vs revert：reset 移动 HEAD，会丢提交；revert 生成一个反向提交，历史保留，更安全。
  • 分支规范：个人 feature 分支先 rebase 拉平历史再提 MR；公共分支（main / develop）绝对不 rebase，只用 merge，避免把别人的提交历史搞乱。
  • 回退线上问题用 revert 而不是 reset，因为 reset 会丢历史。

2. Maven 依赖冲突 ★★☆ ​

A 依赖 B(1.0)、C 依赖 B(2.0)，同一个库的不同版本同时被引入就产生冲突。Maven 默认按两个原则选版本：

  • 最短路径优先：依赖路径短的版本胜出；
  • 最先声明优先：路径长度相同时，取 pom 中先声明的那条。

典型现象是运行时报 NoSuchMethodError 这类错误：编译能过，运行才炸，因为编译期用的是另一个版本的签名。这类问题在 Spring Boot 多模块项目里比较常见，不同模块各自引了不同版本的公共库就会撞上。解决手段：

  • mvn dependency:tree 打印依赖树，定位是哪个模块传递引进来的；
  • <exclusion> 在引入方排除掉冲突的传递依赖；
  • dependencyManagement 统一锁版本，多模块项目里由父 pom 统一管理。

3. Docker 基础概念 ★★☆ ​

  • 镜像：只读模板，分层构建；
  • 容器：镜像的运行实例，共享宿主机内核；
  • Dockerfile：构建镜像的脚本；
  • 仓库：集中存放镜像的地方，如 Harbor / Docker Hub。

与虚拟机的区别：虚拟机虚拟一整套 OS，重、隔离彻底；容器共享内核，轻、秒级启动，隔离弱一些。分层的好处是公共层可复用，构建和传输都省。

易错点：容器内存限制和 JVM 堆要配套设置。容器有内存限制时如果 JVM 不显式设堆大小，可能被 OOM Killer 干掉（进程 exit 137），详见 04-JVM 篇。

  • 进程 / CPU：top、ps -ef | grep、kill -9、nohup ... &
  • 日志：tail -f、grep、less
  • 端口：netstat -tlnp、ss -tlnp、lsof -i:8080

5. 常见安全：XSS、CSRF、SQL 注入 ★★★ 【简历亮点，高频追问】 ​

  • SQL 注入：用户输入被当成 SQL 拼进去了（典型 payload ' OR '1'='1）。防御核心是预编译（#{} / PreparedStatement），让参数只能当值、不能当语法；MyBatis 里禁止用 ${} 拼接。
  • XSS：恶意脚本被注入页面并在浏览器执行，偷 cookie、冒充用户操作。防御：输出转义、CSP、Cookie 加 HttpOnly、输入过滤。
  • CSRF：诱导你在已登录状态下点恶意链接，冒充你发请求。防御：CSRF Token、SameSite Cookie、校验 Referer。
  • 区别一句话：XSS 是注入脚本利用「用户」，CSRF 是利用「登录态」冒用身份。
  • 密码存法：加盐哈希（BCrypt），不能明文、不能裸 MD5。

6. 越权漏洞（IDOR）★★★ 【简历亮点，高频追问】 ​

  • 水平越权：同级用户之间越界，A 用户改一下 URL 里的 id 就能看到 B 用户的数据。
  • 垂直越权：普通用户访问了管理员功能，低权限干了高权限的事。
  • 防御关键：服务端必须做资源归属校验，正确做法是查询时就把当前用户的身份条件带进查询（如 where user_id = 当前用户），而不是查出结果再判断，这样从根上避免越权。
  • 前端隐藏按钮只能算体验优化，不算安全措施。

7. 线上排查完整流程 ★★★ 【简历亮点，高频追问】 ​

固定五步：

  1. 确认现象：报错内容、影响范围、能否复现。
  2. 看监控：CPU / 内存 / GC / 慢 SQL / 错误率，先判断是资源问题还是逻辑问题。
  3. 看日志：读错误堆栈，用 traceId 串联一次请求的完整链路。
  4. 定位：按现象分头查，见下面的口诀。
  5. 修复 + 验证 + 复盘加监控：光修完不加告警，下次还会被打个措手不及。

定位的口诀：

  • CPU 高 → top + top -Hp + jstack
  • 内存高 / OOM → dump + MAT
  • 响应慢 → 查慢 SQL、下游服务、GC 频率
  • 报错 → 直接看堆栈

典型例子：接口偶发变慢，最后定位到 Redis 大 key 阻塞（见 06-Redis 篇）。

8. 线程 dump 分析 ★★☆ ​

用 jstack pid > dump.txt 导出线程快照，重点看线程状态：BLOCKED（等锁）、WAITING、RUNNABLE。JDK 自带的死锁检测会直接打印出死锁线程和锁的持有关系。大量 BLOCKED 说明锁竞争严重，要顺着 dump 找「谁持有锁」。

排查 CPU 飙高的标准动作：top 找进程 → top -Hp 找最耗 CPU 的线程 → 把线程 id 转成十六进制 → 在 jstack 输出里搜这个 nid，定位到具体代码行（与 02-JVM 篇是同一套手法）。

9. JVM 调优参数 ★★☆ ​

详见 04-JVM 篇，核心就几个：

  • -Xms / -Xmx：初始堆和最大堆，生产一般设为相同值，避免运行期扩容；
  • -XX:+UseG1GC：启用 G1 收集器；
  • -XX:MaxGCPauseMillis：G1 的期望最大停顿时间目标；
  • OOM 时 dump：-XX:+HeapDumpOnOutOfMemoryError（配 -XX:HeapDumpPath 指定路径），保留现场给 MAT 分析。

容器环境尤其要显式设堆：容器内存限制要和 JVM 堆配套，不设 -Xmx 会让 JVM 的内存认知和容器限制不一致，进程被 OOM Killer 杀掉（exit 137）。

10. 日志框架与监控体系 ★★☆ ​

日志：

  • SLF4J 门面 + Logback 实现，业务代码面向门面编程，换实现不用改代码；
  • 级别从细到粗 TRACE / DEBUG / INFO / WARN / ERROR；
  • 输出最好用结构化 JSON，并打 traceId 贯穿全链路，排查时能把同一次请求的日志串起来；
  • 不打印敏感信息：手机号、身份证这类字段要脱敏。

监控：

  • 指标：Prometheus 采集 + Grafana 展示；
  • 链路：SkyWalking；
  • 日志：ELK；
  • 配阈值告警（接口耗时、错误率等）。

11. 如果程序员删库跑路了，怎么恢复数据 ★★★ （场景题） ​

思路三步走：

  1. 止损：立刻停写、锁访问，别再让数据被覆盖。
  2. 恢复：先恢复最近的全量备份，再用 binlog 增量回放到删库前一刻，回放时过滤掉 drop/delete 那一段。
  3. 救命：如果从库没被同步删掉（尤其延迟从库），直接从从库捞数据。

预防比恢复更重要 —— 定期全量备份 + 开 binlog + 异地备份、配置延迟从库、生产库不给开发 drop 权限、删除走逻辑删除（is_deleted 标记）、定期做恢复演练。

12. 删除数据的几种恢复手段 ★★☆ ​

  • 备份恢复：全量备份 + binlog 增量回放，最通用的兜底手段。
  • 延迟从库：故意慢同步（如延迟一段时间），主库误删时从库还有数据，可以在延迟窗口内拦截。
  • 闪回（Flashback）：把 binlog 里的 delete/update 反向解析成 insert/update，工具如 binlog2sql、MyFlash。
  • 回收站：部分云数据库支持 drop 先入回收站，可以从回收站找回。

13. 在线调试工具 Arthas ★★☆ 【简历亮点，高频追问】 ​

阿里开源的 Java 在线诊断工具，原理是 attach 到运行中的 JVM，不用重启、不用改代码就能排查线上问题。和 jstack / jmap 这类 JDK 自带、功能单一的工具相比，Arthas 是交互式在线诊断：能反编译类、观测方法入参出参、追踪调用耗时。

最常用的几个命令：

  • dashboard：总览线程 / 内存 / GC；
  • thread -n 3：最忙的 3 个线程；thread -b 直接找死锁；
  • trace 类 方法：看方法调用耗时，定位性能瓶颈；
  • watch 类 方法 '{params, returnObj, throwExp}'：看入参、返回值、异常，不用加日志重新发版；
  • jad 类名：反编译，确认线上跑的到底是哪个版本的代码，比猜更可靠。

37. Maven能为我们解决什么问题？ ​

①添加第三方jar包

按照最原始的做法，我们是手动复制jar包到项目WEB-INF/lib下，每个项目都会有一份，造成大量重复文件。而Maven将jar包放在本地仓库中统一管理，需要jar包只需要用坐标的方式引用即可。

②jar包之间的依赖关系

jar包之间往往不是独立的，很多jar需要在其他jar包的支持下才能够正常工作，称为jar包之间的依赖关系。如果我们手动去导入，要知道jar包之间的依赖关系并一一导入是及其麻烦而且容易出错的。如果使用Maven，它能够将当前jar包所依赖的其他所有jar包全部导入。

③获取第三方jar包

开发过程中我们需要用到很多jar包，每个jar包在官网获取的方式不尽相同，给工作带来了额外困难。但是使用Maven可以以坐标的方式依赖一个jar包，Maven从中央仓库进行下载，并同时下载这

个jar包依赖的其他jar包。

④将项目拆分为多个工程模块

项目的规模越来越大，已经不可能通过package结构来划分模块，必须将项目拆分为多个工程协同开发。

43. 说说依赖的解析机制？ ​

当依赖的范围是 system 的时候，Maven 直接从本地文件系统中解析构件。

根据依赖坐标计算仓库路径，尝试直接从本地仓库寻找构件，如果发现对应的构件，就解析成功。

如果在本地仓库不存在相应的构件，就遍历所有的远程仓库，发现后，下载并解析使用。

如果依赖的版本是 RELEASE 或 LATEST，就基于更新策略读取所有远程仓库的元数据文件 （ groupId/artifactId/maven-metadata.xml），将其与本地仓库的对应元合并后，计算出 RELEASE 或者 LATEST 真实的值，然后基于该值检查本地仓库，或者从远程仓库下载。

如果依赖的版本是 SNAPSHOT，就基于更新策略读取所有远程仓库的元数据文件，将它与本地仓库

对应的元数据合并，得到最新快照版本的值，然后根据该值检查本地仓库，或从远程仓库下载。

如果最后解析得到的构件版本包含有时间戳，先将该文件下载下来，再将文件名中时间戳信息删除，剩下 SNAPSHOT 并使用（以非时间戳的形式使用）。

50. Nginx是如何处理一个HTTP请求的呢？ ​

Nginx 是一个高性能的 Web 服务器，能够同时处理大量的并发请求。它结合多进程机制和异步机制 ,异步机制使用的是异步非阻塞方式，接下来就给大家介绍一下 Nginx 的多线程机制和异步非阻塞机制。

1、多进程机制

服务器每当收到一个客户端时，就有服务器主进程（ master process）生成一个子进程( worker process）出来和客户端建立连接进行交互，直到连接断开，该子进程就结束了。

使用进程的好处是各个进程之间相互独立，不需要加锁，减少了使用锁对性能造成影响，同时降低编程的复杂度，降低开发成本。其次，采用独立的进程，可以让进程互相之间不会影响，如果一个进程发生异常退出时，其它进程正常工作， master 进程则很快启动新的 worker 进程，确保服务不会中断，从而将风险降到最低。

缺点是操作系统生成一个子进程需要进行内存复制等操作，在资源和时间上会产生一定的开销。当有大量请求时，会导致系统性能下降。

2、异步非阻塞机制

每个工作进程使用异步非阻塞方式，可以处理多个客户端请求。

当某个工作进程接收到客户端的请求以后，调用 IO 进行处理，如果不能立即得到结果，就去处理其他请求 （即为非阻塞）；而客户端在此期间也无需等待响应，可以去处理其他事情（即为异步）。

当 IO 返回时，就会通知此工作进程；该进程得到通知，暂时挂起当前处理的事务去响应客户端请求。
