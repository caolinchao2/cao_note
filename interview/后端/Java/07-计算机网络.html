计算机网络 ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

本篇怎么借力：计算机网络我最大的优势是做 TCP 长连接网关（充电桩接入 + T-CEC 互联互通）。凡是 TCP 相关的题（握手、保活、粘包、长连接），我都能讲出真实场景；纯前端侧的（URL 渲染、CDN）我也有前端背景可讲。这是前端转全栈最好讲的一篇。

1. OSI 七层模型与 TCP/IP 四层模型 ★★☆ ​

通俗理解OSI 七层从下到上：物理、链路、网络、传输、会话、表示、应用。实际用的是 TCP/IP 四层：应用层、传输层、网络层、网络接口层（记「应传网链」）。 分工：应用层（HTTP）负责业务通信，传输层（TCP/UDP、端口）负责端到端，网络层（IP）负责寻址路由，链路层（MAC）负责相邻节点传输。

我的项目关联我们这套系统天然对应这些层：充电桩跑的是 TCP（传输层），Netty 网关处理的是应用层的自定义协议（协议帧），业务之间走 HTTP/HTTPS。讲分层我可以直接拿协议栈举例。

面试答题话术 「四层记住『应传网链』就行。我们的充电桩协议栈正好对应上：底座是 TCP 长连接，上面是我们自定义的应用层协议，管理端和开放接口走 HTTP。分层的意义就是各层解耦、各管一段。」

2. TCP 三次握手、四次挥手 ★★★ 【简历亮点，高频追问】 ​

通俗理解三次握手：客户端 SYN → 服务端 SYN+ACK → 客户端 ACK，双方进入 ESTABLISHED。为什么三次不是两次：两次无法确认双方收发能力都正常，还会让「过期的旧 SYN」白白建立连接浪费资源。 四次挥手：主动方 FIN → 被动方 ACK → 被动方 FIN → 主动方 ACK。为什么四次：对方说不再发数据了，但我可能还有数据要发，所以 ACK 和 FIN 要分开发。 TIME_WAIT 等 2MSL：保证最后那个 ACK 能送到（丢了对方会重发 FIN），顺便让旧连接的报文在网络里消散。

我的项目关联 这个我可以讲真的。线上真实经验：我们的 Netty 网关跑的是 TCP 长连接，所以重点是握手之后怎么保活 —— 靠心跳（IdleStateHandler 检测空闲，超时没心跳就断连），断线后客户端重连。通用坑：TIME_WAIT 堆积这个问题我们网关侧没直接踩过，但如果大量短连接会耗尽端口，这是个经典问题，我是从资料里了解的。

面试答题话术 「三次握手是为了双向确认收发能力，两次不够，四次多余。四次挥手是因为对方还有数据没发完，ACK 和 FIN 不能合并。TIME_WAIT 等 2MSL 是保证最后的 ACK 能到。不过我们网关是长连接，握手不是重点，重点在于心跳保活和断线重连，这是真实的工程问题。」

3. TCP 与 UDP 区别 ★★★ 【简历亮点，高频追问】 ​

通俗理解TCP 面向连接、可靠（确认+重传）、有序、慢，头部 20 字节，面向字节流；UDP 无连接、不可靠、无序、快，头部 8 字节，面向报文（保留消息边界）。 场景：TCP 用于 HTTP、文件、数据库；UDP 用于视频语音、DNS、游戏。

我的项目关联真实场景：充电桩和我们的协议网关之间是 TCP 长连接——因为下发的启停指令、上报的充电数据绝对不能丢，必须可靠。而设备侧跟充电桩自己通信的 BMS 部分有走 CAN 的，那是另一个层面。另外 T-CEC 对接上级监管平台走的也是 HTTP（基于 TCP）。

面试答题话术 「TCP 可靠有序但慢，UDP 快但可能丢。我们充电桩接入用的是 TCP 长连接，因为启停指令和计费数据不能丢。选型逻辑很简单：要可靠性就用 TCP，要极致低延迟、能容忍丢包才用 UDP。」

4. HTTP 与 HTTPS 区别 ★★★ ​

通俗理解HTTP 明文、80 端口、无证书；HTTPS 加密（TLS）、443 端口、要 CA 证书、握手有加密开销所以略慢。 HTTPS 用的是混合加密：握手阶段用非对称加密交换对称密钥，数据传输用对称加密（快）。证书链用来验证服务器身份、防中间人攻击。

我的项目关联真实在用的：我们对外接口（支付回调、开放平台、T-CEC 对接）都是 HTTPS。T-CEC 互联互通里，光靠 HTTPS 还不够，还要做签名验签 + 时间戳防重放，因为监管/第三方平台要求双向确认身份。

面试答题话术 「HTTPS 是 HTTP 加 TLS，混合加密：握手用非对称加密换密钥，数据用对称加密。它的核心价值是防窃听和防中间人。我们对外接口都走 HTTPS，互联互通对接还额外加了签名和时间戳防重放。」

5. HTTPS 握手过程 ★★☆ ​

通俗理解 客户端发 ClientHello（支持的版本、加密套件、随机数）→ 服务端回 ServerHello + 证书 → 客户端验证证书、生成预主密钥用服务端公钥加密发过去 → 双方用随机数算出会话密钥 → 之后对称加密通信。 TLS 1.3 把它优化到 1-RTT，还废掉了弱算法。

我的项目关联 认知层面。我做前端时就接触过证书配置（Nginx 配 HTTPS），转全栈后对握手流程有概念，但深入不到源码。

面试答题话术 「大致是：协商算法、验证书、换密钥、转对称加密。TLS 1.3 把握手压到 1-RTT 更安全。这个我知道流程和结论就够了，实际排障更多是看证书有没有过期。」

6. HTTP 版本演进：1.0 / 1.1 / 2 / 3 ★★★ ​

通俗理解 1.0 短连接（每次新建）；1.1 长连接 keep-alive、Host 头；2 二进制分帧、多路复用（一个连接并发多请求）、头部压缩，解决了应用层的队头阻塞；3 换 QUIC（基于 UDP），解决传输层队头阻塞、支持 0-RTT。 关键点：HTTP/2 虽然多路复用，但底层还是 TCP，一旦丢包还是会阻塞后续（传输层队头阻塞），这是 HTTP/3 存在的理由。

我的项目关联真实用到的：我们对外的 API 有走 HTTP/2 的，长连接复用能显著减少握手开销。通用坑：HTTP/2 的传输层队头阻塞问题我们没实锤踩过，属于原理层面了解。

面试答题话术 「1.1 是长连接，2 是多路复用加头部压缩，解决了应用层队头阻塞，但因为底层还是 TCP，丢包照样阻塞，所以 3 换成 QUIC 基于 UDP。我们对外接口用到了 HTTP/2 的长连接复用。」

7. HTTP 状态码 ★★★ ​

通俗理解2xx 成功（200、201、204）；3xx 重定向（301 永久、302 临时、304 走缓存）；4xx 客户端错（400、401 未认证、403 无权限、404、429 限流）；5xx 服务端错（500、502 网关收到无效响应、503 不可用、504 网关超时）。

我的项目关联真实排障用得上：对接第三方支付和 T-CEC 平台时，看状态码就能快速定位是谁的问题 —— 502/504 大概率是我们网关或上游超时，400/401 是我们请求参数或鉴权不对。这是线上真实排查手段。

面试答题话术 「重点记 301/302 区别、304 走缓存、429 限流。502 和 504 的区别很实用：502 是上游返回了无效响应（通常挂了），504 是上游响应超时。我们对接第三方时就是靠这个快速判断问题在哪一侧。」

8. GET 与 POST 区别 ★★★ ​

通俗理解GET 取资源、参数在 URL、可缓存、幂等；POST 提交数据、参数在请求体、一般不缓存、不幂等。 关键结论：POST 不等于安全，参数只是不在 URL 里可见，抓包一样能看到，安全要靠 HTTPS。两者底层都是 HTTP 方法，没有绝对的大小限制。

我的项目关联真实约束：我们做接口设计时，所有会改变状态的操作（下单、启用充电、支付）都必须用 POST，这是规范也是安全底线。查询类用 GET，方便缓存和调试。

面试答题话术 「区别主要是语义：GET 取数据、幂等、可缓存，POST 提交数据、不幂等。要强调的是 POST 并不更安全，抓包都能看到，安全靠 HTTPS。我们规范上就是所有写操作都用 POST。」

9. Cookie 与 Session ★★★ ​

通俗理解Cookie 存在客户端，每次请求自动带上；Session 存在服务端，靠 Cookie 里的 session id 关联。 分布式下 Session 的关键问题是共享：解决方案是存 Redis（集中式）、用 JWT（无状态）、或粘性会话。

我的项目关联我们的后台管理系统是 JWT 无状态的（04 笔记 Spring Security 那节讲过完整链路）。不用服务端 Session，就是为了多实例部署时不用管会话共享。小程序端同理，用 token 而不是 Cookie。

面试答题话术 「Cookie 存客户端、Session 存服务端。分布式下 Session 要共享，一般存 Redis 或干脆用 JWT 无状态。我们的后台和小程序都用 JWT，token 无状态，服务端不用存会话，多实例天然没问题。」

10. 从输入 URL 到页面展示全过程 ★★★ 【前端转全栈优势】 ​

通俗理解 解析 URL → DNS 解析（浏览器缓存 → 系统缓存 → 递归查询根/顶级/权威）→ TCP 三次握手（HTTPS 再加 TLS）→ 发 HTTP 请求 → 服务端处理（可能过网关、负载均衡）→ 浏览器解析 HTML/CSS、执行 JS、渲染（回流/重绘）→ 保持或四次挥手关闭。

我的项目关联这题是我前端背景的最大加分项。三年小程序/H5 经验让我对渲染、回流重绘、资源加载顺序这些有真实体感；转后端之后，我能把后半段（网关、服务端处理、数据库）也讲清楚。这是我少有的能讲全链路的题。

面试答题话术 「这题我可以从前后端两头讲。前端侧：DNS 解析、TCP 连接、请求、解析渲染、回流重绘优化我做过。后端侧：请求到网关后做鉴权和限流，再路由到服务，查缓存和数据库。这种全链路视角是我从写页面转到写服务之后慢慢建立起来的。」

11. TCP 拥塞控制、滑动窗口、流量控制 ★★☆ ​

通俗理解流量控制：接收方通过滑动窗口告诉发送方「我还能收多少」，别发太快把我淹了。拥塞控制：慢启动（指数增长）→ 拥塞避免（线性增长）→ 快速重传（3 个重复 ACK 立即重传）→ 快速恢复。区别：流量控制看接收方能力，拥塞控制看整个网络状况。

我的项目关联 认知层面。做 Netty 网关时接触过 TCP 层的参数，但拥塞控制这块主要是了解。

面试答题话术 「滑动窗口是接收方告诉发送方能收多少；拥塞控制是看网络整体状况，慢启动、拥塞避免、快速重传。一个是端到端能力，一个是全局网络状态。」

12. DNS 解析、CDN 原理 ★★☆ ​

通俗理解DNS 把域名解析成 IP，走递归 + 迭代查询。CDN 把静态资源缓存到离用户近的边缘节点，用 DNS 调度（CNAME）把请求导向最近节点，就近返回、减少源站压力。

我的项目关联前端背景用得上的：小程序/H5 的图片、静态资源都在 CDN 上，我对缓存策略、回源、刷新有实际操作经验。后端这边主要是运维在配。

面试答题话术 「DNS 是域名查 IP，走递归加迭代。CDN 是把静态资源放边缘节点、就近返回，靠 DNS 调度。我之前做前端时静态资源都是走 CDN 的，对缓存和回源比较熟。」

13. ARP、ICMP、WebSocket ★★☆ ​

通俗理解ARP：局域网内用 IP 找 MAC。ICMP：网络诊断（ping、traceroute 都基于它）。WebSocket：基于 HTTP 升级的全双工长连接，适合实时双向通信。

我的项目关联WebSocket 我有真实场景：后台的 3D 大屏需要实时刷新设备状态和充电数据，这种实时推送就是 WebSocket 的典型用法。这也是我前端转后端能讲的一个连接点 —— 我做过后端主动推给前端。

面试答题话术 「ARP 是 IP 找 MAC，ICMP 是 ping 用的。WebSocket 是 HTTP 升级上来的全双工长连接，适合服务端主动推。我们后台的 3D 大屏实时数据就是 WebSocket 推的，这个我前后端都参与过。」

14. 对称加密与非对称加密 ★★☆ ​

通俗理解对称加密：加解密用同一把钥匙，快（AES），问题是钥匙怎么安全地给对方。非对称加密：公钥加密私钥解密，慢（RSA/ECC），用来换钥匙和做签名。数字签名是用私钥加密摘要、公钥验签，保证完整性和身份。

我的项目关联真实在用的：跟第三方平台/支付渠道对接，签名验签就是这套。我们用商户私钥签名、对方用我们公钥验签，防止请求被篡改和伪造。T-CEC 互联互通的身份认证也是这个思路。

面试答题话术 「对称加密快但密钥分发难，非对称加密慢但能安全交换密钥，所以 HTTPS 是混合着用。我们对接第三方平台用的是签名验签：私钥签名、公钥验签，保证请求没被篡改、身份是真的。这在支付和互联互通里是必须的。」

15. 负载均衡算法 ★★☆ ​

通俗理解轮询、加权轮询、随机、最少连接、一致性哈希、源地址哈希。 一致性哈希的用处：节点增删时只影响相邻一段数据，把迁移量降到最小，适合缓存/分片场景。数据倾斜用虚拟节点解决。

我的项目关联真实环境：我们多个网关/服务实例前面有负载均衡，对外是轮询策略。一致性哈希我们在缓存分片上有概念，但真实业务还没到要自己实现一致性哈希路由的程度。

面试答题话术 「常见的就是轮询、加权轮询、最少连接、一致性哈希。一致性哈希的价值是扩缩容时数据迁移最少，配虚拟节点解决倾斜。我们服务前用的是轮询，一致性哈希属于了解层面。」

附：一句话速记（可以跳过 ★☆☆） ​

  • 正向代理 / 反向代理：正向代理代表客户端（如翻墙），反向代理代表服务端（如 Nginx 负载均衡）。
  • Nagle 算法 / TCP_NODELAY：Nagle 会攒小包再发（延迟），对实时性要求高的场景要开 TCP_NODELAY 关掉它 —— 网关调优时值得知道这个词。
  • 粘包 / 半包：TCP 是字节流没有消息边界，所以要靠应用层协议解决（定长、分隔符、长度字段），Netty 里用 LengthFieldBasedFrameDecoder —— 这个我在网关里是真实用过的，比上面两条重要得多。
