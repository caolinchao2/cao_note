MySQL ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

1. InnoDB 与 MyISAM 区别 ★★★ ​

通俗理解InnoDB 支持事务、行级锁、外键、崩溃恢复，索引是聚簇的（数据即索引）；MyISAM 都不支持，只有表级锁、索引和数据分离，但无事务开销所以某些只读查询略快。MySQL 5.5 之后默认就是 InnoDB。一句话：生产一律 InnoDB。

我的项目关联 我们全部表都是 InnoDB，没得选——订单、支付、对账这些都要事务，MyISAM 根本不能用。这条基本是送分题，记住「要事务就 InnoDB」即可。

面试答题话术 「InnoDB 有事务、行锁、外键、崩溃恢复，索引是聚簇的；MyISAM 没事务、表锁、索引数据分离。MySQL 5.5 之后默认 InnoDB，生产上只要涉及事务就只能 InnoDB，我们项目全是它。」

2. 索引为什么用 B+ 树 ★★★ ​

通俗理解 哈希不支持范围查询和排序；二叉搜索树/红黑树太高，磁盘 IO 次数跟着树高走；B 树每个节点既存索引又存数据，一页能放的索引少，树也高。B+ 树则是「非叶子只存索引、数据全在叶子」，一页能塞更多索引，树更矮（3 层能存千万级）；叶子节点还用双向链表连起来，天然支持范围和排序。

我的项目关联 知道「B+ 树矮、叶子有链表、支持范围查询」这个结论就够。我们的查询大量是「按桩编号 + 时间范围查订单」，正好吃 B+ 树范围扫描的红利，这也是为什么时间字段要进联合索引。

面试答题话术 「选 B+ 树的核心是磁盘 IO：树越矮 IO 越少。B+ 树非叶子只存索引、能塞更多，所以树矮；数据全在叶子，叶子之间还有链表，范围查询和排序天然支持。哈希不能范围查，二叉树太高。项目里订单按桩加时间范围查，就靠叶子的链表顺序扫。」

3. 聚簇索引、回表、覆盖索引 ★★★ ​

通俗理解聚簇索引（主键索引）的叶子存整行数据，一张表只能有一个。二级索引的叶子存「索引列 + 主键值」，所以用它查完还得拿主键回聚簇索引捞整行，这叫回表。如果查的列全在二级索引里，就不用回表，这就是覆盖索引，性能最好。另外主键建议自增：顺序插入减少页分裂，UUID 随机插入会频繁页分裂、出碎片。

我的项目关联 优化时最常用的手段就是覆盖索引。比如「按桩编号 + 时间查订单状态」，我把要查的字段一起放进联合索引，就能避免回表。主键我们统一用自增或雪花 ID，不用 UUID，就是防页分裂。说清楚：我们没被 UUID 主键搞出过线上事故，这是建表规范上直接禁掉的。

面试答题话术 「聚簇索引叶子存整行，二级索引叶子存索引列加主键，所以二级索引查完要回表。查的列都在索引里叫覆盖索引，不用回表，是最常见的优化点。主键建议自增，为的是顺序插入少页分裂，UUID 随机插会频繁分裂。项目里我们流行『把要查的列一起建进联合索引』来避免回表。」

4. 最左前缀与联合索引 ★★★ ​

通俗理解联合索引 (a,b,c) 是按 a、b、c 的字典序排的，所以查询必须从最左列连续匹配才能用上索引：(a)、(a,b)、(a,b,c) 能命中；直接查 b、c 不行。还有一点：范围查询会「中断」，a=1 and b>2 用到 a 和 b，但 b 后面的 c 就用不上了，所以范围列尽量往联合索引后面放。

我的项目关联 这直接决定我们联合索引的字段顺序：等值条件、区分度高的列放最左，时间范围这种范围查询放最后。比如「桩编号（等值）+ 订单状态（等值）+ 创建时间（范围）」。

面试答题话术 「联合索引按最左列顺序排，所以必须从最左连续匹配。范围查询会中断后续列，所以设计时等值条件放前面、范围条件放最后。项目里我们的索引就是这个顺序：桩编号、状态这些等值列在前，时间范围在后。」

5. 索引失效场景 ★★★ 【简历亮点，高频追问】 ​

通俗理解 常见失效：索引列上做函数或运算（YEAR(create_time)=2024、id+1=5）；隐式类型转换（字符串字段没加引号，比如手机号）；不满足最左前缀；范围查询后面的列；!=、NOT IN；前导模糊 LIKE '%xx'；OR 连了非索引列；数据量特别小时优化器干脆全表扫。

我的项目关联隐式类型转换这个坑我们踩过。 现象是「明明建了索引，查询还是很慢」，排查发现是某个查询把字符串类型的编号当成数字传进去（或者反过来），字段类型和参数类型不一致触发隐式转换，索引直接失效。修复就是保证参数类型和字段类型一致。这是真实踩过的，后来我们把「类型必须一致」写进了 SQL review 规范。

面试答题话术 「常见失效有：索引列上用函数或运算、隐式类型转换、违反最左前缀、范围后面的列、前导模糊 like %xx、or 连非索引列。我踩过隐式类型转换——字符串编号当数字传，索引直接失效，查询变慢，改回类型一致就好了。判断走没走索引就是 explain 看 type 和 key。」

6. EXPLAIN 关键字段 ★★★ ​

通俗理解 重点看四样：type（访问类型，好坏顺序 system > const > eq_ref > ref > range > index > ALL）、key（实际用的索引）、rows（预估扫描行数）、Extra。Extra 里 Using index 是覆盖索引（好），Using filesort 是额外排序（要优化），Using temporary 是用了临时表（group by/distinct 没走索引）。

我的项目关联 我日常排查慢 SQL 就是 explain 起手，先看 type 是不是 ALL、再看 Extra 有没有 filesort 或 temporary。看到 ALL 基本就是缺索引或者索引失效了。

面试答题话术 「explain 重点看四列：type、key、rows、Extra。type 从好到差是 const、ref、range、index、ALL，看到 ALL 就是全表扫；Extra 里 Using index 是覆盖索引，Using filesort 和 Using temporary 是性能隐患。我排慢 SQL 就是先看 type 和 Extra。」

7. 事务 ACID 及实现原理 ★★★ ​

通俗理解原子性靠 undo log（能回滚）；持久性靠 redo log（提交后不丢）；隔离性靠锁 + MVCC；一致性是前三个共同保证的结果，不是单独一个机制。redo 记「改了什么」用于崩溃恢复，undo 记「改前的值」用于回滚和 MVCC。

我的项目关联 支付、订单、对账这些强一致场景全靠事务兜底。提醒一点：事务别写太大——大事务会占锁久、undo 膨胀、还可能拖慢主从，所以我们跑批是分批提交。

面试答题话术 「A 靠 undo log，D 靠 redo log，I 靠锁加 MVCC，C 是这三个共同的结果。redo 记改了什么、用于崩溃恢复；undo 记改前的值、用于回滚和 MVCC。项目里事务是我们的底线，但不会写大事务，批量场景分批提交。」

8. 隔离级别与并发问题 ★★★ ​

通俗理解 三种并发问题：脏读（读到别人没提交的）、不可重复读（同一事务两次读，中间别人 update 了）、幻读（中间别人 insert/delete，行数变了）。四个级别：读未提交（全有）、读已提交 RC（解决脏读）、可重复读 RR（解决脏读+不可重复读，MVCC 下基本解决幻读，MySQL 默认）、串行化（全解决但慢）。Oracle 默认是 RC。

我的项目关联 我们用 MySQL 默认的 RR。但要注意：RR 下间隙锁多，并发写容易死锁；所以像对账这种批量更新的场景，反而要控制锁范围、缩短事务。

面试答题话术 「三种问题：脏读、不可重复读、幻读。四个级别：读未提交、读已提交、可重复读、串行化。MySQL 默认 RR，靠 MVCC 加间隙锁基本解决幻读；Oracle 默认 RC。这个差异常考。项目里用默认 RR，但批量更新时我会特别小心间隙锁带来的死锁。」

9. MVCC 多版本并发控制 ★★★ 【简历亮点，高频追问】 ​

通俗理解MVCC 让「读不加锁、写不阻塞读」。原理是每行有隐藏列：最近修改的事务 id、指向 undo log 旧版本的回滚指针。读的时候根据 ReadView（快照）判断哪些版本可见，读的是历史版本。RC 和 RR 的区别就在 ReadView：RC 每次 SELECT 都新建一个（所以能看到别人新提交的），RR 是事务内第一次 SELECT 建一次然后复用（所以可重复读）。

我的项目关联 理解 MVCC 对我实际有用：为什么我的长事务里读到的还是老数据、为什么长事务会让 undo 链变长拖慢查询——都跟 ReadView 和版本链有关。所以我们规范是事务尽量短，尤其别在事务里做远程调用。

面试答题话术 「MVCC 是隐藏列加 undo log 加 ReadView，做到读不加锁、读写不阻塞。RC 和 RR 的差别就在 ReadView 的生成时机：RC 每次查都新建，所以能看到别人刚提交的；RR 只在事务第一次查时建一次然后复用，所以可重复读。项目里我特别注意别开长事务，因为长事务会让版本链变长、读变慢。」

10. MySQL 锁：行锁、间隙锁、临键锁 ★★★ ​

通俗理解InnoDB 有行锁。记录锁锁单行；间隙锁锁的是「区间之间的空隙」，防止别人往里插；临键锁 = 记录锁 + 间隙锁，锁「左开右闭」的区间，RR 下用来解决幻读。死锁排查用 SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK。

我的项目关联 对账、批量更新订单状态时最容易撞间隙锁。我们的做法是：更新条件尽量走主键或唯一索引，把范围锁降成单行锁，减少死锁概率。死锁真发生了 MySQL 会自动回滚一个事务，业务侧做好重试。

面试答题话术 「行锁里记录锁锁单行，间隙锁锁空隙防插入，临键锁是两者的结合、锁左开右闭区间，RR 下用来解决幻读。死锁排查看 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK。项目里批量更新我尽量走主键，缩小锁范围，死锁就让业务重试。」

11. 三大范式与反范式 ★★☆ ​

通俗理解1NF 列不可再分，2NF 消除部分依赖，3NF 消除传递依赖。反范式就是故意冗余字段（比如订单表冗余桩编号、用户名），用空间换时间、减少 join。

我的项目关联 我们是「范式打底 + 关键查询适度冗余」。比如订单表里会冗余一些场站名、桩编号，避免每次都 join 设备表。这是为了查询性能，值得的取舍。

面试答题话术 「三大范式解决冗余和依赖问题；反范式是故意冗余，用空间换减少 join。项目里我们是范式打底、关键查询适度冗余，比如订单表冗余场站名，避免 join 设备表。」

12. 三大日志：redo、undo、binlog ★★★ ​

通俗理解redo log 是 InnoDB 的物理日志，记「数据页改了什么」，顺序写、循环写，用于崩溃恢复（持久性）。undo log 记「改前的值」，用于回滚和 MVCC。binlog 是 Server 层的逻辑日志，记录所有变更，用于主从复制和数据恢复，是追加写。redo 和 binlog 靠两阶段提交保证一致，不然主从会不一致。binlog 格式主流是 row。

我的项目关联 我们做过 binlog 监听同步数据（比如把订单变更同步到搜索或缓存）。知道「redo 是引擎层物理、binlog 是 Server 层逻辑」这个区别，答两阶段提交的时候就顺。

面试答题话术 「redo 是 InnoDB 的物理日志、循环写、做崩溃恢复；undo 记改前的值、做回滚和 MVCC；binlog 是 Server 层的逻辑日志、追加写、做主从复制和数据恢复。redo 和 binlog 靠两阶段提交保证一致，不然主从数据会不一致。」

13. 主从复制原理 ★★★ ​

通俗理解 主库写 binlog → 从库 IO 线程拉 binlog 写本地 relay log → 从库 SQL 线程重放 relay log。作用是读写分离、备份、高可用。延迟原因是：从库重放慢（单线程）、有大事务、硬件差、网络慢。

我的项目关联 我们做了读写分离，查询走从库、写走主库。但有个必须注意的点：写完立刻要读的场景（比如下单后马上查订单），必须强制走主库，不然主从延迟会读到旧数据。这是通用坑，我们用「关键读走主库」来规避。

面试答题话术 「主库写 binlog，从库 IO 线程拉过来写 relay log，SQL 线程再重放。延迟主要是从库重放慢和大事务。项目里我们读写分离，但『写完立刻读』的场景强制走主库，不然会读到旧数据。」

14. 慢查询优化思路 ★★★ 【简历亮点，高频追问】 ​

通俗理解 四步走：先用慢查询日志 + EXPLAIN 定位；看 type 是不是 ALL、缺不缺索引；加合适的索引（最左前缀、覆盖索引、避免失效）；再优化 SQL（别 SELECT *、别在索引列上用函数、小表驱动大表）；还不行才上读写分离 / 缓存 / 分库分表。

我的项目关联 这个流程我走得比较多。说明一下现象：我们遇到过订单列表接口变慢，explain 一看是新增的查询条件没走索引、type 是 ALL，加了联合索引就好了。这是真实排查过的，不是纸上谈兵。经验是：先看执行计划，别盲目加缓存。

面试答题话术 「四步：慢日志和 explain 定位、看 type 和索引、加索引、优化 SQL。项目里订单列表变慢就是这么查的——explain 发现全表扫，加了联合索引解决。原则是先看执行计划再动手，别上来就加缓存或分表。」

15. 分库分表 ★★☆ ​

通俗理解垂直拆：按业务拆库（订单库、用户库）、按列拆表（冷热字段）。水平拆：按行分，id 哈希或范围分到多表多库。中间件用 ShardingSphere。带来的问题：分布式主键（雪花）、跨库 join、分布式事务、路由。

我的项目关联 目前我们订单量还没到必须先分表的程度，优先做的是索引优化 + 冷热分离 + 归档。这条属于了解即可：真到单表千万级、单库有瓶颈了才考虑，顺序是「索引 → 缓存 → 读写分离 → 分表」。

面试答题话术 「分库分表分垂直和水平，垂直按业务或字段拆，水平按行分。中间件一般用 ShardingSphere。但这是最后手段，顺序是索引优化、缓存、读写分离，都不行了才分。项目里我们现在靠索引加冷热归档，还没到分表。」

16. 大表如何优化 ★★★ ​

通俗理解 索引优化、覆盖索引避免回表；冷热数据分离、历史数据归档；读写分离 + 缓存热点；再往后是垂直/水平拆分；最后才考虑换列式存储/大数据引擎。

我的项目关联 充电订单和历史流水是典型的大表。我们的做法：近期订单留 MySQL（热），历史订单归档到冷库或者 ClickHouse（冷），查询走对应数据源。这样主表一直保持比较小。

面试答题话术 「大表优化从轻到重：先索引和覆盖索引，再冷热分离和归档，然后是读写分离加缓存，最后才分库分表。项目里充电订单就是这么做的——近期数据留 MySQL，历史归档到 ClickHouse，主表保持小。」

17. SQL 执行顺序 ★★☆ ​

通俗理解 FROM → JOIN/ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。记住它，才不会写错 SQL：WHERE 在分组前所以不能用聚合函数，聚合条件得用 HAVING；SELECT 的别名在 WHERE 里不能用，因为它比 SELECT 晚执行。

我的项目关联结论够用。实际写统计 SQL 时靠它判断条件该放 WHERE 还是 HAVING。

面试答题话术 「顺序是 FROM、JOIN、WHERE、GROUP BY、HAVING、SELECT、DISTINCT、ORDER BY、LIMIT。两个易错点：WHERE 不能用聚合函数要用 HAVING；SELECT 的别名在 WHERE 里用不了，因为它执行得晚。」

18. 索引下推（ICP）★★★ ​

通俗理解 MySQL 5.6 的优化：把「能在索引层判断的条件」下推到存储引擎层过滤，减少回表次数。例：联合索引 (name, age) 查 name like '张%' and age=20，没 ICP 是先把所有「张」开头的都回表、再在 Server 层过滤 age；有 ICP 就直接在索引层用 age 过滤，只有两条都满足的才回表。

我的项目关联 知道「ICP 减少回表」这个结论就够。它解释了为什么「联合索引里带上过滤字段」能加速——因为可以在索引层就过滤掉大部分数据。

面试答题话术 「ICP 是把能下推的过滤条件推到存储引擎层，在索引里就把不满足的过滤掉，减少回表。只对二级索引生效，条件是函数或运算就不下推。项目里体现就是：把常用过滤字段一起放进联合索引，能让 ICP 帮忙减少回表。」

19. 索引设计原则 ★★★ ​

通俗理解 选区分度高的列；为 WHERE、ORDER BY、GROUP BY、JOIN 的列建索引；联合索引按最左前缀、等值列在前；尽量做覆盖索引；索引别建太多（拖慢写入）；长字符串用前缀索引；主键用自增。区分度极低的列（性别、状态枚举）单独建索引没意义。

我的项目关联 我们建索引基本围绕「查询模式」来：订单按桩编号 + 状态 + 时间查，就建对应的联合索引。状态这种低区分度列不单独建，而是放在联合索引里起过滤作用。

面试答题话术 「原则就是：围绕 where、order by、join 建索引；联合索引等值列在前、区分度高的在前；尽量覆盖索引；控制数量因为拖慢写入。低区分度的列像状态、性别不单独建索引，放联合索引里当过滤列就行。项目里索引都是按实际查询模式设计的。」

20. 如何优化表结构 ★★☆ ​

通俗理解 字段类型够用就行（能用 int 不用 varchar）；尽量 NOT NULL 给默认值；大字段（TEXT/BLOB）拆到扩展表，别撑大主表；范式打底 + 适度反范式。

我的项目关联 我们建表规范里有两条：状态、类型这种用 tinyint 而不是 varchar；报文原文这种大字段单独放扩展表，主表不存，避免拖慢查询。

面试答题话术 「字段类型选够用的最小类型，尽量 NOT NULL，大字段拆到独立表。项目里状态类型用 tinyint，报文原文这种大字段单独一张表，主表保持轻。」

21. MySQL 如何避免死锁 ★★★ ​

通俗理解死锁是两个事务按不同顺序加锁、互相等对方。避免手段：按固定顺序访问表和行；尽量用主键/唯一索引定位，缩小锁范围；事务尽量小、尽快提交；一次申请完所需锁；加锁超时和死锁检测。发生死锁时 MySQL 会自动检测并回滚代价小的那个事务。

我的项目关联 我们批量更新订单状态时踩过（通用坑）：先按 A 顺序更新、另一个业务按 B 顺序更新，交叉就死锁。解决是按统一顺序处理、并且用主键定位精确到行。MySQL 自动回滚后业务侧重试一次即可。

面试答题话术 「避免死锁就几条：统一加锁顺序、用主键精确定位缩小锁范围、事务小且快提交。排查看 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK。死锁发生后 MySQL 会自动回滚一个事务，业务侧做好重试。项目里批量更新就是统一顺序加主键定位。」

22. 大量数据插入的性能优化 ★★★ ​

通俗理解批量插（一条 INSERT 带多个 VALUES）比一条条插快很多——省网络往返、省事务提交、省 SQL 解析。再进一步：autocommit=0 批量提交、LOAD DATA INFILE 导数据、临时关唯一性/外键检查、必要时先关索引导完再重建。

我的项目关联 对账、账单生成这种批量写我们用「分批 + 批量 insert」，比如每 500~1000 条一批提交，兼顾速度和事务大小。注意：不是越大越好，批次太大就变成大事务，会锁久、undo 膨胀、还可能拖慢主从。

面试答题话术 「批量插入快是因为省了网络往返、事务提交、SQL 解析。手段是批量 VALUES、批量提交、LOAD DATA INFILE，必要时导完再重建索引。但批次不能无限大，太大了变大事务，会锁久、拖主从。项目里我们是分批批量插入，每批几百到一千条。」

23. 大数据量批量写会导致什么问题 ★★☆ ​

通俗理解大事务（undo 膨胀、占锁久、主从延迟）；锁竞争（批量更新锁范围大，容易死锁或长时间阻塞）；binlog 膨胀；主从延迟；随机主键插入还会页分裂。解决就是分批提交、控制批次大小、用顺序主键、避开高峰。

我的项目关联 这就是为什么我们坚持分批。跑对账时如果一次性更新几十万行，锁和主从延迟都会出问题，分成小批次提交就稳很多。

面试答题话术 「批量写大了会有几个问题：大事务导致 undo 膨胀、占锁久、主从延迟，还有锁竞争和 binlog 膨胀。解决就是分批提交、控制批次大小、顺序主键、避开高峰期。项目里跑批都是分批的。」

24. IP 地址如何存数据库 ★★☆ ​

通俗理解IPv4 推荐用 INT UNSIGNED 存（4 字节），配 INET_ATON()/INET_NTOA() 转换：省空间（比 varchar 短）、比较大小快、IP 段范围查询能走索引。IPv6 是 128 位，用 VARBINARY(16) 配 INET6_ATON()。

我的项目关联 我们记录充电桩、网关请求的来源 IP、以及互联互通上报的 IP，就是用整数存 IPv4 的，方便做「某 IP 段」的统计和过滤。这条知道方案就行。

面试答题话术 「IPv4 用 INT UNSIGNED 存，配 INET_ATON 和 INET_NTOA 转换，好处是省空间、能比较大小、IP 段范围查询能走索引；IPv6 用 VARBINARY(16)。项目里记录来源 IP 就是这种存法。」

25. drop、truncate、delete 的区别 ★★★ ​

通俗理解delete 是 DML，逐行删、可带 WHERE、走 undo log 可回滚、会触发触发器，自增主键不会重置，最慢；truncate 是 DDL，清空整张表、不能带 WHERE、隐式提交不可回滚、不触发触发器、自增值重置，本质是重建表（或直接释放数据页），快；drop 也是 DDL，直接删掉表结构和数据，连表定义都没了，最快。一句话：delete 删数据、truncate 清空表、drop 删表。

我的项目关联 我们的历史数据归档流程是「先同步到 ClickHouse，再清理 MySQL 老数据」，清理用 truncate 比 delete 快一个量级。但要特别注意：truncate 是 DDL 会隐式提交，不能回滚，所以线上从不直接 truncate 业务主表，都是走归档脚本分批 delete 或按分区清理。通用坑：有人误以为 truncate 和 delete 一样能回滚，结果误清数据救不回来——面试别把这个说成自己踩过。

面试答题话术 「delete 是 DML，逐行删、可回滚、能带 WHERE、自增不重置、会触发触发器；truncate 是 DDL，清空整表、不能带 WHERE、隐式提交不能回滚、自增重置、不触发触发器；drop 是 DDL，连表结构一起删。速度上 drop 最快、truncate 次之、delete 最慢。生产上清理历史数据我会用 truncate 提效，但业务主表删除都走归档脚本分批 delete，因为 truncate 不能回滚。」

26. MySQL 关联查询（JOIN 类型及原理）★★★ ​

通俗理解INNER JOIN 只保留两表都匹配的行；LEFT JOIN 左表全保留、右表没匹配补 NULL；RIGHT JOIN 右表全保留；FULL JOIN MySQL 不支持，用 LEFT JOIN UNION RIGHT JOIN 模拟。执行原理是嵌套循环连接（Nested-Loop Join）：驱动表逐行去被驱动表找匹配，所以「小表驱动大表」、并且被驱动表的连接字段必须有索引，否则驱动表每行都要对被驱动表做一次全表扫，复杂度 O(N*M) 直接爆炸。MySQL 8.0 也引入了 Hash Join 用于等值连接。

我的项目关联 订单详情查询经常要 join 场站表、设备表拿冗余信息。我们两点经验：一是被驱动表的连接字段（桩编号、场站 id）必须建索引；二是能冗余就冗余，很多列表查询直接用订单表冗余字段，根本不 join，避免多表连接。JOIN 数量控制在两三个以内，再多就拆成多次查询或反范式。

面试答题话术 「JOIN 分 inner、left、right，full 在 MySQL 里要用 left union right 模拟。原理是嵌套循环连接，驱动表逐行去被驱动表查，所以有两个铁律：小表驱动大表、被驱动表连接字段必须有索引，否则就是驱动表每行对被驱动表全表扫，复杂度 O(N×M)。8.0 还有 Hash Join。项目里我尽量用冗余字段减少 join，真要 join 就保证连接字段有索引、控制在三张表以内。」

27. 分库分表之后，id 主键如何处理（雪花算法等分布式主键方案）★★★ ​

通俗理解 单表自增主键在分库分表后会重复，需要分布式主键。主流方案：①雪花算法 Snowflake，64 位长整型，1 位符号 + 41 位时间戳（约 69 年）+ 10 位机器 id + 12 位序列号，本地生成、趋势递增、全局唯一、性能高，缺点是依赖机器时钟，时钟回拨会导致重复；②数据库号段模式（如美团 Leaf），从一张表里批量取号段放内存，用完再取，严格有序但多一次 DB 依赖；③Redis INCR 自增；④UUID，最简单但无序，做主键会随机插入导致页分裂，且占空间，不推荐。雪花算法应对时钟回拨：等待时钟追上、复用上次序列、或校验兜底。

我的项目关联 我们主键统一用雪花算法——MyBatis-Plus 默认的 ASSIGN_ID 就是雪花，分布式部署时各微服务本地生成 id，不会冲突也无需中心化分配。订单号、对账批次号这类业务单号也按「时间戳 + 机器位 + 序列」的规则拼，保证唯一可追溯。分库分表我们还没大规模上，但主键方案已经按分布式标准准备好了。

面试答题话术 「分库分表后自增主键会重复，方案主要有四种：雪花算法、数据库号段、Redis 自增、UUID。雪花是 64 位，41 位时间戳加 10 位机器 id 加 12 位序列，本地生成、趋势递增、全局唯一，缺点是时钟回拨会重复，处理方式是等待或复用上次序列。UUID 无序会导致页分裂不推荐。我们项目主键就是 MyBatis-Plus 默认的雪花，业务单号也用时间戳加机器位加序列拼，天然支持分布式。」

28. 一条查询 SQL 的执行流程（连接器→分析器→优化器→执行器→存储引擎）★★★ ​

通俗理解 ①连接器：建立 TCP 连接、校验用户名密码和权限（长连接复用，连接数有限制）；②查询缓存（MySQL 8.0 已整体移除）：命中直接返回；③分析器：词法分析 + 语法分析，识别 SQL 关键字、表名列名，生成解析树，语法错误在这一层报；④优化器：决定用哪个索引、表的连接顺序，生成执行计划（可能选错索引）；⑤执行器：调用存储引擎接口逐行取数据、过滤、返回给客户端；⑥存储引擎 InnoDB 负责真正的数据读写（走 buffer pool、索引、回表）。

我的项目关联 这个流程能解释很多现象：连接数打满报 too many connections，是连接器/连接池这层；慢查询里 explain 显示走了不该走的索引，是优化器选错了，可以用 force index 或 analyze table 更新统计信息纠正。通用坑：优化器偶尔会基于过期统计信息选错索引导致全表扫，这个在资料里常见，别当成自己踩过。

面试答题话术 「一条查询先过连接器建连接鉴权，8.0 之前还有查询缓存、现在移除了；然后分析器做词法语法分析，语法错误这层就报；接着优化器生成执行计划，决定走哪个索引、join 顺序；执行器再调存储引擎接口取数。我实际用到的点：连接打满是连接器那层的问题，索引选错就是优化器的问题，可以用 force index 或 analyze table 纠正。」

29. DDL / DML / DCL / DQL 的区别 ★★☆ ​

通俗理解DDL（数据定义语言）操作表结构：CREATE、DROP、ALTER、TRUNCATE，会隐式提交、不可回滚；DML（数据操纵语言）操作数据：INSERT、UPDATE、DELETE，可回滚；DCL（数据控制语言）管权限：GRANT、REVOKE；DQL（数据查询语言）就是 SELECT。常考点：truncate 归 DDL 不归 DML，所以它不能回滚、不触发触发器，这就是它和 delete 本质区别的来源。

我的项目关联 分清楚的意义在于生产操作：DDL 要格外小心，大表 alter 会锁表或整表重建，我们有专门的上线窗口，必要时用在线变更工具；DML 批量写走分批提交。这条属于概念题，记清分类和「truncate 是 DDL」即可。

面试答题话术 「DDL 定义结构，create、drop、alter、truncate，隐式提交不可回滚；DML 操纵数据，insert、update、delete，可回滚；DCL 管权限，grant、revoke；DQL 就是 select。常考的坑是 truncate 属于 DDL 不是 DML，所以它清空表不能回滚、也不触发触发器，这跟 delete 的本质区别就来自这里。」

30. 存储过程和触发器的作用及优缺点 ★★☆ ​

通俗理解存储过程是把一段 SQL 逻辑预编译存到数据库里，可以传参调用，好处是减少网络往返、复用逻辑、权限可控；缺点是难调试、难维护、难版本化、跨库迁移麻烦，逻辑藏在数据库里不好排查。触发器是绑定在表上的、在 INSERT/UPDATE/DELETE 前后自动执行的逻辑，常用于审计、数据校验、同步，缺点是逻辑隐蔽、逐行触发影响写入性能、出问题难定位。互联网公司普遍把逻辑放应用层，少用或不用它们。

我的项目关联 我们基本不用存储过程和触发器，业务逻辑全部在 Java 微服务里用 MyBatis-Plus 实现，好处是可版本管理、可单测、可灰度。审计日志也是在应用层写，不用触发器。这条了解即可，面试重点是「为什么不用」——应用层更可控。

面试答题话术 「存储过程是预编译的 SQL 集合，减少网络往返、可复用，但难调试难维护难迁移；触发器是表上自动执行的逻辑，适合审计，但逻辑隐蔽、逐行触发影响性能。我们的做法是基本不用，逻辑都放 Java 服务层，好处是能版本管理、能写单测、出问题好排查。这是互联网项目的常见取舍。」

31. MySQL 如何行转列和列转行（CASE WHEN、GROUP_CONCAT、UNION）★★☆ ​

通俗理解行转列：把同一维度下的多行数据变成多列，用 CASE WHEN（或 IF）做条件判断，再套聚合函数 SUM/MAX，配合 GROUP BY 分组。例：统计每个场站「待支付/充电中/已完成」三类订单数，就是 CASE WHEN status 分组再 SUM。列转行：把多列拆成多行，用 UNION ALL 把每列 SELECT 出来拼在一起。GROUP_CONCAT 是另一个方向——把多行合成一行里的一个字符串列，可指定分隔符，但默认长度有限制（group_concat_max_len）。

我的项目关联 报表和统计里用得多：场站维度按状态汇总、按天汇总订单量，就是 CASE WHEN + GROUP BY 行转列。GROUP_CONCAT 偶尔用来把多个桩编号拼成一个字段展示。列转行我们用得少，UNION ALL 拆列即可。这条记住三个工具各干什么就行。

面试答题话术 「行转列用 CASE WHEN 加聚合函数再加 GROUP BY，比如统计每个场站各状态订单数；列转行用 UNION ALL 把多列分别 SELECT 出来拼；GROUP_CONCAT 是把多行拼成一行的一个字符串列，注意有默认长度限制。项目里报表统计各状态汇总就是 CASE WHEN 行转列。」

32. UNION 和 UNION ALL 的区别 ★★★ ​

通俗理解UNION 合并两个结果集并去重：内部会对合并结果做排序去重，有额外开销，慢；UNION ALL 直接拼接不去重，快。要求两个 SELECT 的列数、类型、顺序一致。规则：能确定结果无重复、或本来就允许重复时，一律用 UNION ALL，别用 UNION 白花去重排序的代价。

我的项目关联 我们把「热数据（MySQL 主表）+ 冷数据（归档）union all」合成完整订单列表时就用 UNION ALL，因为两边天然不重复，用 UNION 反而多一次去重排序拖慢接口。通用坑：无脑用 UNION 导致不必要的去重排序、SQL 变慢，这是资料里的经典坑，我们没实际踩到。

面试答题话术 「UNION 会去重，内部要做排序去重所以慢；UNION ALL 直接拼接不去重，快。只要结果不重复或者允许重复，就优先用 UNION ALL。两个结果集要列数和类型一致。项目里主表加归档表合并查询就用 UNION ALL，两边不重复，用 UNION 反而白费一次去重排序。」

33. HAVING 和 WHERE 的区别 ★★★ ​

通俗理解WHERE 在分组（GROUP BY）之前过滤行，不能使用聚合函数，也不能用 SELECT 的别名；HAVING 在分组之后过滤分组，可以使用聚合函数。执行顺序是 WHERE → GROUP BY → HAVING → SELECT。性能原则：能放 WHERE 的就放 WHERE，先把数据量过滤小，再分组，HAVING 只处理「必须基于聚合结果」的条件（如 COUNT(*) > 10）。

我的项目关联 写统计 SQL 时靠执行顺序来判断：比如「查订单数超过 10 的场站」，场站状态这种行级条件放 WHERE，COUNT(*) > 10 这种聚合条件只能放 HAVING。判断依据就是 WHERE 在分组前、HAVING 在分组后。

面试答题话术 「WHERE 在分组前过滤行，不能用聚合函数；HAVING 在分组后过滤分组，能用聚合函数。执行顺序 WHERE、GROUP BY、HAVING、SELECT。原则是能放 WHERE 的先放 WHERE 减少数据量，HAVING 只放基于聚合结果的过滤。项目里写统计 SQL 就是按这个判断条件放哪。」

34. IN 和 EXISTS 子句的区别及选择 ★★★ ​

通俗理解IN 是先执行子查询、把结果集拿到手，再和外层逐行做集合匹配，适合子查询结果集小、外层表大的场景；EXISTS 是外层每行去子查询「探测是否存在」，找到一个匹配就返回 true、可提前终止，不加载整个结果集，适合外层表小、子查询大、且子查询能走索引的场景。重要的坑：NOT IN 遇到子查询结果里有 NULL 时，整个结果会变成空（NULL 参与比较结果为 unknown，全部被过滤），而 NOT EXISTS 没有这个问题。所以否定判断优先用 NOT EXISTS。

我的项目关联 我们关联筛选场景其实更多用 JOIN + 索引，IN/EXISTS 用于子查询筛选。真正要记的是 NOT IN 的 NULL 坑——子查询结果含 NULL 时 NOT IN 查不到任何数据，这是「明明有数据却查不出来」的通用坑，我们没实际踩到，但排查思路要先想到它。选择原则记「子查询小用 IN、外层小用 EXISTS」即可。

面试答题话术 「IN 是拿子查询结果集做匹配，适合子查询小、外层大；EXISTS 是逐行探测是否存在、找到就返回，适合外层小、子查询大且能走索引。最大的坑是 NOT IN 遇到子查询里有 NULL，比较结果是 unknown，整个结果就空了，而 NOT EXISTS 没这个问题，所以否定判断我优先用 NOT EXISTS。」

35. MySQL 如何处理 NULL 值，对索引/查询的影响 ★★★ ​

通俗理解NULL 表示「未知/缺失」，它不等于任何值、包括它自己，所以 NULL = NULL 结果是 NULL 不是 true，判断必须用 IS NULL / IS NOT NULL。聚合影响：COUNT(列) 会忽略 NULL 行，COUNT(*) 才数全部行；SUM/AVG 也会忽略 NULL。索引方面：唯一索引允许插入多个 NULL，因为 NULL 之间被认为不相等；普通索引可以存 NULL，IS NULL 一般能走索引。典型坑：NOT IN 子查询含 NULL 导致结果为空；字段可空时 = 判断查不到 NULL 行。所以建表建议尽量 NOT NULL 给默认值，避免一堆判断。

我的项目关联 我们的建表规范要求「尽量 NOT NULL + 默认值」，可空字段明确标注并小心使用，因为 NULL 会让 = 判断失效、让 NOT IN 结果异常，还会让 COUNT 统计口径混乱。订单表里少数可空字段（比如结束时间、退款时间），查询时我都用 IS NULL 判断而不是 = NULL。通用坑：NOT IN 遇 NULL 查不出数据，属于资料经典坑。

面试答题话术 「NULL 是未知值，不等于任何值包括它自己，判断只能用 IS NULL。聚合上 COUNT 列会忽略 NULL、COUNT(*) 才数全部；唯一索引允许多个 NULL，因为 NULL 互不相等。最大的坑是 NOT IN 子查询含 NULL 会整个结果为空，以及可空字段用 = 查不到 NULL 行。所以我们建表尽量 NOT NULL 给默认值，可空字段查询用 IS NULL。」

36. 如何在 MySQL 中处理和避免全表扫描 ★★★ ​

通俗理解全表扫描就是 explain 里 type=ALL，逐行读整张表的所有数据页，数据一大就慢。处理和避免手段：①建对索引并确保走索引——满足最左前缀、避免索引列用函数/隐式转换等失效场景；②避免 SELECT *，只取需要的列，尽量用覆盖索引；③用 WHERE 有效缩小范围，避免无过滤条件或低区分度单列条件；④JOIN 用小表驱动大表、被驱动表连接字段建索引；⑤深分页优化：大 OFFSET 会扫大量行，用「先查主键再回表」的延迟关联或游标分页；⑥冷热分离、历史归档，让主表一直保持小，从根上减小全表扫的代价。最终用 EXPLAIN 确认 type 不是 ALL。

我的项目关联 这就是我们优化慢查询的主线：订单列表接口排查时 explain 看到 type=ALL，加联合索引后从 ALL 降到 range 就好了。深分页场景我们用「先按主键查一页 id 再回表」避免大 OFFSET 扫几万行。历史订单归档到 ClickHouse 让主表保持小，也是从源头避免大表全表扫。

面试答题话术 「全表扫就是 explain 的 type=ALL。避免手段依次是：建对索引并保证走索引、避免 SELECT * 用覆盖索引、用 WHERE 缩小范围、join 小表驱动大表且连接字段建索引、深分页用延迟关联、最后冷热分离归档让主表保持小。项目里订单列表变慢就是 explain 发现全表扫，加联合索引解决；深分页用先查主键再回表，历史数据归档到 ClickHouse 保持主表小。」
