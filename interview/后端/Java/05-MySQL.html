MySQL ​

常问等级：★★★ 高频必考 / ★★☆ 中频常见 / ★☆☆ 低频了解 深度标准：每个考点讲清「是什么 → 为什么 → 源码关键点 → 追问应对 → 易错点」。

InnoDB 与 MyISAM 区别 ★★★ ​

维度InnoDBMyISAM
事务支持（ACID）不支持
锁行级锁（+表锁/间隙锁）表级锁
外键支持不支持
崩溃恢复支持（redo/undo）不支持（易损坏）
索引聚簇索引（数据即索引）非聚簇（索引与数据分离）
全文索引MySQL5.6+ 支持支持
适用默认、OLTP 事务场景只读/日志等无事务场景
  • MySQL5.5+ 默认引擎是 InnoDB，绝大多数场景选 InnoDB。

追问应对 ​

  • 「为什么 MyISAM 查询快？」→ 无事务开销、表级锁简单、索引数据分离，但并发写和可靠性差。

索引的数据结构：为什么是 B+ 树 ★★★ ​

为什么不用其他结构 ​

  • 哈希：只支持等值查询、无法范围查询、无法排序，冲突退化。
  • 二叉搜索树/AVL：树过高，磁盘 IO 次数多（树高决定 IO 次数）。
  • 红黑树：仍是二叉，高度高。
  • B 树：每个节点既存索引又存数据，单个节点能存的关键字少，树更高、IO 多。
  • B+ 树：数据只存叶子节点、非叶子只存索引（能存更多索引，树更矮，IO 少）；叶子节点用链表连接，天然支持范围查询和排序。

B+ 树特点 ​

  • 所有数据在叶子层，非叶节点仅索引，树高通常 2~4 层，3 层即可存千万级数据。
  • 叶子节点之间用双向链表相连，支持范围扫描。
  • 磁盘按页（默认 16KB）读取，B+ 树一个节点一页，减少 IO。

追问应对 ​

  • 「B+ 树和 B 树区别？」→ B+ 树数据只在叶子、非叶只存索引、叶子有链表，范围查询更优、树更矮。
  • 「为什么不用哈希做主键索引？」→ 哈希不支持范围、排序、最左前缀。

聚簇索引与非聚簇索引、回表 ★★★ ​

聚簇索引（主键索引） ​

  • 数据和索引存在一起，叶子节点存的是整行数据。
  • 每张表只能有一个聚簇索引（因为数据只能存一份），通常是主键。

非聚簇索引（二级索引/辅助索引） ​

  • 叶子节点存的是「索引列 + 主键值」。
  • 通过二级索引查到主键，再回「聚簇索引」查整行数据，这个过程叫「回表」。

覆盖索引 ​

  • 查询的列都在二级索引里，不用回表，性能最好（SELECT 索引列 FROM ...）。
  • 经典优化：把要查的列建成联合索引，实现覆盖索引避免回表。

追问应对 ​

  • 「为什么主键建议自增？」→ 自增主键顺序插入，页分裂少；UUID 随机插入会导致频繁页分裂、索引碎片。
  • 「回表一定慢吗？」→ 回表多一次 IO；用覆盖索引可避免。

最左前缀原则、联合索引 ★★★ ​

原则 ​

  • 联合索引 (a, b, c) 遵循最左前缀：只有从最左列开始连续匹配才能命中索引。
  • 可命中：a、a,b、a,b,c、a,c（a 能命中，但 c 无法用索引，因为中间 b 断了）。
  • 不可命中：b、c、b,c（未从 a 开始）。

为什么 ​

  • 联合索引按 (a,b,c) 的字典序排列，跳过 a 直接用 b 无法利用有序性。

设计原则 ​

  • 区分度高的列放最左、经常用于 where/order by/group by 的列优先。

追问应对 ​

  • 「范围查询会中断索引吗？」→ 会，a = 1 AND b > 2 只能用到 a 和 b，b 之后（c）失效；所以范围列尽量放联合索引靠后位置。

索引失效场景 ★★★ ​

  • 对索引列做函数/运算（WHERE YEAR(create_time)=2024、WHERE id+1=5）。
  • 隐式类型转换（WHERE phone = 138...，phone 是字符串却没加引号）。
  • 最左前缀不满足（跳过最左列）。
  • 范围查询之后的列失效。
  • 用 !=、<>、NOT IN、NOT EXISTS（部分情况）。
  • LIKE '%xx' 前导模糊（LIKE 'xx%' 可走索引，'%xx' 不能）。
  • OR 连接的非索引列。
  • 优化器认为全表扫描更快（数据量小时可能不走索引）。

追问应对 ​

  • 「怎么判断走了索引？」→ EXPLAIN 看 type（const/ref/range 好，ALL 全表扫）、key、rows。

EXPLAIN 关键字段 ★★★ ​

  • type（访问类型，从好到差）：system > const > eq_ref > ref > range > index > ALL。
  • key：实际使用的索引；possible_keys：可能用到的索引。
  • rows：预估扫描行数。
  • Extra：
    • Using index：覆盖索引（好，不用回表）。
    • Using where：存储引擎层过滤后还需回表过滤。
    • Using filesort：额外排序（可优化，加索引避免）。
    • Using temporary：用了临时表（group by/distinct 未用索引，需优化）。

追问应对 ​

  • 「type 为 ALL 怎么办？」→ 检查是否缺索引/索引失效，加合适索引。

事务 ACID 及实现原理 ★★★ ​

  • 原子性（Atomicity）：要么全成功要么全失败 → undo log 回滚实现。
  • 一致性（Consistency）：事务前后数据满足约束 → 由其他三个特性共同保证。
  • 隔离性（Isolation）：并发事务互不干扰 → 锁 + MVCC。
  • 持久性（Durability）：提交后不丢失 → redo log 落盘。

追问应对 ​

  • 「redo 和 undo 区别？」→ redo 记录「改了什么」用于崩溃恢复（持久性）；undo 记录「改之前的值」用于回滚和 MVCC（原子性/隔离性）。

事务隔离级别与并发问题 ★★★ ​

三种并发问题 ​

  • 脏读：读到别的事务未提交的数据。
  • 不可重复读：同一事务两次读，中间别的事务提交了 update，两次结果不一致。
  • 幻读：同一事务两次读，中间别的事务 insert/delete，导致行数变化。

四种隔离级别 ​

  • 读未提交（Read Uncommitted）：三种问题都可能。
  • 读已提交（Read Committed，RC）：解决脏读。
  • 可重复读（Repeatable Read，RR，MySQL 默认）：解决脏读、不可重复读，MVCC 下基本解决幻读。
  • 串行化（Serializable）：全部解决，但并发差。

追问应对 ​

  • 「MySQL 默认 RR 为什么？」→ RR 通过 MVCC + 间隙锁（Next-Key Lock）基本解决幻读，且并发比串行化好。
  • 「Oracle 默认是什么？」→ RC，所以面试常考 MySQL 与 Oracle 默认隔离级别差异。

MVCC 多版本并发控制 ★★★ ​

原理 ​

  • 通过「隐藏列 + undo log + ReadView」实现无锁读写并发。
  • 每行有隐藏列：DB_TRX_ID（最近修改事务 id）、DB_ROLL_PTR（回滚指针指向 undo log 旧版本）、DB_ROW_ID（无主键时生成）。
  • 读操作根据 ReadView（快照）判断哪些版本可见，读的是历史版本，不与写互斥。

ReadView 可见性规则 ​

  • 记录版本事务 id < 当前活跃最小事务 id → 可见；> 当前事务 id → 不可见（沿 undo 链往前找）。

RC 与 RR 的 ReadView 区别 ​

  • RC：每次 SELECT 生成新 ReadView（能看到别的事务已提交的修改）。
  • RR：事务内第一次 SELECT 生成 ReadView，之后复用（保证可重复读）。

追问应对 ​

  • 「MVCC 解决了什么？」→ 读写不阻塞，解决脏读/不可重复读/幻读（RR 下）。

MySQL 锁：行锁、表锁、间隙锁、临键锁 ★★★ ​

  • 全局锁/表锁/行锁，行锁是 InnoDB 的。
  • 行锁：记录锁（Record Lock）锁单行；间隙锁（Gap Lock）锁区间防插入；临键锁（Next-Key Lock）= 记录锁 + 间隙锁，锁定「左开右闭」区间。
  • 行锁在 RR 隔离级别下用来解决幻读。

死锁与排查 ​

  • 死锁产生：两个事务互相等待对方的锁。
  • 排查：SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK；SELECT * FROM information_schema.innodb_trx 看当前事务。

追问应对 ​

  • 「为什么 RR 要用间隙锁？」→ 防止其他事务在范围内插入，解决幻读；代价是降低并发。

三大范式与反范式 ★★☆ ​

  • 1NF：列不可再分（原子性）。
  • 2NF：非主键列完全依赖主键（消除部分依赖，针对联合主键）。
  • 3NF：非主键列不传递依赖主键（消除传递依赖）。
  • 反范式：为性能冗余字段（如订单表冗余用户名），用空间换时间，减少 join。

追问应对 ​

  • 「什么时候反范式？」→ 高频查询需要冗余、join 成本高时；权衡一致性与性能。

三大日志：redo log、undo log、binlog ★★★ ​

redo log（重做日志，InnoDB） ​

  • 记录「数据页做了什么修改」，用于崩溃恢复（持久性）。
  • 特点：顺序写、循环写（固定大小，写满触发刷盘）、WAL（先写日志再写磁盘）。
  • innodb_flush_log_at_trx_commit=1 每次提交刷盘（最安全）。

undo log（回滚日志） ​

  • 记录「修改前的值」，用于回滚和 MVCC。

binlog（二进制日志，Server 层） ​

  • 记录所有逻辑变更（SQL），用于主从复制、数据恢复。
  • 三种格式：statement（SQL 语句）、row（行变更，主流）、mixed。

redo 和 binlog 区别 ​

  • redo 是 InnoDB 引擎层、物理日志、循环写；binlog 是 Server 层、逻辑日志、追加写。
  • 两阶段提交保证 redo 与 binlog 一致。

追问应对 ​

  • 「为什么需要两阶段提交？」→ 保证 redo 与 binlog 一致，避免主从复制数据不一致。

主从复制原理 ★★★ ​

  • 流程：主库写 binlog → 从库 IO 线程读 binlog 写 relay log → 从库 SQL 线程执行 relay log。
  • 作用：读写分离、数据备份、高可用。
  • 延迟原因：从库 SQL 单线程重放慢、大事务、主从配置差、网络。

追问应对 ​

  • 「主从延迟怎么解决？」→ 并行复制（多线程 SQL）、优化大事务、升级硬件、读写分离时对实时性要求高的读走主库。

慢查询优化思路 ★★★ ​

  1. 定位：慢查询日志（slow_query_log）、EXPLAIN 分析。
  2. 看 type 是否为 ALL（全表扫）、是否缺索引。
  3. 加合适索引（遵循最左前缀、覆盖索引、避免失效）。
  4. 优化 SQL（避免 SELECT *、避免函数作用于索引列、小表驱动大表）。
  5. 分库分表/读写分离/缓存（Redis）。

追问应对 ​

  • 「一条 SQL 突然变慢怎么排查？」→ 看是否缺索引/索引失效/数据量增长/锁等待/大事务；用 EXPLAIN 和慢日志定位。

分库分表 ★★☆ ​

  • 垂直拆分：按业务拆库（订单库、用户库）；按列拆表（热冷字段）。
  • 水平拆分：按行拆（按 id 哈希/范围分片到多表多库）。
  • 中间件：ShardingSphere、MyCat。
  • 问题：分布式主键（雪花算法）、跨库 join、分布式事务、路由。

追问应对 ​

  • 「什么时候需要分库分表？」→ 单表千万级、单库连接数/容量瓶颈时；优先索引优化、缓存、读写分离，最后才分库分表。

大表如何优化 ★★★ ​

  • 索引优化、覆盖索引、避免回表。
  • 冷热数据分离、归档历史数据。
  • 读写分离、缓存热点数据。
  • 垂直拆分 + 水平分库分表。
  • 换列式存储/大数据引擎（可选）。

MySQL 优化器、执行顺序 ★★☆ ​

  • SQL 执行顺序：FROM → JOIN/ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。
  • 理解执行顺序有助于写正确 SQL（如 WHERE 在 GROUP BY 前，聚合条件用 HAVING）。

易错点 ​

  • WHERE 不能用聚合函数，HAVING 可以；别名在 SELECT 之后才生效，WHERE 里不能用 SELECT 的别名。
