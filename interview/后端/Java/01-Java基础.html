Java 基础 ​

常问等级：★★★ 高频必考 / ★★☆ 中频常见 / ★☆☆ 低频了解 深度标准：每个考点讲清「是什么 → 为什么 → 源码关键点 → 追问应对 → 易错点」，做到能扛住连续追问。

基本数据类型和包装类区别、Integer 缓存、自动装箱拆箱 ★★★ ​

是什么 ​

  • 8 种基本类型：byte(1) / short(2) / int(4) / long(8) / float(4) / double(8) / char(2) / boolean，对应包装类 Byte、Short、Integer、Long、Float、Double、Character、Boolean。
  • 区别：
    维度基本类型包装类
    存储值，存栈对象，存堆（引用在栈）
    默认值0 / falsenull
    泛型不能用可以用
    性能高低（有对象头、装箱开销）

为什么会有自动装箱拆箱 ​

  • Java 集合、泛型只支持对象，基本类型要放进去必须先包装，为了书写方便编译器自动插入装箱/拆箱代码。

源码关键点 ​

  • 装箱：编译器把 Integer a = 100 编译成 Integer.valueOf(100)。
  • 拆箱：把 int b = a 编译成 a.intValue()。
  • Integer.valueOf(int) 内部：

  • IntegerCache 默认缓存 -128 ~ 127，可通过 -XX:AutoBoxCacheMax=<size> 调大上限。

追问应对 ​

  • 「Integer a=100, b=100; a==b 为什么是 true，128 是 false？」→ 100 在缓存内 valueOf 返回同一个缓存对象，所以 == 为 true；128 超出缓存，各自 new Integer 地址不同。
  • 「Integer 之间比较应该用什么？」→ 用 equals 或先拆箱成 int 再 ==，别用 == 直接比包装类。

易错点 ​

  • 循环里 Integer sum = 0; for(...) sum += i; 每次 += 都会拆箱+装箱，产生大量临时对象；大循环用 int。
  • Long 也有类似缓存（-128~127），Long l1 = 100L 走缓存。
  • 三元运算符 condition ? 1 : new Integer(2) 两个分支类型不一致时会触发自动拆箱/装箱，可能 NPE。

面向对象三大特性、抽象类和接口区别 ★★★ ​

是什么 ​

  • 封装：把数据和操作数据的方法绑定，隐藏内部实现（private + 对外暴露 public getter/setter），只暴露必要接口。
  • 继承：子类复用父类字段与方法，Java 单继承（一个类只能有一个直接父类）、多层继承。
  • 多态：同一操作作用于不同对象产生不同行为。编译期多态 = 重载；运行期多态 = 重写 + 父类引用指向子类对象，方法调用在运行时动态分派。

为什么多态靠动态分派 ​

  • 方法调用分静态分派（重载，编译期根据参数静态类型确定）和动态分派（重写，运行期根据对象实际类型确定）。JVM 用 invokevirtual 指令，先在常量池找到方法符号引用，运行时到实际对象类型的类的方法表中找实现。

抽象类 vs 接口（表格） ​

维度抽象类接口
关键字abstract classinterface
继承实现单继承多实现，接口间可多继承
成员可有构造器、普通字段、具体方法、静态方法常量 + 抽象方法；Java8 default/static，Java9 private
设计语义is-a，抽取公共代码can-do，定义能力契约
构造器有无

追问应对 ​

  • 「接口为什么要有 default 方法？」→ 接口演进：给老接口加方法时，实现类不用全部被迫修改（如 List.stream()），同时保留实现灵活性。
  • 「抽象类和接口怎么选？」→ 需要共享字段/构造器/非静态代码逻辑用抽象类；只定义能力、需要多实现用接口；优先接口（组合优于继承）。

易错点 ​

  • 接口的字段默认 public static final（常量），方法默认 public abstract；Java8 default 方法必须写方法体。

String、StringBuilder、StringBuffer；String 不可变；常量池；intern() ★★★ ​

String 为什么不可变 ​

  • 底层用 private final byte[] value（JDK9 起 char[] 改 byte[]，节省空间）+ 类本身 final。
  • final 修饰 value 只保证引用不换对象，不保证数组内容不被改；真正不可变靠「类不提供修改 value 的 public 方法 + 所有修改操作都 new 新对象」。
  • 好处：① 可安全共享（常量池）；② 可作 HashMap/HashSet 的 key（hash 不变）；③ 线程安全；④ 类加载器、安全机制依赖不可变 String。

三兄弟区别 ​

  • String 不可变；StringBuilder 可变、非线程安全（快）；StringBuffer 可变、方法加 synchronized（慢、线程安全）。

常量池与 intern() ​

  • 字符串常量池：JDK7 起从永久代移到堆中，存字符串字面量与 intern 结果。
  • intern()：若池中已有 equals 相等的字符串，返回池内引用；否则把该字符串引用放入池并返回。
  • 经典面试：String s = new String("a") 创建了几个对象？—— 字面量 "a" 一个（放常量池）+ new 的一个 = 2 个。

源码关键点 ​

  • "a" + "b" 编译期常量折叠为 "ab"（字面量拼接直接优化）；含变量的 "a" + b 编译成 new StringBuilder().append("a").append(b).toString()。
  • JDK9 起 + 拼接编译为 StringConcatFactory 的 invokedynamic，性能更好。

追问应对 ​

  • 「为什么不用 String 做频繁拼接？」→ 每次 + 都 new 新对象，产生大量中间对象 + 常量池压力，用 StringBuilder。
  • 「intern() 有性能问题吗？」→ JDK7 后常量池在堆，intern 可能让堆里对象无法回收，滥用会 OOM；JDK8 后有所改善，但仍不建议频繁 intern。

易错点 ​

  • new String("abc") == "abc" 为 false（一个堆对象、一个常量池）。
  • StringBuilder 默认容量 16，扩容为「旧容量*2 + 2」。

ArrayList / LinkedList 底层、扩容机制 ★★★ ​

ArrayList ​

  • 底层 Object[] elementData，随机访问 O(1)，增删（中间）O(n)（要移动元素）。
  • 扩容（源码 grow）：默认初始容量 10（首次 add 时才真正分配），扩容为 oldCapacity + (oldCapacity >> 1) 即 1.5 倍，Arrays.copyOf 复制到新数组。
  • 扩容本质是「新数组 + 拷贝」，代价高，若预知大小用 new ArrayList<>(n) 避免多次扩容。

LinkedList ​

  • 底层双向链表，每个节点存 prev/next/item；头尾增删 O(1)，按索引访问 O(n)（要从头/尾遍历）。
  • 额外维护前后指针，内存占用比 ArrayList 大。

为什么说 LinkedList 实际用得少 ​

  • 表面「中段插入快」，但插入前要先遍历定位（O(n)），整体并不比 ArrayList 快多少；且链表缓存不友好（内存不连续，无法利用 CPU 缓存）。多数场景 ArrayList 更优。

追问应对 ​

  • 「ArrayList 是线程安全的吗？」→ 不是；并发用 CopyOnWriteArrayList（读多写少）或 Collections.synchronizedList。
  • 「扩容为什么是 1.5 倍不是 2 倍？」→ 经验值，平衡空间浪费与扩容频率；1.5 倍能复用部分旧数组内存（偏移），2 倍不能。

易错点 ​

  • ArrayList 的 size() 是元素个数，不是数组容量；elementData.length 才是容量。
  • 用迭代器遍历时 remove 要用 iterator.remove()，直接 list.remove() 会 ConcurrentModificationException（见 fail-fast）。

HashMap 底层原理（1.7 vs 1.8、红黑树、扩容）★★★ ​

数据结构 ​

  • JDK1.7：数组 + 链表（Entry）。
  • JDK1.8：数组 + 链表 + 红黑树（Node/TreeNode），链表过长时树化，查询从 O(n) 降到 O(logn)。

为什么容量必须是 2 的幂 ​

  • 定位桶用 (n - 1) & hash，等价 hash % n，位运算更快。
  • 扩容迁移时：新位置只需看 hash & oldCap 是否为 0，为 0 留在原位，为 1 移到 原位 + oldCap，无需重新计算 hash，这是 2 的幂的最大收益。

扰动函数为什么是 (h = key.hashCode()) ^ (h >>> 16) ​

  • 若直接用 hashCode 低几位做 (n-1)&hash，高位不参与，分布不均。
  • 右移 16 位让高 16 位与低 16 位异或，把高位特征混入低位，降低碰撞。

为什么链表阈值 8、退化 6 ​

  • 桶中元素个数服从泊松分布，负载因子 0.75 时链表长度达 8 的概率约 6e-8，极小，用 8 树化是成本收益权衡（红黑树节点更大、更复杂）。
  • 退化阈值 6 不是 7，留缓冲避免「反复树化/退化」抖动。

put 流程（putVal 源码步骤） ​

  1. 计算 hash = (h = key.hashCode()) ^ (h >>> 16)。
  2. 数组为空先 resize()。
  3. 定位桶 (n-1) & hash：
    • 桶空：直接放入。
    • 桶是红黑树：走树插入。
    • 桶是链表：遍历，key 相同覆盖 value；否则尾插；遍历中链表长度 ≥ 8 且数组 ≥ 64 时树化。
  4. 插入后 size++，超过阈值 capacity * loadFactor 触发 resize()。

扩容 resize 过程 ​

  • 容量翻倍（2 倍），新建数组，遍历旧数组每个桶，按 hash & oldCap 拆成低位链、高位链；低位链留在原位，高位链移到 原位+oldCap；链表可能重新拆分，树可能退化为链表。

1.7 头插法死循环 ​

  • 1.7 扩容用头插法（新元素插头部），链表逆序；多线程同时扩容时，两个线程迁移互相指向形成环，get 时死循环。
  • 1.8 改尾插法解决成环，但并发下仍有「丢数据」「数据覆盖」问题，所以并发场景必须用 ConcurrentHashMap。

追问应对 ​

  • 「负载因子为什么 0.75？」→ 时间空间折中，太高碰撞多（链表变长查询慢），太低空间浪费。
  • 「为什么不用 hash 取模？」→ 位运算更快 + 2 的幂扩容迁移优化。
  • 「HashMap 的 key 为什么建议用 String/不可变对象？」→ hashCode 稳定，改 key 内容会导致哈希定位错乱。
  • 「红黑树 vs AVL 树为什么用红黑树？」→ 红黑树牺牲部分平衡换更少旋转，插入删除更高效，查询 O(logn) 也够用。

易错点 ​

  • 重写 equals 必须重写 hashCode（见下文契约），否则 HashMap 会 key 定位错误。
  • HashMap 允许一个 null key、多个 null value；Hashtable/ConcurrentHashMap 不允许 null。

ConcurrentHashMap 1.7 和 1.8 实现区别 ★★★ ​

1.7：Segment 分段锁 ​

  • 结构：Segment（继承 ReentrantLock）+ 每段一个 HashEntry 数组。
  • 锁粒度：Segment 级别，不同 Segment 间可并发；并发度 = Segment 数量（默认 16，可调）。
  • put 需先定位 Segment 再加锁。

1.8：synchronized + CAS 桶级锁 ​

  • 结构：和 HashMap 一样「数组 + 链表 + 红黑树」，不再有 Segment。
  • 写：对「单个桶的头节点」加 synchronized，粒度更细；空桶用 CAS 无锁写入（如 casTabAt 初始化、tabAt 读）。
  • 读：完全无锁，因为 Node.val 和 Node.next 用 volatile 修饰，保证可见性。
  • 扩容：多线程协助迁移（ForwardingNode 标记已迁移的桶），并发扩容。

为什么 1.8 更快 ​

  • 锁粒度从「段」细化到「桶」；读无锁；红黑树降低查询复杂度；synchronized 经 JDK1.6 锁升级优化后性能已很高。

追问应对 ​

  • 「1.8 用 synchronized 而不是 ReentrantLock，为什么？」→ 锁升级优化后 synchronized 性能接近，且写法更简洁、JVM 层面可自动优化。
  • 「ConcurrentHashMap 为什么不允许 null key/value？」→ 并发下 get 返回 null 无法区分「不存在」还是「存的是 null」，会歧义，故设计上禁止。

易错点 ​

  • size() 在 1.8 用 baseCount + CounterCell 累加，非精确实时（弱一致）。
  • 单机替代 Hashtable 首选 ConcurrentHashMap。

Hashtable 与 HashMap 对比 ★★☆ ​

  • Hashtable 线程安全（方法级 synchronized）、不允许 null 键值；HashMap 非线程安全、允许一个 null key 多个 null value。
  • Hashtable 初始容量 11、扩容 2n+1（质数减少碰撞）；HashMap 初始 16、扩容 2 倍。
  • Hashtable 已被 ConcurrentHashMap 取代（后者分段/桶级锁，性能远高于方法级锁）。
  • 追问：「HashMap 如何做到线程安全？」→ 用 ConcurrentHashMap 或 Collections.synchronizedMap（后者仍是方法级锁，性能差）。

异常体系、受检/非受检；try-finally / try-with-resources ★★★ ​

体系 ​

  • 根 Throwable → Error（JVM 级错误，如 OOM、StackOverflowError，不可恢复，不捕获）和 Exception。
  • Exception 分：
    • 受检异常（checked）：编译期强制处理（try-catch 或 throws），如 IOException、SQLException。
    • 非受检异常（unchecked）：RuntimeException 及其子类，如 NPE、IndexOutOfBoundsException、IllegalArgumentException，编译期不强制。

为什么分受检/非受检 ​

  • 受检异常是「调用者能预判并恢复」的（文件不存在、网络失败），强制处理避免遗漏；非受检通常是「编程错误」（空指针、越界），应该靠修复代码而非捕获。

try-finally 与 try-with-resources ​

  • finally 总执行（除非 System.exit 或线程被 kill）；finally 中 return 会覆盖 try 的 return 值。
  • try-with-resources：资源实现 AutoCloseable，在 try 括号内声明，自动 close（编译后仍生成 finally close 代码），避免重复关闭，且 close 异常被压制（suppressed）。
  • JDK9 起允许 try 括号内用已有变量：try (resource) {...}。

追问应对 ​

  • 「finally 一定能执行吗？」→ 不是，System.exit(0)、JVM 崩溃、守护线程中断等不会执行。
  • 「catch 和 finally 都有 return，返回哪个？」→ finally 的 return 覆盖 catch 的 return（但不推荐，可读性差）。

易错点 ​

  • return 在 finally 会吞掉 try 抛出的异常，导致异常丢失。
  • 自定义业务异常建议继承 RuntimeException（避免全链路 throws 污染）。

泛型原理、泛型擦除；通配符 ? / ? extends / ? super ★★★ ​

泛型擦除 ​

  • Java 泛型是编译期概念，编译时擦除类型参数：
    • 无边界的 T 擦除为 Object；
    • 有上界的 T extends Number 擦除为 Number；
    • 使用处插入强制类型转换（checkcast）。
  • 所以运行时 List<String> 与 List<Integer> 是同一个 Class（ArrayList.class），无法通过反射拿到泛型实参（除字段/方法签名上的泛型信息，那存在常量池 Signature 里）。

为什么擦除 ​

  • 为兼容 Java5 之前的旧代码（二进制兼容），泛型只是「编译期类型安全检查」，运行时不改变 JVM 字节码结构。

通配符 ​

  • ? 无限制通配符。
  • ? extends T（上界，协变）：只能读（取出来是 T），不能写（add 报错，除 null）——因为不知道具体子类型。
  • ? super T（下界，逆变）：可写 T，读出是 Object。
  • 口诀 PECS：Producer Extends（生产数据用 extends），Consumer Super（消费数据用 super）。

追问应对 ​

  • 「List<Object> 能接收 List<String> 吗？」→ 不能，泛型不变（invariant），List<String> 不是 List<Object> 的子类型；需要协变用 List<? extends Object>。
  • 「泛型数组为什么不能 new？」→ new T[]、new List<String>[] 编译错误，因擦除后无法保证类型安全；用 (T[]) new Object[n] 或集合替代。

易错点 ​

  • 泛型不支持基本类型（List<int> 非法，用 List<Integer>）。
  • 静态方法/静态字段不能使用类的泛型类型参数（泛型参数属于实例）。

反射机制、获取 Class 的几种方式、优缺点 ★★★ ​

是什么 ​

  • 反射：运行期动态获取类的结构信息（构造器、字段、方法、注解）并调用，突破编译期类型检查。

获取 Class 对象的方式 ​

  • 类名.class（编译期已知，最常用，不触发初始化）。
  • 对象.getClass()（已有对象）。
  • Class.forName("全限定名")（会触发类初始化）。
  • 类加载器.loadClass("全限定名")（不触发初始化）。

用途 ​

  • 框架底层：Spring 通过反射实例化 Bean、注入依赖；MyBatis 通过反射做结果映射；JUnit 运行测试方法；动态代理。

优点 / 缺点 ​

  • 优点：动态、灵活，能编写通用框架。
  • 缺点：① 绕过编译检查，运行时才暴露错误；② 性能较低（可缓存 Method/Field/Constructor 缓解）；③ 破坏封装，可访问 private 成员（setAccessible(true)）。

追问应对 ​

  • 「反射性能为什么慢？怎么优化？」→ 慢在动态解析 + 安全检查 + 自动装箱；优化：缓存反射对象、setAccessible(true) 关闭安全检查、用 MethodHandle 或代码生成（如 CGLIB）替代频繁反射。

易错点 ​

  • Class.forName 会触发静态初始化（执行 static 块），loadClass 不会——JDBC 驱动加载就用 Class.forName 触发驱动注册。

注解、元注解、自定义注解 ★★☆ ​

是什么 ​

  • 注解是给代码附加元数据的标记，本身不改变逻辑，需通过反射（运行期）或注解处理器（编译期）读取生效。

元注解 ​

  • @Target：作用范围（TYPE/METHOD/FIELD/PARAMETER 等）。
  • @Retention：保留级别 SOURCE（源码，编译丢弃）、CLASS（字节码，默认）、RUNTIME（运行期可反射读取）。
  • @Documented：写入 javadoc。
  • @Inherited：子类继承父类注解（只对类注解有效）。
  • JDK8 新增 @Repeatable（可重复注解）。

BIO / NIO / AIO；Buffer、Channel、Selector ★★★ ​

三模型 ​

  • BIO（同步阻塞）：一连接一线程，读写阻塞，线程开销大，不适合高并发。
  • NIO（同步非阻塞）：Selector 多路复用，一个线程管理多个连接，连接有事件才处理，适合高并发。
  • AIO（异步非阻塞）：读写完成回调通知，不主动轮询，Java7 引入。

NIO 三大组件 ​

  • Buffer：缓冲区（capacity 容量、position 当前读写位置、limit 上限），读写通过 flip/clear 切换。
  • Channel：双向通道（FileChannel、SocketChannel、ServerSocketChannel），可读可写。
  • Selector：多路复用器，注册多个 Channel，监听 OP_READ/OP_WRITE/OP_ACCEPT/OP_CONNECT 就绪事件。

底层原理 ​

  • NIO 依赖操作系统的 IO 多路复用（Linux 的 select/poll/epoll），epoll 事件驱动、O(1) 获取就绪连接，Netty 就是基于 NIO 封装。

追问应对 ​

  • 「Netty 为什么用 NIO 不用 BIO/AIO？」→ NIO 多路复用适合高并发长连接；AIO 在 Linux 实现不成熟（底层仍是 epoll 模拟），跨平台一致性和性能不如 NIO。

易错点 ​

  • BIO 的「阻塞」是线程阻塞在 read/write；NIO 的「非阻塞」是线程不阻塞在单个连接，而是轮询就绪事件。

== 与 equals、hashCode 契约 ★★★ ​

是什么 ​

  • ==：比较基本类型的「值」，或引用类型的「内存地址」。
  • equals：Object 默认也是比较地址（等价 ==），String/Integer 等重写为「值比较」。
  • hashCode：返回对象哈希码，用于 HashMap/HashSet 定位桶。

契约（重点） ​

  1. 重写 equals 必须重写 hashCode（相等对象的 hashCode 必须相等）。
  2. 两个对象 equals 相等 → hashCode 必须相等（单向，反过来不成立：hashCode 相等不代表 equals 相等，即哈希碰撞）。
  • 违反后果：对象放入 HashSet/HashMap 后，若只重写 equals 不重写 hashCode，两个 equals 相等的对象 hashCode 不同，会落到不同桶，contains/get 找不到，出现「相同对象能重复加入」的 bug。

追问应对 ​

  • 「为什么 hashCode 冲突是允许的？」→ 哈希表本身就有碰撞，靠链表/红黑树解决；只要 equals 相等 hash 一致即可。

易错点 ​

  • equals 要满足自反、对称、传递、一致、非空（对 null 返回 false）。

深拷贝与浅拷贝、序列化 serialVersionUID ★★☆ ​

是什么 ​

  • 浅拷贝：只复制对象本身，其内部引用类型字段仍指向原对象（共享）。
  • 深拷贝：对象及其引用链上的对象全部独立复制。

实现 ​

  • 浅拷贝：实现 Cloneable + 覆写 clone()（super.clone() 是浅拷贝）。
  • 深拷贝：① 递归 clone 内部对象；② 序列化 + 反序列化（对象及内部对象都需 Serializable）；③ 手动 new 复制。

serialVersionUID ​

  • 序列化版本号；不显式声明时 JVM 根据类结构自动生成，类结构一变（加字段/方法）生成值改变，反序列化旧数据会抛 InvalidClassException。
  • 显式声明 private static final long serialVersionUID = 1L; 保证兼容。

追问应对 ​

  • 「transient 关键字作用？」→ 标记字段不参与序列化；反序列化后为默认值；常用于敏感信息（密码）或不可序列化字段。
  • 「序列化怎么破坏单例？」→ 反序列化会 new 新对象绕过单例构造器；解决：单例类加 readResolve() 返回已有实例。

BigDecimal 与浮点精度 ★★★ ​

为什么 float/double 有精度问题 ​

  • 二进制无法精确表示部分十进制小数（如 0.1 是无限循环二进制），运算产生舍入误差。金额计算必须用 BigDecimal。

BigDecimal 用法 ​

  • 构造必须用字符串：new BigDecimal("0.1")，不能用 new BigDecimal(0.1)（double 已失真）。
  • 运算用 add/subtract/multiply/divide，divide 必须指定 RoundingMode 或精度，否则除不尽抛 ArithmeticException。
  • 比较用 compareTo（比较数值，忽略 scale），不能用 equals（equals 会比较 scale，0.1 与 0.10 的 equals 为 false）。

追问应对 ​

  • 「为什么 0.1+0.2 != 0.3？」→ 二进制浮点表示误差，0.1 和 0.2 存储时就是近似值。

易错点 ​

  • BigDecimal 是不可变对象，运算后必须接返回值（a.add(b) 不会改 a）。
  • 金额通常存 long（分）或 Decimal 类型，避免浮点。

四种内部类 ★☆☆ ​

  • 成员内部类：可访问外部类所有成员；持有外部类引用（Outer.this）。
  • 静态内部类（static nested class）：不依赖外部实例，只能访问外部静态成员；最常用（如 Builder 模式、静态工具）。
  • 局部内部类：定义在方法内，作用域仅方法内。
  • 匿名内部类：一次性实现，new Runnable(){...}；只能访问 final 或 effectively final 的局部变量（JDK8 起不强制 final，但要求不被修改）。

追问应对 ​

  • 「匿名内部类为什么要求局部变量 effectively final？」→ 内部类持有的是变量副本，若变量可变，副本与原始变量会不一致，故语言强制其不变以保证语义一致。

枚举原理 ★★☆ ​

是什么 ​

  • enum 本质是继承 java.lang.Enum 的 final 类，每个枚举常量是 public static final 的实例，构造器私有。
  • 可定义字段、构造器、方法、实现接口。

为什么枚举是安全的单例 ​

  • JVM 保证枚举实例在类加载时创建且唯一，且能天然防反射（反射 newInstance 会抛异常）和防序列化破坏（反序列化返回同一实例）。所以《Effective Java》推荐枚举实现单例。

追问应对 ​

  • 「枚举和普通类区别？」→ 继承 Enum、实例固定且唯一、不能继承其他类、可比较（ordinal）、自带 name()/values()/valueOf()。

函数式接口、Lambda、Stream ★★★ ​

函数式接口 ​

  • 仅一个抽象方法的接口，可用 @FunctionalInterface 标注（编译器强制检查）。
  • 常见：Function<T,R>（转换）、Predicate<T>（断言）、Consumer<T>（消费）、Supplier<T>（提供）、BiFunction 等。

Lambda ​

  • 函数式接口的简洁实现：(参数) -> 表达式；本质是编译成 invokedynamic 生成函数式接口实现（JDK8 用 LambdaMetafactory，非匿名内部类，无额外 class 文件）。

Stream ​

  • 三部分：数据源 → 中间操作（惰性，不立即执行）→ 终结操作（触发执行）。
  • 中间操作：filter/map/sorted/distinct/limit/skip；终结操作：collect/forEach/reduce/count/anyMatch。
  • 惰性求值：没有终结操作时中间操作不执行。

追问应对 ​

  • 「Stream 和循环区别？」→ Stream 声明式、可链式、可并行（parallelStream），但注意并行流用共享线程池 ForkJoinPool，不适合有状态/阻塞操作。
  • 「map 和 flatMap 区别？」→ map 一对一转换；flatMap 一对多，把嵌套流拍平（如 List<List<T>> 转 List<T>）。

易错点 ​

  • Stream 只能消费一次，重复使用报 IllegalStateException。
  • parallelStream 在低并发小数据量下可能比串行还慢（线程调度开销）。

值传递与引用传递（前端转全栈必考）★★★ ​

结论 ​

  • Java 只有「值传递」，没有引用传递：
    • 基本类型：传「值的副本」，方法内改参数不影响外部。
    • 引用类型：传「引用（地址）的副本」，副本和原引用指向同一个对象，所以方法内修改「对象内容」会影响外部；但修改「引用本身」（重新 new / 指向别的对象）不影响外部引用。

经典例子 ​

  • swap(a, b) 交换两个对象引用，方法外不会真正交换，因为改的是副本引用。
  • 方法内 obj.field = x（改内容）→ 外部可见；方法内 obj = new X()（改引用）→ 外部不可见。

与 JS 对比 ​

  • JS 对 primitive 也是按值、对 object 是传「引用副本」，行为一致；差别是 Java 面试强调「只有值传递」这个结论，常让人辨析。

追问应对 ​

  • 「为什么说 Java 只有值传递？」→ 因为无论基本类型还是引用，传入的都是「副本」；引用传递的含义是「方法能拿到调用者的变量本身并修改它指向」，Java 做不到。

易错点 ​

  • 别被「引用类型传的是引用」误导成「引用传递」；区分「传的是引用副本」和「传引用（可改原引用指向）」。

final、finally、finalize 区别 ★★★ ​

final ​

  • 修饰类：不能被继承；修饰方法：不能被重写；修饰变量：基本类型值不可变、引用类型引用不可变（但指向的对象内容可变）。
  • final 变量修饰引用时，引用不能重新赋值，但 obj.field 仍可改。

finally ​

  • 异常处理关键字，无论是否抛异常都执行（除非 System.exit / 线程被 kill）；常考 finally 中 return 覆盖 try 的 return。

finalize ​

  • Object 的方法，对象被 GC 回收前调用一次；JDK9 起废弃（执行时机不确定、可能复活对象、性能差），替代方案是 Cleaner 或 try-with-resources。

追问应对 ​

  • 「final 和 finally 有关系吗？」→ 无，只是拼写相似。
  • 「finalize 为什么废弃？」→ 触发时机不确定、可能延迟 GC、甚至复活对象导致二次回收，建议显式释放资源。

Object 类常用方法 ★★☆ ​

  • equals、hashCode（成对重写，见契约）、toString（建议重写便于日志）、clone（需实现 Cloneable）、getClass（获取 Class，final 不可覆写）、finalize（废弃）。
  • 线程相关：wait()、notify()、notifyAll()（用于线程协作，见多线程篇）。
  • 追问：「Object 有哪些方法？」→ 上述 9 个 + registerNatives（native 方法注册）。

类初始化顺序、静态变量/代码块 ★★☆ ​

顺序 ​

  1. 父类静态变量 / 静态代码块（按书写顺序）。
  2. 子类静态变量 / 静态代码块。
  3. 父类实例变量 / 实例代码块 / 构造器。
  4. 子类实例变量 / 实例代码块 / 构造器。

关键 ​

  • 静态变量和静态块只在类「首次被主动使用」时执行一次（类加载的初始化阶段）。
  • 实例代码块每次 new 都执行，且在构造器之前。
  • 同类内部按书写顺序执行，构造器最后。

触发类初始化的时机（主动引用） ​

  • new 对象、访问类的静态变量/静态方法、反射（Class.forName）、初始化子类先初始化父类、main 所在类。
  • 被动引用不触发初始化：通过子类访问父类静态变量（只初始化父类）、引用常量（编译期已入常量池）、定义数组。

易错点 ​

  • 「new 子类 会初始化父类吗？」→ 会，先父后子。

Comparable 与 Comparator 区别 ★★☆ ​

  • Comparable（内部比较器）：类实现 compareTo(o)，定义「自然排序」，侵入类内部，只能一种排序。
  • Comparator（外部比较器）：实现 compare(a, b)，不改原类，可定义多种排序；常配合 lambda Comparator.comparing(...).thenComparing(...)。
  • 用法：Collections.sort(list, comparator)、stream().sorted(comparator)；TreeSet/TreeMap 依赖它们。

追问应对 ​

  • 「什么时候用哪个？」→ 一种自然顺序用 Comparable；多种/临时/外部排序规则用 Comparator；Comparator 更灵活，优先用。

Java 8 新特性汇总、Optional ★★★ ​

新特性 ​

  • Lambda、函数式接口、方法引用（::）、Stream、Optional、新时间 API（LocalDate/LocalDateTime/Instant/DateTimeFormatter）、接口 default/static 方法、CompletableFuture、Base64、可重复注解、方法参数反射。

Optional ★★★ ​

  • 用途：包装可能为 null 的值，显式表达「可能为空」，避免 NPE。
  • 创建：of（值不能 null）、ofNullable、empty。
  • 判断执行：isPresent、ifPresent。
  • 兜底：orElse（惰性求值用 orElseGet）、orElseThrow。
  • 转换：map、flatMap。
  • 注意：orElse 无论值是否存在都计算参数（orElse(expensive()) 会先算 expensive），orElseGet 才惰性。
  • 最佳实践：Optional 只作方法返回值，不作字段、不作方法参数、不用于集合元素（会增加装箱开销）。

易错点 ​

  • Optional.get() 在 empty 时抛 NoSuchElementException，应先判断或 orElse 兜底。

集合框架选型总结 ★★★ ​

  • List：有序可重复 → 读多 ArrayList，频繁头尾/队列栈 LinkedList。
  • Set：去重 → HashSet（无序 O(1)）、LinkedHashSet（保持插入顺序）、TreeSet（排序）。
  • Map：HashMap（无序）、LinkedHashMap（保持插入顺序，可做 LRU）、TreeMap（按 key 排序）、ConcurrentHashMap（并发）。
  • 线程安全：ConcurrentHashMap、CopyOnWriteArrayList，或 Collections.synchronizedXxx 包装。

追问应对 ​

  • 「LinkedHashMap 怎么实现 LRU？」→ 继承 LinkedHashMap 重写 removeEldestEntry，accessOrder=true 时访问过的元素移到尾部，超出容量删最老元素。

fail-fast 与 fail-safe ★★☆ ​

是什么 ​

  • fail-fast（快速失败）：遍历时用 modCount 检测并发修改，结构一变立即抛 ConcurrentModificationException；ArrayList/HashMap 的迭代器属于此类。
  • fail-safe（安全失败）：遍历的是副本（快照），修改不影响遍历、不抛异常；CopyOnWriteArrayList、ConcurrentHashMap 属于此类。

原理 ​

  • fail-fast：集合有 modCount（结构修改计数器），迭代器创建时记录期望值，每次 next() 前校验，不一致即抛异常。
  • fail-safe：CopyOnWriteArrayList 的迭代器遍历的是写时复制的旧数组快照。

易错点 ​

  • for-each 里调 list.remove() 抛 ConcurrentModificationException；正确做法 iterator.remove() 或 removeIf。
  • fail-safe 读到的可能是「旧数据」（弱一致）。

JDK 版本演进：8 / 11 / 17 / 21 新特性 ★★☆ ​

  • Java 8（LTS）：Lambda、Stream、Optional、新时间 API、接口 default/static（最重要，绝大多数项目基线）。
  • Java 11（LTS）：var 局部变量类型推断、HTTP Client API、String 增强（isBlank/lines/strip）、单文件运行。
  • Java 17（LTS）：sealed 类、switch 表达式增强、record 记录类、文本块（"""..."""）、instanceof 模式匹配。
  • Java 21（LTS，重点）：
    • 虚拟线程（Virtual Thread）：轻量级线程，JVM 调度，可百万级并发。
    • 结构化并发、ScopedValue（虚拟线程中替代 ThreadLocal 传递）。
    • 记录模式匹配、switch 模式匹配、字符串模板（预览）。

追问应对 ​

  • 「record 是什么？」→ 不可变数据载体，自动生成构造器/getter/equals/hashCode/toString，替代繁琐 POJO。
  • 「sealed 类？」→ 限制哪些类能继承/实现它，增强类型安全与模式匹配穷尽性。

虚拟线程 vs 平台线程 ★★☆ ​

是什么 ​

  • 平台线程（传统 Thread）：1:1 映射 OS 线程，创建/切换成本高、数量有限（几百到几千），IO 阻塞会占住线程。
  • 虚拟线程：M:N 映射到少量载体线程（OS 线程），由 JVM 调度；IO 阻塞时 JVM 自动挂起该虚拟线程并切换执行其他虚拟线程，创建成本极低，支持百万级并发。

适用场景 ​

  • 适合 IO 密集型、高并发（Web 请求处理、大量下游/DB 调用）。
  • 不适合 CPU 密集计算（无收益，甚至增加调度开销）。

用法 ​

  • Thread.ofVirtual().start(task) 或 Executors.newVirtualThreadPerTaskExecutor()（每任务一虚拟线程，无需大线程池）。

追问应对 ​

  • 「虚拟线程会取代线程池吗？」→ 虚拟线程场景下不再需要为「每请求一线程」配置庞大线程池，但 CPU 密集或需要限流/隔离的场景仍会配合信号量/线程池使用。
  • 「为什么 IO 密集用虚拟线程收益大？」→ 传统线程阻塞在 IO 时 OS 线程被占住，无法复用；虚拟线程阻塞时载体线程可立即切走执行其他任务，吞吐大幅提升。
