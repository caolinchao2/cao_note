中间件（Redis & 消息队列） ​

常问等级：★★★ 高频必考 / ★★☆ 中频常见 / ★☆☆ 低频了解 深度标准：每个考点讲清「是什么 → 为什么 → 源码关键点 → 追问应对 → 易错点」。

Redis 为什么快（单线程模型）★★★ ​

为什么单线程还快 ​

  • 纯内存操作，瓶颈在内存/网络而非 CPU。
  • 单线程避免线程切换、锁竞争开销。
  • IO 多路复用（epoll）：一个线程监听多个连接，事件驱动处理。
  • 高效数据结构（跳表、压缩列表、哈希表）。

为什么用单线程 ​

  • Redis 操作主要在内存，单线程足够快且简单；多线程会引入锁与上下文切换。

注意 ​

  • Redis 6.0 引入多线程（仅网络 IO 读写多线程，命令执行仍是单线程），因为网络 IO 成为瓶颈。

追问应对 ​

  • 「单线程为什么能高并发？」→ 内存 + IO 多路复用 + 无锁；单线程指命令执行，网络 IO 可多线程。
  • 「单线程的缺点？」→ 单个慢命令（keys、大 key 删除）会阻塞整个实例，需用 scan/渐进删除。

Redis 数据类型及底层数据结构 ★★★ ​

常用数据类型 ​

  • String：SDS（简单动态字符串），可存数字/字符串/位图。
  • Hash：哈希表 + 压缩列表（小数据）→ listpack（7.0）。
  • List：链表/压缩列表，可做消息队列、栈。
  • Set：哈希表/intset（整数集合），去重。
  • ZSet（有序集合）：跳表 + 哈希表，做排行榜。

底层结构演进 ​

  • 跳表（skiplist）：ZSet 底层，支持 O(logn) 范围查询和排序。
  • 压缩列表（ziplist）/listpack：元素少且小的时候用，省内存。
  • SDS：比 C 字符串更安全（O(1) 取长度、二进制安全、避免溢出）。

追问应对 ​

  • 「ZSet 为什么用跳表不用红黑树？」→ 跳表实现简单、支持范围查询、并发场景友好；红黑树实现复杂。
  • 「SDS 和 C 字符串区别？」→ SDS 有 len 字段 O(1) 取长度、二进制安全、预分配减少重分配。

缓存穿透、击穿、雪崩 ★★★ ​

缓存穿透 ​

  • 查询不存在的数据（key 也不在缓存和 DB），每次都打 DB。
  • 解决：① 缓存空值（设短过期）；② 布隆过滤器（拦截不存在的 key）；③ 参数校验。

缓存击穿 ​

  • 某个热点 key 过期瞬间，大量请求同时打 DB。
  • 解决：① 热点 key 不过期/永不过期；② 互斥锁（只有一个请求回源重建缓存）；③ 逻辑过期。

缓存雪崩 ​

  • 大量 key 同时过期或 Redis 宕机，请求全打 DB。
  • 解决：① 过期时间加随机值；② 多级缓存；③ Redis 高可用（集群/哨兵）；④ 限流降级。

追问应对 ​

  • 「布隆过滤器原理？」→ 多个哈希函数把 key 映射到位数组，判断「可能存在」或「一定不存在」，可拦截不存在 key；有误判率。

缓存与数据库一致性 ★★★ ​

方案 ​

  • Cache Aside（旁路缓存，主流）：读时先查缓存未命中则查库并回填；写时「先更新数据库，再删除缓存」。
  • 为什么不先删缓存：先删缓存再更新库，中间可能被别的请求读到旧数据回填缓存，导致不一致。

保证最终一致 ​

  • 延时双删：更新库 → 删缓存 → 延迟再删一次。
  • 订阅 binlog（Canal）异步删缓存。
  • 事务消息/重试机制。

追问应对 ​

  • 「为什么是删除缓存而不是更新缓存？」→ 删除更简单、避免并发更新顺序问题；懒加载避免写不常读的数据。
  • 「强一致性怎么保证？」→ 缓存场景通常接受最终一致；强一致可加分布式锁或读写都走库。

Redis 持久化：RDB 与 AOF ★★★ ​

RDB（快照） ​

  • 定时把内存数据快照写入磁盘（fork 子进程 + 写时复制）。
  • 优点：文件小、恢复快、对性能影响小；缺点：两次快照间数据可能丢失。
  • 触发：save（阻塞）、bgsave（fork 子进程）、配置 save 900 1。

AOF（追加日志） ​

  • 记录每次写命令，追加写入。
  • 策略：always（每条刷盘，最安全慢）、everysec（每秒，默认折中）、no（OS 决定）。
  • 优点：数据更完整；缺点：文件大、恢复慢；AOF 重写压缩。

混合持久化 ​

  • Redis 4.0+：RDB 快照 + 增量 AOF，兼顾恢复速度与数据完整性。

追问应对 ​

  • 「生产怎么选？」→ 数据不能丢用 AOF everysec，或 RDB + AOF 混合；能容忍少量丢失可只用 RDB。
  • 「bgsave 为什么 fork？」→ 子进程写时复制，主进程继续服务，不阻塞。

Redis 过期删除策略与内存淘汰 ★★★ ​

过期删除 ​

  • 惰性删除：访问 key 时才检查是否过期。
  • 定期删除：周期性随机抽样一批 key 检查删除。
  • 二者结合（Redis 实际采用）：平衡 CPU 与内存。

内存淘汰策略（内存满时） ​

  • noeviction：不淘汰，写入报错。
  • allkeys-lru：所有 key 里淘汰最久未用（推荐）。
  • volatile-lru：只在有过期时间的 key 里淘汰。
  • allkeys-random / volatile-random：随机。
  • volatile-ttl：淘汰最早过期的。
  • allkeys-lfu / volatile-lfu：淘汰最不常用（LFU）。

追问应对 ​

  • 「为什么不只靠惰性删除？」→ 惰性删除下长期不访问的过期 key 会占内存，需定期删除兜底。
  • 「LRU 和 LFU 区别？」→ LRU 按最近访问时间，LFU 按访问频率；LFU 更抗「偶发热点」。

Redis 分布式锁（Redisson）★★★ ​

基本实现 ​

  • SET key value NX EX 秒：原子加锁 + 设过期时间。
  • value 用唯一标识（UUID + 线程 id），释放时校验 value 一致再删除（防误删他人锁）。

为什么用 Lua ​

  • 「判断 value + 删除」需原子，用 Lua 脚本保证（避免释放锁时误删）。

关键问题 ​

  • 锁续期：业务执行超过锁过期时间会提前释放，Redisson 用看门狗（Watch Dog）自动续期。
  • 锁重入：Redisson 支持可重入。
  • 主从切换丢锁：主节点宕机锁丢失，用 RedLock（多节点）缓解，但 RedLock 也有争议。

追问应对 ​

  • 「SET NX 为什么不安全？」→ 可能业务未完成锁就过期；需续期或设足够长过期 + 看门狗。
  • 「释放锁为什么要校验 value？」→ 防止 A 线程删了 B 线程的锁。

Redis 集群：主从、哨兵、Cluster ★★★ ​

主从复制 ​

  • 从节点复制主节点数据，实现读写分离和备份；主写从读。

哨兵（Sentinel） ​

  • 监控主从节点，主节点宕机自动选举新主（故障转移），高可用。

Cluster（集群） ​

  • 数据分片（16384 个 hash slot 分配到不同节点），水平扩展。
  • 通过 CRC16(key) % 16384 定位槽和节点。
  • 支持故障转移、客户端重定向（MOVED/ASK）。

追问应对 ​

  • 「哨兵和集群区别？」→ 哨兵解决「高可用」（一个主），集群解决「扩展性」（多个主分片），集群自带高可用。
  • 「为什么是 16384 个槽？」→ 16384 足够分片且心跳包小、槽位图传输开销低。

缓存预热、缓存降级、热点 key ★★☆ ​

  • 缓存预热：启动时提前加载热点数据到缓存，避免冷启动击穿。
  • 缓存降级：缓存/DB 压力大时，降级为兜底数据/限流。
  • 热点 key：发现访问集中的 key，可做本地缓存（如 Caffeine）+ Redis 二级缓存。

为什么用消息队列，作用 ★★★ ​

  • 解耦：生产者和消费者不直接依赖，通过 MQ 中转。
  • 异步：非核心流程异步处理，提升响应速度。
  • 削峰：高峰期请求入队，消费者按自身能力消费，保护下游。
  • 缺点：系统复杂度增加、一致性问题（消息丢失/重复）、可用性依赖 MQ。

追问应对 ​

  • 「什么时候不该用 MQ？」→ 同步强一致、低延迟、简单调用场景，别为了用而用。

消息丢失怎么解决 ★★★ ​

三个环节 ​

  1. 生产者丢失：发送失败/网络问题 → 发送确认机制（ack）、事务消息、重试。
  2. MQ 丢失：消息未持久化 → 开启持久化（刷盘）、同步复制（主从）。
  3. 消费者丢失：消费后未提交就挂 → 手动 ack，处理完成再确认。

结论 ​

  • 端到端：生产确认 + MQ 持久化 + 消费手动 ack，保证至少一次投递。

追问应对 ​

  • 「怎么保证消息不丢？」→ 三层：producer confirm、broker 持久化 + 复制、consumer 手动 ack。

消息重复消费怎么解决 ★★★ ​

为什么重复 ​

  • 至少一次投递 + 网络重试/超时重发，天然可能重复。

解决 ​

  • 幂等：消费端做幂等处理。
    • 唯一键（数据库唯一索引 + 插入冲突忽略）。
    • Redis setnx 记录已处理的消息 id。
    • 状态机（订单状态已支付则跳过）。

追问应对 ​

  • 「MQ 能保证不重复吗？」→ 不能（除非恰好一次语义，代价大），业务端必须幂等。

消息顺序消费 ★★☆ ​

  • 保证顺序：单分区/单队列（同一业务消息发到同一分区/队列），消费者单线程消费。
  • RocketMQ：顺序消息按 MessageQueue 顺序；Kafka：同一 partition 内有序。
  • 若要求全局有序，只能一个队列 + 单消费者，牺牲并发。

追问应对 ​

  • 「全局有序和局部有序？」→ 全局有序性能差（单队列）；一般只需保证「同一业务 key（如订单）内有序」。

消息积压怎么解决 ★★☆ ​

  • 增加消费者实例、消费者并发度。
  • 优化消费逻辑（批处理、减少 IO）。
  • 临时新建 topic 分流、降级非核心消息。
  • 检查消费者是否故障/慢。

死信队列、延迟消息 ★★☆ ​

  • 死信队列：消费失败达重试上限、消息过期、队列满时进入死信队列，用于人工处理/告警。
  • 延迟消息：消息延迟一定时间后才投递（RocketMQ 延迟等级、RabbitMQ 死信 + TTL 模拟、Kafka 需额外实现）。
  • 应用：订单超时未支付自动取消。

缓存设计模式 ★★★ ​

Cache Aside（旁路缓存，最常用） ​

  • 读：先查缓存，未命中则查库并回填缓存。
  • 写：先更新数据库，再删除缓存（不是更新缓存）。
  • 优点：简单、缓存与库解耦；缺点：存在短暂不一致窗口。

Read Through（读穿透） ​

  • 缓存层自己负责查库回填（应用不感知数据库），读逻辑封装在缓存组件里。

Write Through（写穿透） ​

  • 写时同时更新缓存和数据库，保证缓存与库一致，但写开销大（每次写都更新缓存，即使数据不常读）。

Write Behind / Write Back（写回） ​

  • 写时只更新缓存，异步批量刷到数据库；性能最高但一致性最弱，缓存挂了可能丢数据。

追问应对 ​

  • 「为什么 Cache Aside 写是删缓存而不是更新？」→ 删除更简单、避免并发更新顺序问题、懒加载避免写不常读的数据。
  • 「Write Through 和 Write Back 区别？」→ Write Through 同步写库（一致性好、慢），Write Back 异步批量写库（快、可能丢数据）。

Redis Pipeline 的好处 ★★☆ ​

是什么 ​

  • 把多条命令打包一次性发给 Redis，减少「每条命令一次网络往返（RTT）」的开销。

为什么快 ​

  • Redis 处理单条命令很快，瓶颈常在网络 RTT；pipeline 把 N 次 RTT 变成 1 次，批量命令执行仍是单线程顺序执行。

注意 ​

  • Pipeline 不是原子操作（命令间可能被其他客户端命令穿插，除非用事务 MULTI/EXEC）。
  • 与传统「批量命令（mget/mset）」区别：mget/mset 是单条命令操作多个 key（原子），pipeline 是多条命令打包（非原子）。

追问应对 ​

  • 「Pipeline 和事务区别？」→ Pipeline 只减少 RTT、非原子；事务（MULTI/EXEC）保证原子但不减少 RTT（可结合使用）。

Redis 和 HashMap 的区别 ★★☆ ​

  • Redis 是「独立的分布式缓存服务」，基于网络通信，支持持久化、集群、过期、多种数据类型、跨进程/跨机器共享。
  • HashMap 是「JVM 内的本地数据结构」，仅单机单进程内有效，无持久化、无网络、GC 管理内存。
  • 对比维度：Redis 容量大（可集群）、可共享、有持久化和淘汰；HashMap 速度快（内存直读、无网络）但受单机内存限制、重启丢失。

追问应对 ​

  • 「为什么有了 HashMap 还要 Redis？」→ HashMap 无法跨实例共享、无法持久化、容量受单机限制；Redis 解决分布式缓存/共享/持久化。

什么时候选 Redis，什么时候选本地缓存（Caffeine）/ Memcached ★★☆ ​

  • Redis：需要跨服务/跨实例共享、持久化、丰富数据结构、分布式场景。
  • 本地缓存（Caffeine/Guava Cache）：单机内热点数据、要求纳秒级低延迟、无需跨实例共享（如配置、字典）。
  • 常见组合：本地缓存 + Redis 二级缓存（本地缓存做第一层，Redis 做第二层，减少网络开销）。
  • Memcached vs Redis：Memcached 只支持简单 KV、无持久化、多线程、纯内存；Redis 数据结构丰富、支持持久化、单线程（6.0 网络多线程）。现在多数场景选 Redis。

追问应对 ​

  • 「Redis 和本地缓存怎么配合？」→ 本地缓存做一级（快、容量小），Redis 做二级（共享、容量大），注意两级缓存的一致性问题。

Redis 内存用完了会发生什么 ★★★ ​

结果 ​

  • 取决于「内存淘汰策略（maxmemory-policy）」：
    1. 默认 noeviction：内存满后，写操作（SET 等会新增内存的命令）直接报错 OOM command not allowed，但读操作、删除操作仍可用。
    2. allkeys-lru / volatile-lru 等：内存满时按策略淘汰 key，腾出空间，写操作继续成功。
  • 注意：不管哪种策略，内存到 maxmemory 上限就会触发淘汰或报错；没有配置 maxmemory 时，Redis 会一直吃内存直到系统内存耗尽，可能被 OS OOM Killer 杀掉。

配置 ​

  • maxmemory 设置最大内存，maxmemory-policy 设置淘汰策略。

追问应对 ​

  • 「生产怎么配？」→ 一定设置 maxmemory + 合适的淘汰策略（一般 allkeys-lru），避免内存打爆系统。

MQ 部署单机还是集群、高可用怎么保证 ★★★ ​

结论 ​

  • 生产必须集群部署，单机有单点故障。

Kafka 高可用 ​

  • 多副本机制：每个 partition 有多个 replica（leader + follower），leader 挂掉自动选举新 leader，保证消息不丢、服务可用。

RocketMQ 高可用 ​

  • 主从复制 + NameServer 集群；Broker 主从同步，主挂自动切换（配合 Dledger 实现主从自动切换）。

RabbitMQ 高可用 ​

  • 镜像队列（mirrored queue）：队列在多个节点间镜像，主节点挂掉从镜像节点接管；或 Quorum Queue（仲裁队列，Raft 协议）。

追问应对 ​

  • 「为什么集群能保证高可用？」→ 数据多副本 + 故障自动切换（选举新主），单节点挂了不影响整体。

如何解决消息队列的延时、过期失效问题 ★★★ ​

延迟消息 ​

  • 定时/延迟投递：RocketMQ 延迟等级、RabbitMQ 死信 + TTL 模拟、Kafka 需自实现（时间轮）。

消息过期失效 ​

  • 问题：消息设置了 TTL 却一直没被消费，过期进入死信队列，导致「本来该处理的业务没处理」。
  • 解决：
    1. 死信队列兜底：消费死信队列做补偿/告警。
    2. 监控积压：告警并及时扩容消费者。
    3. 避免设过短的 TTL；确保消费者正常消费。

消息积压 ​

  • 增加消费者、提升并发、临时分流、优化消费逻辑（见消息积压部分）。

追问应对 ​

  • 「消息积压导致大量过期怎么办？」→ 紧急扩容消费者 + 提高消费速度 + 死信补偿 + 修复消费瓶颈。

如果让你写一个消息队列，如何架构 ★★★ ​

核心模块 ​

  1. 存储：消息持久化（顺序写日志文件，如 commit log）。
  2. 分区/队列：支持多个 topic 分区，实现并行与顺序。
  3. 网络通信：高性能网络框架（Netty），生产者/消费者协议。
  4. 消息投递：push/pull 模型、消费位移（offset）管理。
  5. 高可用：多副本、主从同步、故障转移。
  6. 可靠投递：ack 机制、重试、持久化。

关键设计点 ​

  • 顺序写 + 零拷贝提升吞吐。
  • 消费位移记录支持重复消费与进度管理。
  • 副本机制保证不丢消息。

追问应对 ​

  • 「为什么 Kafka 用顺序写？」→ 顺序写磁盘接近内存速度（相比随机写快很多），配合页缓存 + 零拷贝大幅提升吞吐。

Redis 慢查询怎么找、怎么优化 ★★★ ​

找慢查询 ​

  • 配置：slowlog-log-slower-than（阈值，微秒）、slowlog-max-len（保留条数）。
  • 查看：slowlog get [n] 查看最近慢命令。
  • 也可用 latency monitor、redis-cli --stat、INFO commandstats 观察。

优化方向 ​

  1. 避免慢命令：keys *（改 scan）、hgetall 大 key、smembers 大集合、sort。
  2. 大 key 拆分：大 value 拆成多个小 key，或用 hash 分片。
  3. 避免阻塞命令：删除大 key 用 unlink（异步删除）而非 del。
  4. 合理数据结构：用合适类型减少内存与命令开销。
  5. 用 pipeline 批量、减少 RTT。
  6. 持久化策略调优（AOF 重写、RDB 触发时机）。

追问应对 ​

  • 「Redis 为什么单线程下还有慢命令？」→ 单命令执行是串行的，一个慢命令（如大 key 遍历）会阻塞后续所有命令。

Redis 性能优化 ★★★ ​

  • 内存：合理淘汰策略、压缩编码（ziplist/listpack）、控制大 key。
  • 命令：避免 O(n) 慢命令、用 scan、批量用 pipeline/mget。
  • 网络：多线程 IO（6.0）、pipeline 减少 RTT。
  • 持久化：RDB/AOF 平衡，AOF 用 everysec、及时重写。
  • 架构：主从读写分离、Cluster 分片、热点 key 本地缓存。
  • 参数：maxmemory、连接池大小、超时配置。

追问应对 ​

  • 「怎么发现热点 key？」→ 监控访问频率（redis-cli --hotkeys 或监控统计），热点数据做本地缓存/分片分流。
