中间件（Redis & 消息队列） ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

1. Redis 为什么快（单线程模型）★★★ ​

通俗理解 四件事：纯内存操作、单线程避免锁和线程切换、IO 多路复用（epoll 一个线程监听多连接）、数据结构高效。 注意「单线程」指的是命令执行是单线程，Redis 6.0 之后网络 IO 读写已经是多线程了。所以单个慢命令（keys *、删大 key）会卡住整个实例。

我的项目关联 Redis 在我们这儿是最基础的依赖：设备在线状态、订单、字典、分布式锁都靠它。因为它单线程，我们上线前特意排查过 keys * 这类命令，改成了 scan；删大 key 用 unlink 异步删，避免阻塞。

面试答题话术 「Redis 快主要是内存 + 单线程无锁 + IO 多路复用。单线程指的是命令执行，6.0 网络 IO 是多线程的。它最大的坑也是单线程——一个慢命令会阻塞整个实例，所以线上我们禁用 keys，删大 key 用 unlink。」

2. Redis 数据类型及底层结构 ★★★ ​

通俗理解 String（字符串/计数/位图）、Hash（对象）、List（列表/队列）、Set（去重）、ZSet（有序集合，排行榜）。 底层：ZSet 用跳表（查询 O(logn)、好做范围查询），小数据量时用 ziplist/listpack 省内存；String 用的是 SDS，有长度字段所以取长度为 O(1)、二进制安全。记结论就行，别抠跳表实现细节。

我的项目关联 选结构是体现功力的地方：设备最新状态用 Hash（一个设备一个 key，字段存电量/功率/状态）；排行榜、延迟任务用 ZSet；Bitmap 做设备在线/签到统计；HyperLogLog 做 UV 估算。

面试答题话术 「常用的五种结构我都用过：Hash 存设备状态、ZSet 做延迟队列和排行、Bitmap 做在线统计。底层 ZSet 是跳表，查询 O(logn)，范围查询友好，比红黑树好实现。具体源码我不过深，知道结论够用了。」

3. 缓存穿透、击穿、雪崩 ★★★ 【简历亮点，高频追问】 ​

通俗理解 三个长得像但原因完全不同的问题：

  • 穿透：查一个根本不存在的数据，缓存和库都没有，每次都打库。解法：缓存空值（短过期）、布隆过滤器、参数校验。
  • 击穿：某个热点 key 刚好过期，瞬间大量请求一起打库。解法：互斥锁重建、热点 key 不设过期、逻辑过期。
  • 雪崩：大批 key 同时过期，或 Redis 整个挂了，请求全砸库。解法：过期时间加随机值、多级缓存、集群高可用、限流降级。

我的项目关联真实经验：这类问题我们是靠「过期时间打散 + 空值缓存 + 限流」一起扛的。设备编号、订单号这类查询很适合被恶意扫，比如拿一堆不存在的桩编号来刷，我们就是靠缓存空值 + 网关限流拦的，属于线上处理过的场景。 布隆过滤器我在文档里研究过，也了解原理（多个哈希映射位数组，只会误判「存在」），但我们这块没实装，属于学习了解，面试别说是线上用的。

面试答题话术 「三个问题我分开说：穿透是查不存在的数据，我用缓存空值加参数校验挡；击穿是热点 key 过期，我用互斥锁重建；雪崩是批量过期或 Redis 挂了，我把过期时间打散，加上限流降级兜底。布隆过滤器原理我清楚，但我们项目没用上，就不硬说用过了。」

4. 缓存与数据库一致性 ★★★ 【简历亮点，高频追问】 ​

通俗理解 最主流是 Cache Aside（旁路缓存）：读的时候先查缓存、没有再查库并回填；写的时候先更新数据库，再删除缓存。 为什么是「删缓存」不是「更新缓存」：删更简单，也避免并发写把旧值刷进缓存。为什么不是先删缓存：先删了缓存再更新库，中间有窗口会被别的请求读到旧数据又回填回去。 要做到最终一致可以加「延时双删」或订阅 binlog（Canal）异步删。缓存场景一般只承诺最终一致，做不到强一致。

我的项目关联真实经验：订单、设备状态这类缓存，我们走的就是「先更库再删缓存」。支付对账场景里我们对一致性的要求比一般业务高，所以最敏感的对账数据是直接读库不走缓存的，缓存只用在允许短暂不一致的展示类数据上。这是业务取舍，不是纯技术选型。

面试答题话术 「标准答案先更库再删缓存，因为删比更新简单、也不容易出错。但关键看业务：像对账、支付金额这种，我们宁可走库也不要缓存那点不一致窗口，缓存只用在展示类数据上。一致性上缓存只能做到最终一致，强一致就别用缓存。」

5. Redis 持久化：RDB 与 AOF ★★★ ​

通俗理解

  • RDB：定时把内存数据快照存盘（fork 子进程写，主进程照常服务）。文件小、恢复快，但两次快照之间的数据会丢。
  • AOF：记录每条写命令追加到日志。everysec 是默认折中档（最多丢 1 秒）；always 最安全最慢；no 交给操作系统。文件大、恢复慢，靠 AOF 重写压缩。
  • 混合持久化（4.0+）：RDB 快照 + 增量 AOF，恢复快又少丢数据。

我的项目关联 我们的 Redis 是当缓存和锁用的，核心数据都在 MySQL/Kafka 里，Redis 丢了可以重建，所以持久化不是我们的生命线。但如果被问「你线上怎么配」，我会说：缓存型实例可以只开 RDB，混合持久化是更稳的默认选择。

面试答题话术 「RDB 是定时快照，恢复快、文件小但可能丢一段数据；AOF 记录每条写命令，everysec 最多丢一秒，但文件大恢复慢。生产一般用混合持久化。不过要说清：Redis 在我们项目里是缓存，真正不能丢的数据在 MySQL 和 Kafka，所以持久化对我们不是最关键的一环。」

6. Redis 过期删除策略与内存淘汰 ★★★ ​

通俗理解

  • 过期删除：惰性删除（访问时才判断过期）+ 定期删除（周期随机抽一批查），两者结合，平衡 CPU 和内存。
  • 内存淘汰（内存满时按 maxmemory-policy）：noeviction 不淘汰直接报错、allkeys-lru 淘汰最久未用、volatile-lru 只在设了过期时间的 key 里淘汰、allkeys-lfu 按访问频率淘汰。

我的项目关联 这个问题跟我上一题「Redis 内存满」是连着的。真实教训：没设 maxmemory 是最危险的，Redis 会一直吃内存直到被系统的 OOM Killer 干掉。我们后来是显式设置 maxmemory + allkeys-lru。

面试答题话术 「过期删除是惰性加定期结合。淘汰策略我一般配 allkeys-lru。这里有个坑：不设 maxmemory，Redis 会把系统内存吃光然后被杀掉，我们踩过这个方向的风险，所以一定要显式设上限。」

7. Redis 分布式锁（Redisson）★★★ 【简历亮点，高频追问】 ​

通俗理解 最基础写法是 SET key value NX EX 秒，value 放唯一标识（UUID + 线程 id），释放时先校验 value 再删，防止删错别人的锁。 几个必须知道的点：

  • 释放锁要用 Lua：把「判断 + 删除」做成原子操作。
  • 锁续期：业务没跑完锁就过期了 → Redisson 的看门狗（Watch Dog）自动续期。
  • 可重入：Redisson 支持。
  • 主从丢锁：主节点宕机、锁还没同步到从节点就丢了 → 用 RedLock 缓解，但 RedLock 本身有争议。

我的项目关联这是真实在用的。充电场景对「同一把枪不能同时下两条启动指令」很敏感，我们就是用 Redisson 加锁保证同一把枪/同一个订单串行处理；对账任务也用它防止多个实例重复跑。真实踩过的坑：早期写业务时没注意锁的释放要在 finally 里，且要判当前线程持有，后来统一改用 Redisson 的 tryLock + 看门狗，才把「业务没跑完锁过期」的问题解决掉。

面试答题话术 「分布式锁我用的是 Redisson。基础是 SET NX EX 加 Lua 释放，Redisson 额外解决了看门狗续期和可重入。项目里用来保证同一把充电枪、同一个订单不会并发出问题。要说坑就是——锁的过期时间要跟业务耗时匹配，不然业务没跑完锁就没了，这个我们用看门狗兜的。」

8. Redis 集群：主从、哨兵、Cluster ★★★ ​

通俗理解

  • 主从复制：主写从读，做备份和读写分离。
  • 哨兵（Sentinel）：监控主从，主挂了自动选举新主，解决高可用。
  • Cluster：数据分片到 16384 个槽，多主水平扩展，解决容量和扩展性，自带故障转移。 一句话区分：哨兵解决「一个主的高可用」，集群解决「要多主扩展」。

我的项目关联 我们用的是主从 + 哨兵，数据量还没到需要 Cluster 分片的程度。涉及分布式锁时要注意主从切换期间的丢锁窗口（见上一题）。

面试答题话术 「主从做读写分离和备份，哨兵做故障转移保证高可用，Cluster 做分片扩展。我们现在是主从加哨兵就够了，没到要 Cluster 的量级。要注意主从切换时分布式锁可能丢，这是个经典问题。」

9. 缓存预热、缓存降级、热点 key ★★☆ ​

通俗理解 缓存预热：启动时提前把热点数据加载进缓存，避免冷启动打库。缓存降级：缓存/库压力大时返回兜底数据或直接限流。热点 key：访问过度集中，可以做本地缓存 + Redis 二级缓存分流。

我的项目关联 后台的字典、配置类数据我们是启动预热 + 本地缓存扛的，量不大但查询频繁。热点 key 目前没到需要专门分片的程度。

面试答题话术 「预热就是启动时先把热点数据放缓存，降级是扛不住时返回兜底数据，热点 key 用本地缓存加 Redis 两级分流。了解这些思路就行，我们实际主要用了预热。」

10. 为什么用消息队列 ★★★ ​

通俗理解 三大作用：解耦（生产消费不直接依赖）、异步（非核心流程异步跑，接口更快返回）、削峰（高峰入队，消费者按自己的节奏消费，保护下游）。 代价是：系统变复杂、有消息丢失/重复的一致性问题、强依赖 MQ 的可用性。

我的项目关联这就是我们 Kafka 的定位。充电桩上报的实时数据、订单状态变更、支付回调后的异步处理都是走 Kafka。核心价值是削峰：大量设备同时上报，不可能同步一条条写库；先丢进 Kafka，消费者按能力消费，把数据库压力抹平。

面试答题话术 「我们用 MQ 主要是削峰和解耦。设备上报、订单状态变更量很大而且有突发，同步处理会把库打爆，所以先进 Kafka 异步消费。代价是引入了消息丢失和重复的问题，所以消费端必须做幂等。」

11. 消息丢失怎么解决 ★★★ 【简历亮点，高频追问】 ​

通俗理解 分三个环节堵：

  1. 生产者丢：发的时候网络挂了 → 用发送确认（ack）/ 重试 / 事务消息。
  2. MQ 自己丢：没持久化就宕机 → 开持久化 + 多副本（主从）。
  3. 消费者丢：消息收到还没处理完就挂 → 关掉自动提交，改成处理完手动 ack。

我的项目关联真实经验：这套「生产确认 + broker 持久化多副本 + 消费手动提交」是我们的标配。对账场景最怕丢消息，所以消费端一律手动提交，处理成功才提交位移。这是线上一直在用的方案。

面试答题话术 「消息丢失分三段防：生产者用发送确认加重试，broker 开持久化和多副本，消费者关自动提交、处理完手动 ack。核心是保证『至少一次』投递。我们在支付、对账这类消息上就是手动提交，宁可重复也不能丢。」

12. 消息重复消费怎么解决 ★★★ 【简历亮点，高频追问】 ​

通俗理解 因为保证「至少一次」投递，加上网络重试，重复是天然的、避不开的。MQ 本身保证不了不重复，只能靠消费端做幂等。 常用幂等手段：数据库唯一索引（插入冲突就忽略）、Redis setnx 记录处理过的消息 id、状态机（订单已支付就跳过）。

我的项目关联真实经验：充电订单的状态流转就是典型的状态机 —— 一条「充电结束」的消息重复消费，第二次会被状态判断挡掉。支付回调同理，用唯一索引 + 状态判断防重复扣款。这是我们线上真在用的设计，也是面试最容易被追问的点。

面试答题话术 「至少一次投递必然可能重复，所以幂等只能消费端做。我们的做法是：订单走状态机，已经结束的订单再收到消息直接跳过；支付相关用唯一索引兜底。原则就是——不假设消息只来一次。」

13. 消息顺序消费 ★★☆ ​

通俗理解 要顺序就两点：同一业务的消息发到同一个分区/队列，消费者单线程消费。Kafka 只保证分区内有序。 全局有序只能用一个队列 + 单消费者，性能很差，一般没必要。

我的项目关联 我们只需要保证「同一个订单/同一把枪」的消息有序，不是全局有序，所以按 key 哈希到同一分区就够了。

面试答题话术 「顺序只在同一个分区内保证，做法是按业务 key 哈希到同一分区、单线程消费。全局有序性能太差，一般只要同一订单内有序就够了。」

14. 消息积压怎么解决 ★★☆ ​

通俗理解 方向就三个：加消费者/提并发、优化消费逻辑（批处理、减少 IO）、临时分流到新 topic。前提是先看消费者是不是卡住了。

我的项目关联 通用坑。我们目前量级没出现严重积压，但监控里是会对消费延迟告警的。

面试答题话术 「积压先查是不是消费卡了，然后加消费者、提并发、优化消费逻辑、必要时开新 topic 分流。核心是先定位瓶颈再扩容。」

15. 死信队列、延迟消息 ★★☆ ​

通俗理解 死信队列：消息重试到上限、过期了、队列满了，会进死信队列，用来人工排查和告警。延迟消息：消息延迟一段时间才投递，RocketMQ 原生支持，RabbitMQ 用 TTL + 死信模拟，Kafka 要自己实现。

我的项目关联限时订单的超时取消就跟这个相关 —— 不过我们不是靠 MQ 延迟消息，而是延迟消息 + 定时任务兜底（08 笔记里详细讲了）。

面试答题话术 「死信队列存重试失败或过期的消息，用来告警和人工补偿。延迟消息可以拿来做订单超时取消，但只靠延迟消息不够稳，得有定时任务兜底。」

16. Kafka、RocketMQ、RabbitMQ 对比 ★★☆ ​

通俗理解

  • Kafka：大数据/日志/高吞吐场景，性能最强，事务和延迟消息相对弱。
  • RocketMQ：业务消息，支持事务消息、原生延迟消息，Java 生态。
  • RabbitMQ：通用、协议标准（AMQP），吞吐中等。

我的项目关联 我们选 Kafka 是因为设备上报数据量大、吞吐要求高，对事务消息和延迟消息没强需求（超时用定时任务兜底）。

面试答题话术 「Kafka 吞吐最高，适合数据量大、日志/流场景；RocketMQ 业务消息能力强，有事务消息和延迟消息；RabbitMQ 通用、生态成熟。我们选 Kafka 就是冲吞吐，业务上的超时兜底用定时任务解决。」

17. 缓存设计模式 ★★★ ​

通俗理解

  • Cache Aside（最常用）：读先查缓存、未命中查库回填；写先更库再删缓存。
  • Read Through：查库回填的逻辑封装在缓存组件里，应用不感知数据库。
  • Write Through：写的时候缓存和库同步更新，一致性好但写开销大。
  • Write Behind：只写缓存，异步批量刷库，性能最高但最可能丢数据。

我的项目关联 我们实际就一种：Cache Aside。其余三种属于了解概念，面试提一下区别就够。

面试答题话术 「我们用的是旁路缓存 Cache Aside，读回填、写删缓存。Write Through 和 Write Behind 属于了解——前者同步写库一致性好但慢，后者异步批量写快但可能丢数据，一般业务不会选。」

18. Redis Pipeline 的好处 ★★☆ ​

通俗理解 把多条命令打包一次发过去，把 N 次网络往返（RTT）变成 1 次。 注意：Pipeline 不是原子操作，命令之间可能被别的客户端插进来；要原子得配事务 MULTI/EXEC。

我的项目关联 批量查设备状态时用过，就是减少网络往返。我们没做原生化，属于常规优化。

面试答题话术 「Pipeline 就是把多条命令打包发，省网络往返时间。要注意它不是原子的，要原子得配事务。适合批量写、批量查的场景。」

19. Redis 和 HashMap 的区别 ★★☆ ​

通俗理解 Redis 是独立部署的分布式缓存服务，走网络，能跨进程跨机器共享、有持久化和过期。HashMap 是 JVM 里的本地数据结构，单机单进程，重启就没了，也不共享。

我的项目关联 认知层面的东西。多实例部署的服务必须用 Redis 共享数据，本地 HashMap 只能放配置类只读数据。这个点跟 04 笔记里「单例 Bean 里放 HashMap 当缓存翻车」是同一个道理。

面试答题话术 「本质区别是 Redis 是独立服务、能跨机器共享还有持久化；HashMap 是 JVM 内的，多实例之间不共享。我们多副本部署，所以共享数据必须走 Redis，本地 Map 只能放只读配置。」

20. Redis、本地缓存（Caffeine）、Memcached 怎么选 ★★☆ ​

通俗理解

  • 需要跨服务共享、要持久化、要丰富数据结构 → Redis。
  • 单机内热点数据、要纳秒级低延迟、不用共享（配置、字典）→ 本地缓存。
  • 常见组合：本地缓存做一层，Redis 做二层，减少网络开销。
  • Memcached 只有简单 KV、无持久化，现在基本被 Redis 取代。

我的项目关联 字典、协议参数这类只读数据我们走本地缓存；需要跨实例一致的走 Redis。两级缓存的一致性问题要留意。

面试答题话术 「共享数据用 Redis，单机热点和只读字典用本地缓存，两者可以组合成两级。Memcached 现在基本被 Redis 替代了。」

21. Redis 内存用完了会发生什么 ★★★ 【简历亮点，高频追问】 ​

通俗理解 看淘汰策略：默认 noeviction 的话，内存满了写命令直接报错，读还能用；配了 allkeys-lru 之类就会淘汰旧 key 继续写。 最危险的是没配 maxmemory —— Redis 会一直吃内存直到被系统 OOM Killer 杀掉。

我的项目关联真实关注点：容器里跑的服务最怕被 OOM Killer 干掉（02 笔记里 JVM 也讲过这个）。Redis 同理，我们一定会显式配 maxmemory，不让它把宿主机内存吃光。

面试答题话术 「内存满的行为由淘汰策略决定：noeviction 写报错、lru 就淘汰旧数据。真正的坑是不设 maxmemory，Redis 会把机器内存吃光然后被系统杀掉。所以我们线上一定显式设上限和策略。」

22. MQ 部署单机还是集群、高可用怎么保证 ★★★ ​

通俗理解 生产必须集群。Kafka 靠 partition 多副本（leader + follower）自动选主；RocketMQ 靠主从 + NameServer 集群；RabbitMQ 用镜像队列或 Quorum Queue。

我的项目关联 我们 Kafka 是多副本部署的。真实踩过的方向：单副本时 broker 一挂消息就丢，必须把副本数设够、且 acks 配置到位，这是上线前要确认的。

面试答题话术 「生产必须集群。Kafka 是多副本加自动选主，副本数和 acks 配置要配对，不然后面数据丢了都发现不了。我们上线前专门确认过这两个配置。」

23. 消息队列的延时、过期失效问题 ★★★ ​

通俗理解 消息设了 TTL 又一直没人消费，过期进死信，导致该处理的业务没处理。 解法：死信队列兜底做补偿/告警、监控积压及时扩容、别设过短 TTL。

我的项目关联 通用坑。我们的做法是不依赖 MQ 的 TTL 做兜底，关键业务用定时任务扫表补偿，避免「消息过期了业务就静默丢了」。

面试答题话术 「消息过期失效的本质是该处理的业务静默丢了。解法是死信队列兜底加监控告警，更重要的是关键业务别只依赖 MQ，要用定时任务兜底。」

24. 如果让你写一个消息队列，如何架构 ★★★ ​

通俗理解 设计题，讲清模块就行：存储（顺序写日志）、分区（并行 + 局部顺序）、网络通信（高性能框架如 Netty）、投递与位移管理、多副本高可用、可靠投递（ack + 重试）。 亮点：顺序写 + 页缓存 + 零拷贝提升吞吐。

我的项目关联这个题我有个天然优势 —— 我在 T-CEC 互联互通网关里就是用 Netty 做长连接接入的，对「高性能网络 + 协议编解码 + 连接管理」是真实经验。虽然没写过 MQ，但网络层这块能讲得很实。

面试答题话术 「它的核心模块是：顺序写日志做存储、分区做并行、Netty 做网络层、offset 管进度、多副本做高可用。Kafka 快的关键是顺序写加页缓存加零拷贝。网络这块我有实际经验——我们的协议网关就是 Netty 做的长连接接入，所以高并发连接处理我比较有体感。」

25. Redis 慢查询怎么找、怎么优化 ★★★ 【简历亮点，高频追问】 ​

通俗理解 找：配 slowlog-log-slower-than 阈值，用 slowlog get 看慢命令，也可以用 latency monitor。 优化：禁用 keys * 改 scan、拆大 key、异步 unlink 删大 key、用 pipeline、调持久化策略。

我的项目关联真实排查过。现象是接口偶发变慢，查下来是某个大 key 操作阻塞了单线程。定位手段就是 slowlog，修复是拆 key + 改 unlink，之后就没再出现。这条是线上真实排查过的。

面试答题话术 「Redis 慢的根因是单线程，一个慢命令会卡住后面所有请求。定位靠 slowlog。我们真遇到过一次，接口偶发变慢，slowlog 里看到是在操作大 key，拆了 key、删除改成 unlink 就好了。」

26. Redis 性能优化 ★★★ ​

通俗理解 按层看：内存（淘汰策略、控制大 key）、命令（避开 O(n)、用 scan/pipeline）、网络（pipeline、6.0 多线程 IO）、持久化（AOF everysec + 及时重写）、架构（主从读写分离、Cluster 分片、热点 key 本地缓存）、参数（maxmemory、连接池）。

我的项目关联 我们实际做的主要是：控制大 key、连接池调优、热点数据本地缓存。Cluster 暂时没上。

面试答题话术 「优化我分几层说：命令层避开慢命令和大 key，网络层用 pipeline，架构层主从读写分离加热点本地缓存，参数层设好 maxmemory 和连接池。我们主要做的是大 key 控制和连接池调优。」

附：一句话速记（可以跳过 ★☆☆） ​

  • Redis 事务（MULTI/EXEC）：多条命令打包执行，但不支持回滚，某条失败其余照常执行，所以基本没人拿它当事务用。
  • Redis 发布订阅：能广播但消息不持久化、不可靠，业务里一般用 Kafka 代替。
  • Memcached：纯内存 KV、多线程、无持久化，现在基本被 Redis 取代，了解概念即可。
