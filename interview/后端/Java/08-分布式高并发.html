分布式 & 高并发 ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

1. CAP 与 BASE ★★★ ​

通俗理解CAP：一致性、可用性、分区容错。分布式系统里网络分区不可避免，所以 P 必须保，只能在 C 和 A 之间取舍，三者不能同时要。BASE 是对 CAP 的妥协：基本可用、软状态、最终一致——不强求一致，接受「过一会儿才一致」。CP 例子是 ZooKeeper、etcd；AP 例子是 Eureka。

我的项目关联 充电、支付这类业务里，我的选择是「核心链路要一致，非核心链路最终一致」。比如扣费、订单状态要强一致；而 T-CEC 互联互通上报、统计报表这类，用消息 + 重试做到最终一致就够了，不追求跨系统强一致。

面试答题话术 「CAP 三者不能同时满足，分布式下 P 必须保，所以是在 C 和 A 之间取舍。BASE 是退一步要最终一致。项目里我按链路分：扣费、订单状态这种核心链路要强一致；互联互通上报、报表这种用消息加重试做最终一致，不硬追强一致，这样可用性更好。」

2. 分布式事务方案 ★★★ ​

通俗理解 跨服务跨库就不能用本地事务了。常见方案：2PC（强一致但同步阻塞、协调者单点）、TCC（Try 预留 / Confirm 确认 / Cancel 取消，灵活但侵入业务）、SAGA（长事务拆多个本地事务 + 补偿）、本地消息表（本地事务 + 消息表，靠定时任务重试）、事务消息（RocketMQ 半消息）、最大努力通知（配合对账兜底）。中间件就是 Seata。

我的项目关联我们的首选不是强一致的分布式事务，而是「本地事务 + 消息 + 对账补偿」。 比如支付成功后要改订单状态、通知业务方，就是本地事务落库 + 发消息，发失败靠重试和定时对账兜底。原因很实际：充电业务量大，2PC/TCC 的成本和复杂度划不来，最终一致更稳。说明一下：我们没上 Seata，走的是轻量的消息 + 对账路线。

面试答题话术 「方案有 2PC、TCC、SAGA、本地消息表、事务消息，中间件是 Seata。2PC 强一致但阻塞、有单点；TCC 灵活但侵入业务。项目里我没用 Seata，走的是本地事务加消息、再加定时对账兜底，也就是最终一致，因为业务量大、对账本来就存在，这样最稳也最省。」

3. 分布式 ID 生成 ★★★ ​

通俗理解UUID 简单但无序、做数据库主键会页分裂；数据库自增有单点和性能瓶颈；号段模式是批量取一段缓存在本地；雪花算法是主流：1 位符号 + 41 位时间戳 + 10 位机器 id + 12 位序列号，本地生成、趋势递增、高性能。雪花的坑是依赖时钟，时钟回拨会生成重复 ID。

我的项目关联 订单号、流水号我们用雪花或号段模式生成，好处是不依赖数据库、性能高、趋势递增（对 B+ 树友好）。时钟回拨的坑属于通用坑，我们规范上做了「回拨时等待或换机器 id」的防护。

面试答题话术 「主流是雪花算法：时间戳加机器 id 加序列号，本地生成、趋势递增、性能高，做 MySQL 主键也不容易页分裂。UUID 无序、不适合做主键；数据库自增有单点问题。雪花要注意时钟回拨会重复，得处理。项目里订单号就是这么生成的。」

4. 限流算法：令牌桶、漏桶、滑动窗口 ★★★ ​

通俗理解固定窗口简单但有临界突发问题；滑动窗口细分窗口解决突变；漏桶固定速率流出、严格平滑但扛不住突发；令牌桶按固定速率放令牌、桶满为止、有令牌就能过，所以允许一定突发，最常用。工具：Sentinel、Guava RateLimiter、Redis + Lua、网关限流。

我的项目关联 我们限流主要在两个地方：网关/接口层用令牌桶限制单用户或单接口的请求频率；调用第三方（运营商、高德）时用信号量或令牌桶限制并发，防止把对方打挂。

面试答题话术 「固定窗口有临界问题，滑动窗口解决它；漏桶是严格匀速、不扛突发；令牌桶允许突发，最常用。项目里接口层用令牌桶限制请求频率，调第三方接口时用限流控制并发，别把下游打挂。」

5. 熔断、降级、隔离 ★★★ ​

通俗理解熔断是「被动应对」：依赖服务错误率超阈值就直接返回兜底、快速失败，避免级联雪崩（关闭 → 打开 → 半开）。降级是「主动关功能」：压力大时关掉非核心功能，保核心链路。隔离是用线程池/信号量把不同依赖分开，防止一个依赖占满资源拖垮整体。

我的项目关联 调第三方运营商、高德的接口我们做了超时 + 熔断 + 降级：对方超时就返回兜底数据（比如用上次缓存的位置），不影响我们的核心充电流程。隔离上，我们会给不同的外部调用分配独立线程池，避免互相影响。

面试答题话术 「熔断是被动的，依赖出错率高了就快速失败、防雪崩；降级是主动关非核心功能保核心。隔离是给不同依赖分独立的线程池，别一个拖垮全部。项目里调第三方接口都配了超时加熔断降级，对方挂了我们就返回兜底数据，不影响充电主流程。」

6. 接口幂等性 ★★★ 【简历亮点，高频追问】 ​

通俗理解幂等就是「同一个请求执行多次，结果和执行一次一样」。为什么需要：网络重试、用户重复点击、消息重复投递都会导致重复请求。方案：唯一索引（数据库兜底）、Token 机制（提交前取 token，提交时校验并删除）、状态机（只有特定状态能流转）、乐观锁（版本号）、Redis 分布式锁。

我的项目关联这是支付和对账的核心问题。 支付回调、互联互通上报、订单状态变更都必须幂等。我们的做法是「唯一约束 + 状态机 + 分布式锁」三层兜底：比如支付回调带订单号唯一约束，重复回调直接忽略；状态机保证「只有待支付才能改成已支付」。说明一下：回调重复投递是这类业务必然会遇到的（通用坑级别），我们是从设计上就按幂等做的，不是踩了坑才补。

面试答题话术 「幂等就是重复执行结果不变。方案有唯一索引、Token、状态机、乐观锁、分布式锁。项目里支付回调和互联互通上报都是强幂等的——用唯一约束加状态机加分布式锁三层兜底，比如支付回调重复来直接忽略，状态机保证只有待支付能变已支付。这类业务回调重复是常态，所以我们是设计阶段就做了。」

7. 一致性哈希 ★★★ ​

通俗理解 普通取模哈希的问题是：节点数一变，几乎所有 key 都要重新映射。一致性哈希把节点和 key 都放到一个环上，key 顺时针找到的第一个节点就是它的归属；节点增删只影响相邻一小段数据。虚拟节点是为了解决数据倾斜——每个真实节点映射成多个虚拟节点，分布更均匀。

我的项目关联 我们用 Redis 集群和本地缓存分片时会用到这个思路。属于了解即可：知道「一致性哈希是为了减少节点变动时的数据迁移」就够了，具体实现不用自己写，客户端和中间件都封装好了。

面试答题话术 「普通取模在节点增减时几乎全部 key 要重映射；一致性哈希是把节点和 key 放环上，key 顺时针找节点，节点变动只迁移相邻一小段。虚拟节点是解决分布不均。项目里用的是封装好的客户端，我理解原理就行。」

8. 秒杀系统设计 ★★★（场景题） ​

通俗理解 核心是「把流量挡在数据库之前」：前端限流 + CDN 静态化；Nginx/网关限流；Redis 预扣库存（用 Lua 保证原子，防超卖）；消息队列削峰；数据库乐观锁 where stock > 0 兜底；一人一单防风控。链路是：点击 → CDN → 网关限流 → Redis 预扣 → MQ → 生成订单 → 落库 → 异步扣真实库存。

我的项目关联 充电业务没有典型秒杀，但**「限时优惠充电券秒杀」这类营销活动是类似的**。我们复用的就是这套思路：Redis 原子预扣名额、MQ 异步落单、数据库唯一约束防一人多单。注意说清：这是营销活动的设计思路，不是我们充电主流程。

面试答题话术 「秒杀的关键是把流量挡在 DB 前面：CDN 静态化、网关限流、Redis 用 Lua 原子预扣防超卖、MQ 削峰、数据库乐观锁兜底。我们项目里没有典型秒杀，但营销发券活动用的是同一套思路：Redis 预扣 + MQ 异步 + 唯一约束防重复领。」

9. 分布式锁的实现与问题 ★★★ 【简历亮点，高频追问】 ​

通俗理解 Redis 分布式锁：SET key value NX EX 加锁，释放时要用 Lua 校验 value 再删（防止误删别人的锁），再加看门狗自动续期（防止业务没跑完锁就过期）。ZooKeeper 分布式锁用临时顺序节点，强一致但性能低。Redis 锁的隐患是主从切换时锁可能丢。

我的项目关联 我们用 Redisson 做分布式锁，典型场景是「同一充电桩/同一订单的并发操作串行化」——比如同一把枪的下发指令、同一订单的状态变更。这里的坑是必须讲清楚的：① 释放锁要校验持有者，不然会误删别人的锁；② 业务执行时间可能超过锁过期时间，所以要有续期（Redisson 的看门狗）；③ 加锁要设等待超时，避免线程一直卡。这些属于通用坑，我们靠 Redisson 封装规避。

面试答题话术 「Redis 分布式锁是 SET NX EX，释放用 Lua 校验 value 再删，防误删；还要有看门狗续期，防业务没跑完锁就过期。ZK 锁是临时顺序节点，强一致但性能低。项目里用 Redisson，场景是同一桩、同一订单的并发操作串行化。三个点必须注意：释放校验持有者、自动续期、加锁超时。」

10. 服务治理：注册发现、配置中心、网关 ★★★ ​

通俗理解注册发现：服务启动注册到注册中心，调用方拉实例列表 + 心跳续约，再配负载均衡去调。配置中心：集中管配置、能动态刷新。网关：统一入口、路由、鉴权、限流、灰度。

我的项目关联 我们的微服务之间就是注册发现 + 配置中心这套。再强调一次别混淆：这里是 HTTP/RPC 层的服务治理网关；我们还有个基于 Netty 的 TCP 协议网关用来接充电桩，两者不是一回事。

面试答题话术 「注册发现是服务注册加心跳续约加拉列表加负载均衡调用；配置中心集中管理还能动态刷新；网关做统一入口、鉴权、限流。需要区分的是，服务治理网关是 HTTP 层的，我们项目里还有一个 Netty 的 TCP 协议网关专门接充电桩，两个完全不同。」

11. 分布式链路追踪 ★★☆ ​

通俗理解 目的是把一次请求跨多个服务的调用串起来，定位瓶颈和故障。核心是 traceId 贯穿整条链路，span 表示一次调用。方案有 SkyWalking、Zipkin、Jaeger。

我的项目关联 我们用 traceId 贯穿网关到业务服务，日志里都带上，出事能顺着一个 traceId 把全链路捞出来。注意：跨线程要透传 traceId（这里会碰到 ThreadLocal 那个坑），跨服务走请求头。这条属于了解即可。

面试答题话术 「链路追踪就是 traceId 贯穿全链路，span 表示一次调用，工具是 SkyWalking 这类。项目里我们用 traceId 串日志，注意跨线程要透传、跨服务走请求头。」

12. 缓存双写一致性与读写分离 ★★☆ ​

通俗理解 缓存和数据库的一致性常用 Cache Aside：先更库、再删缓存。为了防「删缓存失败」和「并发读写」，加延迟双删或者订阅 binlog 异步删。读写分离就是主写从读，注意主从延迟，实时性要求高的读强制走主库。

我的项目关联 我们缓存策略统一是「更新数据库 + 删缓存」，不是更新缓存（更新缓存更容易不一致）。对实时性要求高的读（比如刚下完单查订单）强制走主库。这块在后面对账、桩状态缓存上都用。

面试答题话术 「缓存一致性我用 Cache Aside：先更新库再删缓存，不更新缓存。要更稳就延迟双删或订阅 binlog。读写分离时，写完立刻要读的场景强制走主库，避免主从延迟读到旧数据。项目里桩状态、配置这些缓存都是这个策略。」

13. 幂等 + 分布式锁 + 限流在订单场景的综合运用 ★★☆ ​

通俗理解 下单这条链路是把多个手段叠起来：限流（防刷）→ 幂等（防重复提交）→ 分布式锁（防并发扣减）→ 库存扣减（乐观锁）→ 生成订单 → 消息通知。

我的项目关联 我们的下单/启动充电流程就是这个套路：限流防刷、Token 防重复提交、按订单加分布式锁、库存/余额乐观锁扣减、最后发消息。这是面试里很加分的一条，能把多个知识点串成一个真实链路讲。

面试答题话术 「下单链路我一层层讲：先限流防刷，再 Token 做幂等防重复提交，然后按订单加分布式锁防止并发扣减，库存或余额用乐观锁，最后生成订单发消息。项目里启动充电下单就是这个流程，多个手段叠加保证高并发下不出错。」

14. 亿级黑名单快速定位 URL（布隆过滤器）★★★ ​

通俗理解布隆过滤器 = 一个比特数组 + k 个哈希函数。加元素就把 k 个位置置 1；查询时如果有一位是 0，那「一定不存在」；如果全是 1，是「可能存在」（有误判）。特点是极省空间（亿级也就几百 MB）、快，但不支持删除。用法是：布隆过滤器做第一层拦截，命中的再去数据库精确确认。

我的项目关联 我们目前没有亿级黑名单这种场景，这条属于面试场景题，了解原理即可。理解它的价值在于：用极小的空间换「一定不存在」的快速判断。

面试答题话术 「布隆过滤器是比特数组加多个哈希，判断结果是『一定不存在』或『可能存在』，有误判但不漏判，特别省空间。因为是布隆过滤器做第一层，命中的还要回数据库二次确认。不支持删除，要删就用计数布隆或定期重建。项目里暂时没这个量级，属于场景题。」

15. 设计短网址系统 ★★★（场景题） ​

通俗理解 核心是「长 URL ↔ 短码」的映射。短码生成两条路：哈希 + 截断（要处理冲突），或者发号器（自增 id 转 Base62，无冲突、推荐）。存储用 MySQL 存映射 + Redis 缓存热点。访问用 302 重定向，因为 302 是临时的、还能统计点击。

我的项目关联 纯场景题，了解即可。答题价值在于：会说「短码生成优先用发号器而不是哈希，因为不用处理冲突」，以及「用 302 不用 301，为了保留统计能力」。

面试答题话术 「短码用发号器最稳：自增 id 转 Base62，无冲突。存储是 MySQL 存映射、Redis 扛热点读。重定向用 302 不用 301，因为 301 会被浏览器缓存、后续不经过服务器，就统计不到点击了。这是场景题，我主要是把生成和重定向这两个点讲清楚。」

16. 限时订单设计（超时未支付取消）★★★ 【项目强相关】 ​

通俗理解 订单创建后限时（比如 30 分钟）没支付就自动取消、释放资源。三种做法：延迟消息（下单发一条延迟消息，到点消费检查状态，没支付就取消，最推荐）、定时任务扫描超时订单（简单但有延迟和扫库压力）、Redis 过期监听（精度和可靠性差，慎用）。关键点：取消要幂等、要回补库存、状态机保证只有待支付能取消。

我的项目关联这个跟我们的充电订单完全对应。 「用户下单后超时未支付要释放充电枪/车位资源」就是典型场景。我们的做法是延迟消息 + 定时任务兜底双保险：延迟消息保证准时触发，定时任务防止消息丢了漏掉。取消操作做幂等，用状态机控制「只有待支付能改成已取消」，同时回补资源。这是项目里的真实设计。

面试答题话术 「限时订单我优先用延迟消息：下单发一条延迟消息，到点检查状态、没支付就取消；再配一个定时任务兜底，防止消息丢了。取消动作要幂等，用状态机限制只有待支付能取消，还要回补库存或资源。项目里充电订单超时释放就是这么做的——延迟消息加定时兜底，加上幂等和状态机。」

17. 设计高并发支付网关 ★★★ 【项目强相关】 ​

通俗理解 关注点七个：安全（签名验签、防重放）、高可用（多节点、限流熔断）、一致性（支付结果与订单一致）、幂等（同一订单不能重复扣款）、异步通知（回调走 MQ、失败重试）、对账（定时和渠道对账、处理差错账）、状态机（状态严格流转）。回调丢了的兜底是「主动查询 + 重试 + 对账」。

我的项目关联这就是我们支付对账 SaaS 的日常。 几个关键点我都能结合实际讲：① 支付回调必须幂等；② 回调可能丢，所以有主动查询兜底 + 定时对账；③ 对账是为了发现掉单和差错账。真实经验：支付回调丢单、状态不一致这类问题是必须靠「回调 + 主动查询 + 对账」三层兜底才能收敛的，单靠回调一定会漏。

面试答题话术 「支付网关我讲几个核心：安全上签名验签、防重放；一致性上靠幂等加对账；回调丢了用主动查询兜底。关键是三层兜底——回调通知、定时主动查询、T+1 对账，只靠回调一定会漏单。项目里支付对账就是这么设计的，对账专门处理掉单和差错账。」

18. 设计打车服务 ★★☆（场景题） ​

通俗理解 核心是「位置存储 + 附近检索 + 派单」。位置用 GeoHash/空间索引，找附近司机用 Redis GEO；派单防重复用分布式锁或状态机；位置上报用 WebSocket/MQ 削峰。

我的项目关联 纯场景题，了解即可。但有个可迁移的点：GeoHash 的思路跟「找附近充电站」是一样的——我们查附近场站也是按经纬度做距离检索，只不过数据量和实时性没打车那么高。

面试答题话术 「打车的核心是位置检索和派单。位置用 GeoHash 编码，相近位置前缀相同，查附近司机就用 Redis GEO；派单防重复用分布式锁加状态机。这个思路跟找附近充电站是一样的，只是数据量小一些。属于场景题，我理解主线就行。」

19. 设计视频流系统 ★★☆ ​

通俗理解 存储用对象存储 + CDN 分发；上传做分片上传、多码率转码、审核；播放走 CDN、支持断点续传和自适应码率；元数据存库里、读多用缓存。

我的项目关联 跟项目无关，了解即可。记住一句话结论：视频分发的核心是「对象存储 + CDN + 多码率转码」。

面试答题话术 「视频系统核心是对象存储加 CDN 分发，上传要分片和转码，播放靠 CDN 加自适应码率。重点是 CDN 就近分发减轻源站压力、多码率适配不同网络。这跟我的项目没直接关系，属于了解。」

20. 实时统计 DAU/WAU/MAU（Bitmap）★★★ ​

通俗理解 用 Redis Bitmap：一个用户一个 bit 位，setbit 记录当天活跃，bitcount 统计当天活跃数。周活/月活就是把多天的 bitmap 做 bitop OR 求并集再统计。好处是极省内存（1 亿用户约 12MB）、能去重、位运算快。

我的项目关联 我们用类似思路做「日活充电用户数」这类统计。前提条件：用户 id 要能映射成连续整数，不然稀疏数据用 Bitmap 反而浪费——那种情况用 HyperLogLog。

面试答题话术 「日活用 Bitmap，一个用户一个 bit，setbit 记录、bitcount 统计；周活月活就把多天 bitmap 做 OR 再统计。好处是省内存还能去重。前提是用户 id 能映射成连续整数，稀疏数据就改用 HyperLogLog。项目里活跃用户统计就是这个思路。」

21. 统计网站每个网页的 UV（HyperLogLog）★★★ ​

通俗理解HyperLogLog 是概率数据结构，用极小内存（约 12KB）估算独立元素个数（UV），标准误差约 0.81%。每个网页每天一个 key，pfadd 记录访客、pfcount 得 UV。相比 Set，它是用「近似值」换「固定的小内存」。

我的项目关联 需要「近似去重计数」且用户 id 不连续时用它，比如统计某活动的独立访问用户数。选型口诀：id 连续用 Bitmap，稀疏/超大去重用 HyperLogLog，要精确就用 Set（但费内存）。

面试答题话术 「UV 用 HyperLogLog，pfadd 记录、pfcount 统计，12KB 左右就能算千万级去重，误差 0.81%。它和 Bitmap 的区别是：Bitmap 精确但内存跟最大 id 成正比，HLL 近似但内存固定。选型就是 id 连续用 Bitmap，稀疏去重用 HLL，要精确就 Set。」

22. 10 亿数量高效排序（外部排序）★★☆ ​

通俗理解 内存装不下就用外部归并排序：先分块，每块装进内存排好序落盘；再多路归并把多个有序块合并成一个有序大文件，用堆维护每路当前最小值。分治 + 归并，内存可控，瓶颈在磁盘 IO。

我的项目关联 纯算法场景题，了解即可。实际我们的大数据量统计直接交给 ClickHouse/InfluxDB 这类引擎，不会自己写外部排序。

面试答题话术 「10 亿数据超内存，得用外部归并排序：分块内存内排序落盘，再堆做多路归并合成一个大文件。瓶颈是磁盘 IO，优化就是加大内存块、并行。项目里这种量级的统计我们直接用 ClickHouse 这类引擎，不自己写排序。」

23. 为什么要系统拆分、如何拆分 ★★★ ​

通俗理解 单体随业务变大有几个问题：编译部署慢、代码耦合、团队协作冲突、故障影响面大、没法独立扩容。拆分后能独立部署、独立扩展、故障隔离。怎么拆：按业务域拆（识别核心领域，参考 DDD 限界上下文），每个服务独立数据库，先拆边缘、耦合低的服务；配套注册中心、配置中心、网关、链路追踪。别过度拆，小规模先单体。

我的项目关联 我们就是按业务域拆的：后台管理服务、App 服务、互联互通服务（yld-tcec）、协议网关服务，各自独立数据库。换来的代价是跨服务一致性和对账要额外处理。建议别吹：我们不是拆得特别细的微服务，是按业务线合理拆，规模匹配。

面试答题话术 「拆分的动机是单体大了之后部署慢、耦合高、故障影响面大。拆法是按业务域拆、每个服务独立库，先拆边缘和低耦合的。但别过度拆，拆太细分布式复杂度剧增。项目里我们按业务线拆了后台、App、互联互通、协议网关几个服务，规模匹配，不是那种特别细的微服务。」

24. 设计一个类 Dubbo 的 RPC 框架 ★★★ 【简历亮点，高频追问】 ​

通俗理解 核心六块：服务发现（注册中心）、动态代理（屏蔽远程调用）、序列化、网络通信（Netty + 自定义协议，报文头有魔数、长度、序列化方式、请求 id）、负载均衡、容错（超时重试熔断）。调用链路：客户端代理拦截 → 从注册中心选实例 → 序列化 → 网络发送 → 服务端反序列化 → 反射调用 → 返回。

我的项目关联这块跟我们的协议网关强相关，能讲。 T-CEC 互联互通和充电桩接入用的都是「自定义协议的 TCP 长连接」，跟 RPC 的自定义协议思路一样——都要设计报文头（魔数、长度、序列化方式），都用 Netty 做编解码。不同的是 RPC 面向内部服务调用，我们的协议面向设备和外部平台。别混淆：我不会说自己手写过 RPC 框架，而是说「自定义协议 + Netty 编解码这套我做过，RPC 的原理我理解」。

面试答题话术 「RPC 框架核心是服务发现、动态代理、序列化、Netty 网络通信、负载均衡、容错。协议要自定义报文头，有魔数、长度、序列化方式、请求 id。我们项目里没有自研 RPC 框架，但自定义协议加 Netty 编解码这套我做过——互联互通和桩接入就是自定义 TCP 协议，报文头设计和 RPC 是一个思路，区别是面向设备和外部平台而不是内部服务。」

25. Dubbo 工作原理 ★★☆ ​

通俗理解 角色：Provider、Consumer、Registry、Monitor。流程：Provider 注册到注册中心 → Consumer 订阅并缓存服务列表 → 按负载均衡选实例 → 发起远程调用 → 服务端执行返回。注册中心挂了也不影响调用，因为 Consumer 本地有缓存的服务列表。

我的项目关联 我们服务间调用不是 Dubbo，这条了解即可。但「注册中心挂了还能调，因为本地有服务列表缓存」这个点跟我们的注册发现是相通的。

面试答题话术 「Dubbo 是 Provider 注册、Consumer 订阅并缓存列表、按负载均衡调。一个常考点：注册中心挂了还能调，因为消费端本地缓存了服务列表，只是感知不到实例变化。我们项目用的不是 Dubbo，但注册发现这块思路一样。」

26. Dubbo 负载均衡策略 ★★☆ ​

通俗理解随机（默认，按权重）、轮询（按权重）、最少活跃数（挑当前请求最少的）、一致性哈希（同一参数路由到同一实例，做会话粘性）。

我的项目关联 了解即可。一句话：一般用随机或轮询，需要「同一请求固定打到一台机器」时才用一致性哈希。

面试答题话术 「Dubbo 默认随机，还有轮询、最少活跃数、一致性哈希。一致性哈希适合需要同一请求打到同一台机器的场景，比如缓存或会话保持。这是了解性的点。」

27. Dubbo 服务治理与降级 ★★☆ ​

通俗理解服务治理包括路由规则、灰度、权重调整、限流熔断、监控、链路追踪。服务降级是依赖不可用时返回兜底。容错策略有 Failover（失败重试，默认）、Failfast、Failsafe、Failback、Forking。

我的项目关联 了解即可。核心就一句：容错默认是失败重试，但写操作重试要小心，必须配合幂等，不然会重复扣款。

面试答题话术 「服务治理是路由、灰度、限流熔断、监控。降级是依赖挂了返回兜底。容错默认 Failover 失败重试，但重试写操作一定要配幂等，不然会重复执行。项目里我们没上 Dubbo，这些是了解。」

28. Dubbo SPI 与 Java SPI 的区别 ★★☆ ​

通俗理解Java SPI 靠 META-INF/services 文件，ServiceLoader 一次性把所有实现都加载出来，不能按名取、不能懒加载。Dubbo SPI 用 META-INF/dubbo/ 里「key=实现类」的形式，支持按名获取、懒加载、默认实现、自适应扩展（@Adaptive）、包装和激活。

我的项目关联 了解即可。之前讲类加载时提过「破坏双亲委派和 SPI」，这里是同一个知识点的延伸。

面试答题话术 「Java SPI 一次性加载所有实现，不能按名取；Dubbo SPI 用 key=实现类的配置，能按名获取、懒加载、支持默认值和自适应扩展，所以更灵活也更省资源。这是了解性的点。」

29. 为什么做分库分表 ★★☆ ​

通俗理解 单表上千万行后查询变慢、索引维护贵、DDL 慢；单库连接数、容量、IO 到瓶颈。分库分表就是横向扩展，让每个库/表数据量变小、压力分散。但代价是分布式事务、跨库 join、分布式主键、路由路由复杂度。

我的项目关联 跟 05-MySQL 那条一样：我们现在靠索引优化 + 冷热归档 + 读写分离，还没到必须分表。顺序别忘了：索引 → 缓存 → 读写分离 → 最后才是分库分表。

面试答题话术 「分库分表是单表、单库到瓶颈后的横向扩展手段，但会引入分布式事务、跨库 join、分布式主键这些复杂度。所以它是最后手段，前面还有索引优化、缓存、读写分离。项目里我们现在是索引加归档在撑，还没分表。」
