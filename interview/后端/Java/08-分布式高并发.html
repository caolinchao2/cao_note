分布式 & 高并发 ​

常问等级：★★★ 高频必考 / ★★☆ 中频常见 / ★☆☆ 低频了解 深度标准：每个考点讲清「是什么 → 为什么 → 追问应对 → 易错点」。

CAP 定理与 BASE 理论 ★★★ ​

CAP ​

  • Consistency（一致性）：所有节点同一时间数据一致。
  • Availability（可用性）：每个请求都能得到响应（不保证最新）。
  • Partition tolerance（分区容错性）：网络分区时系统仍能工作。
  • 结论：分布式系统必须保证 P（网络分区不可避免），所以只能在 C 和 A 之间取舍，无法三者兼得。

BASE ​

  • Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）。
  • 对 CAP 的权衡：不追求强一致，接受最终一致，保证基本可用。

追问应对 ​

  • 「CP 和 AP 例子？」→ CP 牺牲可用性保证一致（如 ZooKeeper、etcd、Nacos CP 模式）；AP 牺牲强一致保证可用（如 Eureka、Nacos AP 模式）。

分布式事务解决方案 ★★★ ​

为什么需要 ​

  • 单机事务靠数据库本地事务，微服务下跨服务/跨库需分布式事务。

方案 ​

  1. 2PC（两阶段提交）：准备阶段 + 提交阶段；强一致但同步阻塞、协调者单点、性能差。
  2. TCC（Try-Confirm-Cancel）：业务层三段，Try 预留资源、Confirm 确认、Cancel 取消；灵活但侵入业务、实现复杂。
  3. SAGA：长事务拆成多个本地事务 + 补偿，适合长流程、高并发；最终一致。
  4. 本地消息表：本地事务 + 消息表，通过消息驱动后续服务，靠定时任务/重试保证最终一致。
  5. 事务消息（RocketMQ 半消息）：先发半消息，本地事务成功后提交，否则回滚。
  6. 最大努力通知：尽力通知，配合对账/人工兜底。

中间件 ​

  • Seata：AT（自动，无侵入，基于 undo log + 全局锁）、TCC、SAGA、XA 模式。

追问应对 ​

  • 「2PC 有什么问题？」→ 同步阻塞、协调者单点故障、数据不一致风险。
  • 「Seata AT 模式原理？」→ 全局事务协调 + 各服务本地事务 + undo log 回滚 + 全局锁防脏写。

分布式 ID 生成 ★★★ ​

方案对比 ​

  • UUID：本地生成、简单，但无序（不适合做数据库主键，导致页分裂）、过长。
  • 数据库自增：简单但单点、性能瓶颈，不适合分布式。
  • 号段模式（如 Leaf）：从数据库批量取一段 id 缓存，减少访问。
  • 雪花算法（Snowflake）：时间戳 + 机器 id + 序列号，趋势递增、高性能，主流。

雪花算法 ​

  • 结构：1 位符号 + 41 位时间戳 + 10 位机器 id + 12 位序列号。
  • 优点：本地生成、趋势递增、高性能；缺点：依赖时钟，时钟回拨会导致重复 id（需处理）。

追问应对 ​

  • 「时钟回拨怎么处理？」→ 等待时钟追上、抛异常、用备用机器 id、记录上次时间戳。

限流算法：令牌桶、漏桶、滑动窗口 ★★★ ​

算法 ​

  • 固定窗口计数器：一段时间内限固定次数；边界问题（窗口临界突发）。
  • 滑动窗口：细分窗口平滑，解决固定窗口边界问题。
  • 漏桶：固定速率流出，能限制平均速率，但无法应对突发（超出即丢弃）。
  • 令牌桶：固定速率放令牌，桶满停止；能允许一定突发（有令牌即可）。

选择 ​

  • 令牌桶允许突发，适合大多数 API 限流；漏桶严格平滑，适合需要恒定速率的场景。

工具 ​

  • Sentinel、Guava RateLimiter（令牌桶）、Redis + Lua 脚本、网关限流。

追问应对 ​

  • 「令牌桶和漏桶区别？」→ 令牌桶允许突发流量，漏桶严格匀速。

熔断、降级、隔离 ★★★ ​

  • 熔断：依赖服务异常比例超阈值时，直接返回兜底，快速失败，防止级联故障（断路器：关闭→打开→半开）。
  • 降级：系统压力大时，关闭非核心功能，保核心链路。
  • 隔离：线程池/信号量隔离，防止某个依赖占满资源拖垮整体（Hystrix 线程池隔离）。

工具 ​

  • Sentinel、Resilience4j、Hystrix（已停维护）。

追问应对 ​

  • 「熔断和降级区别？」→ 熔断是「被动应对依赖故障」，降级是「主动关功能保核心」。

接口幂等性 ★★★ ​

为什么 ​

  • 网络重试、用户重复点击、消息重复投递导致重复请求，需保证重复执行结果一致。

方案 ​

  • 唯一索引：数据库唯一约束，重复插入失败。
  • Token 机制：提交前先获取 token，提交时校验并删除 token（防重复提交）。
  • 状态机：只有特定状态能流转（如待支付→已支付）。
  • 乐观锁：版本号/条件更新。
  • Redis 分布式锁 / setnx。

追问应对 ​

  • 「哪些操作天然幂等？」→ 查询、删除（按 id）、更新（绝对值）；非幂等如「余额 += 100」。

一致性哈希 ★★★ ​

原理 ​

  • 把节点和 key 都哈希到同一个环上，key 顺时针找到的第一个节点就是它归属的节点。
  • 节点增删时，只影响相邻的一小段数据，最小化迁移。

虚拟节点 ​

  • 每个真实节点映射多个虚拟节点，解决数据倾斜和分布不均。

应用 ​

  • 分布式缓存分片（如 Memcached 客户端）、负载均衡、数据分片。

追问应对 ​

  • 「一致性哈希 vs 普通哈希取模？」→ 取模在节点数变化时几乎所有 key 都要重新映射；一致性哈希只迁移少部分。

高并发场景：秒杀系统设计 ★★★ ​

核心问题与方案 ​

  1. 高并发读/写 → 前端限流、CDN 缓存、Nginx 限流、Redis 预扣库存。
  2. 超卖 → Redis 原子扣减（decr/lua）、数据库乐观锁（update ... where stock > 0）。
  3. 流量洪峰 → 消息队列削峰、令牌桶限流。
  4. 数据库压力 → 读写分离、分库分表。
  5. 防黄牛 → 验证码、限购（一人一单）、风控。
  6. 数据一致性 → 库存扣减 + 订单 + 异步消息 + 补偿。

完整链路 ​

  • 用户点击 → CDN/静态页 → 网关限流 → 秒杀接口 → Redis 预扣库存（原子）→ 消息队列 → 生成订单 → 数据库落库 → 异步扣真实库存。

追问应对 ​

  • 「怎么防超卖？」→ Redis 原子扣减 + 数据库乐观锁/唯一索引兜底。
  • 「热点商品怎么处理？」→ 本地缓存 + Redis 集群 + 分桶/多副本分流。

分布式锁的实现与问题 ★★★ ​

  • 见中间件 Redis 部分：SET NX EX + Lua 释放 + 看门狗续期。
  • 其他：ZooKeeper 临时顺序节点（watch 机制，羊群效应）、数据库唯一索引。

追问应对 ​

  • 「Redis 和 ZK 分布式锁区别？」→ Redis 基于过期时间 + 续期，性能高但主从切换可能丢锁；ZK 基于临时节点，强一致但性能较低。

服务治理：注册发现、配置中心、网关 ★★★ ​

  • 注册发现：服务启动注册到注册中心（Nacos/Eureka），调用方从注册中心拉取实例列表，配合负载均衡。
  • 配置中心：集中管理配置，动态刷新（Nacos Config）。
  • 网关：统一入口、路由、鉴权、限流、灰度。

追问应对 ​

  • 「服务发现怎么实现？」→ 服务注册 + 心跳续约 + 拉取服务列表 + 负载均衡调用。

分布式链路追踪 ★★☆ ​

  • 目的：定位跨服务调用链、性能瓶颈、故障。
  • 方案：SkyWalking、Zipkin、Jaeger。
  • 核心：traceId 贯穿整条链路，span 表示一次调用。

追问应对 ​

  • 「traceId 怎么传递？」→ 通过请求头（如 X-Trace-Id）透传，各服务日志记录。

高并发下的数据一致性：缓存双写、读写分离 ★★☆ ​

  • 缓存双写一致性：见中间件篇（Cache Aside + 延迟双删 + binlog 订阅）。
  • 读写分离：主写从读，注意主从延迟（实时性要求高的读走主库）。

幂等 + 分布式锁 + 限流在订单场景的综合运用 ★★☆ ​

  • 下单流程：限流（防刷）→ 幂等（防重复提交）→ 分布式锁（防并发扣减）→ 库存扣减（乐观锁）→ 生成订单 → 消息通知。
  • 体现：多个手段叠加保证高并发下的正确性与可用性。

亿级黑名单快速定位 URL ★★★ ​

核心 ​

  • 用布隆过滤器（Bloom Filter）判断「某个 URL 是否可能在黑名单中」。

布隆过滤器原理 ​

  • 一个 m 位比特数组 + k 个哈希函数。
  • 加入元素：用 k 个哈希函数算 k 个位置，都置 1。
  • 查询元素：算 k 个位置，若都为 1 → 「可能存在」（可能误判）；若任一为 0 → 「一定不存在」。
  • 特点：省空间（亿级只需几百 MB）、快（O(k)）；有误判率（可通过增大 m、增多 k 降低），不支持删除。

为什么用布隆过滤器 ​

  • 亿级黑名单存内存全量 set 太大；布隆过滤器用极小空间做到「一定不存在」快速拦截，只对「可能存在」的少量再查真实库确认。

追问应对 ​

  • 「布隆过滤器有误判怎么处理？」→ 只做第一层拦截，命中的再去数据库/精确集合二次确认。
  • 「怎么选 m 和 k？」→ 根据数据量和可接受误判率计算；误判率越低 m 越大、k 越接近最优值。
  • 「布隆过滤器支持删除吗？」→ 不支持，需用计数布隆（Counting Bloom）或定期重建。

设计短网址系统 ★★★ ​

需求 ​

  • 长 URL → 短码（如 t.cn/ab3f）；短码 → 重定向到长 URL。

核心设计 ​

  1. 短码生成：对长 URL 生成唯一短码，可选：
    • 哈希 + 截断（MD5/Base62 取 6-7 位），冲突则加盐重试。
    • 发号器（自增 id → Base62 编码），无冲突，推荐。
  2. 存储：短码 → 长 URL 的映射，存 MySQL/Redis（短码做唯一索引，长 URL 可哈希判重）。
  3. 访问：302 重定向到长 URL；热点短链缓存到 Redis/CDN。
  4. 高并发读：读多写少，用缓存扛读；写用号段/雪花 id 生成短码。

追问应对 ​

  • 「短码会不会重复？」→ 发号器保证唯一；哈希方案需判重处理冲突。
  • 「为什么用 302 不用 301？」→ 302 临时重定向，保留统计点击能力；301 永久重定向浏览器会缓存，后续不经过服务器。

限时订单设计 ★★★ ​

是什么 ​

  • 订单创建后限时（如 30 分钟）未支付则自动取消，释放库存。

核心方案 ​

  • 延迟消息：RocketMQ 延迟消息 / RabbitMQ 死信 + TTL，下单后发一条延迟 30 分钟的消息，到点消费检查订单状态，未支付则取消。
  • 定时任务扫描：定时扫描「超时未支付」订单批量取消（简单但有时延、压力）。
  • Redis 过期 key + 过期监听：下单设 key 过期 30 分钟，监听过期事件取消（有精度/可靠性问题，慎用）。

关键点 ​

  • 幂等：取消操作要幂等（可能被重复触发）。
  • 库存回补：取消订单要回补库存（注意与并发扣减的一致性）。
  • 状态机：订单状态「待支付 → 已取消/已支付」，只有待支付才能取消。

追问应对 ​

  • 「为什么用延迟消息而不是轮询？」→ 延迟消息精确到点、不额外扫库、解耦；轮询有时延和扫描压力。

设计高并发支付网关 ★★★ ​

关注点 ​

  1. 安全：签名/验签、加密、防篡改、防重放（时间戳 + nonce）、防重复支付（幂等）。
  2. 高可用：多机房/多节点、限流、熔断降级、集群。
  3. 一致性：支付结果与订单状态一致（对账、回调、主动查询兜底）。
  4. 幂等：同一笔订单不能重复扣款（订单号 + 唯一约束 + 分布式锁）。
  5. 异步通知：支付回调用 MQ 异步处理，失败重试。
  6. 对账：定时与渠道对账，处理掉单/差错账。
  7. 状态机：订单支付状态严格流转。

追问应对 ​

  • 「支付回调丢了怎么办？」→ 主动查询兜底（定时查渠道支付结果）+ 重试 + 对账。
  • 「怎么防重复支付？」→ 幂等（订单号唯一、状态机、分布式锁）。

设计打车服务 ★★☆ ​

关注点 ​

  • 位置存储与检索：乘客/司机位置用地理位置索引（GeoHash/空间索引）。
  • 匹配：按距离/评分派单，用 Redis GEO 或地理索引查询附近司机。
  • 状态机：订单（呼叫→接单→上车→行程中→完成→支付）。
  • 实时性：司机位置上报（WebSocket/MQ 削峰）、轨迹存储。
  • 高并发：地理查询压力大，用缓存/分区/索引优化。
  • 一致性：派单防重复（分布式锁/状态机）。

追问应对 ​

  • 「怎么找附近司机？」→ 用 GeoHash 把经纬度编码，相近位置 hash 前缀相同，按前缀查附近司机。

设计视频流系统 ★★☆ ​

关注点 ​

  • 存储：视频对象存储（OSS/S3）+ CDN 分发。
  • 上传：分片上传、转码（多码率）、鉴黄审核。
  • 播放：CDN 加速、断点续传、自适应码率（HLS/DASH）。
  • 元数据：视频信息、评论、点赞存数据库，读多用缓存。
  • 高并发读：CDN + 缓存扛住读流量。

追问应对 ​

  • 「视频为什么用 CDN？」→ 就近分发、减轻源站压力、降低延迟。
  • 「为什么要转码？」→ 适配不同网络/设备的多码率，降低带宽、提升播放体验。

实时统计日/周/月活跃用户（DAU/WAU/MAU）★★★ ​

方案 ​

  • Redis Bitmap：一个用户一个 bit 位，setbit 记录当日活跃，按位统计去重活跃数（bitcount）。
    • 日活：每天一个 bitmap；周活/月活：对多天 bitmap 做 bitop OR 求并集再 bitcount。
  • 优点：省内存（1 亿用户约 12MB）、去重、位运算快。

追问应对 ​

  • 「Bitmap 适合什么场景？」→ 用户 id 连续或可映射成连续整数的去重统计；稀疏数据用 HyperLogLog。

统计高并发网站每个网页每天 UV ★★★ ​

方案 ​

  • HyperLogLog（HLL）：概率数据结构，用极小内存（约 12KB/键）统计独立元素个数（UV）。
  • 每个网页每天一个 HLL 键，pfadd 记录访客 id，pfcount 得到 UV（有约 0.81% 误差）。
  • 相比 set：set 精确但内存大（UV 多时爆内存），HLL 用固定小内存换近似值。

追问应对 ​

  • 「HLL 和 Bitmap 区别？」→ Bitmap 精确但内存与最大 id 成正比；HLL 近似、固定小内存、适合超大去重统计。
  • 「HLL 为什么有误差？」→ 基于哈希 + 概率统计，用固定桶近似基数，标准误差约 0.81%。

10 亿数量高效排序 ★★☆ ​

核心：外部排序 ​

  • 数据量大无法一次性载入内存，用「外部归并排序」：
    1. 把大数据分成能装进内存的小块，每块内部排序后落盘（生成多个有序子文件）。
    2. 用多路归并，把多个有序子文件合并成一个大有序文件（用堆维护每路当前最小值）。
  • 分治 + 归并，内存占用可控，磁盘 IO 是瓶颈。

追问应对 ​

  • 「为什么不能直接内存排序？」→ 10 亿数据超内存，需外部排序。
  • 「怎么加速？」→ 增加内存块大小、多路归并、并行处理、分布式（MapReduce/Spark 外部排序）。

为什么要进行系统拆分，如何拆分 ★★★ ​

为什么拆分 ​

  • 单体会随业务增长变得臃肿：编译部署慢、代码耦合、团队协作冲突、故障影响面大、难以独立扩容。
  • 拆分后：独立部署、独立扩展、故障隔离、团队自治、技术栈灵活。

如何拆分 ​

  1. 按业务域拆分：先识别核心领域（用户、订单、商品、支付、库存等），按「高内聚、低耦合」拆成独立服务（可参考 DDD 限界上下文）。
  2. 拆分顺序：先拆边缘/独立性强的服务，再拆核心服务；先拆读多写少、耦合低的。
  3. 数据库拆分：每个服务独立数据库，避免跨服务直接 join，数据通过接口/消息交互。
  4. 配套治理：注册中心、配置中心、网关、服务调用（RPC）、链路追踪、熔断限流。

注意 ​

  • 别过度拆分：拆太细导致分布式复杂度（网络、一致性、运维）剧增；小规模先单体，业务/团队到了一定规模再拆。

追问应对 ​

  • 「拆分后分布式事务怎么办？」→ 用最终一致（本地消息表/TCC/SAGA/事务消息），不强求跨服务强一致。

如何设计一个类似 Dubbo 的 RPC 框架 ★★★ ​

核心组成 ​

  1. 服务发现：注册中心（服务注册/订阅/心跳）。
  2. 代理：客户端生成接口动态代理，屏蔽远程调用细节。
  3. 序列化：请求/响应对象序列化（Hessian、Protobuf、JSON）。
  4. 网络通信：高性能传输（Netty），自定义协议（报文头：魔数、长度、序列化方式、请求 id）。
  5. 负载均衡：多个服务实例间选择（随机、轮询、加权、最小连接、一致性哈希）。
  6. 容错：超时、重试、熔断、降级。
  7. 服务治理：路由、灰度、限流、监控、链路追踪。

调用流程 ​

  • 客户端调用接口 → 动态代理拦截 → 从注册中心选一个服务实例 → 序列化请求 → 网络发送 → 服务端反序列化 → 反射调用实现 → 序列化响应 → 返回客户端。

追问应对 ​

  • 「RPC 和 HTTP 区别？」→ RPC 是自定义协议、二进制序列化、基于长连接/连接池，性能更高、更适合内部服务调用；HTTP 通用、跨语言、易调试，适合对外接口。

Dubbo 的工作原理 ★★☆ ​

核心角色 ​

  • Provider（服务提供者）、Consumer（服务消费者）、Registry（注册中心，如 Zookeeper/Nacos）、Monitor（监控）。
  • 流程：Provider 启动注册到注册中心 → Consumer 订阅并缓存服务列表 → Consumer 按负载均衡选实例 → 发起远程调用（Netty）→ 服务端执行并返回。

调用链路 ​

  • 客户端代理 → 集群容错（重试/失败切换）→ 负载均衡 → 协议编解码 → 网络传输 → 服务端过滤链 → 反射调用实现。

追问应对 ​

  • 「注册中心挂了 Dubbo 还能调用吗？」→ 能，Consumer 本地有缓存的服务列表，可继续用本地缓存调用（只是新实例变化感知不到）。

Dubbo 负载均衡策略 ★★☆ ​

  • Random（随机，默认）：按权重随机。
  • RoundRobin（轮询）：按权重轮询。
  • LeastActive（最少活跃数）：选当前活跃请求最少的实例。
  • ConsistentHash（一致性哈希）：同一参数/请求路由到同一实例（会话粘性）。
  • 可自定义实现 LoadBalance 接口。

追问应对 ​

  • 「一致性哈希负载均衡适合什么？」→ 需要同一请求打到同一台机器的场景（如缓存、会话保持）。

Dubbo 服务治理、服务降级 ★★☆ ​

  • 服务治理：路由规则、灰度发布、权重调整、限流、熔断、监控、链路追踪。
  • 服务降级：依赖服务不可用/超时时，返回兜底结果（mock/容错）。
  • 容错策略：Failover（失败重试，默认）、Failfast（快速失败）、Failsafe（忽略异常）、Failback（失败记录后定时重发）、Forking（并行调用多实例）。

追问应对 ​

  • 「Dubbo 怎么做熔断限流？」→ 可集成 Sentinel/Hystrix，或自定义 Filter 实现。

Dubbo SPI 和 Java SPI 的区别 ★★☆ ​

Java SPI ​

  • 通过 META-INF/services/接口全限定名 文件列出实现类，ServiceLoader 加载。
  • 缺点：一次性加载所有实现（不能按需）、不支持按名获取、扩展点不够灵活。

Dubbo SPI ​

  • 通过 META-INF/dubbo/ 目录配置，用「key=实现类」形式。
  • 支持按 name 精确获取（ExtensionLoader.getExtension("name")）、支持默认实现、自适应扩展（@Adaptive）、包装/激活（Wrapper、Activate）、按需加载。
  • 是 Dubbo 扩展机制的核心。

追问应对 ​

  • 「Dubbo SPI 为什么比 Java SPI 强？」→ 支持按 key 获取、懒加载、默认值、自适应、依赖注入，灵活度和性能都更好。

为什么做分库分表（业务侧）★★☆ ​

  • 单表数据量过大（千万级+）：查询变慢、索引维护开销大、DDL 变慢。
  • 单库连接数、容量、IO 达到瓶颈，无法横向扩展。
  • 写多读多，单库扛不住高并发。
  • 分库分表实现横向扩展：分片后每个库/表数据量变小，读写压力分散。

追问应对 ​

  • 「分库分表一定好吗？」→ 不是，引入分布式事务、跨库 join、分布式主键、路由等复杂度；先做索引优化、缓存、读写分离，仍不够再分。
