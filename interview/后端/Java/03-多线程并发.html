多线程并发 ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

1. 线程状态、创建方式、start 与 run ★★★ ​

通俗理解 线程有 6 种状态：新建、可运行（就绪+运行）、阻塞（等锁）、无限等待、限时等待、终止。创建线程有三条路：继承 Thread、实现 Runnable、实现 Callable（有返回值能抛异常，配 Future 用）。生产上一律用线程池。start() 才是真开新线程，JVM 调度后在新线程回调 run()；直接调 run() 就是个普通方法调用，还在当前线程跑。

我的项目关联 网关和业务服务里我不手写 new Thread，线程来源就两类：Netty 的 IO 线程池、业务自己的线程池。需要返回值的批量任务（比如批量查订单、批量查桩状态）用 Callable + Future 汇总结果。这块属于基本功，没出过坑。

面试答题话术 「线程状态六种，重点记 BLOCKED 是等锁、WAITING 是无限等、TIMED_WAITING 是限时等。创建方式三种，实际都用线程池。start 才是开新线程，run 只是普通方法调用，在调用者线程跑，这是常考陷阱。要返回值就用 Callable 配 Future，不需要就 Runnable。」

2. synchronized 原理与锁升级 ★★★ ​

通俗理解 synchronized 底层是对象头 Mark Word + Monitor（监视器锁），字节码上是 monitorenter/monitorexit。锁会升级：无锁 → 偏向锁（同一线程反复进，记个线程 ID 不用 CAS）→ 轻量级锁（有竞争，CAS 自旋）→ 重量级锁（竞争激烈，真阻塞）。升级的原因是大多数锁竞争并不激烈，自旋比直接阻塞便宜。注意偏向锁 JDK15 起已废弃，别当成重点讲。锁的是对象不是代码块：普通方法锁 this，静态方法锁 Class。

我的项目关联 网关里设备会话状态、下发队列这些共享结构，早期用 synchronized 保证一致性，现在更高频的并发场景换成 ConcurrentHashMap 和原子类。记住一句话：两把锁锁的必须是同一个对象才互斥，锁不同对象等于没锁——我们做「同一设备串行处理」时，就是按设备编号取同一把锁对象来保证串行的。

面试答题话术 「synchronized 是对象头 Mark Word 加 Monitor，monitorenter/monitorexit。锁升级是偏向锁、轻量级锁、重量级锁一路上去，核心原因是大部分场景竞争不激烈，自旋比阻塞划算。它可重入，锁的是对象不是方法。偏向锁 JDK15 之后废弃了，现在主要讲轻量级到重量级这一段。项目里高频并发我一般不用它，用 ConcurrentHashMap 或原子类。」

3. volatile、三大特性、happens-before ★★★ ​

通俗理解 volatile 保证两件事：可见性（写立刻刷主存、读之前失效工作内存）和有序性（禁止指令重排），靠内存屏障实现。但它不保证原子性——i++ 是「读-改-写」三步，volatile 拦不住丢更新。并发三要素是可见性、原子性、有序性，volatile 只解决前两个。happens-before 是一套规则（程序顺序、锁 unlock 先于 lock、volatile 写先于读、start/join、传递性），用来判断两个操作之间有没有可见性保证。

我的项目关联 网关的「停止标志位」、开关配置必须用 volatile，不然一个线程改了另一个线程读不到旧值，循环停不下来。计数这类复合操作用 AtomicLong 而不是 volatile。双重校验锁单例为什么加 volatile，是因为 new 对象本身分三步（分配、初始化、赋引用），重排后别的线程可能拿到没初始化完的对象——这是通用坑，我们项目没实际踩过，但代码 review 时是必查项。

面试答题话术 「volatile 保证可见性和有序性，不保证原子性。i++ 这种复合操作它没用。它靠内存屏障实现，写插 Store 屏障、读插 Load 屏障。经典题是双重校验锁为什么加 volatile：防的是 new 对象时指令重排，让别的线程拿到半成品对象。项目里我的用法很固定：状态标志用 volatile，计数用 AtomicLong。」

4. AQS、ReentrantLock、Condition ★★★ ​

通俗理解 AQS 是并发包的地基：核心就一个 volatile int state（同步状态）+ 一个 FIFO 等待队列。state 用 CAS 改，独占模式表示重入次数（ReentrantLock），共享模式表示许可数（Semaphore、CountDownLatch）。抢不到锁的线程入队并 park，前面释放了再唤醒。ReentrantLock 分公平和非公平：非公平是新线程先抢一把，抢不到再排队（默认、吞吐高）；公平是先看队列有没有人。Condition 配 await/signal 做精准唤醒，一把锁能建多个条件队列。

我的项目关联 实际开发我不继承 AQS，但它解释了三个我常用的东西：ReentrantLock 的可重入（按设备维度加锁做串行）、Semaphore 做限流（控制同时下发的报文数、同时调第三方接口的并发）、CountDownLatch 做批任务等待。用 ReentrantLock 时一定 try/finally 里 unlock，不然异常了锁不释放——这是通用坑，规范上一直有要求。

面试答题话术 「AQS 就是 state 加一个 FIFO 队列。state 在独占锁里是重入次数，在共享锁里是许可数。抢不到就入队 park，前驱释放再唤醒。ReentrantLock 默认非公平，新线程先抢，抢不到才排队，吞吐比公平高。Condition 比 wait/notify 精细，一把锁能建多个条件队列。项目里我用它主要是按设备加锁做串行、用 Semaphore 限制并发调用第三方的数量。」

5. ThreadPoolExecutor 七大参数、拒绝策略、为什么不推荐 Executors ★★★ 【简历亮点，高频追问】 ​

通俗理解 七大参数：核心线程数、最大线程数、空闲存活时间、时间单位、任务队列、线程工厂、拒绝策略。执行流程记死：核心线程没满就开核心线程 → 满了进队列 → 队列满了才开非核心线程到最大 → 都满了走拒绝策略。四种拒绝策略：Abort 抛异常（默认）、CallerRuns 让提交的线程自己跑、Discard 直接丢、DiscardOldest 丢最老的。不用 Executors 的原因：Fixed/Single 用无界队列会堆爆 OOM，Cached 线程数无上限也会 OOM。

我的项目关联 我们所有线程池都是手动 new ThreadPoolExecutor，参数显式指定。网关下发报文、对账跑批、互联互通批量上报都是各自独立的线程池，互不干扰，队列一定用有界的（ArrayBlockingQueue），拒绝策略按业务选：可丢的用 Discard，不能丢的用 CallerRuns 降速。说明一下：我们没真被 Executors 的无界队列搞出过线上 OOM，这是规范上直接禁用了，从源头防住。

面试答题话术 「七参数、执行流程、拒绝策略都要背熟。最关键的一句话是：核心满了先入队，队列满了才开非核心线程——所以无界队列会让 maximumPoolSize 形同虚设。不用 Executors 就是因为它的队列或线程数无上限，容易 OOM。我项目里一律手动 new ThreadPoolExecutor，有界队列，线程池按业务隔离，一个池子扛不住不影响别的。」

6. 线程池参数怎么按业务设 ★★★ ​

通俗理解 CPU 密集型：线程数 ≈ 核数 + 1，多了反而因切换掉性能。IO 密集型：线程数 = 核数 × 2 甚至更多，看阻塞比，公式是 核数 × (1 + 等待时间/计算时间)。队列选有界，然后压测 + 监控来调，不要一步到位拍脑袋。

我的项目关联 我们的任务基本是 IO 密集型：等充电桩响应、等第三方接口、等数据库。所以线程池核心数在核数 2~4 倍这个区间，配合监控看队列积压和活跃线程数再调。原则是「先有监控再调参」，不是一上来就设个几百。

面试答题话术 「分两类：CPU 密集是核数加一，IO 密集按阻塞比放大，一般核数的 2 到 4 倍。但公式只是起点，真正靠压测和监控调——看队列有没有积压、线程活跃度、有没有频繁拒绝。我项目的任务基本都是 IO 密集，等桩、等第三方、等 DB，所以线程数比核数高一些，队列有界，配合监控调。」

7. CountDownLatch / CyclicBarrier / Semaphore ★★★ ​

通俗理解 CountDownLatch：一个线程等 N 个线程干完（一次性，不能重用），比如主线程等所有子任务结束。CyclicBarrier：N 个线程互相等，都到齐了一起走，能循环用（reset）。Semaphore：信号量，控制同时能有多少个线程访问某个资源，用来限流。

我的项目关联 互联互通批量上报、对账批量处理这种「并发跑 + 等全部结果」的场景用 CountDownLatch；分阶段任务（每阶段要所有线程对齐）用 CyclicBarrier；调用高德、第三方运营商接口时用 Semaphore 限并发，防止把对方打挂。这三个是我们批量任务的标准搭配。

面试答题话术 「CountDownLatch 是一等多、一次性；CyclicBarrier 是多等多的栅栏，能复用；Semaphore 是限流控制并发数。我项目里批量上报用 Latch 等全部完成，调第三方接口用 Semaphore 限并发，避免把下游打挂。」

8. ConcurrentHashMap、CopyOnWriteArrayList ★★★ ​

通俗理解 ConcurrentHashMap 在 1.8 是 CAS + synchronized 桶级锁（只锁一个桶，不是整表）+ 红黑树，读完全无锁，所以并发性能好。CopyOnWriteArrayList 是写时复制：写的时候加锁、复制整个数组改完再换新的，读永远读旧数组，所以读无锁；代价是写贵、内存翻倍、数据是弱一致（读到的可能是旧值）。

我的项目关联 网关里「设备号 → 会话」「场站 → 枪状态」这些并发读写的缓存表，全部用 ConcurrentHashMap，绝不用 HashMap（多线程下 HashMap 会丢数据甚至死循环）。CopyOnWriteArrayList 我们用得少，只适合那种「读极多写极少」的监听器/回调列表——比如注册的报文处理器列表，启动时注册、运行期只读。

面试答题话术 「CHM 1.8 是 CAS 加 synchronized 锁单个桶，读无锁，所以并发安全又高效。实际项目里网关的会话表、状态表全用它，多线程下绝对不用 HashMap。CopyOnWriteArrayList 是写时复制，读无锁，但写要复制整个数组，只适合读多写极少的场景，比如启动时注册的处理器列表。」

9. 死锁四个条件、如何避免、活锁与饥饿 ★★★ ​

通俗理解 死锁四个必要条件：互斥、持有并等待、不可剥夺、循环等待，缺一个就不会死锁。避免就是破坏其中一个，最常用的是破坏循环等待——所有线程按固定的同一顺序加锁。还能加锁超时（tryLock + 超时）、一次性申请所有资源。活锁是大家互相礼让谁都不动，饥饿是非公平锁或低优先级线程一直抢不到。

我的项目关联 我们踩过的场景是「通用坑」级别：一个方法里同时要「设备锁」和「订单锁」，如果一处先锁设备再锁订单、另一处反过来，就形成循环等待。规范是所有涉及双锁的地方统一按固定顺序加。排查死锁全靠 jstack，输出里会直接打 Found one Java-level deadlock，把等待环画出来。

面试答题话术 「死锁四个条件：互斥、持有并等待、不可剥夺、循环等待，破坏任意一个就行。实践里最常用的是统一加锁顺序，破坏循环等待。还可以用 tryLock 加超时。排查就是 jstack 打线程栈，它会直接告诉你 Found one Java-level deadlock。项目里我们约定多把锁必须按固定顺序拿，避免交叉等待。」

10. 线程安全问题产生的根本原因 ★★☆ ​

通俗理解 根本原因就一句：多个线程共享了可变数据，读写交叠产生数据竞争。落到三要素上就是可见性、原子性、有序性被破坏。解决手段对应着来：volatile 管可见性和有序性，synchronized/原子类管原子性，再加并发容器和不可变对象。

我的项目关联 记结论就行。我们网关共享的是会话和状态，所以一律用并发容器 + 原子类，尽量让共享数据是「只读」或「不可变」的，从设计上减少竞争。

面试答题话术 「根本原因是共享可变数据的读写交叠。对应三要素：可见性、原子性、有序性。解决就是 volatile 管可见性、原子类或 synchronized 管原子性、并发容器管容器的安全，能不变就不可变。项目里我尽量少共享，必须共享就用并发容器。」

11. ThreadLocal 原理与内存泄漏 ★★★ 【简历亮点，高频追问】 ​

通俗理解 每个 Thread 里挂一个 ThreadLocalMap，set/get 是以「当前线程」为索引去自己的 map 里读写，数据天然隔离。Entry 的 key 是 ThreadLocal 的弱引用、value 是强引用。泄漏的原因：ThreadLocal 被回收后 key 变 null，但 value 还被 Entry 强引用，加上线程池线程不销毁，value 就一直留着。所以规范是用完必须 remove()。

我的项目关联 我常用它透传上下文，最典型的是链路 traceId——请求进来 set 一个 traceId，日志和下游调用都从 ThreadLocal 取。网关用 Netty，Netty 还专门有 FastThreadLocal 替代 ThreadLocal，性能更好、定位更快。这里有个必问的坑：线程池里线程是复用的，如果不 remove，下一个任务会读到上一个任务的 traceId，数据串台——这是通用坑，我们在框架里统一在 finally 里 remove 来防。

面试答题话术 「ThreadLocal 是每个线程一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是强引用，天然隔离。泄漏是因为 key 被回收后 value 还挂着，线程池线程又不销毁。解决办法就一句：用完必须 remove。我项目里用它透传 traceId，因为线程池复用，不 remove 会串台，所以框架里统一在 finally 里清理。Netty 里还有 FastThreadLocal，原理类似但更快。」

12. CAS 原理与 ABA 问题 ★★★ ​

通俗理解 CAS 就是「比较并交换」：拿内存里的值和预期值比，一样才写新值，底层是一条 CPU 原子指令，不用加锁。三个缺点：ABA 问题、自旋空转费 CPU、只能保证单个变量原子。ABA 是值从 A 改 B 又改回 A，CAS 以为没变过；解决是加版本号（AtomicStampedReference）。

我的项目关联 订单扣款、余额变更这类场景我们更倾向用数据库乐观锁（version 字段），因为 CAS 只管单个变量，跨字段、跨表不适用。单纯的内存计数用 AtomicLong。ABA 在业务上要小心：如果状态是「待支付 → 已取消 → 待支付」，光看状态值没变就会误判，必须带版本号。

面试答题话术 「CAS 是比较并交换，靠 CPU 原子指令，无锁。缺点是 ABA、自旋耗 CPU、只能管一个变量。ABA 就是值改走了又改回来，CAS 察觉不到，解决是加版本号 AtomicStampedReference。项目里跨字段的并发我用数据库 version 乐观锁，纯内存计数才用原子类。」

13. 原子类 AtomicInteger、LongAdder ★★☆ ​

通俗理解 AtomicInteger 是 volatile + CAS。LongAdder 更聪明：把热点拆成多个 Cell，不同线程加到不同 Cell 上，减少 CAS 竞争，最后 sum 汇总——高并发累加快得多，代价是 sum 不保证实时精确。

我的项目关联 记结论。网关的实时统计（在线数、报文数）这种高并发累加用 LongAdder，需要立刻准确的场景用 AtomicLong。这块没踩过坑，属于选型知识。

面试答题话术 「AtomicInteger 是 volatile 加 CAS；LongAdder 是把热点拆成多个 Cell 分散竞争，所以高并发累加快，但 sum 是汇总的、不是强一致。选型就一句：高并发累加用 LongAdder，要精确即时值用 AtomicLong。」

14. CompletableFuture 异步编排 ★★★ 【简历亮点，高频追问】 ​

通俗理解 Future 只能阻塞 get 拿结果，没法链式组合。CompletableFuture 支持链式编排和回调：thenApply 转换结果、thenAccept 消费、thenCombine 合并两个结果、allOf 等全部完成、anyOf 任一完成，exceptionally/handle 处理异常。创建用 supplyAsync/runAsync。

我的项目关联 这个我用得多。典型场景：一个大接口要同时查「桩状态 + 订单 + 计费规则 + 用户余额」，串行太慢，就用 CompletableFuture 并发查再合并，allOf 等齐。重点提醒：默认线程池是 ForkJoinPool.commonPool，如果里面跑阻塞任务会拖垮整个 JVM 的公共池，所以我们一律传自己的线程池。这是通用坑，但规范上强制。

面试答题话术 「CompletableFuture 比 Future 强在能链式编排、能组合、能处理异常。我项目里做过聚合接口，同时查桩、订单、计费规则，用 allOf 等全部返回再合并，把串行改成并发。有个坑必须注意：默认用 ForkJoinPool 公共池，跑阻塞任务会影响全局，所以一定要传自定义线程池。」

15. JMM 内存屏障、指令重排 ★★☆ ​

通俗理解 CPU 和编译器为了快会重排指令，单线程看不出问题，多线程可能语义就变了。内存屏障就是拦这个的：volatile 写会插 Store 屏障、读会插 Load 屏障，保证屏障前后的读写顺序和可见性。双重校验锁单例加 volatile 就是防重排。

我的项目关联 结论够用。双重校验锁单例我们在工具类、配置持有类里会用，volatile 一定加。其他场景基本不直接碰屏障。

面试答题话术 「指令重排是编译器和 CPU 为性能做的，多线程下可能出问题，所以用内存屏障拦。volatile 的写和读分别插不同的屏障。最经典的例子是双重校验锁单例为什么加 volatile——防 new 对象的重排。知道这个结论就够了。」

16. BlockingQueue、线程中断 ★★☆ ​

通俗理解 BlockingQueue 的 put/take 会阻塞：满了 put 等、空了 take 等，是线程池和生产者-消费者的底座。常见的有 ArrayBlockingQueue（有界）、LinkedBlockingQueue（可选有界）、SynchronousQueue（不存，直接交接）、DelayQueue（延迟）。interrupt() 只是打个中断标志，不是强杀线程；sleep/wait 收到中断会抛 InterruptedException 并清标志，要靠 isInterrupted() 自己响应退出。

我的项目关联 网关内部做过一个下发队列，用 BlockingQueue 做生产者-消费者，Netty 收报文入队、业务线程出队处理，天然削峰。优雅停机时靠 interrupt 标志让工作线程退出去。

面试答题话术 「BlockingQueue 就是满了等、空了等的队列，线程池就是靠它。interrupt 只设标志位不真停线程，阻塞方法会抛 InterruptedException。项目里网关的下发队列就是生产者-消费者模式，用阻塞队列削峰。」

17. synchronized 与 ReentrantLock 区别 ★★★ ​

通俗理解 synchronized 是 JVM 层实现（Monitor），自动释放，不能中断、不能超时、非公平。ReentrantLock 是 JDK 层实现（AQS + CAS），要手动 unlock，支持可中断、超时、可选公平、多条件队列。JDK6 优化后两者性能差不多，选型看功能不看性能：简单同步用 synchronized，需要超时/中断/多条件才用 ReentrantLock。

我的项目关联 绝大部分地方我用 synchronized，够用又不会忘释放。真要超时控制时才上 ReentrantLock，比如「按设备加锁 + tryLock 超时，拿不到就放弃本次处理」，避免线程一直卡着。重申：ReentrantLock 的 unlock 必须放 finally。

面试答题话术 「区别就几点：synchronized 是 JVM 层、自动释放、不可中断、非公平；ReentrantLock 是 JDK 层、手动释放、可中断、可超时、可公平、支持多个 Condition。JDK6 之后性能差不多，选型看功能。我一般用 synchronized，需要超时或按维度加锁才用 ReentrantLock，unlock 一定放 finally。」

18. sleep() 与 wait() 区别 ★★★ ​

通俗理解 sleep 是 Thread 的静态方法，不释放锁，时间到了自己醒，随便哪都能调。wait 是 Object 的方法，释放锁，要别人 notify 才醒，必须在 synchronized 块里调（否则抛 IllegalMonitorStateException）。sleep 是让线程歇会儿让出 CPU，wait 是线程间协作。

我的项目关联 记结论+一个场景。wait/notify 我们很少手写（有阻塞队列了），主要是面试和手撕生产者消费者会用。

面试答题话术 「sleep 不释放锁、wait 释放锁；sleep 到点自己醒、wait 要别人 notify；wait 必须在 synchronized 里，不然抛 IllegalMonitorStateException。sleep 是 Thread 的，wait 是 Object 的。项目里线程协作我基本用阻塞队列，不用手写 wait/notify。」

19. volatile 与 synchronized 区别 ★★☆ ​

通俗理解 volatile 只保可见性和有序性，不保原子性，只能修饰变量，轻量。synchronized 三样都保，能修饰方法和代码块，会加锁阻塞。状态标志用 volatile，复合操作用 synchronized 或原子类。

我的项目关联 一句话：开关标志用 volatile，计数和「读改写」用原子类。

面试答题话术 「volatile 保可见性和有序性，不保原子性，轻量；synchronized 三性全保，但会阻塞。所以状态标志用 volatile，i++ 这种复合操作用原子类或 synchronized。」

20. wait/notify 线程协作 ★★☆ ​

通俗理解 wait 释放锁并等待，notify 唤醒一个、notifyAll 唤醒全部，都必须在 synchronized 里。条件判断要用 while 不用 if，因为可能被虚假唤醒，醒来条件已经不满足了，while 会重新判断。

我的项目关联 同上，实际用阻塞队列替代。while 不用 if 这个点面试常问，记住就行。

面试答题话术 「wait 释放锁等唤醒，notify/notifyAll 唤醒，必须在 synchronized 里。判断条件必须用 while 不用 if，防虚假唤醒。实际项目我直接用阻塞队列，不手写这套。」

21. 手写生产者消费者 ★★★ ​

通俗理解 经典手撕题。用 wait/notify 的话：put 时队列满了就 wait，放进去后 notifyAll；take 时队列空了就 wait，取出来后 notifyAll。注意 while 判断、注意 notifyAll。更优的写法是用 ArrayBlockingQueue 或 Lock + 两个 Condition（notFull/notEmpty），能精准唤醒生产者或消费者。

我的项目关联 我项目里不会手写，直接用 ArrayBlockingQueue。手撕时我会写 wait/notify 版本，然后补一句「生产上我用阻塞队列或 Lock+Condition」。

面试答题话术 「手撕的话我用 wait/notify：满就 wait、放完 notifyAll，空就 wait、取完 notifyAll，条件判断用 while。但我会补一句：生产代码直接用 ArrayBlockingQueue，或者 Lock 配两个 Condition 做精准唤醒，比 notifyAll 效率高。」

java
// 面试手写版（生产用 ArrayBlockingQueue 即可）
class BoundedBuffer {
    private final int[] buf = new int[10];
    private int count = 0, put = 0, take = 0;

    public synchronized void put(int v) throws InterruptedException {
        while (count == buf.length) wait();   // 满则等
        buf[put] = v; put = (put + 1) % buf.length; count++;
        notifyAll();
    }
    public synchronized int take() throws InterruptedException {
        while (count == 0) wait();            // 空则等
        int v = buf[take]; take = (take + 1) % buf.length; count--;
        notifyAll();
        return v;
    }
}

22. 手写线程池 / LRU ★★☆ ​

通俗理解 手写线程池核心是「任务队列 + 工作线程集合 + 拒绝策略」。手写 LRU 用 LinkedHashMap 最省事：构造时 accessOrder=true，重写 removeEldestEntry 超过容量就删最老的。

我的项目关联 LRU 我用在本地热点缓存上，比如「最近访问的场站配置」，超过容量就淘汰最不常用的。线程池直接用手写的没有，都是 ThreadPoolExecutor。

面试答题话术 「LRU 我用 LinkedHashMap 实现，accessOrder 设 true，重写 removeEldestEntry，超容量删头部。线程池手写的话就是任务队列加工作线程加拒绝策略，但生产直接 ThreadPoolExecutor。」

java
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int cap;
    public LRUCache(int cap) { super(cap, 0.75f, true); this.cap = cap; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) { return size() > cap; }
}

23. 悲观锁与乐观锁 ★★★ ​

通俗理解 悲观锁：假设一定会冲突，先加锁独占再操作（synchronized、数据库 select ... for update）。乐观锁：假设冲突少，不加锁，用版本号或 CAS 检测有没有被改过，冲突就重试。冲突多用悲观，冲突少、读多写少用乐观。

我的项目关联 订单状态流转、余额变更我们用数据库乐观锁：update ... set status=?, version=version+1 where id=? and version=?，影响行数是 0 就说明被别人改了，重试或返回失败。说明一下：我们确实在处理并发订单时遇到过「同一订单被重复更新」，改用 version 乐观锁 + 幂等校验后解决了——这类并发更新是充电业务的高频问题，用得比较多。

面试答题话术 「悲观锁是先加锁再操作，乐观锁是用 version 或 CAS 检测冲突再重试。冲突多用悲观，读多写少用乐观。项目里订单状态和余额更新我用数据库乐观锁：带 version 条件更新，影响行数为 0 就重试或报冲突，配合幂等，避免同一订单被并发改。」

24. 线程池任务抛异常会怎样 ★★★ ​

通俗理解 两种提交方式差别很大。submit 提交的任务抛异常会被「吞掉」，只有调 future.get() 时才会以 ExecutionException 抛出来。execute 提交的任务抛异常会直接抛，而且这个工作线程会退出销毁，线程池再新建一个补上——所以异常可能只出现在兜底日志里。处理办法：submit 后 get 捕获、重写 afterExecute 记录异常、任务内部 try-catch 兜底。

我的项目关联这一条我特别有感触。 网关的报文处理线程池一开始用 submit，异常全被吞了，日志里啥都看不到，任务「静默失败」；后来在 afterExecute 钩子里统一记录异常，并给 ThreadFactory 设了 UncaughtExceptionHandler，问题才暴露出来。这是真实踩过的坑：现象就是「任务明明提交了却没结果、日志也不报错」，修复就是补异常钩子。

面试答题话术 「区别很大：submit 会把异常吞进 Future，只有 get 才抛 ExecutionException；execute 会直接抛，而且线程会死掉重建，异常容易只留在兜底日志里。项目里我踩过这个坑——网关线程池用 submit，任务失败日志里什么都看不到，后来重写 afterExecute 加异常钩子才暴露出来。所以线程池我一定配 afterExecute 或 UncaughtExceptionHandler。」

25. ConcurrentHashMap 扩容与树化 ★★★ ​

通俗理解 1.8 的 CHM 支持多线程协助扩容：触发扩容的线程建新表，迁移过的桶放一个 ForwardingNode 标记；别的线程 put 时撞到它就顺手帮忙迁移，不用干等。靠 sizeCtl 和 transferIndex 分配任务，各线程迁移不同桶段，所以扩容快、读不阻塞（读到转发节点就去新表查）。树化条件和 HashMap 一样：链表长度 ≥ 8 且容量 ≥ 64 才转红黑树，否则优先扩容；退化阈值是 6，8 和 6 之间留缓冲防抖动。

我的项目关联 结论够用。实际知道「CHM 扩容是多线程协作、读不阻塞」就行，面试追到细节能说 ForwardingNode 和协助迁移。网关会话表用它，扩容时也需要保证读不卡，这点对长连接场景很重要。

面试答题话术 「CHM 1.8 支持多线程协助扩容，被迁移的桶放 ForwardingNode 标记，别的线程 put 撞到就帮着一块迁，靠 sizeCtl 和 transferIndex 分工。扩容期间读不阻塞，读到转发节点就去新表。树化和 HashMap 一样：长度到 8 且容量到 64 才树化，否则先扩容。我项目里会话表用它，就是看中扩容期间读也不卡。」

26. 线程池为什么先入队列而不是先开满线程 ★★★ ​

通俗理解 因为线程创建销毁成本高，队列能起削峰缓冲作用。顺序是：核心线程满 → 入队 → 队列满 → 才开到最大线程 → 再满才拒绝。这样瞬时高峰先排队被核心线程慢慢消化，不用一上来就开满线程。副作用是：如果队列无界，maximumPoolSize 永远用不到，任务全堆在队列里，可能 OOM。

我的项目关联 这就是为什么我们严禁无界队列：网关下游如果变慢，无界队列会一路堆积到 OOM，还会掩盖问题（以为没事，其实全堵着）。我们用有界队列 + CallerRuns 拒绝策略，队列一满就让提交方（比如 Netty 线程）自己跑，起到背压作用。

面试答题话术 「顺序是核心线程、队列、最大线程、拒绝，队列起到削峰缓冲的作用，避免频繁创建销毁线程。坑在于无界队列会让 maximumPoolSize 失效，任务全堆队列里、最后 OOM。我项目里队列一定有界，配 CallerRuns 做背压，队列满了让提交方自己处理，把压力顶回去。」

27. 自旋锁的优缺点 ★★★ ​

通俗理解 自旋锁不阻塞线程，而是循环 CAS 尝试拿锁。好处是省了线程阻塞唤醒的上下文切换，锁持有时间短时很划算。坏处是竞争激烈时空转烧 CPU，还可能饥饿。所以只适合「临界区短、竞争不激烈、多核」的场景。JVM 用自适应自旋，根据上次成没成功动态调次数。

我的项目关联 记结论。JVM 的轻量级锁和 AtomicLong 都是自旋思路，知道「短临界区用自旋、长临界区用阻塞」就行。

面试答题话术 「自旋锁就是不阻塞、循环 CAS 抢锁，优点是省上下文切换，短临界区快；缺点是竞争激烈时空转烧 CPU。适合临界区短、竞争少的场景。JDK 是自适应自旋，按上次结果动态调次数。」

28. 进程和线程的区别、线程一定省时间吗 ★★★ ​

通俗理解 进程有独立地址空间，是资源分配单位；线程共享进程资源，是调度单位，所以线程切换比进程快（只需换寄存器和栈）。线程不一定省时间：多核并行任务、IO 密集场景能提速；单核跑 CPU 密集任务反而因切换变慢。

我的项目关联 我们服务是单个 JVM 进程内多线程，网关也是 Netty 多线程模型。真正要多进程隔离的是不同微服务（各自一个容器）。线程切换快这点解释了为什么我们敢开较大的 IO 线程池。

面试答题话术 「进程独立地址空间、是资源分配单位，线程共享进程资源、是调度单位，线程切换只换寄存器和栈所以更快。但线程不是一定省时间：多核并行和 IO 密集能提速，单核 CPU 密集反而更慢。项目里我们是单进程多线程，不同微服务用容器做隔离。」

29. Java 线程间通信方式 ★★★ ​

通俗理解 几种：共享变量 + volatile/synchronized（最基本）、wait/notify、Lock + Condition、阻塞队列（生产者-消费者）、并发工具类（CountDownLatch 等）、join 等待线程结束。ThreadLocal 严格说是隔离不是通信。

我的项目关联 我们最常用「阻塞队列 + 共享变量」：上报/下发用阻塞队列解耦，状态用 volatile。批量任务用 Latch 协调。

面试答题话术 「最基础是共享变量配 volatile/synchronized，然后是 wait/notify、Lock+Condition，工程上最常用阻塞队列做生产者消费者，批量场景用 Latch/CyclicBarrier 协调。ThreadLocal 算隔离不算通信。」

30. ThreadLocalMap 结构与扩容 ★★☆ ​

通俗理解 ThreadLocalMap 是 ThreadLocal 的内部类，本质是个 Entry[] 数组，Entry 继承 WeakReference（key 弱引用）。它不用链表，用开放定址法（线性探测）解决冲突。初始容量 16，负载因子 2/3，到阈值先清 key 为 null 的失效 Entry，清完还超就扩容 2 倍。

我的项目关联 知道「数组 + 开放定址 + 弱引用 + 会顺手清理」这个结论就行，不用背扩容细节。

面试答题话术 「ThreadLocalMap 是个 Entry 数组，Entry 的 key 是弱引用，用开放定址法解决冲突，不是链表。到阈值先清理 key 为 null 的 Entry，再考虑扩容。知道这些就够了，实际不会去调它的参数。」

31. InheritableThreadLocal 父子线程共享★★★ ​

通俗理解 普通 ThreadLocal 父子线程不共享。InheritableThreadLocal 在创建子线程时会把父线程的值复制一份过去。局限是只复制一次（之后父线程改值子线程不同步），而且在线程池里直接失效——池里的线程是预创建复用的，不是现开的，继承不到。

我的项目关联 这也是链路追踪的坑：我们用线程池处理任务，父线程的 traceId 传不进子线程，就是 InheritableThreadLocal 失效的典型。解决办法是「任务提交时抓取上下文、执行时再 set 回去」，阿里开源的 TransmittableThreadLocal（TTL）就是干这个的。

面试答题话术 「InheritableThreadLocal 在创建子线程时复制父线程的值，但只复制一次，而且线程池下失效，因为线程是提前建好复用的。链路追踪里就踩这个坑，父线程的 traceId 进不了子线程。解决是用 TransmittableThreadLocal，在任务提交时捕获上下文、执行时透传。」

32. 进程、线程、协程的区别 ★★☆ ​

通俗理解 进程是资源分配单位，线程是 CPU 调度单位，协程是用户态的轻量线程、由程序自己调度、切换开销极小。Java 的虚拟线程可以理解为 JVM 层的协程。

我的项目关联 一句话记住就行：Java 21 的虚拟线程就是「JVM 版协程」，我们网关高并发连接场景未来可以考虑用它替代线程池，但目前还是 Netty 自己的线程模型为主。

面试答题话术 「进程管资源，线程管调度，协程是用户态轻量线程、切换开销极小。Java 的虚拟线程就相当于 JVM 层的协程，适合大量阻塞式 IO 的任务。项目里网关是 Netty 自己的线程模型，还没用虚拟线程。」

附：一句话速记（可以跳过 ★☆☆） ​

  • 管道通信（PipedStream）：线程间 IO 流通信，实际很少用，知道有这回事即可。
  • Thread.stop()：已废弃，会破坏一致性，一律用 interrupt + 标志位优雅退出。
