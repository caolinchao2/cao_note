多线程并发 ​

常问等级：★★★ 高频必考 / ★★☆ 中频常见 / ★☆☆ 低频了解 深度标准：每个考点讲清「是什么 → 为什么 → 源码关键点 → 追问应对 → 易错点」。

线程状态；创建线程的几种方式；start() 和 run() 区别 ★★★ ​

线程 6 种状态 ​

  • NEW（新建）、RUNNABLE（可运行，含就绪和运行）、BLOCKED（阻塞，等待锁）、WAITING（无限等待）、TIMED_WAITING（限时等待）、TERMINATED（终止）。

创建方式 ​

  • 继承 Thread：重写 run()，耦合度高。
  • 实现 Runnable：重写 run()，推荐（解耦，可被线程池复用）。
  • 实现 Callable：有返回值、可抛异常，配合 Future/FutureTask。
  • 线程池：复用线程，推荐生产使用。

start() vs run() ​

  • start() 启动新线程，由 JVM 调度后在新线程回调 run()。
  • 直接调 run() 只是普通方法调用，在调用者线程执行，不新建线程。

追问应对 ​

  • 「Runnable 和 Callable 区别？」→ Callable 有返回值、可抛异常，Runnable 无；Callable 需配合 FutureTask/线程池 submit。
  • 「为什么推荐 Runnable/线程池而非继承 Thread？」→ 单继承限制、解耦、线程可复用。

synchronized 底层原理；锁升级过程 ★★★ ​

底层 ​

  • 基于对象头 Mark Word 与 Monitor（监视器锁）：monitorenter / monitorexit 指令。
  • 每个对象关联一个 Monitor，持有锁的线程是 Monitor 的 owner。

锁升级过程（JDK6 起） ​

  • 无锁 → 偏向锁（同一线程反复获取，记录线程 ID，无需 CAS）→ 轻量级锁（竞争时用 CAS 自旋）→ 重量级锁（膨胀为 Monitor，阻塞线程）。
  • 偏向锁：JDK15 起逐步废弃（维护成本高、收益小）。

为什么锁会升级 ​

  • 大多数情况下锁竞争不激烈，用轻量级的自旋（轻量级锁）比直接阻塞（重量级锁，涉及系统调用、线程切换）开销小；只有竞争激烈自旋浪费 CPU 时才升级为重量级锁。

追问应对 ​

  • 「synchronized 是可重入的吗？」→ 是，同一线程可重复获取同一把锁（Monitor 记录重入次数）。
  • 「synchronized 锁的是对象还是代码？」→ 锁的是对象（普通方法锁 this，静态方法锁 Class 对象），不是代码块。

易错点 ​

  • 锁的是对象不是方法；两个线程用「同一个对象」加锁才互斥，不同对象各锁各的。

volatile 作用；可见性/原子性/有序性；happens-before ★★★ ​

volatile 保证什么 ​

  • 可见性：写后立即刷主存，读前失效工作内存（靠内存屏障）。
  • 有序性：禁止指令重排（内存屏障）。
  • 不保证原子性：i++ 是「读-改-写」三步，volatile 无法保证复合操作原子。

三大特性 ​

  • 可见性、原子性、有序性是并发编程三要素，volatile 只解决其中两个。

happens-before 规则 ​

  • 程序次序、监视器锁（unlock 先于后续 lock）、volatile（写先于读）、线程 start/join、传递性等。
  • 用于判断两个操作之间的可见性/有序性保证。

追问应对 ​

  • 「volatile 能保证线程安全吗？」→ 不能保证复合操作原子性，i++ 仍会丢更新；状态标志用 volatile，计数用原子类。
  • 「双重校验锁为什么加 volatile？」→ 防止 new 对象时指令重排，导致其他线程拿到未初始化完成的对象。

AQS 原理；ReentrantLock 公平/非公平锁；Condition ★★★ ​

AQS（AbstractQueuedSynchronizer） ​

  • 核心：一个 volatile int state（同步状态）+ FIFO 双向队列（等待线程）。
  • state 通过 CAS 修改；提供独占（ReentrantLock）与共享（Semaphore、CountDownLatch）两种模式。
  • 线程获取锁失败则入队并 park（阻塞），前驱释放后唤醒。

ReentrantLock ​

  • 公平锁：新线程先检查队列，若有等待者则排队（FIFO）。
  • 非公平锁：新线程先 CAS 抢占，抢不到再排队；性能更高但可能饥饿。
  • 可重入：state 计数，同一线程重入 +1，释放 -1，减到 0 才真正释放。

Condition ​

  • 配合 await / signal 实现精准唤醒，同一锁可创建多个条件队列（比 wait/notify 更精细）。

追问应对 ​

  • 「AQS 的 state 是什么？」→ 抽象同步状态，独占锁表示重入次数，共享锁表示许可数量。
  • 「公平锁 vs 非公平锁怎么选？」→ 非公平吞吐高（默认），公平避免饥饿；业务无强公平要求用非公平。

ThreadPoolExecutor 七大参数；四种拒绝策略；为什么不推荐 Executors ★★★ ​

七大参数 ​

  • corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（非核心线程空闲存活时间）、unit（时间单位）、workQueue（任务队列）、threadFactory（线程工厂）、handler（拒绝策略）。

执行流程 ​

  1. 任务提交，若线程数 < corePoolSize → 新建核心线程执行。
  2. 若 ≥ corePoolSize 且队列未满 → 入队。
  3. 队列已满且线程数 < maximumPoolSize → 新建非核心线程执行。
  4. 队列满且线程数 = maximumPoolSize → 执行拒绝策略。

四种拒绝策略 ​

  • AbortPolicy（默认，抛 RejectedExecutionException）。
  • CallerRunsPolicy（调用者线程执行，可降低提交速度）。
  • DiscardPolicy（直接丢弃）。
  • DiscardOldestPolicy（丢弃队列最老任务）。

为什么不推荐 Executors ​

  • FixedThreadPool/SingleThreadPool 用无界队列（LinkedBlockingQueue），任务堆积可能 OOM。
  • CachedThreadPool 线程数无上限（Integer.MAX_VALUE），高并发会创建大量线程 OOM。
  • 建议手动 new ThreadPoolExecutor(...) 指定有界队列 + 合理参数。

追问应对 ​

  • 「核心线程会被回收吗？」→ 默认不会，allowCoreThreadTimeOut(true) 可让核心线程也超时回收。
  • 「线程池大小怎么定？」→ 见下一条。

线程池参数如何根据业务设置 ★★★ ​

  • IO 密集：线程数 = CPU 核数 * 2（甚至更多，取决于阻塞比）。
  • CPU 密集：线程数 = CPU 核数 + 1。
  • 公式参考：N = 核数 * (1 + 等待时间/计算时间)。
  • 队列选有界（如 ArrayBlockingQueue）避免无限堆积；结合监控与压测调优。

追问应对 ​

  • 「为什么不直接把线程数设很大？」→ 线程切换有开销、占用内存（每个线程有栈）、过大会导致上下文切换频繁，吞吐反而下降。

CountDownLatch / CyclicBarrier / Semaphore ★★★ ​

  • CountDownLatch：计数器减到 0 释放等待线程，一次性，用于主线程等待多个子任务完成。
  • CyclicBarrier：N 个线程相互等待到齐后一起继续，可重复使用（reset），用于多线程分阶段同步。
  • Semaphore：信号量，控制同时访问资源的线程数（限流、连接池）。

追问应对 ​

  • 「CountDownLatch 和 CyclicBarrier 区别？」→ CountDownLatch 是一个线程等多个线程（一次性）；CyclicBarrier 是多个线程互相等（可循环）。

ConcurrentHashMap、CopyOnWriteArrayList 原理 ★★★ ​

ConcurrentHashMap ​

  • 见 Java 基础篇：1.8 用 synchronized + CAS 桶级锁 + 红黑树，读无锁。

CopyOnWriteArrayList ​

  • 写时复制：写操作（add/remove）加 ReentrantLock，复制整个数组改完再替换；读完全无锁。
  • 适合读多写极少；写开销大、内存占用高（每次写都复制数组）、数据弱一致。

追问应对 ​

  • 「CopyOnWriteArrayList 为什么读无锁？」→ 读的是旧数组引用（volatile），写是新数组，读写不干扰。
  • 「它适合什么场景？」→ 读多写极少（如监听器列表、配置白名单），写频繁会内存爆。

死锁四个条件；如何避免；活锁、饥饿 ★★★ ​

四个必要条件（缺一不可） ​

  1. 互斥：资源同时只能一个线程占用。
  2. 持有并等待：持有一个资源又等待另一个。
  3. 不可剥夺：已获得的资源不能被强制夺走。
  4. 循环等待：线程间形成资源等待环。

避免 ​

  • 破坏任一条件，常用「破坏循环等待」：按固定顺序加锁。
  • 其他：加锁超时（tryLock）、一次性申请所有资源、检测死锁后释放。

活锁 / 饥饿 ​

  • 活锁：线程互相礼让，导致都停不下来/停滞。
  • 饥饿：低优先级或非公平锁下，某线程一直拿不到资源。

排查 ​

  • jstack 输出 Found one Java-level deadlock。

追问应对 ​

  • 「死锁怎么排查？」→ jstack 看线程 dump，找到 BLOCKED 线程和它等待的锁持有者，画出等待环。

线程安全问题产生原因 ★★☆ ​

  • 根本原因：多线程共享可变数据，读写交叠导致数据竞争。
  • 三要素被破坏：可见性、原子性、有序性。
  • 解决：volatile（可见性/有序性）、synchronized（原子性）、原子类、并发容器、不可变对象（final）。

ThreadLocal 原理与内存泄漏 ★★★ ​

原理 ​

  • 每个线程 Thread 持有一个 ThreadLocalMap；key 是 ThreadLocal 的弱引用，value 是存的值。
  • set/get 时以当前线程为索引，从自己的 ThreadLocalMap 里读写，天然线程隔离。

内存泄漏 ​

  • ThreadLocal 被 GC 后 key 变 null，但 value 仍被 Entry 强引用，且线程池的线程长期存活，导致 value 无法回收 → 泄漏。
  • Entry 的 key 用弱引用，是为了在 ThreadLocal 回收后，下次 get/set 时清理 key 为 null 的 Entry。
  • 解决：用完必须调用 remove()。

追问应对 ​

  • 「为什么 key 用弱引用？」→ 让 ThreadLocal 对象可被回收；但 value 仍需手动 remove 清理。
  • 「ThreadLocal 和 synchronized 区别？」→ ThreadLocal 是「以空间换时间」的线程隔离（数据私有），synchronized 是「以时间换空间」的互斥。

CAS 原理与 ABA 问题 ★★★ ​

CAS（Compare And Swap） ​

  • 比较内存值与预期值，相等则交换；底层 CPU 原子指令（cmpxchg），无锁。
  • 缺点：① ABA 问题；② 自旋开销（高竞争下 CPU 空转）；③ 只能保证单个变量原子。

ABA ​

  • 值从 A 被改成 B 又改回 A，CAS 误以为没变。
  • 解决：加版本号 AtomicStampedReference（带版本戳）、AtomicMarkableReference（布尔标记）。

追问应对 ​

  • 「ABA 一定有问题吗？」→ 视场景，若只关心值是否变回原值则无所谓；若涉及引用语义（链表节点被换过）则需版本号。

原子类 AtomicInteger、LongAdder ★★☆ ​

  • AtomicInteger：基于 volatile + CAS（Unsafe）。
  • LongAdder：分段累加（多个 Cell 分散热点），高并发累加性能更好，但 sum() 非实时精确（汇总各 Cell）。
  • 选择：高并发频繁累加用 LongAdder，需要精确即时值用 AtomicLong。

追问应对 ​

  • 「LongAdder 为什么快？」→ 分散热点到多个 Cell，减少 CAS 竞争；代价是 sum 需汇总、非强一致。

CompletableFuture 异步编排 ★★★ ​

用途 ​

  • 异步任务编排，比 Future 的回调更灵活，可链式组合、异常处理。

常用方法 ​

  • thenApply（有依赖，转换结果）、thenAccept（消费结果）、thenRun（只执行）。
  • thenCombine（合并两个结果）、allOf（等待所有完成）、anyOf（任一完成）。
  • exceptionally（异常兜底）、handle（无论成败都处理）。
  • supplyAsync/runAsync 创建异步任务（可传自定义线程池）。

追问应对 ​

  • 「CompletableFuture 和 Future 区别？」→ Future 需阻塞 get 才能拿结果、无法链式编排；CompletableFuture 支持回调、组合、异常处理。
  • 「默认线程池问题？」→ 默认用 ForkJoinPool.commonPool，阻塞任务可能拖垮其他任务，建议传自定义线程池。

JMM 内存屏障、指令重排 ★★☆ ​

  • 内存屏障：屏障前的写对屏障后的读可见；volatile 写插 StoreStore+StoreLoad，读插 LoadLoad+LoadStore。
  • 指令重排：编译器/CPU 为提高性能重排指令，无同步时可能改变语义；双重校验锁单例需 volatile 防重排。

BlockingQueue、线程中断 interrupt ★★☆ ​

BlockingQueue ​

  • put/take 阻塞式；ArrayBlockingQueue（有界数组）、LinkedBlockingQueue（可选有界链表）、SynchronousQueue（无容量，直接交付）、DelayQueue（延迟）。
  • 是线程池与生产者消费者的基础。

interrupt ​

  • interrupt() 只设置中断标志，不真正停止线程。
  • sleep/wait 等阻塞方法收到中断抛 InterruptedException 并清除标志。
  • 配合 isInterrupted() 优雅退出。

易错点 ​

  • interrupt() 不会立即终止线程，需要线程自己检查中断标志响应。

synchronized 与 ReentrantLock 区别（前端转全栈必考）★★★ ​

维度synchronizedReentrantLock
实现JVM 层面（Monitor 指令）JDK 层面（AQS + CAS）
释放自动释放手动 unlock（finally 中）
功能不可中断、无超时、非公平可中断、超时、可选公平、多条件
底层锁升级AQS 队列
  • 建议：简单同步用 synchronized；需可中断/超时/公平/多条件用 ReentrantLock。

追问应对 ​

  • 「性能有区别吗？」→ JDK6 锁优化后差距很小；关注功能差异而非性能。

sleep() 与 wait() 区别 ★★★ ​

维度sleepwait
来源Thread 静态方法Object 实例方法
锁不释放锁释放锁
唤醒到时间自动醒notify/notifyAll 或超时
调用位置任意必须 synchronized 内（持有监视器）
  • 用途：sleep 让线程休眠让出 CPU；wait 用于线程协作（生产者-消费者）。

追问应对 ​

  • 「wait 为什么必须在 synchronized 内？」→ 需先持有对象监视器，否则抛 IllegalMonitorStateException。

volatile 与 synchronized 区别 ★★☆ ​

  • volatile：只保证可见性 + 有序性，不保证原子性，只能修饰变量，轻量级。
  • synchronized：保证可见性 + 原子性 + 有序性，可修饰方法/代码块，会加锁阻塞。
  • 选择：状态标志可见用 volatile；复合操作（读改写）用 synchronized 或原子类。

wait/notify 线程协作机制 ★★☆ ​

  • wait()：释放锁并等待，直到 notify/notifyAll 唤醒。
  • notify 唤醒一个等待线程，notifyAll 唤醒所有。
  • 必须在 synchronized 内调用。
  • 条件判断用 while 而非 if，防止虚假唤醒导致条件不满足仍往下执行。

追问应对 ​

  • 「为什么用 while 不用 if？」→ 虚假唤醒/多线程唤醒后条件可能已不满足，while 会重新判断。

手写生产者消费者（经典手撕）★★★ ​

// 用 wait/notify 实现（面试常让手写）
class BoundedBuffer {
    private final int[] buffer = new int[10];
    private int count = 0;
    private int putIndex = 0;
    private int takeIndex = 0;

    public synchronized void put(int v) throws InterruptedException {
        while (count == buffer.length) wait(); // 满则等待
        buffer[putIndex] = v;
        putIndex = (putIndex + 1) % buffer.length;
        count++;
        notifyAll();
    }

    public synchronized int take() throws InterruptedException {
        while (count == 0) wait(); // 空则等待
        int v = buffer[takeIndex];
        takeIndex = (takeIndex + 1) % buffer.length;
        count--;
        notifyAll();
        return v;
    }
}

手写线程池 / LRU（扩展）★★☆ ​

手写线程池核心思路 ​

  • 核心：任务队列 + 工作线程集合 + 拒绝策略。
  • 提交任务：线程数 < coreSize 新建线程，否则入队；工作线程循环从队列取任务执行。

class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    public LRUCache(int capacity) {
        super(capacity, 0.75f, true); // accessOrder=true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

悲观锁与乐观锁 ★★★ ​

是什么 ​

  • 悲观锁：假设并发冲突大概率发生，操作前先加锁，独占资源，其他线程阻塞等待（如 synchronized、ReentrantLock、数据库行锁 SELECT ... FOR UPDATE）。
  • 乐观锁：假设冲突概率低，不加锁，操作时用「版本号/CAS」检测是否被改过，冲突则重试（如 CAS、数据库乐观锁 version 字段）。

为什么 synchronized 是悲观锁 ​

  • synchronized 无论是否真的冲突，先加锁阻塞，属于「先锁再操作」的悲观策略。

乐观锁实现原理 ​

  • CAS（Compare And Swap）：比较内存值与预期值，相等则交换，否则重试。
  • 数据库乐观锁：UPDATE ... SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ?，影响行数为 0 则重试。

追问应对 ​

  • 「乐观锁和悲观锁怎么选？」→ 冲突多、竞争激烈用悲观锁；冲突少、读多写少用乐观锁（避免加锁开销）。
  • 「乐观锁有什么问题？」→ 自旋 CPU 开销、ABA、只适合单变量（见 CAS）。

线程池处理任务出现异常会发生什么 ★★★ ​

现象 ​

  • 通过 submit 提交的任务若抛异常，异常会被「吞掉」，不会直接抛出，而是封装到 Future 里，调用 future.get() 时才抛出 ExecutionException。
  • 通过 execute 提交的任务抛异常，会直接抛出，且该工作线程会「退出」并销毁，线程池会新建线程补上（所以线上日志可能看不到 execute 的异常）。

怎么处理 ​

  • submit 后用 future.get() 捕获异常。
  • 重写线程池的 afterExecute(Runnable r, Throwable t) 钩子方法记录异常。
  • 任务内部 try-catch 兜底，打印日志。
  • 自定义 ThreadFactory 设置 UncaughtExceptionHandler。

追问应对 ​

  • 「为什么 submit 会吞异常？」→ 因为任务返回值是 Future，异常被捕获存进 Future，等 get 时再抛。
  • 「execute 线程抛异常线程会怎样？」→ 线程终止，线程池自动新建线程补充。

ConcurrentHashMap 扩容机制 ★★★ ​

核心 ​

  • 1.8 扩容支持「多线程协助扩容」，不再只由一个线程完成。
  • 关键字段 sizeCtl：控制表初始化和扩容；transferIndex：标记迁移进度。
  • 扩容流程：
    1. 触发扩容的线程把 nextTable（新表）建好，容量翻倍。
    2. 迁移旧桶时，用 ForwardingNode（转发节点）标记「已迁移」的桶。
    3. 其他线程 put 时若命中 ForwardingNode，会「协助迁移」（helpTransfer），而不是阻塞等待。
    4. 每个线程领取一段桶区间（transferIndex 递减分配），各自迁移，减少竞争。

为什么能协助扩容 ​

  • 通过 sizeCtl 和 transferIndex 的 CAS 协作，多个线程分工迁移不同桶段，加速扩容。

追问应对 ​

  • 「CHM 扩容和 HashMap 扩容区别？」→ CHM 支持多线程协助扩容 + 用 ForwardingNode 保证读不阻塞；HashMap 单线程扩容。
  • 「扩容时读操作会阻塞吗？」→ 不会，读到 ForwardingNode 会转发到新表继续查。

ConcurrentHashMap 链表转红黑树的条件 ★★☆ ​

  • 与 HashMap 一致：链表长度 ≥ 8（TREEIFY_THRESHOLD）且数组容量 ≥ 64（MIN_TREEIFY_CAPACITY）时才树化，否则优先扩容。
  • 退化：节点数 ≤ 6（UNTREEIFY_THRESHOLD）时红黑树退化为链表。

为什么用 8 不用更小 ​

  • 泊松分布下链表长度到 8 的概率极低（约 6e-8），用 8 作为树化阈值是「树化开销」与「查询性能」的权衡；阈值太小会频繁树化（红黑树节点更占内存、维护复杂）。

为什么退化用 6 不用 7 ​

  • 8 和 6 之间留缓冲，避免「树化/退化」反复横跳（抖动）。

追问应对 ​

  • 「为什么链表长度到 8 还不树化？」→ 还要看数组容量，容量 < 64 时优先扩容（把链表分散），而不是树化。

线程池为什么先入队列而不是先创建最大线程 ★★★ ​

原因 ​

  • ThreadPoolExecutor 的执行逻辑：核心线程满 → 入队列 → 队列满 → 再创建到最大线程 → 仍满才拒绝。
  • 为什么不是「先创建到最大线程再入队」：
    1. 线程创建和销毁成本高（内存 + 调度），优先用队列缓冲能避免频繁扩缩容。
    2. 核心线程能处理时，用队列排队即可，没必要一上来就开满最大线程（浪费资源）。
    3. 队列起到「削峰 + 缓冲」作用，把瞬时高峰平摊给核心线程慢慢消化。

这带来的坑 ​

  • 若队列是无界队列（如 LinkedBlockingQueue），任务永远堆积在队列，maximumPoolSize 形同虚设（永远不会创建非核心线程），可能 OOM。

追问应对 ​

  • 「想先打满线程再入队怎么办？」→ 用有界队列 + 合理的 core/max 参数；或自定义队列，让队列在满之前先触发线程扩容。

自旋锁的优缺点 ★★★ ​

是什么 ​

  • 自旋锁：线程不阻塞（不放弃 CPU），而是「循环尝试获取锁」（CAS 自旋），直到成功。
  • JVM 里轻量级锁就是 CAS 自旋获取；AtomicInteger 的 CAS 也类似自旋。

优点 ​

  • 避免线程阻塞/唤醒的上下文切换开销（系统调用、线程调度），锁持有时间短时效率高。

缺点 ​

  • 锁竞争激烈时，自旋线程空转浪费 CPU（忙等），可能反而比阻塞更差。
  • 自旋不能保证公平，可能饥饿。

适用场景 ​

  • 锁持有时间短、竞争不激烈、多核 CPU。

追问应对 ​

  • 「自旋锁和阻塞锁怎么选？」→ 临界区短、竞争少用自旋；临界区长、竞争激烈用阻塞。
  • 「JDK 怎么处理自旋？」→ 自适应自旋（根据上次自旋是否成功动态调整自旋次数），避免固定自旋浪费。

进程和线程的区别，线程真的能节省时间吗 ★★★ ​

区别 ​

维度进程线程
资源独立地址空间、资源共享进程资源
独立性独立，隔离进程内共享
切换开销大小
通信IPC（管道/队列/共享内存）共享内存直接通信
崩溃影响一个进程挂不影响其他一个线程异常可能影响整个进程

线程能节省时间吗 ​

  • 能，但要分场景：
    • 多核 + 可并行任务：多线程真正并行，缩短总耗时。
    • IO 密集：线程等待 IO 时切换其他线程，提高 CPU 利用率。
    • 单核 CPU 密集：多线程反而因上下文切换降低效率（不一定省时间）。

追问应对 ​

  • 「为什么线程切换比进程快？」→ 线程共享地址空间，切换时只需切换寄存器和栈，不需切换内存映射等进程上下文。

Java 线程间通信方式 ★★★ ​

  • 共享内存：通过共享变量 + volatile/synchronized 保证可见性。
  • wait/notify/notifyAll：基于锁的等待唤醒（Object 方法）。
  • Lock + Condition：更精细的条件队列。
  • 阻塞队列（BlockingQueue）：生产者-消费者模式。
  • 管道（PipedStream）：线程间 IO 流通信（少用）。
  • CountDownLatch/CyclicBarrier/Semaphore：并发工具类协调。
  • join()：等待其他线程结束。
  • ThreadLocal：线程私有数据（严格说是隔离，不是通信）。

追问应对 ​

  • 「线程间通信最常用哪种？」→ 生产环境常用阻塞队列 + 共享内存 + volatile/synchronized。

ThreadLocalMap 结构与扩容机制 ★★☆ ​

结构 ​

  • ThreadLocalMap 是 ThreadLocal 的静态内部类，本质是一个 Entry[] 数组（不是 HashMap 的链表结构）。
  • Entry 继承 WeakReference，key 是 ThreadLocal 的弱引用，value 是值。
  • 用「开放定址法」解决 hash 冲突（线性探测，冲突时往后找空位），因为 Entry 数组通常不会太大且要配合弱引用清理。

扩容 ​

  • 默认初始容量 16，负载因子 2/3。
  • 当元素数量 ≥ 阈值（size >= threshold）时触发 rehash：
    1. 先清理所有 key 为 null 的失效 Entry。
    2. 清理后仍超过 threshold * 3/4 时，扩容为原来的 2 倍，重新计算 index 重新散列。

追问应对 ​

  • 「ThreadLocalMap 为什么用开放定址不用拉链？」→ 结构简单、避免链表节点额外开销，且 Entry 用弱引用需频繁清理，线性探测实现清理更直接。

ThreadLocal 父子线程如何共享数据（InheritableThreadLocal）★★★ ​

结论 ​

  • 普通 ThreadLocal 无法在父子线程间共享（父线程 set 的值，子线程拿不到）。
  • 用 InheritableThreadLocal：子线程创建时会「复制」父线程的 InheritableThreadLocal 值。

原理 ​

  • Thread 创建子线程时（构造器里 init()），会调用 parent.inheritableThreadLocals，把父线程的 InheritableThreadLocal 值复制一份到子线程。

局限 ​

  • 只在线程创建时复制一次，之后父线程再改值，子线程不会同步。
  • 线程池场景失效：线程是复用的，不是在父线程中即时创建，无法继承（需用阿里开源的 TransmittableThreadLocal 解决）。

追问应对 ​

  • 「线程池下 InheritableThreadLocal 为什么失效？」→ 线程池线程是预先创建复用的，不在「父线程创建子线程」时点复制，所以继承不到；需用 TransmittableThreadLocal 在任务提交/执行时透传。

进程、线程、协程的区别 ★★☆ ​

  • 进程：资源分配的最小单位，独立地址空间。
  • 线程：CPU 调度的最小单位，共享进程资源。
  • 协程：用户态轻量级线程，由程序自己调度，切换开销极小，不依赖 OS 调度（如 Go goroutine、Java 虚拟线程/纤程）。

追问应对 ​

  • 「虚拟线程和协程什么关系？」→ 虚拟线程可看作 JVM 层面的协程/纤程，由 JVM 调度而非 OS，轻量、可海量创建。
