Spring 全家桶 ​

怎么用这份笔记

  • 分级：★★★ 必须吃透 / ★★☆ 了解即可（记结论就行） / ★☆☆ 可以跳过（一句话看一眼）
  • 【简历亮点，高频追问】：简历里写过的技术，面试官会顺着往下挖，这段必须能展开讲
  • 每个考点固定三段：通俗理解 → 我的项目关联 → 面试答题话术
  • 「我的项目关联」里的坑分两种，别搞混：
    • 写**「线上」**= 真实发生过的问题，可以直接讲现象和修复
    • 写**「通用坑」= 经典坑 / 资料里学到的，我们项目没实际踩到，面试时别说成自己踩过**

1. IOC 与 DI ★★★ ​

通俗理解IOC 是思想：对象的创建和依赖由「业务代码自己 new」反转给 Spring 容器管。DI 是实现手段：容器通过构造器 / setter / 字段把依赖塞进来。好处是解耦、好测试（能注入 mock）。注入方式优先构造器（依赖不可变、能暴露循环依赖、方便测试），字段注入（@Autowired 直接标在字段上）不推荐，因为它隐藏了依赖、单测时只能靠反射。

我的项目关联 我们所有服务都是 SpringBoot，Service 之间全靠构造器注入。后台管理服务（yld-admin-service）和 App 服务（yld-app-service）里都是这么写的，不写 new，也好写单测。

面试答题话术 「IOC 是思想，DI 是实现。好处是解耦和好测试。注入方式我优先构造器注入，因为依赖是 final 不可变、循环依赖能早点暴露、单测直接 new 就行；字段注入我不用，隐藏依赖还不好测。项目里 Service 全是构造器注入。」

2. BeanFactory 与 ApplicationContext ★★☆ ​

通俗理解BeanFactory 是最底层容器，懒加载，getBean 时才创建，功能少。ApplicationContext 继承它，启动时就把单例 Bean 全建好（饿加载），还提供国际化、事件发布、资源加载、AOP 等。生产上用的都是 ApplicationContext。

我的项目关联 记结论：平时说的 Spring 容器就是 ApplicationContext，SpringBoot 里也是它。启动慢一点但换来实时可用，这对我们网关这种启动后要立刻扛流量的服务是好事。

面试答题话术 「BeanFactory 是底层接口，懒加载、功能少；ApplicationContext 继承它，启动就预实例化单例，还多了事件、国际化、资源加载这些。生产用 ApplicationContext，SpringBoot 里内置的就是它。」

3. Bean 生命周期 ★★★ ​

通俗理解 八步：实例化（构造器）→ 属性注入 → Aware 接口回调 → BeanPostProcessor 前置 → 初始化（@PostConstruct → afterPropertiesSet → init-method）→ BeanPostProcessor 后置（AOP 代理就在这一步生成）→ 使用 → 销毁（@PreDestroy → destroy → destroy-method）。重点记两件事：@PostConstruct 比 afterPropertiesSet 先执行；AOP 代理在「后置处理」这一环产生。

我的项目关联 我们用它做初始化：比如网关启动时要把「协议命令处理器」注册到一张表里，就写在 @PostConstruct 或 afterPropertiesSet 里。不用深挖 BeanPostProcessor 内部源码，记住它是「Bean 初始化的前后钩子、AOP 靠它」就够了。

面试答题话术 「生命周期核心是：实例化、属性注入、Aware、初始化前后两个 BeanPostProcessor、使用、销毁。两个高频点：@PostConstruct 比 InitializingBean 的 afterPropertiesSet 早；AOP 代理是在 postProcessAfterInitialization 里生成的。我用它做启动初始化，比如把协议处理器注册到本地表。」

4. Bean 作用域 ★★☆ ​

通俗理解 默认 singleton（容器里一个），prototype 每次拿新的，Web 里还有 request/session/application。有个坑：prototype Bean 注入到 singleton Bean 里，只会注入一次，之后不会每次新建——想每次拿新的得用 @Lookup 或注入 ObjectFactory。

我的项目关联 我们 99% 是单例，无状态的 Service 都用默认单例。prototype 基本不用，所以那个注入坑属于「通用坑」，没实际踩过，知道有这回事就行。

面试答题话术 「默认单例，prototype 每次新建。坑是 prototype 注入到单例里只注入一次，要每次新实例得用 @Lookup 或 ObjectFactory。项目里几乎全用单例。」

5. 单例 Bean 的线程安全 ★★★ 【简历亮点，高频追问】 ​

通俗理解单例 Bean 只要「无状态」（只有方法、没有可变的成员变量）就是线程安全的。一旦在单例 Bean 里放了共享可变字段（比如一个计数器、一个 Map 当本地缓存），多线程访问就出问题。解决办法：尽量无状态；要状态就用 ThreadLocal 隔离，或者用并发容器 / 原子类；再不行才改 prototype。Controller 默认单例，只要不写可变成员变量就安全，方法里的局部变量天然安全。

我的项目关联这条我特别有体会。 网关里有些处理器 Bean 是单例的，早期有人在里面写了 private Map 当本地缓存，多线程一跑数据就乱了（现象是「同一个设备的状态莫名其妙被覆盖」），后来改成 ConcurrentHashMap 或者干脆挪到 Redis 才解决。这是真实踩过的坑，也是我现在写单例 Bean 的铁律：不放可变字段。

面试答题话术 「单例 Bean 只要无状态就线程安全。我踩过这个坑——网关里一个单例处理器里放了普通 HashMap 当缓存，多线程下数据互相覆盖，后来换成 ConcurrentHashMap 或者直接放 Redis。所以我的原则是：单例 Bean 不放共享可变字段，要状态就用并发容器或 ThreadLocal。Controller 单例安全也是同一个道理，别写成员变量。」

6. 循环依赖与三级缓存 ★★☆（记结论即可） ​

通俗理解 Spring 用三级缓存解决「单例 + 字段/setter 注入」的循环依赖：一级放成品 Bean，二级放提前暴露的半成品，三级放能生成半成品的 ObjectFactory（AOP 场景下保证拿到的是代理）。结论就三句：只能解决单例 + setter/字段注入；构造器注入的循环依赖解决不了（直接抛 BeanCurrentlyInCreationException）；SpringBoot 2.6 之后默认禁止循环依赖，要用得手动开。不用去背三级缓存的逐行流转。

我的项目关联 现在基本不让自己写出循环依赖——SpringBoot 2.6 之后默认就报错了。我们遇到时的处理不是去开开关，而是直接重构：把公共逻辑抽到第三个 Bean 里。这属于设计问题，别靠框架兜。

面试答题话术 「三级缓存解决的是单例加 setter/字段注入的循环依赖，一级是成品、二级是提前暴露的半成品、三级是生成半成品的工厂。结论最重要：构造器注入的循环依赖解决不了，而且 SpringBoot 2.6 之后默认就禁止循环依赖了。我项目里遇到就直接重构抽公共 Bean，不靠框架兜底。」

7. AOP 原理（JDK 动态代理 vs CGLIB）★★★ 【简历亮点，高频追问】 ​

通俗理解AOP 就是把日志、事务、权限这些「横切逻辑」从业务代码里抽出来，用代理在方法前后织进去。两种实现：JDK 动态代理基于接口（Proxy.newProxyInstance），要求目标有接口；CGLIB 基于继承生成子类，不需要接口，但 final 类/方法代理不了。Spring 默认「有接口用 JDK、没接口用 CGLIB」，SpringBoot 2.x 起默认直接 CGLIB。

我的项目关联 我们用它做统一日志、接口耗时统计、权限校验，还有最关键的——声明式事务（@Transactional 本质就是 AOP）。这里有个认知要点：因为事务是 AOP 实现的，所以它依赖「走代理」，同一类内部 this.方法() 调用不走代理、事务就会失效。

面试答题话术 「AOP 是用代理把横切逻辑织进方法前后。JDK 代理基于接口，CGLIB 基于继承、不需要接口但不能代理 final。SpringBoot 现在默认用 CGLIB。项目里事务、日志、权限都是 AOP 做的。关键认知是：事务靠代理生效，所以 this 自调用会失效。」

8. @Transactional 失效场景 ★★★ 【简历亮点，高频追问】 ​

通俗理解 最常见六种失效：① 方法不是 public（事务只对 public 生效）；② 同类内部 this.xxx() 自调用，不走代理；③ 异常被自己 catch 吞了，事务感知不到；④ 抛的是受检异常，默认只回滚 RuntimeException/Error，要加 rollbackFor = Exception.class；⑤ 方法所在类不是 Spring Bean；⑥ 数据库引擎不支持事务（如 MyISAM）。自调用的三种解法：注入自己、AopContext.currentProxy()、或者把方法抽到另一个 Bean。

我的项目关联这个坑我们在订单、支付相关逻辑上确实遇到过。 现象是「内部方法报错了但数据没回滚」，排查发现是同类里的 this.xxx() 调用绕过了代理。修复就是把这段逻辑抽到独立的 Service Bean，或者注入自身调。现在团队规范是：事务方法绝不和调用方放同一个类。

面试答题话术 「失效主要有六种：非 public、自调用、异常被吞、受检异常不回滚、类不是 Bean、引擎不支持事务。最常见的是自调用，因为事务是代理实现的，this 调用不走代理。我项目里真遇到过——内部方法报错但没回滚，后来把逻辑抽到独立 Bean 解决。我的规范是：事务方法不和调用方放一个类，受检异常一定加 rollbackFor。」

9. 事务传播行为 ★★★ ​

通俗理解 七种，重点记两个：REQUIRED（默认，有事务就加入，没有就新建，事务内任何一处回滚全体回滚）；REQUIRES_NEW（永远新建独立事务，把当前事务挂起，内层回滚不影响外层）。其余知道名字即可：SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER、NESTED。

我的项目关联 最典型的用法是「主流程失败要回滚，但操作日志必须记下来」——日志那块就用 REQUIRES_NEW，保证主事务回滚了日志还在。对账、订单主流程用默认 REQUIRED。

面试答题话术 「七种传播行为，重点就两个：REQUIRED 是默认，共用事务，一处回滚全回滚；REQUIRES_NEW 是独立事务，挂起外层，内层回滚不影响外层。项目里操作日志用 REQUIRES_NEW，保证主事务回滚了日志还在，主流程用默认 REQUIRED。」

10. SpringBoot 自动配置原理 ★★★ ​

通俗理解@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。@EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector) 去读 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（2.7 之后的新位置，老版本才是 spring.factories），拿到一堆自动配置类，再用 @ConditionalOnClass、@ConditionalOnMissingBean、@ConditionalOnProperty 判断要不要生效，从而实现「约定大于配置」。

我的项目关联 我们写过内部 starter 封装公共能力（比如统一异常、日志、埋点），就是照着这个套路：写配置类 + 在 imports 文件里注册 + 条件注解，业务服务引依赖就自动生效。注意：现在面试要答 AutoConfiguration.imports，老说 spring.factories 会显旧。

面试答题话术 「@SpringBootApplication 拆开是配置类、开启自动配置、组件扫描。自动配置的核心是 @Import 导入 AutoConfigurationImportSelector，读 AutoConfiguration.imports 文件拿到自动配置类，再用 ConditionalOnClass、ConditionalOnMissingBean 这些条件注解判断是否生效。注意 2.7 之后是 imports 文件，不是老的 spring.factories。我项目里封装公共 starter 就是这个套路。」

11. SpringMVC 请求处理流程 ★★★ ​

通俗理解 请求先到 DispatcherServlet（前端控制器）→ HandlerMapping 按 URL 找到对应的方法 → HandlerAdapter 执行方法（做参数解析、类型转换、校验）→ 返回 ModelAndView 或者 @ResponseBody 直接写 JSON → ViewResolver 解析视图（返回 JSON 就不走这步）→ 响应。

我的项目关联 我们基本都是前后端分离 + REST 接口，所以「@ResponseBody 直接返回 JSON」这条路径最多，ViewResolver 基本用不到。参数解析这块我们在自定义注解上做过扩展，所以知道它由 HandlerAdapter 里的参数解析器负责。

面试答题话术 「流程是：请求到 DispatcherServlet，HandlerMapping 找 Handler，HandlerAdapter 执行并处理参数，返回 ModelAndView 或 @ResponseBody 直接写 JSON，最后 ViewResolver 解析视图。前后端分离的项目基本都走 @ResponseBody 返 JSON，视图解析那步用不上。」

12. Bean 装配注解区别 ★★☆ ​

通俗理解 @Autowired 是 Spring 的，默认按类型注入，配合 @Qualifier 按名字。@Resource 是 JDK 标准的，默认按名字，找不到再按类型。@Inject 是 JSR-330 的，跟 @Autowired 差不多。

我的项目关联 一句话：同一个类型有多个实现时，我用 @Qualifier 或者 @Resource 按名字指明。这是常规用法，没坑。

面试答题话术 「@Autowired 是 Spring 的、默认按类型；@Resource 是 JDK 的、默认按名字找不到再按类型。多个同类型实现时用 @Qualifier 或 @Resource 指定名字。」

13. Spring、SpringBoot、SpringCloud 区别 ★★★ ​

通俗理解Spring 是地基：提供 IOC 和 AOP，但配置繁琐。SpringBoot 是脚手架：自动配置 + 起步依赖 + 内嵌服务器，让搭建变快。SpringCloud 是微服务工具集：注册中心、配置中心、网关、服务调用、熔断。一句话：Spring 是地基，SpringBoot 是快速建房，SpringCloud 是城市基础设施。

我的项目关联 我们的服务全是 SpringBoot 打底，像 yld-tcec 互联互通、yld-admin-service 后台服务都是独立的 SpringBoot 应用，之间再靠远程调用和消息串起来。

面试答题话术 「Spring 是核心框架，IOC 加 AOP，但配置麻烦；SpringBoot 是它的封装，自动配置加起步依赖，开箱即用；SpringCloud 是微服务工具集，管注册、配置、网关、调用、熔断。一句话：Spring 是地基，Boot 是快速建房，Cloud 是城市基础设施。我们项目就是 SpringBoot 应用之间靠远程调用和消息串联。」

14. Spring Security 鉴权链路（JWT）★★★ 【简历亮点，高频追问】 ​

通俗理解 基于过滤器链：请求先过认证和授权的过滤器，再进 Controller。JWT 认证流程：请求带 Token → 自定义 JWT 过滤器解析并校验签名和有效期 → 把用户信息塞进 SecurityContextHolder → 后续授权就基于它判断。JWT 是 Header.Payload.Signature 三段 Base64，Payload 只放用户 id、角色这些非敏感信息。

我的项目关联 后台管理端和 App 端都是 JWT 鉴权：登录发 token，之后每个请求走 JWT 过滤器。一个必须讲的坑：JWT 是无状态的，签出去就收不回，没法主动踢人下线——我们的做法是配合 Redis 存黑名单或者存登录态。另外 JWT 过滤器一定要排在用户名密码过滤器之前，白名单（登录、静态资源）要放行。这是通用坑，我们规范上处理了。

面试答题话术 「Security 是过滤器链，请求先认证再授权。JWT 流程是：前端带 token，自定义过滤器解析校验，把用户信息放进 SecurityContextHolder，后面授权基于它。JWT 本身无状态、签了收不回，所以踢下线要配合 Redis 黑名单。还有过滤器顺序要在用户名密码过滤器之前，白名单要放行。项目里后台和 App 都是这套。」

15. MyBatis 一级缓存、二级缓存 ★★★ ​

通俗理解一级缓存是 SqlSession 级别，默认开，同一个 SqlSession 内相同查询走缓存；SqlSession 关闭或执行增删改就清空。二级缓存是 Mapper（namespace）级别，跨 SqlSession，需要显式开（cacheEnabled=true + <cache/>），实体要序列化。结论：MyBatis 缓存粒度粗、分布式下容易读到旧数据，所以我们线上基本关掉二级缓存，用 Redis 做缓存。

我的项目关联 我们直接关二级缓存。原因很直接：服务是多实例部署，二级缓存是「单机」的，A 实例改了数据，B 实例的缓存还是旧的，会读到脏数据。缓存统一交给 Redis，可控、能主动失效。

面试答题话术 「一级缓存是 SqlSession 级、默认开，执行增删改或关闭就清；二级缓存是 Mapper 级、跨 SqlSession、要显式开。但二级缓存是单机的，多实例部署会读到脏数据，所以线上我一般关掉，缓存统一用 Redis。项目里就是这么做的。」

16. MyBatis 执行流程 ★★☆ ​

通俗理解 配置阶段解析 XML/注解生成 Configuration 和 MappedStatement；然后开 SqlSession，内部建 Executor；执行时 Mapper 接口的动态代理找到对应的 MappedStatement，Executor 交给 StatementHandler 处理参数、ResultSetHandler 把结果映射成对象。插件（Interceptor）就是在这几个环节做动态代理拦截，分页插件就是这么实现的。

我的项目关联 知道流程和「分页插件基于 Interceptor」这个结论就行，不用背源码。我们用的 MyBatis-Plus 分页插件就是这个原理。

面试答题话术 「流程是配置解析、开 SqlSession、动态代理找到 MappedStatement、Executor 执行、StatementHandler 处理参数、ResultSetHandler 映射结果。插件是基于 Interceptor 代理这几步，分页插件就是这么做的。」

17. MyBatis-Plus 相比 MyBatis 的优势 ★★☆ ​

通俗理解 内置通用 CRUD（BaseMapper）、条件构造器 Wrapper、分页插件、逻辑删除、字段自动填充、代码生成器，省掉大量样板 SQL。本质还是 MyBatis 的增强，底层没变。

18. #{} 和 ${} 区别（必考）★★★ ​

通俗理解#{} 是预编译占位符（底层是 PreparedStatement 的 ?），参数按值绑定、自动加引号、能防 SQL 注入。${} 是直接字符串拼接，不防注入，只能用在表名、列名这种不能预编译的地方，而且必须做白名单校验。结论一句话：能用 #{} 绝不用 ${}。

我的项目关联 我们项目规范是禁止 ${}，静态扫描会拦。只有极少数动态排序字段（比如后台按哪个字段排序）用 ${}，而且字段名必须走白名单校验。这是安全底线。

面试答题话术 「#{} 是预编译占位符，参数按值绑定，防注入；${} 是字符串拼接，不防注入。所以能用 #{} 就不用 ${}，只有表名、列名、排序字段这种没法预编译的才用，而且必须白名单校验。项目里我们直接禁止 ${}，静态扫描拦住。」

19. Spring 中的设计模式 ★★★ ​

通俗理解工厂（BeanFactory）、单例（默认 Bean）、代理（AOP）、模板方法（JdbcTemplate/RestTemplate）、观察者（ApplicationEvent）、适配器（HandlerAdapter）、策略（资源处理）。重点能展开的是代理模式——AOP 就是它，用来织入事务、日志。

我的项目关联 我用得最多的是「模板方法 + 策略」：充电桩不同协议的命令处理，用策略模式按协议类型分发到不同处理器；公共流程用模板方法抽出来，差异部分子类实现。这样加一种新协议只加一个实现类，不动主流程。

面试答题话术 「Spring 里常见的：工厂用 BeanFactory，单例是默认 Bean 作用域，代理是 AOP，模板方法在 JdbcTemplate，观察者是事件机制，适配器是 HandlerAdapter。我自己在网关里用策略模式按协议分发处理器，加新协议只加实现类不动主流程。」

20. @Async 失效原因 ★★☆ ​

通俗理解 跟事务失效一个道理，都是因为「依赖代理」：同类 this 自调用不走代理、方法非 public、类不是 Spring Bean、没开 @EnableAsync。解法也一样：抽到另一个 Bean、注入自身、用 AopContext.currentProxy()。

我的项目关联 我们异步任务用线程池 + @Async 都行，但记住「自调用失效」这一条就够。它和 @Transactional 失效是同一类问题，底层都是 AOP 代理。

面试答题话术 「@Async 失效原因跟 @Transactional 一样：自调用、非 public、不是 Bean、没开 @EnableAsync。本质是都靠代理，this 调用不走代理。解决就是抽到别的 Bean 或注入自身。」

21. SpringMVC 参数校验、全局异常处理 ★★☆ ​

通俗理解参数校验用 @Valid/@Validated 加 @NotNull/@NotBlank/@Size，失败可以全局统一处理。全局异常用 @RestControllerAdvice + @ExceptionHandler，统一返回错误结构，别让异常堆栈直接暴露给前端。

我的项目关联 我们统一用 @RestControllerAdvice 做全局异常，所有接口返回统一的 code/message/data 结构，参数校验失败、业务异常、系统异常都在这里收口。这样前端处理统一，也不会把栈信息漏出去。

面试答题话术 「参数校验用 @Valid 加注解，失败抛异常。全局异常用 @RestControllerAdvice 加 @ExceptionHandler 统一处理，返回统一结构。项目里所有接口的返回结构、参数校验错误、系统异常都在一个 Advice 里收口，避免把堆栈暴露给前端。」

23. 网关作用、Gateway 过滤器 ★★☆ ​

通俗理解API 网关的作用：统一入口、路由转发、鉴权、限流、日志、灰度。Spring Cloud Gateway 基于 WebFlux（响应式、非阻塞），过滤器分全局 GlobalFilter 和局部 GatewayFilter，断言 Predicate 按路径、方法、header 匹配路由。

我的项目关联注意别和我们的「协议网关」混了：Spring Cloud Gateway 是 HTTP 层的 API 网关；我们说的充电桩网关是基于 Netty 的 TCP 长连接网关。面试时要说清这两个是完全不同的东西，不要一被问「网关」就只说 Netty。

面试答题话术 「API 网关做统一入口、路由、鉴权、限流。Gateway 基于 WebFlux 是非阻塞的，过滤器分全局和局部，断言按路径方法匹配。这里我要区分一下：Spring Cloud Gateway 是 HTTP 层网关，我们项目里还有个基于 Netty 的 TCP 协议网关接充电桩，两个不是一回事。」

24. 微服务架构的优缺点 ★★☆ ​

面试答题话术 「优点是独立部署、故障隔离、可扩展；缺点是分布式复杂度高，事务、一致性、网络、运维都难。项目里我们按业务拆了后台、App、互联互通几个服务，好处是隔离，代价是跨服务一致性要靠消息、幂等和对账补偿来兜。」

28. SpringBoot 启动流程 ★★★ ​

通俗理解 main 方法创建 SpringApplication → 推断应用类型（Servlet 还是 Reactive）→ 加载初始化器和监听器 → 准备 Environment（加载配置、命令行参数、profile）→ 创建 ApplicationContext → refresh 刷新（扫描 Bean、执行自动配置）→ 启动内嵌的 Tomcat → 发布 ApplicationReadyEvent。

我的项目关联 知道「refresh 阶段才会自动配置、内嵌 Tomcat 是自动配置里创建的」这个结论就行。实际排障时有个用处：启动卡住或 Bean 冲突，看日志基本卡在 refresh 阶段。

面试答题话术 「流程是：创建 SpringApplication、推断应用类型、准备 Environment、创建 ApplicationContext、refresh 扫描并自动配置、启动内嵌 Tomcat、发就绪事件。重点知道两件事：自动配置发生在 refresh 阶段，内嵌 Tomcat 也是自动配置里建的。」

29. SpringBoot 核心注解 ★★★ ​

通俗理解@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。条件装配三件套：@ConditionalOnClass（类在才生效）、@ConditionalOnMissingBean（没有这个 Bean 才生效）、@ConditionalOnProperty（配置满足才生效）。@Configuration+@Bean 用来声明 Bean，@Component/@Service/@Repository/@Controller 靠组件扫描。

我的项目关联 我们自定义 starter 或者做条件化配置时就用这三个条件注解，比如「只有当业务方引入了某个依赖、且没自己定义 Bean 时，才注入我们的默认实现」。

面试答题话术 「@SpringBootApplication 拆开是配置类、开启自动配置、组件扫描三个。自动配置靠 @Import 导入选择器。条件装配最关键的是 @ConditionalOnClass、@ConditionalOnMissingBean、@ConditionalOnProperty，我们封装 starter 时就靠这三个控制生效条件。」

30. MyBatis SqlSession 的线程安全问题 ★★★ ​

通俗理解SqlSession 不是线程安全的：它对应一个数据库连接 + 一个一级缓存，多线程共享会互相污染。所以每次操作要用一个新的、用完关闭。跟 Spring 整合后就不用担心了——Mapper 代理是单例，但内部通过 SqlSessionTemplate 用 ThreadLocal 给每个线程绑定独立的 SqlSession。

我的项目关联 我们直接用 Spring 整合的 Mapper，从来不手动开 SqlSession，所以这个坑碰不到。但面试问「Mapper 是单例的为什么不冲突」，答「底层 SqlSessionTemplate 用 ThreadLocal 给每个线程独立的 SqlSession」就对了。

面试答题话术 「SqlSession 非线程安全，因为它绑定连接和一级缓存，多线程共享会污染。Spring 整合后 Mapper 代理虽然是单例，但底层用 SqlSessionTemplate 加 ThreadLocal，每个线程拿到独立的 SqlSession，所以安全。项目里我们只用 Mapper，不手写 SqlSession。」

31. MyBatis 的优缺点 ★★☆ ​

通俗理解 优点：SQL 和代码分离、可手写复杂 SQL、动态 SQL 灵活、轻量无侵入、插件扩展好。缺点：SQL 依赖数据库方言、迁移要改 SQL、样板代码多、缓存粒度粗、复杂关联还得手写 join。

我的项目关联 选它就是看中「SQL 可控」——充电业务里统计、对账、按条件查订单这些复杂查询，要求能精确调优，手写 SQL 比 ORM 生成的更可控。

面试答题话术 「MyBatis 优点是 SQL 可控、能写复杂查询和动态 SQL、轻量、插件扩展好；缺点是依赖数据库方言、样板代码多、缓存粒度粗。选它是因为我们业务里对账、统计这种复杂查询要求 SQL 可控、能精确调优。」

32. SpringBoot 的 starter 机制及自定义 starter ★★★ ​

通俗理解starter 就是一个「开箱即用的依赖包」，把某个功能需要的所有 jar 依赖 + 自动配置类打包在一起。你只要引一个 spring-boot-starter-web，它就把 SpringMVC、内嵌 Tomcat、Jackson 这些依赖和默认配置全带上了。命名规范：官方叫 spring-boot-starter-xxx，第三方自定义叫 xxx-spring-boot-starter（前缀位置相反，一眼区分官方还是第三方）。自定义 starter 套路就三步：写一个 @Configuration 配置类 + 在 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 里注册 + 用 @ConditionalOnXxx 控制生效条件，业务方引依赖就自动生效。

我的项目关联 我们项目里把公共能力抽成了内部 common 模块（common-core、common-redis、common-mybatis），统一异常、日志、埋点这些就是按 starter 套路封装的：写配置类 + 在 imports 文件注册 + 条件注解，各业务服务（互联互通、订单、支付）引依赖就自动生效，不用每个服务重复写。注意：SpringBoot 3.x 下自动配置注册位置就是 AutoConfiguration.imports，不是老的 spring.factories，面试答错了显旧。

面试答题话术 「starter 就是打包了依赖和自动配置的『开箱即用』包，引一个 starter 就把整个功能的依赖和默认配置带进来。命名上官方是 spring-boot-starter-xxx，第三方反过来是 xxx-spring-boot-starter。自定义 starter 三步：写配置类、在 AutoConfiguration.imports 里注册、用 ConditionalOnXxx 控制生效条件。我们项目里就把公共能力封装成内部 starter，各服务引依赖自动生效，注意 3.x 是 imports 文件不是老的 spring.factories。」

33. SpringBoot 的父依赖 spring-boot-starter-parent 的作用 ★★☆ ​

通俗理解spring-boot-starter-parent 是 SpringBoot 提供的「父 POM」，作用三块：① 依赖版本管理——它继承了 spring-boot-dependencies（BOM），把几乎所有常用依赖的版本锁定好，你引 starter 不用写版本号；② 默认插件配置——打包、编译插件、资源过滤都配好，还指定了 Java 版本；③ 默认配置——UTF-8 编码、properties 里可用 @xxx@ 占位符替换等。核心一句话：统一管版本，避免版本冲突。

我的项目关联 我们项目没直接用 spring-boot-starter-parent 当 parent，而是在根 pom 的 dependencyManagement 里直接 import 了 spring-boot-dependencies 这个 BOM，还叠加了自己的 yld-tcec-common-bom、mybatis-plus-bom。效果和 parent 继承的版本管理一样：引 starter、MySQL、Redis、Kafka、MyBatis-Plus 都不用写版本号，版本统一由 BOM 管。区别只是没继承 parent 里的默认插件配置，插件我们在根 pom 自己配。面试时可以顺带说一句「parent 的本质就是 BOM 管版本」。

面试答题话术 「spring-boot-starter-parent 主要三件事：统一依赖版本（继承 spring-boot-dependencies 这个 BOM）、提供默认插件配置、给默认编码和编译级别。最大好处是引 starter 不用写版本号，版本统一不冲突。我们项目里是直接 import 这个 BOM 到 dependencyManagement，效果一样，引 MySQL、Redis、MyBatis-Plus 都不写版本，插件自己在根 pom 配。」

34. SpringBoot 中读取配置的几种方式（@Value、@ConfigurationProperties、Environment）★★★ ​

通俗理解 三种：① @Value("${key}") 读单个值，支持默认值 @Value("${key:default}") 和 SpEL；② @ConfigurationProperties(prefix="xxx") 把一组配置批量绑定到 POJO 类，需配合 @Component 或 @EnableConfigurationProperties 注册成 Bean；③ 注入 Environment 对象，用 environment.getProperty("key") 手动读，适合运行时动态读或非 Bean 场景。配置优先级：命令行参数 > 环境变量 > application-{profile}.yml > application.yml（命令行最高）。

我的项目关联 我们项目里：零散开关用 @Value；一组业务配置（支付参数、对账阈值、互联互通地址）用 @ConfigurationProperties 绑定成配置类，结构化、还能启动时校验必填项；Environment 在工具类或非 Bean 场景手动读。Docker 部署时我们常靠环境变量覆盖配置（优先级高于 application.yml），这也对应上面那条优先级规则。

面试答题话术 「读配置三种方式：@Value 读单个值、还能设默认值和 SpEL；@ConfigurationProperties 按前缀把一组配置批量绑定到 POJO；Environment 手动 getProperty 运行时读。项目里零散开关用 @Value，一组业务配置用 @ConfigurationProperties 绑定成配置类注入，Environment 用在非 Bean 或工具类。优先级命令行最高，然后环境变量，再到 profile 配置和主配置，Docker 部署就靠环境变量覆盖配置。」

35. @ConfigurationProperties 与 @Value 的区别 ★★★ ​

通俗理解@ConfigurationProperties：批量绑定，按 prefix 前缀把一组配置映射到 POJO 字段，支持松散绑定（user-name、userName、USER_NAME 都能绑到 userName 字段）、支持绑定 List/Map 复杂类型、支持 @Validated 校验。@Value：只能单个属性逐个读，支持 SpEL 和默认值，但不支持松散绑定、不支持批量、不支持复杂类型，校验也不方便。结论：一组结构化配置用 @ConfigurationProperties，零散几个值用 @Value。

我的项目关联 我们项目里一组业务配置（支付、对账、互联互通）都封装成 @ConfigurationProperties 配置类，结构化还能在启动时用 @Validated 校验必填项，避免配置漏填、上线才炸。@Value 只用在零散开关上。这是我们在多服务、多配置下的实际用法。

面试答题话术 「区别：@ConfigurationProperties 是批量绑定，按前缀把一组配置映射到 POJO，支持松散绑定、复杂类型和 @Validated 校验；@Value 只能单个读，支持 SpEL 和默认值，但不支持松散绑定和复杂类型。项目里一组业务配置我封装成 @ConfigurationProperties 类，结构化还能启动校验必填，@Value 只用在零散开关。」

36. SpringBoot 启动时会扫描哪些包、如何自定义扫描路径 ★★☆ ​

通俗理解默认扫描「启动类所在包及其所有子包」——因为 @SpringBootApplication 里的 @ComponentScan 没指定 basePackages，就默认扫启动类所在包。所以启动类一般放项目根包，保证所有 @Component/@Service/@Controller 都被扫到。自定义扫描：@SpringBootApplication(scanBasePackages = "com.xxx") 或 @ComponentScan(basePackages = {...})，也可以用 scanBasePackageClasses 按类定位。注意：纯 MyBatis 的 Mapper 接口 @ComponentScan 扫不到，要单独 @MapperScan 指定包。

我的项目关联 我们每个微服务的启动类都放在包根，所有模块都在其子包下，默认扫描就覆盖了，几乎不手写 scanBasePackages。通用坑：Mapper 接口默认 @ComponentScan 不认，我们统一在启动类或配置类上加 @MapperScan 指定 mapper 包，否则报「找不到 Mapper Bean」。这是我们规范里定好的，属于通用坑，不是线上踩出来的。

面试答题话术 「默认扫启动类所在包及所有子包，所以启动类一般放根包。要自定义就用 scanBasePackages 或 @ComponentScan 指定。注意 MyBatis 的 Mapper 接口默认扫不到，要单独加 @MapperScan 指定包。项目里启动类都放包根，Mapper 统一用 @MapperScan 扫。」

37. SpringBoot 支持哪些日志框架、如何切换日志实现 ★★☆ ​

通俗理解 SpringBoot 默认用 SLF4J（门面）+ Logback（实现）。SLF4J 是门面，负责统一 API，实现可以换。SpringBoot 内置 Logback 是默认实现，也支持 Log4j2（引 spring-boot-starter-log4j2 并排除默认的 logback）。日志级别：TRACE < DEBUG < INFO < WARN < ERROR。配置项：logging.level.包名=级别、logging.file.name、logging.pattern.xxx。换实现就是「排除 logback + 引入 log4j2 starter」。

我的项目关联 我们统一用 SLF4J + Logback（默认）。有个细节：根 pom 里引入第三方 starter（比如阿里的 schedulerx2）时，会把它自带的 log4j-api/log4j-core 排除掉，避免日志框架打架，全部走 SLF4J 门面。日志级别按包在配置里调，网关、对账这类关键服务线上 INFO，排查临时调 DEBUG。没换过 Log4j2，知道「排除 logback + 引入 log4j2 starter」的换法即可。

面试答题话术 「SpringBoot 默认是 SLF4J 门面加 Logback 实现，支持换 Log4j2，做法是排除 logback 依赖、引入 spring-boot-starter-log4j2。日志级别从 TRACE 到 ERROR，配置项有 logging.level、logging.file.name。项目里用默认 Logback，还会把第三方 starter 自带的 log4j 排除掉，避免日志框架打架，关键服务线上 INFO，排查再临时开 DEBUG。」

38. SpringBoot 的内置容器有哪些、如何替换 ★★☆ ​

通俗理解 SpringBoot 默认内置 Tomcat，也支持 Jetty、Undertow（都是 Servlet 容器，WebFlux 场景用 Netty）。内嵌容器好处：打成 jar 直接 java -jar 跑，不用外部装 Tomcat。替换方式：在 starter-web 里排除默认 tomcat，再引入对应的 starter（spring-boot-starter-jetty / spring-boot-starter-undertow）。三者对比：Tomcat 生态最大最稳；Jetty 轻量、适合长连接；Undertow 性能好、内存占用低。生产主流还是 Tomcat。

我的项目关联 我们所有微服务都打成 jar 用 Docker 容器部署，内嵌 Tomcat 直接跑，不依赖外部容器。要区分清楚：这是 HTTP 层的 Servlet 容器；我们充电桩协议网关是基于 Netty 的 TCP 长连接服务，跟内置 Web 容器是两码事，别混着说。替换场景我们没做过，默认 Tomcat 够用。

面试答题话术 「SpringBoot 默认内嵌 Tomcat，也支持 Jetty 和 Undertow，替换就是排除 tomcat 依赖再引对应的 starter。内嵌容器好处是打成 jar 直接 java -jar 跑。项目里全是 jar 加 Docker 部署，内嵌 Tomcat 直接跑。补充一下，我们充电桩协议网关是 Netty 的 TCP 长连接，跟这个 Web 容器不是一回事。」

39. SpringBoot 中如何实现 Bean 的注入方式（构造器/Setter/字段/@Bean）★★★ ​

通俗理解 四种：① 构造器注入（最推荐）：依赖写在构造器参数里，final 不可变、依赖明确、便于测试，Spring 4.3 之后单个构造器可省略 @Autowired；② Setter 注入：可选依赖用，可重新赋值；③ 字段注入（@Autowired 直接标字段，不推荐）：隐藏依赖、不好测试、可能循环依赖；④ @Bean 方法注入：在 @Configuration 里用 @Bean 显式声明 Bean，适合第三方类、需要自定义构造逻辑的场景。推荐顺序：构造器 > Setter > 字段。

我的项目关联 我们项目 Service 之间统一构造器注入（依赖 final 不可变、单测好写），第三方组件（客户端、线程池等）用 @Bean 在配置类里显式声明。字段注入基本被团队规范禁止。这是代码规范，也是能顺手讲出「为什么」的点。

面试答题话术 「注入方式四种：构造器注入、Setter、字段注入、@Bean。我优先构造器注入，依赖 final 不可变、依赖明确、好测试，单个构造器还能省略 @Autowired；Setter 用于可选依赖；字段注入不推荐，隐藏依赖还不好测；@Bean 用来显式声明第三方类或需要自定义构造逻辑的 Bean。项目里 Service 全部构造器注入，第三方组件走 @Bean。」

40. SpringBoot 的 actuator 是什么、常用端点 ★★☆ ​

通俗理解actuator 是 SpringBoot 的「应用监控探针」，引 spring-boot-starter-actuator 就暴露一堆 HTTP 端点，能看应用健康、内存、线程、配置等。常用端点：/actuator/health（健康检查，探活用）、/actuator/info（应用信息）、/actuator/metrics（指标，如 JVM 内存、HTTP 请求数）、/actuator/env（环境配置）、/actuator/beans（容器里的 Bean）、/actuator/loggers（动态改日志级别）、/actuator/mappings（接口映射）。安全要点：默认只暴露 health 和 info，其他端点要 management.endpoints.web.exposure.include=* 才开，而且不能裸奔，必须加鉴权 / 限制内网访问。

我的项目关联 我们服务是 Docker 容器部署的，actuator 主要用于给容器编排提供 health 探针（存活/就绪检查），服务不健康能自动重启。通用坑：生产上不能把所有端点直接暴露出去，env、beans 会泄露配置和内部结构，我们只开 health，其余要么不开、要么限内网加鉴权。这是通用安全做法，不是我们踩过的坑，但规范上必须守住。

面试答题话术 「actuator 是应用监控探针，引 starter 就暴露端点。常用的：health 健康检查、metrics 指标、env 环境、beans、loggers 动态改日志级别。默认只暴露 health 和 info，其他要显式配置 include 打开。生产上一定要加鉴权，env、beans 这种不能裸奔。项目里主要用 health 做容器探活，只开放 health，其他端点不开或限内网。」

41. 什么是 MyBatis ★★★ ​

通俗理解 MyBatis 是一个半自动的 ORM（持久层）框架，它把 SQL 和 Java 代码解耦：SQL 写在 XML 或注解里，查询结果自动映射成 Java 对象（POJO）。核心特点：① SQL 完全由开发者手写，可控、可优化；② 通过 XML/注解维护 SQL 和映射关系；③ 支持动态 SQL（if/foreach/where 等标签）；④ 轻量、无侵入、不强制继承框架类。对比全自动 ORM（如 Hibernate），它不自动生成 SQL，所以叫「半自动」。

我的项目关联 我们后端服务是 JDK 21 + SpringBoot + MyBatis-Plus（MyBatis 的增强）做持久层，大量用 BaseMapper、IService、分页插件。复杂查询（对账、统计、按条件查订单）手写 SQL 放 XML，简单单表 CRUD 用 MyBatis-Plus 直接做，不写样板 SQL。这样既可控又省事。

面试答题话术 「MyBatis 是半自动 ORM 框架，SQL 手写、结果自动映射成对象。特点是 SQL 可控、支持动态 SQL、轻量无侵入。对比全自动 ORM 它不生成 SQL，所以叫半自动。项目里我用 MyBatis-Plus 做持久层，复杂查询手写 XML，简单 CRUD 用 BaseMapper。」

42. MyBatis 与 JDBC、Hibernate 的区别 ★★★ ​

通俗理解JDBC：最底层，手写连接、PreparedStatement、ResultSet，还要自己管理连接、异常、资源关闭，样板代码极多。MyBatis：在 JDBC 上封装了连接管理、参数映射、结果映射，SQL 还是要自己写，但样板代码大幅减少，SQL 可控。Hibernate：全自动 ORM，用 HQL/对象操作自动生成 SQL，开发快，但复杂查询、性能调优不可控，学习成本高。一句话：JDBC 是「手动挡」，MyBatis 是「半自动」，Hibernate 是「全自动」。

我的项目关联 选 MyBatis（MyBatis-Plus）就是因为业务里大量复杂查询（对账、统计、条件筛选订单）需要 SQL 可控、能精确调优，Hibernate 生成 SQL 不可控不适合我们。而 MyBatis-Plus 又补上了单表 CRUD 的便捷性，兼顾了两头。这是选型理由，面试可以直接讲。

面试答题话术 「JDBC 最底层，连接、参数、结果全手写，样板代码多；MyBatis 封装了连接管理和结果映射，SQL 还是自己写，可控；Hibernate 全自动生成 SQL，开发快但复杂查询不可控。一句话：JDBC 手动挡、MyBatis 半自动、Hibernate 全自动。项目里选 MyBatis-Plus 就是因为对账、统计这种复杂查询要 SQL 可控，又能用 BaseMapper 省掉单表样板代码。」

43. 为什么说 MyBatis 是半自动 ORM ★★★ ​

通俗理解 判断全自动还是半自动，看「SQL 谁来写、对象关系映射谁来做」：MyBatis 帮你做了「结果映射」这一半（查询结果自动映射成 Java 对象），但「SQL 生成」这一半要你自己写（写 XML/注解）。所以它是「半自动」。Hibernate 两半都自动（SQL 由框架生成），所以叫全自动 ORM；JDBC 两半都手动，压根不算 ORM。

我的项目关联 我们实际就是「半自动」的用法：SQL 全部自己写（复杂查询放 XML），映射交给框架。这样复杂 join、聚合、分页、调优都能精确控制，同时不用手写 ResultSet 映射的样板代码。

面试答题话术 「半自动就是：结果映射这一半框架帮你做，SQL 生成这一半要自己写。Hibernate 是两半都自动所以叫全自动，JDBC 两半都手写不算 ORM，MyBatis 卡在中间。我们项目里就是 SQL 自己写、映射交给框架，复杂查询能精确调优，又不用写 ResultSet 样板。」

44. MyBatis 的适用场景 ★★☆ ​

通俗理解 适合：① SQL 需要精细控制、性能调优的场景；② 复杂查询多（多表 join、动态条件、报表统计）；③ 团队 SQL 能力强、想保留 SQL 自主权；④ 老系统数据库结构复杂、ORM 自动映射搞不定的。不适合：① 业务 CRUD 简单、对象模型清晰，全自动 ORM 更快；② 团队不想碰 SQL。一句话：SQL 复杂、要可控，选 MyBatis。

我的项目关联 我们的场景高度契合：充电业务里对账、交易统计、按多条件查订单，SQL 复杂且要精确调优，手写 SQL 最合适。同时用 MyBatis-Plus 把简单单表 CRUD 也提了效，等于「复杂 SQL 手写 + 简单 CRUD 自动」，兼顾两端。

面试答题话术 「适合 SQL 要精细控制、复杂查询多、团队 SQL 能力强的场景；不适合 CRUD 简单、对象模型清晰、不想写 SQL 的场景。我们的充电业务里对账、统计、条件查订单都是复杂 SQL，需要精确调优，所以选 MyBatis，再用 MyBatis-Plus 把简单 CRUD 也提速了。」

45. MyBatis 核心组件有哪些（SqlSessionFactory、SqlSession、Executor、StatementHandler 等）★★★ ​

通俗理解 核心组件是一条链：① SqlSessionFactoryBuilder：读配置构建 SqlSessionFactory，用完就丢；② SqlSessionFactory：全局唯一、线程安全，负责生产 SqlSession；③ SqlSession：一次数据库会话，非线程安全，执行 SQL 的门面；④ Executor：真正执行器，负责缓存、事务、Statement 处理，有 Simple/Reuse/Batch 三种；⑤ StatementHandler：处理 JDBC Statement，做参数设置和结果映射；⑥ ParameterHandler / ResultSetHandler：分别设参数、映射结果；⑦ TypeHandler：Java 类型和 JDBC 类型互转；⑧ MappedStatement：封装一条 SQL 的所有信息（SQL、参数、返回值）；⑨ Interceptor：插件机制，在 Executor、StatementHandler 等关键点做动态代理拦截。

我的项目关联 这些组件不用背源码，但「一条链」要能串起来讲，因为面试爱问执行链路。最直接的关联：MyBatis-Plus 的分页插件就是 Interceptor，拦在 Executor 这一环改写 SQL 拼 LIMIT。知道这个对应关系，就能把组件串起来讲。

面试答题话术 「核心组件是一条链：SqlSessionFactoryBuilder 读配置建 SqlSessionFactory，工厂生产 SqlSession，SqlSession 是执行 SQL 的门面、非线程安全，真正干活的是 Executor，负责缓存和事务，再往下 StatementHandler 处理 Statement，ParameterHandler 设参数、ResultSetHandler 映射结果，TypeHandler 做类型互转，MappedStatement 封装一条 SQL 的所有信息。插件 Interceptor 就是在 Executor、StatementHandler 这些位置做动态代理拦截，MyBatis-Plus 分页插件拦的就是 Executor。」

46. Mapper 接口为什么不需要实现类（动态代理原理）★★★ ​

通俗理解 你只定义了 Mapper 接口、没写实现类，却能直接注入调用，靠的是 JDK 动态代理：MyBatis 启动时用 MapperProxyFactory 给每个 Mapper 接口生成一个代理对象（MapperProxy），它实现 InvocationHandler。调用 mapper.xxx() 时，代理的 invoke 方法拿到「接口全限定名 + 方法名」组成 statementId，去 Configuration 里找到对应的 MappedStatement，再交给 SqlSession 执行 SQL。所以「接口没有实现类，代理类就是实现」。这也解释了为什么 Mapper 接口方法不能重载（statementId 会冲突）、为什么 Mapper 必须是 interface。

我的项目关联 我们用 MyBatis-Plus 时 BaseMapper 也是这个原理，自定义 Mapper 继承 BaseMapper 就有通用 CRUD。通用坑：Mapper 接口方法不能重载——有人给一个 Mapper 写两个同名不同参的方法，XML 里只有一个 statementId，结果运行时报「找不到映射」。这是通用坑，写的时候注意别重载。面试问「Mapper 为什么不用写实现类」就答动态代理。

面试答题话术 「Mapper 接口没有实现类，靠 JDK 动态代理。MyBatis 启动时给每个 Mapper 接口生成一个 MapperProxy，实现 InvocationHandler。调用时 invoke 拿到接口名加方法名组成 statementId，去 Configuration 找到对应 MappedStatement，交给 SqlSession 执行。所以代理类就是实现类。这也是 Mapper 方法不能重载的原因，因为 statementId 会冲突。项目里 MyBatis-Plus 的 BaseMapper 也是这个原理，自定义 Mapper 继承它就有通用 CRUD。」

47. MyBatis 有几种 Executor 执行器 ★★☆ ​

通俗理解 三种：① SimpleExecutor（默认）：每次执行都创建新的 Statement，用完关闭；② ReuseExecutor：复用 Statement（按 SQL 缓存复用，重复执行同一条 SQL 不重复创建）；③ BatchExecutor：批量执行，把所有 update 攒起来批量提交，适合批量插入。还有个 CachingExecutor 是包装器（开启二级缓存时包在真执行器外面）。SpringBoot 里默认 SimpleExecutor，全局配置 mybatis.executor-type=batch 可改。

我的项目关联 我们默认用 SimpleExecutor，因为一次请求基本就执行一两条 SQL，没必要复用或批量。通用坑：大批量导入、对账落库这种场景，SimpleExecutor 一条一条 insert 很慢，正确做法是换 BatchExecutor、或用 MyBatis-Plus 的 saveBatch / 批量插入、甚至一次性 insert 多条。这是通用坑，值得提一嘴，别傻乎乎逐条插。

面试答题话术 「Executor 三种：Simple 默认、每次新建 Statement；Reuse 复用 Statement；Batch 攒批处理，适合批量更新。SpringBoot 默认 Simple。项目里默认 Simple 够用，但批量导入、对账落库这种场景要换成 Batch 或用批量插入，不能逐条 insert，太慢。」

48. MyBatis 工作流程（完整执行链路）★★★ ​

通俗理解完整链路八步：① 启动时读 mybatis 配置 + Mapper XML，解析成 Configuration（含 MappedStatement）；② 拿到 SqlSessionFactory，再开 SqlSession；③ 调用 Mapper 接口方法 → MapperProxy 动态代理拦截；④ 用「接口名.方法名」定位 MappedStatement；⑤ SqlSession 交给 Executor 执行；⑥ Executor 先查一级缓存，未命中交给 StatementHandler；⑦ StatementHandler 用 ParameterHandler 设参数（#{} 预编译），执行 SQL，再用 ResultSetHandler 映射结果；⑧ 结果回填，SqlSession 关闭清一级缓存。插件 Interceptor 在 ⑤⑥⑦ 各环节可拦截。

我的项目关联 这条链路面试必问，最好一口气串下来。关联到项目：MyBatis-Plus 的分页插件就是拦在 Executor 这一环，把原始 SQL 包一层、拼上 LIMIT 再执行；一级缓存也是这条链路里查的。理解链路后，前面「一级缓存脏数据」「分页插件原理」都能串成一个体系，不用死记。

面试答题话术 「工作流程：启动解析配置和 Mapper XML 生成 Configuration；开 SqlSession；调用 Mapper 方法走动态代理，用接口名加方法名定位 MappedStatement；交给 Executor 执行，先查一级缓存，未命中再给 StatementHandler；StatementHandler 用 ParameterHandler 设参、执行 SQL、ResultSetHandler 映射结果，最后回填。插件就是在 Executor、StatementHandler 这些环节拦截，MyBatis-Plus 分页插件就是拦 Executor 拼 LIMIT，一级缓存也是这条链路里查的，串起来就都通了。」
